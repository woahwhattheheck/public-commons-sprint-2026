# CSKT DEWR receiving-operator acceptance

This sequence is the working acceptance plan for the USD 8,400 content/GIS migration workshare. The prime and DEWR designate an editor, content reviewer, administrator and technical recipient. Use the actual approved source cohort and destination throughout; retain each named decision with the version it approves.

## 1. Establish the complete source and destination

Load the approved original export and file location. Compare its record IDs and capture metadata with the source manifest. The current public baseline contains 33 pages and 353 distinct media objects: 130 PDF, 3 DOCX, 2 ZIP, 201 images and 17 videos. The API header’s 359 count is retained as an observation alongside the repeated 353-ID result, so records are identified from actual responses.

Capture the destination’s original state before applying the selected release. Identify destination URLs, content IDs, existing media and the approved template integration. The administrator confirms that the operating application and WordPress integration use the intended site and customer-owned accounts.

Confirm transfer and destination capacity from the original files. The October 11 capture reports 1,168,620,882 bytes across 335 media records; 18 records need an actual file-size check. Its largest reported file is 96,394,065 bytes, within the 1 GiB per-file transfer limit. Check the actual file responses, generated image variants and the agreed backup allocation before the full transfer. The native media metadata and the subsequent downloaded-byte/hash measurements remain attached to their respective source observations.

Acceptance output: complete selected source manifest, original destination capture, selected site identity, documented missing or separately supplied source files and named role assignments.

## 2. Decide how each source item should appear

For every selected page or media record, save its approved disposition: retain, revise, consolidate, archive or remove. Preserve the original content and source ID while drafting changes. Consolidated records point to their approved destination; retired records retain the reason and responsible reviewer.

Use the actual DEWR program/project structure and the prime’s approved information architecture. Classify document/project/news/notice records and save title, category, date and version metadata needed for their search and filter views. Existing files retain their original bytes unless an explicitly reviewed replacement is supplied.

Acceptance output: every selected record has an accountable disposition; every published replacement resolves to the intended source and current approved content.

## 3. Review content and access roles

An editor opens a source item, changes the draft, records a note and submits the current version for review. The reviewer inspects the source and proposed version, requests a correction or approves it. A changed draft returns through its current review state; historical approval stays attached to the version originally reviewed.

The administrator inspects staff permissions. The editor’s workflow cannot silently grant administration or bypass the release responsibility. The recipient demonstrates creating, revising and archiving a content item and retrieving its prior version.

Acceptance output: named source-linked review and correction history plus a recipient-operated role/revision workflow.

## 4. Approve URLs, documents and GIS presentation

Inspect the complete old-to-new route table. A redirect must lead to the intended current destination; intentional removals are explicit. Check migrated page links, document URLs and the agreed status of externally hosted resources.

Open the document library, locate a document by its agreed category/title/date, inspect its version and download the intended file. An updated document remains connected to its predecessor and source decision.

Inspect all four original GIS app references. The baseline has three accessible StoryMaps and a stale legacy MapSeries URL. For each selected app, verify the approved item URL, actual public or authorized access, its supporting maps/layers where relevant, and the page’s current embed or replacement. The page supplies the approved plain-language purpose, a meaningful direct link and accessible fallback content. When a legacy app is retired, record the approved replacement or fallback as its migration decision.

Run the agreed keyboard, focus, heading, link, image and responsive checks on these delivered views using the selected accessibility standard. Existing PDF/DOCX remediation and new media production use their separately agreed acceptance list.

Acceptance output: reviewed route/document/GIS matrix, actual destination observations and corrected implementation findings.

## 5. Apply the selected release and handle interruption

Freeze the approved migration release and retain its manifest. Preview the destination changes, then apply through the provided WordPress integration. Match each actual result to the selected source, destination ID and intended operation.

Resume the same operation after an interruption, using the retained result for each completed item. The continuation identifies already completed changes and remaining work. If a destination item has been edited by staff since the retained original or prior applied state, inspect that difference before reconciling it; keep the intervening staff version.

Acceptance output: selected immutable release, original target capture, actual destination results and one completed same-operation continuation.

## 6. Complete both correction cycles

The coordinator supplies one consolidated list for each cycle, with source item, current observation and desired correction. Implement approved changes in the original workspace and make a new reviewed release. Preserve the previous release and its decisions.

Recheck all changed records and the affected routes/GIS/document views against the actual destination. Separate implementation errors from a newly requested content revision so the final handoff shows the complete selected scope.

Acceptance output: two reviewed corrections or the coordinator’s recorded decision to use fewer cycles, with final selected release and disposition of every reported item.

## 7. Recover and transfer the operating work

Use the supplied instructions to recover the selected original target state on the agreed staging site. Inspect the result, including staff changes made after the original capture. Reapply or reopen the accepted release through the maintained operation when the recipient chooses it.

Export the full migration workspace, configuration, source manifest, role instructions and release material. Reopen the same work in a fresh process on the receiving runtime and inspect its source/review/history. Confirm that CSKT or its authorized administrator can access the CMS, hosting, domain and applicable service accounts independently.

Acceptance output: recipient-operated recover/reopen, full source/configuration/guide transfer, current credential and account-owner handover through the agreed private channel, and a signed-off technical discrepancy list.

## 8. Enter continuing support

Record the handover date, named support contacts and the applicable working time zone. The 30-day implementation warranty starts at technical handover. Initial response is one business day for loss of the delivered publishing workflow or an implementation-caused public integration failure, and two business days for other implementation issues.

If the optional USD 600/month support service is selected, record its start date, monthly four-hour allowance and approved work channel. The prime continues to manage the public website/customer service relationship.
