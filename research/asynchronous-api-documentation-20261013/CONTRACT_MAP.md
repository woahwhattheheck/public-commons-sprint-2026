# Selected-release contract map

Use the maintained provider source and approved sandbox to fill this map during the paid baseline. The public overview establishes the described capabilities; each exact contract below must bind to its current source and selected release. Preserve disagreements and their source location. Do not invent a field, response or guarantee to make an example look executable.

| Contract question | Required original source | Effect on the delivered guide |
|---|---|---|
| What base URL, release and sandbox organization apply? | Current deployment and release configuration | Every example names its actual environment. |
| How are credentials acquired and attached? | Approved account flow and exact authentication schema | Correct the displayed Bearer interpolation against real client behavior. |
| Which SDK package/version is supported? | Maintained package/repository and release notes | Pin one selected language and compatible version. |
| What is the original operation input and file boundary? | Current request schema, media types and limits | Use valid synthetic input and preserve its identity. |
| Which response proves rejection, acceptance or completion? | Actual status/error/resource schemas | Keep confirmed rejection distinct from unknown outcome. |
| Which identity retrieves the original operation or result? | Current resource/status/list contract | Recover the existing operation without guessing a URL. |
| Where is an idempotency key supplied? | Exact field/header and validation rules | Preserve the provider's actual key location and format. |
| What is its scope, lifetime and repeated-payload behavior? | Maintained idempotency implementation/documentation | Explain the safe repeat and expired-key cases accurately. |
| Which event family belongs to the selected journey? | Original event catalog and schema | Bind event and resource through genuine identifiers. |
| How is event authenticity validated? | Exact provider verification and key-rotation contract | Supply the real receiver setup and error behavior. |
| What delivery, ordering, repeat and acknowledgment semantics apply? | Current delivery contract and supported response codes | Make the durable receive/reconcile course accurate. |
| How do list cursors terminate and behave during changes? | Original pagination/filter/snapshot rules | Export every selected page with honest coverage. |
| Which rate-limit and retry instructions are authoritative? | Current plan/runtime headers and error documentation | Respect provider limits without converting an unknown write into a second operation. |
| What result can the staff member act on, and who decides? | Approved product workflow and policy-owner review | Separate technical completion from the organization's substantive decision. |
| Which sources can be retained or included in a support export? | Approved data handling and support policy | Keep secrets and unnecessary original document contents out of routine exports. |

For each selected answer retain: source URL/path and version; observed example identity when an actual sandbox run is authorized; the documentation section it controls; the reviewer or maintained code that resolves conflicting material; and the current disposition. Source retrieval and synthesis are part of TokenJunkieLabs' work.
