## Intended outcome and funded scope

The day-90 security deliverable is an operated response path for the two selected merchant deployments and their independent buyers. An operator must be able to identify an affected native purchase, acknowledge the incident, recover its unfinished work and let the receiving engineer reopen the same case and useful output.

This work remains the existing **Tranche 2, 50-hour / USD 4,750 package** within the **USD 38,000, 400-hour, 150-day application**. The other 70 T2 hours cover the selected provider and ledger deployments. Historical source development and separately paid company work are not charged again. The application retains its existing merchant, buyer, facilitator, purchase-window and tranche targets. Its current submission state is interest submitted and acknowledged, with the invitation pending. The original application retains the issuer correspondence. [1]

SCF’s current criteria require a self-contained application, and its deliverable guidance includes a T2 threat model and monitoring plan. This baseline supplies the design; the funded work binds it to actual installations, implements the necessary observations and responses, remedies material findings and completes the two operator journeys. The public application contains the acceptance criteria itself. [2][3]

## System and trust boundaries

The system carries a merchant’s selected offer through buyer approval, native settlement, complete useful output, recovery and receiving. The assets at risk are spending authority, the integrity of merchant terms and source identity, correct attribution of transfers and output, private customer material, and the ability to recover the original work.

| Boundary | Authoritative input | What must remain separate |
| --- | --- | --- |
| Merchant publication to discovery | Accepted merchant authority, canonical resource identity and current source generation | Public discovery is an offer; it does not prove settlement or authorize a buyer’s signature. |
| Buyer approval to native dispatch | The saved approved request, selected payment option, network, asset, recipient and applicable limits | An agent’s proposal, a fresh quote and an existing approval are different records. |
| Facilitator/RPC to payment outcome | The selected network’s native transaction and processing evidence for the original intent | An HTTP acknowledgment, an uncertain reply and independently observed settlement are different outcomes. |
| Payment to useful delivery | Original entitlement or delivery session, child work and complete output identities | Settlement can be complete while output is partial. A resumed download does not establish a new purchase. |
| Browser/CLI/agent to private operator | The existing authenticated application, workspace identity and current authority | A local service, another workspace and a public page do not share administrative authority. |
| Saved state to receiving host | Selected source edition, recovery manifest, original state and later operation history | Restoring older state does not erase a later payment or permit replay of completed work. |
| Observations to responder | Current collection coverage, incident identity, notification attempt and acknowledgment | Process liveness is not payment health; missing observations are not a clean security result. |

For each installation, the private deployment annex identifies the actual source edition, merchant and buyer operators, facilitator/RPC selections, network and relevant accounts or contracts, ingress and secret custody, storage and recovery destinations, monitor bindings and named primary/backup responders. It records changes to these selections. A generic address placeholder cannot count as installed coverage.

The published baseline contains no credentials, customer paths or configured incident destinations. A populated monitoring plan remains with the responsible operators; the grant receives a sanitized coverage and outcome report. This follows Stellar’s guidance to retain stable threat/monitor links and keep a populated monitoring map internal. [4]

## Health, privacy and evidence semantics

Process, application, dependency, payment and delivery health are reported separately. The existing discovery wrapper’s process/readiness endpoints explicitly leave ledger/RPC/settlement unchecked. Its rolling latency measures completed responses from that process, not network settlement, complete datasets or historical service availability. Actual payment/dependency monitoring therefore needs its own selected evidence source. [6]

Aggregate labels remain bounded, such as component, monitor ID, decision class and outcome. Wallet addresses, raw URLs, query bodies, payment payloads, customer identities, tokens and case-specific identifiers do not become metric labels. Detailed correlations belong in protected case records. A failed observation must not emit its raw exception or secret-bearing request into the public grant report.

Each incident retains the installation and source edition, threat/monitor IDs, original operation references, first/last observation, confirmed or uncertain condition, notification history, responder acknowledgment, authorized action and result. Financial and delivery clocks remain separate. Repeated observations update the same incident; they do not create purchases, settlements or customer-adoption counts. Any retention period, access grant or evidence export is selected with the actual customer.

## Two complete operator journeys

**Interrupted settled purchase.** Use the original customer-approved intent and its independently observed native settlement. Preserve the interruption and incomplete output. The configured monitor raises the retained incident, the responsible operator acknowledges it, and the original entitlement/session recovers unfinished delivery. The receiving engineer reopens the same case and useful output after drain/restart. The report identifies the original intent, transaction and output, any additional authorization actually required, and whether any new financial dispatch occurred. Reopening an already acquired file is recorded as recovery of the original purchase.

**Merchant-delivery failure.** Observe a real selected delivery failure through the existing provider/application path. Retain the original financial status, source and partial result; no fixture success stands in for the customer outcome. The operator acknowledges the incident, resolves the actual supported delivery condition and continues or records the unresolved fulfillment obligation. The receiving engineer reopens that same state and verifies useful output when complete. A canceled, refunded or unresolved result stays in the report with its actual evidence.

The two journeys are part of the funded installation work. They reuse the current source and original customer operations; no blanket suite, synthetic purchase replay or additional paid acquisition is prescribed here. An unsafe disruption to a customer service is not required to demonstrate recovery. Where a necessary failure cannot be exercised safely, the record distinguishes source review, a controlled authorized exercise and an actual customer outcome.

A provider HTTP 200, a settlement-labelled state or an accepted webhook does not replace the receipt-verification condition. Recorded verification is the merchant's retained result of its original receipt signature/key/payment/term checks; the collector does not repeat those checks or query a ledger. Recorded complete output is the original returned/result metadata and its consistency, not a new byte-level examination of the customer file. The grant's financial acceptance continues to use independently observed native transfer and the complete agreed output. [12][13]

Unresolved age starts at the first original transition of the current state/signature episode. Pending-to-uncertain retries preserve that origin; an inactive state ends the episode. Receipt-to-output age starts at the first retained receipt verification. Polling, updated_at, repeated reconciliation requests and process restarts do not reset either age. The summary carries oldest original timestamps and unknown-anchor counts; the collector evaluates known ages at its actual observation time. An unknown anchor cannot supply a healthy recovery poll.

Both collection modes preserve the original source selection and history. The full observer retains complete immutable history and exchange descriptors. The watcher checkpoints their counts and canonical prefix digests. Summary polling requests those previous row counts and the original history boundary; the owner streams the exact same descriptor projections inside the same read snapshot. The consumer compares both returned counts and hashes, catching an earlier changed/deleted row even when the final history row is unchanged. A valid append retains the earlier prefix. Older original checkpoints adopt the stronger witness after their next valid full capture. [12][13]

The summary inspects every order, including terminal contradictions and authority failures. Its detailed array is separately limited to 1,024 condition-bearing orders and the 2 MiB response budget; matching, returned and omitted counts remain explicit. The response contains no original payload BLOBs. The original full observation has its existing 8 MiB/100,000-row limit. Summary mode is useful for large stores whose complete recurring metadata export would exceed that limit. Complete aggregates do not turn the bounded detail into a complete per-order history.

The watcher obtains a full singular capture on initial observation, source/runtime change, an incident-opening or recovery transition, and its configured capture interval. It evaluates the later full response at its own time and retains the earlier exact summary, source bytes/hash and timing as its optional poll source. A contradictory later identity, history or prefix makes coverage unavailable. A separate timeout, workload or read-availability failure can leave the usable summary retained with the full-capture failure recorded; it does not erase the condition totals or relabel an earlier source as a later one.

The existing two-file x402 capture, original incident snapshot and complete Support handover carry these sources through receiving. The operator opens the incident, records ownership and next action, uses **Prepare case**, retains the original before/after files, and exports the readable report and complete handoff. The receiving console opens that handoff as a new editable case with its full sources, hashes, notes and comparison mapping. Full/full comparisons retain complete history; a comparison involving a summary proves only the retained immutable prefix and complete condition totals, while stating its bounded detail. An absent detailed row is never reported as a deleted or recovered order. [13]

### Control correction in the monitored response path

Review of the original SF40 handler found a concrete completion-classification defect: a handler exception after a successful HTTP header called response.end(), allowing Node's finish event to count a truncated body as a completed 2xx response. The correction destroys an unfinished response when headers have already been sent. The existing close path then records one aborted response, excludes it from completion status/latency samples and releases admission only after the backend operation has also settled. Pre-header errors retain their JSON 500 response. Completed responses retain their existing classification. This change belongs in the original wrapper and uses its existing bounded observer.

## Complete installed response and tranche receiving

The two selected response cases follow the same installed ownership and source paths used for useful customer work.

1. **Interrupted settled purchase.** Select the customer's existing approved intent and independently observed transfer; retain the original incomplete output and operation. Record the first relevant event and configured monitor finding. Deliver the retained incident to the primary, capture acknowledgment, and have the authorized engineer continue the unfinished delivery using the original entitlement/session. For a RETURNED merchant result, recover its retained bytes; for an interrupted handler, reconcile its prior execution first. Verify the agreed complete output and actual financial history, then drain/restart and have the receiver reopen the same incident, operation and files. Record first detection, notification, acknowledgment, useful recovery, active effort and receiver decision.
2. **Merchant-delivery failure.** Use the actual installed delivery path and retain the failure, financial outcome, partial work and outstanding obligation. Follow the same notification and ownership route, resolve the supported provider/storage/application condition, and continue the original request. Retain the complete output and its customer acceptance or the remaining unresolved obligation. Receive that same state after restart. If the failure prevents a fresh capture, retain the last useful capture with its original time and add the actual recovery capture when available.
3. **Coverage and notification continuation within those cases.** Retain a collection gap and an interrupted or rejected original notification in the selected authorized exercise. Reopen the watcher/queue, reconcile any provider receipt, retry the same event where supported, and record the backup escalation and acknowledgment. Verify that a missing observation cannot close the delivery incident and that a changed registration is recorded as retirement rather than measured recovery.
4. **Tranche handover.** Freeze the complete selected incident/case, source editions, observations, notification history, original financial/output references, terms and receiver decisions. The existing Support case and Service Operations reports preserve originals and reviewed response/recovery calculations. Join the sanitized result to the existing Implementation evidence and Tranche completion records, retaining each original request and payment clock.

The existing merchant reservation operation also continued actual original returned bytes across empty and partial reservations and preserved a completed final/partial pair. These operated component histories provide reusable recovery mechanisms. The funded acceptance applies them to the selected customer hosts, actual useful purchases and receiving people. [9][10]
