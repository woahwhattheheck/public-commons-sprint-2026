# Gravitee source and Installation desk

This desk completes the source-to-Installation workflow inside the existing Grant Operations workspace. Open the original Operations case, open **Installations**, and choose **Gravitee API source**. The API application, commercial Workshare, case sources, Installation editor, command journal and complete case receiving remain their original products.

## Before opening a source

Use a whole native Gravitee handover made with software included. It contains the original workspace, all source objects, API drafts, commissioning records, native child responses and editable application source. Attach that exact JSON handover through the case's existing Sources screen. The existing source limits and staff permissions apply; this desk does not enlarge or bypass them.

Receive the complete commercial Workshare in the original Installation editor. Select a new planned draft. Its workorder, funded assignments, original commercial phases, acceptance checks, amounts and currencies stay intact. The source desk prepares a new planned Installation; an already-operated saved Installation keeps its original checks and is edited through the normal saved-edition flow.

An installed host needs the existing supported Node runtime and the full selected original source. The managed manifest includes the original Gravitee application plus its SF49 profile/core, the new desk and the existing hash, staff and native Installation modules. The dedicated distribution selection is **gravitee-installation**. Keep application credentials in the original local environment references; the desk's HTTP input contains case/source identities and original documents.

## Open and review the whole API cohort

Select the attached full handover and name the complete working copy. **Inspect and open complete source** reads the attachment, checks its byte count and SHA-256, invokes the original native package reader, and displays every original draft and commissioning head.

Each row keeps its full kind, ID, revision and SHA. Read the full original record, native state, API ID, selected connection, original source, child requests and observed deployment state. The **Complete source** tab lists every package member. It pages text by Unicode characters and offers original byte downloads for text and binary members.

For every original record choose:

- whether it belongs to this Installation's complete selected cohort;
- its actual staging, production or other environment role;
- a substantive purpose, or a reason for excluding it.

The whole selection always contains every head from the selected edition. An excluded head remains visible and source-bound. An included head must have an actual environment role before preparation. Keep native observations in their original states: an accepted deployment request alone does not establish observed production traffic or customer acceptance.

## Working copies, histories and interrupted requests

A named working copy contains the whole original handover and native inspection, every complete or unfinished cohort decision, the commercial document, technical bindings, preparation, notes and original attachment request. Browser storage is scoped to the original staff session, case, pinned plan and case creation identity.

**Save complete checkpoint** retains the whole current source and document. **Fork complete copy** keeps an independent editable alternative. **Saved history** opens any retained checkpoint as a separate complete copy; it does not overwrite current work.

Changes save atomically to IndexedDB. If another tab has saved first, the current tab keeps all its work and stops replacing the saved store. Download the full current alternatives, reopen the saved store, or preserve the current alternatives as separate named forks. A failed browser save remains visible; keep the complete downloaded JSON before closing that browser.

**Download all working copies** produces the whole editable JSON archive, including original handover bytes and all histories. Receive it in the same original case after reopening the complete case. Exact same-ID copies are reused. If a same-ID copy has different content, choose **Receive conflicting copies as alternatives** to keep both under separate working IDs.

An attachment request is saved before the original command is sent. While its outcome is uncertain, the source-changing controls remain disabled. **Recover original attachment** reuses the exact original request ID, expected case version, actor and body. A known original validation/conflict response retains the rejected request and enables a fresh reviewed preparation. A transport failure keeps the original request pending. Changing tabs or importing a working file never creates a replacement attachment request automatically.

A received pending request is restricted to the original selected-cohort source attachment. Its original bytes, SHA, filename, media type, kind and request body are verified. It cannot act as an arbitrary case command.

## Compare a later complete handover

Attach the later whole native handover through the original Sources screen, then select it in **Later handover**. The workspace identity must match.

The comparison retains both complete source files, every member movement, and every draft/commissioning movement by stable kind and ID. Unchanged native references keep their decisions. Added, removed and changed references require an explicit choice:

- **Prepare new decision** starts an added or changed record with unfinished reviewed fields.
- **Carry previous decision to this changed record** binds that deliberate choice to the new complete native reference.
- **Acknowledge removed source** records that the old record is absent from the later full edition.

Apply only after resolving every movement. The complete earlier working copy becomes a checkpoint, including its old source and decisions. The new source is installed as the current editable cohort. Earlier technical preparation and cohort attachment are cleared from the new selection, so they cannot silently represent the later edition. Their original bytes remain in history.

## Prepare the original Installation

1. In the normal Installation editor receive and review a new complete commercial Workshare draft.
2. Return to the source desk and choose **Receive complete current Workshare draft**.
3. Enter the actual source reference, source-use authority, receiving host and receiving engineer. The complete preserved commercial document and bindings are visible.
4. Finish every included/excluded cohort decision and choose **Attach exact reviewed cohort**.
5. The original `source.add` command retains the exact selected-cohort JSON in the same case. An exact existing attachment is reused.
6. Choose **Prepare complete native Installation**. The reader requires the current case version, original handover SHA and exact cohort attachment SHA. Both attachments join the original Installation source and receiving selections.
7. Read the full preparation, source snapshot and native Installation preview.
8. Choose **Open complete prepared Installation draft**. The original editor receives a separate complete draft; other retained drafts remain available.
9. Review the whole Installation in its original editor, give the reason for the edition and save with the existing command and expected revision.

After another case change, prepare again against the fresh case version. Only the current source selection advances; explicit technical bindings and original commercial terms remain. After changing cohort decisions, attach their new exact bytes before preparing.

A saved Installation and an API deployment are separate original records. Record actual work, checks, production observations, acceptance, invoicing and collected cash through the existing corresponding product, with the original evidence and attributed decision. The desk adds no automatic acceptance.

## HTTP and source contract

Read-only requests are POSTs under the existing authenticated case:

- `/api/operations/{caseId}/gravitee/inspect`
- `/api/operations/{caseId}/gravitee/member`
- `/api/operations/{caseId}/gravitee/template`
- `/api/operations/{caseId}/gravitee/prepare`

All include `expectedVersion`, `sourceId` and `expectedSourceSha256`. Member reads add `path`, Unicode `offset` and a `limit` up to 32,000 characters. Template adds the complete original `document`. Prepare also adds complete `bindings`, `cohortSourceId` and `expectedCohortSha256`.

The result retains `scope`, original source metadata and complete original engine output. Prepare adds the original native Installation preview. These routes read the original aggregate under its existing snapshot. Staff scope is enforced by the existing case/role authorizer. Source attachment and Installation mutation use the existing `/command` route and its permissions, original request journal and expected version.

The browser model is `stellar-forge.gravitee-source-working-copies.v1`. Every copy uses `stellar-forge.gravitee-source-working-copy.v1`. Full copied source and history hashes are checked before receiving. The comparison is reconstructed from the original source and current decisions; an incoming archive cannot replace its identity rows while retaining only a matching headline hash.
