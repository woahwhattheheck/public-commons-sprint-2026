# Customer-use calendar: operating and receiving guide

Operating guide for the existing Installation workspace and its optional `document.useCalendar` contract. The model, CLI and route names below use the maintained implementation. The worked examples describe plans; actual activity comes from the original received records.

The calendar helps an operator turn an intended use into dated work, retain its relationship to the original purchase, and compare that plan with the existing cohort's actual records. It belongs to the same Installation document and its immutable editions. It does not replace the original purchase, settlement, allowance, receiving or cohort engines.

## 1. Begin with a useful customer outcome

Write the question the customer needs answered, the source or service that can answer it, and what the operator must deliver. Then choose its planned date, responsible operator and intended buyer. A payment count by itself is not a useful task.

For a recurring task, state what can change between occurrences: a new source edition, another reporting period, a changed customer request, or a fresh delivery requiring review. When the same retained answer already meets the need, record that reuse. The plan should not create another purchase merely to fill a calendar cell.

Choose the actual existing case and Installation. Keep the case identity, Installation identity and previous immutable edition visible during editing. If the case already has a cohort seed and review, retain those original inputs and its original cohort.rule. The calendar supplies context for that cohort; it does not redefine the rule or its evaluation period.

## 2. Record a complete dated task

Use the supplied calendar controls to retain the following information:

| Information | What to record |
|---|---|
| Customer need | The concrete question, action or deliverable that makes the work useful. |
| Buyer and operator | The original selected buyer or case identity and the person responsible for completing the task. A planning label is not an observed customer. |
| Planned date | A UTC civil date within the selected window, with explicit weekdays and included or excluded dates. Keep the original native event timestamp when actual activity arrives. |
| Input | The selected source edition, service, input file or prior delivery, with its existing identity. |
| Expected result | A result the receiving operator can inspect: a retained answer, report, file, comparison or completed receiving step. |
| Intended use | Purchase, allowed use, reopened delivery or free use, according to the original product's actual route. |
| Settlement relationship | A separate planned settlement group if relevant. Do not manufacture a purchase ID for a plan. |
| Actual binding | The original purchase or other native activity identity only after that record actually exists. |
| Plan state and observed result | Calendar entries use PLANNED or CANCELLED. Keep completion, failure, unresolved outcomes and actual result identities in their original native records; do not invent additional calendar-entry states. A revised date or replacement task belongs to a following Installation edition. |

Keep plans and actual results distinguishable. A task can be useful and completed without a new payment; a settlement can exist before all planned tasks occur. A native purchase result that failed or remains unknown must keep that disposition.

An imported plan is still a plan. Receiving its files does not make its buyers active customers, its dates completed work, or its settlement groups paid.

## 3. Select the calendar explicitly

A fourteen-calendar-day window normally contains ten Monday-to-Friday dates. That arithmetic assumes the selected calendar has no excluded holidays or closures within the window. It is not a promise of ten operating days in every jurisdiction or company.

The following dated example uses 12–25 October 2026, Monday-to-Friday work and no holiday exclusions. This is an illustrative configured calendar, not a statement about any buyer's local holiday policy.

| Working date | Buyer A's useful planned request | Buyer B's useful planned request |
|---|---|---|
| Mon 12 Oct | Establish the selected source baseline and receive its first answer. | Review the selected source for the second buyer's distinct operating question. |
| Tue 13 Oct | Review the next available period or an actual changed input. | Produce the second buyer's next required output from its selected input. |
| Wed 14 Oct | Compare the relevant change with Monday's retained baseline. | Resolve a separately stated customer question using the required source. |
| Thu 15 Oct | Inspect an actual exception or update in the customer's workflow. | Receive and review the output needed for the buyer's current work. |
| Fri 16 Oct | Assemble the week's requested result and retain its source identity. | Complete the buyer's independently useful weekly review. |
| Mon 19 Oct | Begin the next period using its actual selected input. | Check the new period against the buyer's retained requirement. |
| Tue 20 Oct | Produce the result needed for the next operating decision. | Answer the buyer's distinct dated question. |
| Wed 21 Oct | Review an actual change or exception requiring fresh work. | Compare the selected new input with its relevant previous result. |
| Thu 22 Oct | Prepare the customer-required handover or decision material. | Receive the output required by the second buyer's current task. |
| Fri 23 Oct | Finish the period's requested result and reopen its retained delivery. | Finish the buyer's requested review and retain its result. |

Every row needs its real question and input before it is commissioned. The descriptions above illustrate a rhythm; they are not twenty ready-made reasons to charge. If a dated need is absent, cancelled or satisfied by the prior retained result, record that fact using the appropriate original route.

With two buyers and one useful purchase per business day, this plan contains 2 × 10 = 20 planned purchases over fourteen calendar days. It contains no purchases on 17, 18, 24 or 25 October. If the configured calendar excludes another weekday, the same plan has eighteen rather than twenty eligible purchase slots unless the operator explicitly changes the window or the actual customer demand changes.

Do not move the original cohort's start or end merely to make a target count appear. Make the calendar difference visible and evaluate the original cohort rule against the original actual records.

## 4. A thirty-request plan needs thirty useful requests

A separate planning example has three distinct useful requests on each of the ten eligible dates: 3 × 10 = 30 requests. Those may be different buyers or different legitimate questions from one buyer, subject to the original product and cohort rules.

Define each request's input and expected result independently. Three views of one answer, repeated download attempts, a reopened package, or a retry of the same original operation are not automatically three purchases.

If the actual workflow produces two useful requests on a date, retain two. If it produces one purchase followed by two free or allowed uses, retain that observed mix. The calendar can show that the original thirty-request plan was not fully realized without relabelling the activity.

The comparison should preserve:

- The original plan's eligible dates and thirty intended tasks.
- The actual native purchase IDs and their original statuses.
- Allowed, reopened and free-use entries as separate kinds of activity.
- Cancelled tasks and following editions that explicitly reschedule planned work, with their retained reason.
- Missing coverage as unknown when the necessary native records were not received.

A calendar total is a planning total. A cohort result remains the result of its maintained rule applied to the selected actual seed and review.

## 5. Keep settlements separate from use

A prepaid pass illustrates why the calendar needs two views. A buyer may settle for a pass once and then use it on several eligible dates. The settlement group belongs to that commercial arrangement; the dated tasks describe the intended customer work.

For example, a plan can contain two prepaid pass settlements, one for each buyer, and twenty intended uses across the ten working dates. That is two planned settlements and twenty planned uses. Neither number establishes the number of actual purchases or the cohort's eligibility result.

For repeat-potential planning, each distinct funding group contributes its first whole useful-result day. The group's settlement date is not a substitute for that day. A prepaid pass remains one purchase regardless of how many allowance-use dates are planned; several dates funded by the same pass do not become several potential repeat purchases. Distinct useful results and the original cohort.rule still determine the relevant comparison.

After actual activity occurs, bind each native purchase or use to its original identity and the relevant task. Preserve the original pass or settlement identity, allowance balance and native status. The calendar must not consume an allowance, settle funds, retry a payment or infer a successful settlement by itself.

When one settlement covers more than one task, keep that one settlement group intact. When a task requires a separate original purchase, retain that actual purchase separately. Do not divide a single settlement into fictitious receipts or combine distinct native purchases into a synthetic receipt.

Refunds, failed settlement, expired allowance and unresolved provider outcomes belong to their original records. A planning edit cannot repair or erase them. A later confirmed original result can be attached through the maintained workflow.

## 6. Receiving, reopening and free use are useful work

The operator should be able to plan the full customer journey, including activity after the first purchase:

| Planned activity | Actual evidence to retain | What it establishes |
|---|---|---|
| Receive a delivery | Original delivery and receiving identities, selected complete files and native receiving result. | The selected package was received according to that result. |
| Reopen a retained delivery | Original receiving or workspace identity and its actual reopen result. | The retained work remains usable in that environment. |
| Use an existing allowance | Original allowance/purchase/use identity and its actual native disposition. | The maintained engine recorded the particular allowed use. |
| Use a free route | Actual source or service selection and the retained result. | The customer obtained that result without a new paid purchase. |
| Review or compare results | Original source/input identities, the maintained comparison and the operator's disposition. | The selected results were reviewed under that comparison. |

Keep the original monetary and use status even when the customer-facing task is complete. A successful reopen does not prove a new paid purchase. A source file received by the operator does not prove that a customer used it. A free-use result may satisfy the intended need without satisfying a purchase-based cohort criterion.

## 7. Work in the same immutable Installation history

Edit the current Installation through its existing workflow and publish the calendar with the resulting immutable edition. Do not rewrite a previous edition to make it match today's plan.

When a date, buyer, source, question or settlement grouping changes, retain the previous edition and create the next edition through the same writer. An operator reviewing an old result must still be able to see the plan that existed when that result was selected.

If another operator has changed the case or Installation, reopen the current state and resolve that actual change through the original revision/CAS workflow. Do not replace their changes with an older whole document.

For a repeated request, use the existing operation identity and inspect its original result. A transport retry or a repeated import is not a second customer task. If the original outcome is unknown, retain that uncertainty until the original record is reconciled.

The calendar is optional. Receiving an Installation without document.useCalendar should retain the original Installation behavior and history. Adding a calendar later should preserve the existing source, purchases, cohort inputs and previous editions.

## 8. Compare the plan with actual retained activity

Start a comparison from the actual selected case and immutable Installation edition. Select the original cohort seed and review that cover the relevant native activity. Keep the original cohort.rule and its actual eligibility boundaries.

Review the planned and actual counts by category before reading any overall result:

| View | Question to answer |
|---|---|
| Planned tasks | What useful work was intended, on which dates and for which selected buyers? |
| Planned settlements | Which commercial groupings were intended, separately from dated use? |
| Actual purchases | Which original purchase IDs exist, and what do their native statuses say? |
| Other actual use | Which allowed, reopened or free uses exist? |
| Coverage | Which dates or tasks have complete received evidence, and which remain unknown? |
| Cohort result | What does the maintained rule report for the selected actual seed and review? |

Inspect each mismatch. A completed task with no new purchase may be correct because the customer reused a retained answer. A purchase without a task may reveal activity outside the plan. Several tasks pointing to one original purchase may correctly represent a shared pass, or may require the operator to correct a mistaken binding. The original records decide; a count alone does not.

A saved report uses the exact Installation edition and the purchase states captured in its original snapshot. Display a current VOID, missing or changed purchase separately from that saved evidence. Do not silently recompute the historical report from today's mutable records or make its retained snapshot disappear.

Keep the comparison and a named operator disposition with the original case. State what the operator concluded and what remains open. If the calendar is revised after the comparison, preserve the comparison's original edition and create a following review where needed.

## 9. Export and independent receiving

Use the existing complete Installation/case export and receiving workflow. The receiving operator needs the calendar's immutable edition alongside the original source, cohort inputs, purchase references, settlement groupings, comparisons and dispositions that the maintained export includes.

Before handover, check the actual selected export result and its source identities. On the receiving side, use the original receiver, then reopen that received package. Compare the received edition, dated tasks, planned settlement groups and actual bindings with the original export.

The receiving report should identify the original and received workspaces or installations, the exported edition, the exact archive/file identity and the actual receiving/reopen result. Preserve all prior history that the source format carries. Do not call the package complete merely because a JSON file opens.

A second operator should be able to answer these questions from the received product:

1. Which plan was in force for the selected period?
2. Which UTC civil dates, weekdays and explicit exclusions does it use?
3. Which dated tasks are useful customer work, and who owns them?
4. Which entries are plans and which have actual native evidence?
5. How do settlement groups relate to use without replacing original purchase records?
6. Which original cohort rule, seed and review produced the comparison?
7. What did the reviewing operator accept, change or leave unresolved?
8. Can the operator make a following editable edition while the original edition remains intact?

## 10. Complete the operator handoff

Deliver a concise explanation with the complete received package. Name the selected case and Installation edition, the planned period, the actual evidence coverage and the comparison's disposition. Identify the next responsible operator and any customer decision still needed.

For the fourteen-day examples, write counts precisely: “twenty planned useful purchases across ten configured business days” or “thirty distinct planned requests across ten configured business days.” Only report actual purchase, settlement or use totals when the original native records support them.

Keep the original six-package commissioning scope and economics unchanged. Calendar dates and illustrative counts do not create customer demand, establish payment, satisfy a grant milestone or alter an approved commercial agreement by themselves. Actual completed product work, original customer use and the maintained milestone evidence remain the basis of those determinations.

The source owner's original model, Case UI, operations CLI, typed client and MCP routes share this optional Installation document. They preserve the existing export/receiving commands, purchase engine and cohort evaluator.


## 11. Authored Installation contract

The optional field is `document.useCalendar`, with schema `stellar-forge.sf47-customer-use-calendar.v1`. It is saved through the existing Installation preview/save workflow and therefore belongs to the same immutable Installation revision.

| Collection | Authored meaning |
|---|---|
| `tasks[]` | Named useful work, with the selected buyer and source context supplied by the original editor. |
| `settlements[]` | Separate DIRECT or PREPAID funding groups. Actual bindings use original native `purchaseIds`; plans do not mint a purchase identity. |
| `entries[]` | Dated PURCHASE, ALLOWANCE_USE, REOPEN or FREE_USE entries, with PLANNED or CANCELLED state and the selected task/buyer/source and `fundingIds`. |

Use the existing editor's complete document and pattern output. This guide does not substitute an invented reduced schema for the maintained task, buyer, source, funding or reference validators. A missing calendar leaves the original Installation behavior intact.

The Case UI tab is **Customer use**. Open the actual saved Installation revision, edit its draft, then use the original preview/save commands. Expanding a calendar stages the complete editable Installation document. Save the reviewed document through the existing Installation writer.

### Select and continue an exact saved edition

The checkboxes, entered revision numbers and observation date remain available while changing filters, paging, reading another window or reopening the tab. **Read selected calendars** applies those choices to the native report. Until that read succeeds, the displayed report, Cohort handoff and report downloads retain their last successful source selection; the desk identifies a changed selection.

**Edit customer use** opens the revision entered beside that Installation, including a historical revision. **Open original edition** from a dated row opens the exact saved edition that supplied that row. A historical source becomes a draft whose next save appends after the current Installation head.

An existing edited Installation stays in **Retained drafts**. The selected calendar edition opens in its own named draft, with its source Installation ID, revision and SHA retained. Reopening that same source resumes its existing draft and later edits. Review the current saved history when another edition has been appended since that draft began. The original case version and current Installation revision still govern preview and save.

### Prepare a selected buyer schedule

Choose the useful tasks, original buyers, working weekdays and exceptions in **Expand ordinary working dates**. Prepaid funding controls show the selected buyers, and the expansion request carries funding associations for those buyers only. The generator keeps its open panel while buyer or use-mode choices change.

For an allowance-use schedule, choose the original prepaid groups for each selected buyer. For a newly enabled calendar, the initial pattern offers the Installation's buyers, its first useful task and Monday through Friday; each selection remains editable. **Prepare dated uses** returns the complete original document for review and save.

### Retain the original save through access failures

An uncertain Installation save stays available under **Recover original save**. An uncertain Cohort freeze stays available under **Continue original freeze**. Access failures, route failures and interrupted responses retain the exact original request ID and body for recovery after access returns. An accepted save uses the existing exact-result readback. A queued Calendar or Installation handoff remains available through **Open selected edition**, including after reloading the browser or resolving the earlier save.

A native validation, version-conflict or unsupported-input rejection clears the pending dispatch and keeps the edited draft. Refresh the original source, review the entered changes and prepare the corrected request through the normal writer.

### Import, export and resume the complete Cohort draft

From a saved customer-use selection, choose **Open as review draft** or **Export complete draft**. The ordinary Cohort **Export draft** and retained-draft exports carry the same complete source fields:

| Field | Retained meaning |
| --- | --- |
| `originalCaseId` | The original case identified by the incoming draft. |
| `sourceVersion` | That draft's original case source version, retained through import and later source refresh. |
| `reviewCaseId` / `reviewVersion` | The active case and native version used as the exported draft's current preview basis. |
| `inputs` | All entered Cohort scope, operation, purchase association, product, coverage and outcome inputs. |
| `customerUse` | The complete original calendar group and exact Installation ID/revision/SHA selection, when present. |
| `editorState` | Unfinished dialog entries and the selected entry available through **Resume unfinished entry**. |

**Import draft** preserves these original source fields and opens the received inputs against the receiving case's current native Cohort rule. Its current review basis is shown separately from the draft origin. **Refresh source** advances that current review basis while retaining the original source identity, customer-use selection and entered observations.

When a different draft is already present for that tranche, the complete earlier draft and unfinished entries move into **Retained edited drafts** before the imported input opens. **Open retained draft** restores those entries to their own draft. **Export draft** from that row carries the retained source metadata and unfinished entries together. Switching tranches keeps each draft's unfinished entries with that tranche.

Use **Resume unfinished entry**, finish the entry and choose **Keep in review draft** before evaluating it. Then review the current native result and freeze through the original request lifecycle. An already pending or accepted freeze keeps its original recovery controls throughout this workflow.

For another workspace, receive the complete case or selected Installation ZIP to obtain the original source files and native purchase records, then open the portable Cohort draft. The browser's existing 2 MB draft-file limit and twenty retained alternate drafts apply; export a retained draft before removing a local copy.

The pattern selects explicit weekdays, included dates and excluded dates. It never infers the user's holiday calendar. Confirm those dates in the preview before saving.

## 12. Read, expand and seed through the existing model

The following are the source owner's actual model signatures. Here `program` is the already-selected original program, `expectedVersion` is its observed current version, and the reference/document/pattern values come from the maintained editor or retained source.

```python
calendar = model.customer_use_calendar(
    program,
    {
        "expectedVersion": expectedVersion,
        "installationRefs": installationRefs,
        "asOfDate": asOfDate,
    },
)

expanded = model.expand_customer_use_calendar(
    program,
    {
        "expectedVersion": expectedVersion,
        "document": document,
        "pattern": pattern,
    },
)

cohort_input = model.seed_customer_use_cohort(
    program,
    {
        "expectedVersion": expectedVersion,
        "installationRefs": installationRefs,
        "groupId": groupId,
        "asOfAt": asOfAt,
    },
)
```

`installationRefs` and `asOfDate` are optional for the calendar read. `asOfAt` is optional for the cohort seed. Keep the distinct date and timestamp arguments; do not replace the original native event time with a plan date.

These helpers read or prepare the original inputs. Use the returned complete document with Installation preview/save and the returned native cohort inputs with Cohort preview/prepare. They do not purchase a result, consume an allowance or settle funds.

## 13. Use the authored operations CLI

The examples use the original Python operations CLI. Set `SF47_SOURCE` to the installed `stellar/scf_2026/sf47_budget_model/workspace` directory, `WORKSPACE` to the existing private workspace, and `SCENARIO` to its original selected scenario file. This shell function supplies that unchanged launcher context:

```sh
operations() {
  python3 "$SF47_SOURCE/cli.py" operations \
    --workspace "$WORKSPACE" --scenario "$SCENARIO" "$@"
}
```

`CASE_ID` and `VERSION` are actual returned identities. All JSON files below are full files produced by the existing editor or original command. The installed Node launcher forwards the same arguments to this Python entrypoint.

Read the selected calendar and its original evidence:

```sh
operations customer-use-calendar \
  --case "$CASE_ID" --expected-version "$VERSION" \
  --installation-refs installation-refs.json \
  --as-of 2026-10-25 --output customer-use-calendar.json
```

Expand the complete Installation draft using an explicitly configured pattern:

```sh
operations customer-use-calendar-expand \
  --case "$CASE_ID" --expected-version "$VERSION" \
  --document installation-draft.json --pattern calendar-pattern.json \
  --document-only --output expanded-installation.json
```

Pass `expanded-installation.json` to the original installation-preview/save workflow. Read its actual resulting version before a following command. If the current version changed, reopen and resolve that original change; do not replace a peer's current document.

Stage the native Cohort inputs for one selected window:

```sh
operations customer-use-calendar-cohort \
  --case "$CASE_ID" --expected-version "$VERSION" \
  --group "$GROUP_ID" --installation-refs installation-refs.json \
  --as-of "$AS_OF_TIMESTAMP" --inputs-only \
  --output customer-use-cohort-inputs.json
```

`GROUP_ID` is the actual selected window identifier. The inputs-only result feeds the original cohort-preview/prepare commands. Review any existing edited Cohort draft before choosing to stage this new input.

Export one selected representation:

```sh
operations customer-use-calendar-export \
  --case "$CASE_ID" --expected-version "$VERSION" \
  --installation-refs installation-refs.json --as-of 2026-10-25 \
  --format json --output customer-use-calendar.json
```

The same export command accepts `--format csv` and `--format ics` with a matching explicit output filename. Those exports represent the selected calendar; use the original complete case/Installation package for editable independent receiving and historical evidence.

## 15. Typed clients and original Merchant MCP

The existing `GrantWorkspaceClient` exposes `customerUseCalendar(caseId, body)`, `customerUseCalendarExpand(caseId, body)`, and `customerUseCalendarCohort(caseId, body)`. Their bodies carry the same observed `expectedVersion` and selection/document fields as the model above. Responses retain the original complete bytes, native value, source selection, filename and digest. Use `download('customer-use-calendar', {caseId, expectedVersion, installationRefs, asOfDate, format})` for JSON, CSV or ICS.

The original configured Merchant grant-workspace provider exposes:

- `merchant_grant_customer_use_calendar` for saved selections, exact edition reports and current changes.
- `merchant_grant_customer_use_calendar_expand` for a complete editable Installation document plus its explicit expansion pattern.
- `merchant_grant_customer_use_calendar_cohort` for the native Cohort seed from a selected saved window.
- The existing `merchant_grant_export` with kind `customer-use-calendar` for the same complete representations.

All three new preparation/read tools remain read-only. They use the existing configured workspace alias, complete input or retained input reference, immutable response snapshots, paging and downloads. Save an Installation or prepare a Cohort review through its original mutation with the original actor, request ID, current case version and reviewed input hash. No new server, buyer engine or commercial record is created by a calendar read.
