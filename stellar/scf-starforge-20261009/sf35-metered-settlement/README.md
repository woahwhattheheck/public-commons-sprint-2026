# SF-35: Metered x402 `upto` settlement execution

Original MIT / Node.js 22+ source, intended for the **real stateless Stellar Soroban `UptoSettlement`** design—not a replacement for the payment SDK, not a hypothetical token contract. This is the resource server's usage/settlement state machine. Its injected `verifyPayment` and `submitAuthorizedPayment` adapters MUST call a real x402 Stellar facilitator/SDK and enforce Soroban authorization and simulation. The injected `observeTransaction` MUST use real RPC to verify successful ledger execution and decode authoritative SEP-41 transfer events. The module has **no signer, RPC sender, secret, mainnet default, or built-in broadcast**.

## Original first-party source alignment (read 2026-10-10)

- [x402 Foundation Upto proposal #3134](https://github.com/x402-foundation/x402/pull/3134), head `aa268ec942575be8caa69a2b5afb774a6ec4c09e` / new file blob `b0e709d5ad1808cd4f97b4c3af4f6e20decd3d10`: signed auth binds `payTo`, `asset`, `maxAmount`, `validAfter`, `deadline`, `expirationLedger`, `salt`, `autoRevoke` but **excludes variable actual amount**. Soroban consumes the signed auth nonce. Runtime settlement calls `settle` with the metered amount; contract grants allowance in the *same* transaction then `transfer_from` and optionally atomically revokes leftover allowance.
- [Open Stellar design #72](https://github.com/stellar/x402-stellar/issues/72) discloses previous actual testnet settlement proof; **not a testnet transaction from this delivery**.
- [SF-37 source](../sf37-upto-interoperability/upto-profile.mjs) pins incompatibility between Foundation proposals #3134 (stateless only, omission of `extra.uptoProfile` possible) and #3098 (`stateless`/`contract` alternative). **This engine supports ONLY `stateless`** to prevent accidental stateful-profile fallback; it requires trusted operator contract registry, fee sponsorship and `autoRevoke=true`.
- Generic x402 v2 uses signed *maximum* for `/verify`, *actual metered amount* for `/settle`, a `SettlementResponse` and a ledger transaction. `scheme='exact'` remains unchanged elsewhere.

## Integrating a real metered API

Resource server, *not client*, configures `price={numerator:'1',denominator:'1000'}` (one atomic token unit per 1000 response bytes, rounded **up once on cumulative usage**), buyer ceiling, quote, and trusted known contract registry. `mode='bytes'` meters produced `Uint8Array` chunks; `mode='units'` accepts server-local counted units (e.g. verified generated tokens), not public request input. Ceiling is checked **before** the next metering entry is accepted; API operator must stop streaming when metered consumption would exceed signed maximum, and must not confuse bytes *produced* with network-delivered bytes. If the service needs delivered-byte guarantees, implement that separately at its transport acknowledgement boundary. Empty usage has a zero-atomic close, not an invented charge.

```js
import { MeteredUptoSettlement } from './metered-settlement.mjs';
const session = await MeteredUptoSettlement.open({
  journalDir:'/shared/upto-auth-journal',
  paymentRequired, paymentPayload, verifyRequirements, // actual x402 v2 wire
  registry:{'stellar:testnet':{stateless:{settlementContract:TRUSTED_DEPLOYMENT_ID}}},
  price:{numerator:'1',denominator:'1000'},mode:'bytes',
  verifyPayment: ({paymentPayload,paymentRequirements}) =>
    liveFacilitator.verify({paymentPayload,paymentRequirements}),
});
// Measure trusted server-generated bytes as actual resource consumption.
await session.recordBytes(producedResponseChunk);
await session.seal();
const unconfirmed = await session.submit({
  verifyPayment: ({paymentPayload,paymentRequirements}) =>
    liveFacilitator.verify({paymentPayload,paymentRequirements}),
  submitAuthorizedPayment: ({paymentPayload,paymentRequirements}) =>
    liveFacilitator.settle({paymentPayload,paymentRequirements}),
});
// This is NOT finality yet. Your original RPC/XDR-decoding observer must check
// tx SUCCESS, network, *actual* token transfer from/asset/payTo/amount.
const confirmed = await session.reconcile({observeTransaction: realSorobanTransferObserver});
```

## Replay, indeterminate outcomes and observability

- The reservation ID is SHA-256 of the original signed Soroban auth-entry XDR string, not a caller-controlled job ID. Atomic filesystem create `wx`, strict `0600` journal and fsync occur **before verification or use**. A denied or crashed authorization remains reserved; other workers cannot reuse it in the same shared journal directory.
- Each metered event persists cumulative unit/charge counts and a deterministic event digest. Integer-only BigInt protects signed i128 max and avoids float rounding. Pricing is operator-side configuration and should be bound to the product quote/revenue policy separately.
- `seal()` fixes actual usage. `submit()` calls original-maximum `/verify` again, writes `SUBMIT_UNKNOWN` and **fsyncs before any network settlement**, then calls the injected authentic facilitator. Timeout, malformed receipt or process crash **never causes automatic resubmission**. Operator must recover by signed nonce / tx history or escalate indeterminate manual reconciliation. If no hash was returned, `inspect()` surfaces the persisted unknown state; never simply try a second transfer.
- A receipt marked `AWAITING_LEDGER` is NOT finality. Only `reconcile()` can mark `LEDGER_CONFIRMED` after an operator-provided trusted RPC/XDR observer reports a successful tx and exactly matching SEP-41 transfer (or no transfer for zero charge). Keep actual RPC raw evidence and full auth XDR in a protected evidence repository separately; journal intentionally holds only digests and non-secret identifiers.
- One shared journal filesystem/locking domain is needed across all service workers. Different uncoordinated hosts require a distributed unique-authorization reservation service; do **not** assume local file exclusivity solves cross-region duplicates. The shared disk must guarantee atomic `O_EXCL` and durable `rename`/fsync; otherwise substitute a transactional store. Durable history and billing reconciliation require operator backups.
