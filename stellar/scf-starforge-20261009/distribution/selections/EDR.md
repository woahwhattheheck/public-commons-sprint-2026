# EDR and CoverageJSON operator

This selected Starforge package brings OGC Environmental Data Retrieval discovery, exact CoverageJSON interpretation, native parameter-cell editions, the browser operator, managed Applications registration and complete merchant MCP receiving into one installed product. It uses the maintained distribution builder, source manifest, runtime installer and original SF30 native engine.

The included public reference contains two accepted ICOADS selections from the pygeoapi demonstration: a twelve-cell SST point series and a fifty-four-cell SST/AIRT grid. The original capture, query parameters, returned coordinates, source issues, reviewed mappings, native builds and independent receiving result travel with the package. The installed receiving command verifies all sixty-six cells through the installed CLI and MCP client, receives every original source member, then closes and reopens the same workspace.

## Product entry points

| Entry | Purpose |
| --- | --- |
| `starforge edr` | Discover actual query routes, save explicit selections, retain source responses, review mappings, build and compare native editions, query all cursor pages and receive projects. |
| Managed application `edr` | Open the current private native workspace through its maintained HTTP operator and browser interface. |
| Merchant provider `edr-workspaces` | Borrow the original operator through its private connection file and verified live instance. |
| `merchant_edr_*` tools | Operate discovery, queries, acquisition recovery, source review, mappings, builds, native queries, complete collection pages and exact file receiving. |
| `edr merchant` | Prepare and inspect a release using an explicitly selected native edition, public payment terms and seller origin. |
| `edr buyer` | Read the selected seller's original offer and prepare a reviewed draft through the maintained buyer commands. |
| `delivery/installed-receive.mjs` | Receive both accepted ICOADS projects through the installed CLI/MCP, verify every parameter cell and source file, and cold reopen the same workspace. |

The selected source explicitly retains the original XML workspace, source parser, native bridge and SF30 dataset handler. Python/native dependencies participate in the same manifest as the JavaScript import closure. The complete EDR component includes its acquisition/parser, Workspace, operator, CLI, merchant/customer modules, MCP client, browser lifecycle and delivery source.

The contribution carries the canonical Console browser-assets manifest and the three original USGS facility, job intake and job resolution asset registrations. Their original server/manifest pairs preserve served module aliases during a selective build. Each repository keeps its own canonical Console service and manifest; the selected commit determines those exact files.

## Build the selected package

Use the maintained source checkout or its existing complete Git object store. Select the full commit that contains the EDR contribution, this selection, this guide, the installed receiver and all five accepted example files.

```sh
node /absolute/source/stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /absolute/source \
  --ref FULL_SELECTED_COMMIT \
  --selection edr \
  --out /absolute/original-operation/edr-build
```

The builder resolves the commit, reads its contribution and source selection, follows declared module imports, includes explicit native support files, checks browser module aliases and produces the original npm archive. Its receipt identifies the selected commit, archive, byte count and SHA-256. The output's `distribution.json` and `package/manifest.json` retain the complete source selection and file identities.

Use the retained output directory for an interrupted build. `--offline` consumes the original Git objects already present:

```sh
node /absolute/source/stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /absolute/source \
  --selection edr \
  --out /absolute/original-operation/edr-build \
  --resume --offline
```

The maintained builder's lock, pinned commit, partial-file checks and completed-archive adoption remain authoritative. Select the archive from its returned receipt. The distribution's `BUILDING.md` documents the original build and continuation interfaces.

The maintained source is in `woahwhattheheck/public-commons-sprint-2026`, with product adoption in the existing `woahwhattheheck/tjlabs-stellar-merchant-workspace` repository. The manifest records whichever complete repository commit produced the archive.

## Prepare and inspect the runtime

Use Linux, Python 3.11 or newer, npm, util-linux `flock`, and the Node version required by the source-selected runtime. The original baseline is Node.js 22.16 or newer; the maintained dependency resolver reports any stricter requirement. Keep the runtime and receiving work directory private and owned by the operator.

Prepare the exact returned archive:

```sh
node /absolute/maintained/source/stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs prepare \
  --dir /absolute/original-operation/edr-runtime \
  --archive /absolute/original-operation/edr-build/EXACT_ORIGINAL_ARCHIVE.tgz \
  --sha256 EXACT_ARCHIVE_SHA256 \
  --native --feature schema --feature openapi --feature mcp --operator

node /absolute/maintained/source/stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs install \
  --dir /absolute/original-operation/edr-runtime

node /absolute/maintained/source/stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs inspect \
  --dir /absolute/original-operation/edr-runtime --load --source
```

Preparation retains the exact source under `RUNTIME/package/source/` and resolves dependencies from that archive's declarations. Installation preserves its package lock, readiness results and original dependency tree. The returned `sourceRoot`, `dependencyRoot`, `sourceCommit`, `installationId` and `profileId` identify the actual installation.

An existing compatible complete dependency graph can be consumed through the maintained `install --adopt-existing` route. It verifies the selected profile, imports and native bindings against the original lock. Keep the original cumulative installation owner and returned graph identity when reusing that output.

For an interrupted installation use `runtime-install resume --dir RUNTIME`. An explicit offline installation also needs the corresponding npm cache and any required local Node headers. The maintained `RUNTIME_INSTALL.md` describes preparation, adoption, source verification and recovery.

## Receive both accepted projects

After the runtime returns `READY`, invoke its installed source:

```sh
node /absolute/original-operation/edr-runtime/package/source/stellar/scf-starforge-20261009/sf30-seller-sdk/edr/delivery/installed-receive.mjs \
  --runtime /absolute/original-operation/edr-runtime \
  --work-dir /absolute/original-operation/edr-installed-receiving
```

The helper uses the two bundled projects, both raw captures and the bundled original native result. Optional `--point-project`, `--cube-project` and `--native-result` accept independently received copies with those same manifest-pinned bytes. Its own source must match the installed package's complete manifest entry.

This one receiving lifetime:

1. Verifies installation readiness, complete selected source and original EDR CLI, Applications, merchant-provider and package export registrations.
2. Validates both original sources, mappings, builds and project packets against the accepted native result and installed source manifest.
3. Imports each project through the installed CLI into one `WORK/workspace`, checks its reconstructed native files and snapshot, and traverses every query cursor.
4. Re-exports each identical project and its original dataset projection. Each dataset contains exact `data.csv`, `dataset.json` and `edr-lineage.json`, bound to that edition.
5. Starts the installed operator on loopback and binds its actual private instance through the Applications verifier. One canonical merchant MCP setup attaches to this same receiving workspace.
6. Uses `merchant_edr_*` to inspect and import both host-pinned project inputs, read the complete sources and source issues, save the same mappings, rebuild/read the accepted native editions and traverse every cell.
7. Downloads every original source member, both complete project packets and both dataset ZIPs through the maintained chunked file reader. Each completed file must match its full byte length and SHA-256.
8. Pages all eight complete collections through their view-pinned record interface.
9. Drains the MCP family, closes the operator, cold reopens the workspace through the installed CLI, and verifies both builds and every original cell again.

Each traversal uses pages of at most five rows. Both examples therefore exercise actual cursor continuation. The complete ordered-row digest is SHA-256 over each original canonical JSON row followed by one newline, concatenated in cursor order. The helper also checks native fields, the accepted first row, row count and snapshot. The native result's first-row preview is used only for that first-row check.

The installed result is `INSTALLED_RECEIVING_COMPLETE` after the full lifetime returns successfully. It identifies both references, their exact inputs, installation/source identities, all sixty-six rows, actual interface outcomes and complete public output inventory. Native reference completion and installed receiving completion have separate receipts.

## Saved state and continuation

The original `WORK/intent.json` binds the complete source commit, installed runtime/profile, both captures and projects, native result, source/mapping/build/snapshot identities, selected coverage and any explicit merchant/buyer inputs. One original kernel file lock owns that work directory.

An unfinished run records a new `generations/attempt-NNNNNN/` with its exact helper identity, process outcomes, CLI stdout/stderr, MCP results, received files and primary error. Native sources, mappings, editions and exact exports remain in the same workspace. After reconciling its original process, continue the identical command and work directory.

If the latest attempt is already complete, the helper verifies its intent, helper, source, installation, both reference identities and every public output's length and hash. It returns that same result with `recovered: true` before starting another generation or opening an operator. This recovers a lost final stdout response without repeating the completed receiving journey.

The result records `INSTALLED_RECEIVING_INCOMPLETE` for an unfinished journey. Its primary error is emitted before cleanup, and a failure to save that diagnostic is recorded separately. The original work-directory lock is released in the final cleanup. Differing retained source, input or output bytes are preserved and reported with their affected identity.

Keep the complete private work directory in the original operation's checkpoint when moving to another equipped host. Retain the original selected source archive and installation identities with it. Private startup records, capability URLs and merchant connection files remain outside the public output inventory.

## Operate the received workspace

Use the maintained runtime dispatcher:

```sh
node /absolute/maintained/source/stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs run \
  --dir /absolute/original-operation/edr-runtime -- \
  edr --workspace /absolute/original-operation/edr-installed-receiving/workspace state

node /absolute/maintained/source/stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs run \
  --dir /absolute/original-operation/edr-runtime -- \
  edr --workspace /absolute/original-operation/edr-installed-receiving/workspace serve \
  --host 127.0.0.1 --port 0 \
  --connection-file /absolute/original-operation/edr-operator-connection.private.json
```

The original startup URL opens the same workspace in the browser operator. Discovery presents the selected collection's actual advertised query routes. The query editor retains the collection URL, route, ordered parameters, explicit bounds, linked-document limits, tile-set selection and source rights.

Review returned coordinates, axis order, calendars, units, range dimensions, original values and source issues before saving a mapping. Query parameters remain the operator's explicit strings. The default mapping preserves JSON lexical values; a numeric native column is an explicit reviewed conversion.

The default coverage rule is `require-exhausted`. An operator may explicitly choose `allow-partial` for a retained page-limited acquisition after reviewing its actual next link. The saved mapping and native edition keep that decision. The Activity view pages complete records through the original view SHA, including documents and operations beyond the recent-state summary.

Existing acquisitions continue through their original operation IDs and retained response steps. Installed receiving consumes the accepted project captures and does not start a publisher acquisition.

## Optional merchant and buyer preparation

A reference edition can be prepared for the existing seller workflow when the operator supplies public payment terms and seller origin. Select which accepted edition those terms describe:

```sh
node RUNTIME/package/source/stellar/scf-starforge-20261009/sf30-seller-sdk/edr/delivery/installed-receive.mjs \
  --runtime RUNTIME \
  --work-dir ORIGINAL_MERCHANT_RECEIVING_DIR \
  --merchant-reference point \
  --merchant-payment /absolute/reviewed-public-payment-terms.json \
  --merchant-origin https://operator-selected-seller.example
```

`--merchant-reference` accepts `point` or `cube`. All three merchant options are supplied together and become part of that work directory's immutable intent. The helper runs the original `merchant prepare` and `merchant inspect` commands and verifies the selected native snapshot.

For an existing seller that advertises that exact edition, `--buyer-seller` reads its original offer. Draft preparation additionally requires the reviewed `--buyer-intent`, displayed zero-based `--buyer-accept-index` and complete `--buyer-offer-sha`. The helper records the actual returned offer or draft.

The included public-reference invocation uses data receiving; optional merchant and buyer preparation are reported as `NOT_RUN` until their explicit inputs are supplied. The product's configured merchant and SF88 buyer commands handle subsequent selling, signing and paid receiving with that operation's actual terms and account.
