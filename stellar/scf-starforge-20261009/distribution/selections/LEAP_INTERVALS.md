# Leap device intervals and Utility energy product

The `leap-intervals` selection packages the complete Leap interval operator and the original Utility energy product into one Starforge runtime. The original distribution builder owns selection, source acquisition, immutable package metadata and archive recovery. The original runtime installer owns dependency resolution, native preparation, lock validation and READY state.

The product's `leap-intervals` command is a thin Node bridge to its original Python workspace. It supports source intake, explicit DEVICE ownership mapping, exact native load preparation, original upload jobs, errors, full-file reconciliation, complete missing-window pagination and portable receiving.

## Complete selected components

| Capability | Original implementation retained |
| --- | --- |
| Leap operation | All six Python modules, the complete browser, CLI bridge, original primary contract and customer guide |
| Leap receiving | Full browser/CLI/cold-reopen receiver and sequential build → Utility → Leap entrypoint |
| Utility operation | The complete original Utility contribution, all 63 reviewed implementation members, native source, editions, interval analysis, bill reconciliation and original publication/customer files |
| Managed and agent operation | Original Runtime/Applications worker, Utility managed binding and current merchant MCP host with its complete Utility provider |
| Shared native runtime | Existing dataset, release, publisher, buyer, governor, signer, facilitator and supporting components selected by the original Utility recipe |

The Leap recipe extends the complete reviewed Utility recipe. It does not replace common provider registries or edit the Utility implementation to fit a stale dependency graph. Whole component directories cover dynamic source inputs, and explicit support members retain the application, guides, source declarations and executable receiving programs.

The selection includes 9 source-owned contributions and 34 complete component directories. The original builder still discovers static imports and declared browser resources. Missing declared source, imports, licenses or required data remain concrete build failures.

## Build and preserve the original archive

Use a complete checkout of the chosen joined source and its actual full commit:

```sh
node stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /complete/source \
  --ref FULL_JOINED_COMMIT \
  --selection leap-intervals \
  --out /retained/leap-release
```


Retain the returned archive and complete build receipt before beginning dependency installation. The receipt provides the actual source/archive measurements and hash. The package manifest binds the original commit, selected contribution/recipe bytes, every source member and exact Git blob.

To continue that same build:

```sh
node stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /complete/source --out /retained/leap-release --resume
```


The original journal retains the selection. A different recipe or source does not reuse that output. `--offline` is appropriate only after its actual Git object closure is retained.

## Prepare the complete original runtime

Select all three feature groups explicitly:

```sh
node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs prepare \
  --dir /retained/leap-runtime \
  --archive /retained/leap-release/ORIGINAL_ARCHIVE.tgz \
  --sha256 ORIGINAL_ARCHIVE_SHA256 \
  --native --feature schema --feature openapi --feature mcp --operator

node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs install \
  --dir /retained/leap-runtime

node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs inspect \
  --dir /retained/leap-runtime --load --source
```


The installer selects exact dependencies from the original package. It writes its actual package lock and validates native imports and operation before READY. Retained complete dependencies may be accepted through original `--adopt-existing` validation. Preserve an existing runtime instead of modifying its installed source or synthesizing another lock.

Use Linux, Node 22.16 or later, Python 3.11 or later and the original `flock` runtime. The included Utility XML reader requires **Expat 2.6 or later** in the selected Python. The Leap modules use the Python standard library and original Utility time/shared modules. Existing Playwright and Chromium paths are supplied by the receiving host.

The sequence entrypoint calls the same installer API with the caller's exact Python executable, the native and operator flags, and explicit schema/OpenAPI/MCP features.

The READY runtime's source root is:

```text
/retained/leap-runtime/package/source
```


Its dependencies belong to the runtime directory, beside the original package. Do not point customer receiving at an older keeper while naming a newer package.

## Open the Leap operator

The installed command remains original:

```sh
node /retained/leap-runtime/package/source/stellar/scf-starforge-20261009/distribution/cli.mjs \
  leap-intervals --python /host/python3 \
  --workspace /private/leap-workspace init

node /retained/leap-runtime/package/source/stellar/scf-starforge-20261009/distribution/cli.mjs \
  leap-intervals --python /host/python3 \
  --workspace /private/leap-workspace serve \
  --port 0 --connection-file /private/leap-console.url
```


Use the original printed private connection to open the browser. The workspace retains all original records under one lease. Bearer credentials stay in the selected process environment or private listener capability. Closing a browser does not create another owner; the CLI drains its listener, active requests and own connection file on shutdown.

Review the exact source and explicit DEVICE mapping before submitting. The evidence must establish permitted creation through the Create Meters API or Portal CSV, historical account custody for the intervals, and current custody at upload. The source-owned engine retains eligibility and original provider responses.

## One sequential customer operation

Use the complete configuration in the [receiving guide](../../../../operations/scf-leap-interval-receiving-20261012/README.md), then run:

```sh
/host/python3 /complete/source/operations/scf-leap-interval-receiving-20261012/run-sequence.py \
  /private/utility-leap-sequence.json
```


This single entrypoint builds and optionally preserves the selected archive, installs and inspects the original runtime, completes the original Utility receiving and then opens Leap. It preserves the existing stable operation IDs:

- `UTILITY-DATA-ENERGYTOOLBASE-20261012-1FB3`
- `LEAP-DEVICE-INTERVAL-DELIVERY-20261012`

Utility receiving compares the retained original 20-import/1,340-row core, exercises its original browser/client and 22-name MCP interface, completes CLI cold receiving, and runs the original managed start/stop/reopen workflow. It closes before Leap begins.

Leap receives the complete reviewed files, mappings and batches through the real browser. Only explicitly selected provider actions run. It keeps original UUIDs, exact payloads, complete response/file bytes, row errors and missing windows. It exports through the CLI, restores into a separate private directory, and checks the original logical source/batch/upload identities through read-only desktop/mobile receiving.

The final Leap artifacts are `Leap_Interval_Operation.json`, `Leap_Interval_Workspace.zip` and `Leap_Interval_Delivery.zip`. The sequence retains the complete original Utility result alongside them.

A successful local customer workflow is recorded separately from completed provider ingestion. Expired original examples, reviewed invalid input and explicitly authored functional samples keep separate hashes, purposes and outcomes.

## Recovery and delivery

The original builder, installer and each customer owner retain their own journals. A failed later phase uses the same saved earlier result. A missing response is reconciled against the original UUID; it does not authorize another upload or a fresh workspace.

The Leap receiver freezes the successful report and exact customer-file roster before creating its delivery ZIP. Its completed path verifies the original files and finishes outstanding transfers without invoking product phases. The sequence retains any unresolved child PID and log before another owner may be opened.

Use persistent host directories or already prepared file-service targets and finish transfers before an invocation-local environment exits. Record actual archive hashes, native receipts and independently verified saved files. Source publication and a prepared receiving command do not claim that a native build or provider upload has run.
