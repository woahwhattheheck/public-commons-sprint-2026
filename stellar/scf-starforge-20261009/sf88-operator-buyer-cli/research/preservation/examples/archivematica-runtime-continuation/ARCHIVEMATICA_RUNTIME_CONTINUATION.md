## How identity is retained

The adapter reconstructs the original continuation's exact reviewed program and
namespace successor. It preserves the original 29 application files,
source-input.json, source-verification.json, application-binding.json, operation
journals, every saved request, and all prior failed-attempt evidence.

Existing command and cold-child requests continue to identify their original
logical executable paths. Each entered runtime execution adds a separate
immutable request containing the original request's path and byte hash, its
requested argv, the actual launched argv, and the selected runtime-binding hash.
The actual command is never represented as having run under an unavailable
historical executable.

The original169 child enters the retained receiving source through the declared
adapter. Only its subprocess dispatch boundary is adapted. Its cold children
execute the exact reviewed 9b5bd814 source with the selected Python. Inherited
identity pipes bind each child to its actual host PID, namespace PID, parent,
boot/start time, exact request digest and actual process command. Every acquired
child remains owned through START, terminal wait and cleanup. Cold children
inherit the original169 process group, so its outer timeout drains that same
group. Within the receiver, each cold child is stopped through its own held
Popen handle; only the group leader is terminated with a group signal.

Completed command results and exact original log inodes are reused. An unresolved
legacy command without a valid process/terminal proof remains un-dispatched.
New runtime bindings, adapter source, gate source, launch records and complete
original loss history are retained in the receiving-source tree and complete
checkpoints. The final delivery also contains every original command request,
process attempt, terminal result and log, including the browser command started
after the native checkpoint, together with all runtime-execution bindings.
Hash-named runtime directories preserve earlier selections.
