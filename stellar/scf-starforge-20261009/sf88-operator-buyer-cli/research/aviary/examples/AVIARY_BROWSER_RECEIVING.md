# Aviary: complete browser receiving and interruption recovery

This companion runs the original public-source operator journey against the
maintained Aviary application. It opens the already completed native migration
as the saved-operation example. It does not create a second provider migration.

The earlier browser runner did not reach its first UI action: publisher-page
intake stopped before the public workspace and browser were started. This v2
runner therefore establishes its receiving identity before the first actual
browser mutation. The application and its ten maintained runtime files remain
unchanged.

## Source and entry points

The existing repository entry is:

    stellar/scf-starforge-20261009/sf88-operator-buyer-cli/research/aviary/examples/run-aviary-browser-receiving.mjs

Place its Python companion in the same directory:

    examples/aviary_browser_support.py

This guide is:

    examples/AVIARY_BROWSER_RECEIVING.md

The current application source is the complete Aviary closure from PR2164,
head a33feb2ecbd952e2a46245b7f367a86eac787b54 before this receiving-only successor.
The runtime files are aviary.py, aviary_client.py, server.py, index.html, app.js,
cli.mjs, README.md, PROVIDER_CONTRACT.md, managed.py and APPLICATIONS.md. The
runner verifies the five reviewed core/client/server/UI Git blob identities and
records the exact SHA-256 and length of all ten files. A repeated invocation
must use the same complete source and the same original input directories.

This is a receiving companion. It is not an additional application server or a
provider client implementation. The Python bridge imports the actual selected
aviary.py and calls its original mapping, preview, serialization, ZIP
verification, packaging and export functions.

## Prerequisites

Use the completed original native receiving workspace and its existing
operation ID. Every action in that selected operation must already have the
maintained successful state CONFIRMED or ADOPTED. The browser reads those
original provider IDs and retains them unchanged.

The public workspace must contain the completed original USGS source example:
two resource rows, three media rows, one transcript row, two index rows and two
supplemental rows. Complete the original publisher/rights/transcript intake
before starting this journey. Reuse the five previously captured public
binaries; the browser companion does not fetch them again.

The two workspaces must be distinct. The application directory must contain
aviary.py directly. Use Python 3.11 or newer and an existing Node/Playwright/

## Run the original journey

Use the same command on a later invocation if the producing process is
interrupted. Keep the application, public workspace, original provider
workspace, operation ID and output directory unchanged.

    node examples/run-aviary-browser-receiving.mjs \
      --application /absolute/path/to/aviary \
      --workspace /absolute/path/to/original-public-workspace \
      --provider-workspace /absolute/path/to/completed-native-workspace \
      --operation-id ORIGINAL_COMPLETED_NATIVE_OPERATION \
      --out /absolute/path/to/browser-receiving \
      --python python3 \
      --playwright-module /opt/codex/runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright/index.mjs \
      --browser-executable /workspace/scratch/705ebf077387/browser-runtime/chrome-headless-shell-linux64/chrome-headless-shell

Every option is supplied at most once. The receiving output contains a stable
identity, original snapshots, original UI requests, response captures,
historical commit evidence, original queued job IDs, the actual browser
downloads, capture descriptors and per-invocation process/drain records.

The root process that owns a private producing filesystem must retain that
namespace until the requested complete archives and reports have been saved.
Do not assume an interactive PTY or private /dev directory will survive a
disconnected executor. Save the completed outputs through the already
maintained artifact helper before that producing context exits.

## The complete operator path

1. Open the original public workspace and inspect the complete source
   inventory. Read the selected completed native operation before making any
   public-workspace change.

2. Assign Aviary resource and media keys through the original UI once. Record
   the original expected revision and full saved document. The original key
   allocator considers all source rows, including excluded rows, applies the
   maintained defaults/column/value mappings, and allocates the first unused
   four-digit keys. It also appends its review note; a repeated call would
   create another review.

3. Save a source-review note while delaying the actual response from the
   original server. Type a later note before releasing that response. Confirm
   the later input remains visible, remains unsaved and can be saved through
   the ordinary UI. The request, response and typing observation are retained.

4. Exclude one original resource using the actual reason dialog, save that
   review, and then restore the same source row. Check all five source tables
   through their normal preview controls. The final selection restores every
   original example row.

5. Queue the native CSV/assets package through the ordinary Delivery panel.
   Retain the original job and its timestamped output path, then download that
   exact completed archive through the browser.

6. Queue and download the complete original application/workspace export.
   Check its manifest, original review, source fingerprint and all ten
   application members.

7. Capture the public workspace at desktop and narrow widths, close the
   original server, receive the first complete export through the maintained
   CLI, and reopen that received application/workspace in the browser. Verify
   its original identity, source bytes and saved mapping.

8. Open the already completed native provider workspace, select the original
   operation, enter a new destination draft, return to the saved operation and
   then return to the new draft. Verify the entered draft is preserved and
   select the original operation again. The Run, Reconcile and Prepare
   controls are not invoked. Every original provider action and identifier
   must remain unchanged.

9. Capture that saved operation at desktop and narrow widths, close every
   owned page, server, browser context, browser and CLI child, and only then
   publish the final PASS result.

The browser's request guard allows the normal read/preview operations and the
specific recorded review/package/export requests. An unexpected provider,
planning, migration or reconciliation request aborts the journey.

## Recovery uses the original committed evidence

### Mapping and key allocation

A request file is published before its original UI request is forwarded. On a
later invocation, the Python bridge reads the actual retained review revision
through mapping(db, revision) and compares the document using the application's
own digest function. That digest includes the original canonical JSON and
terminal LF.

If the server committed the review but the response or phase receipt was lost,
the existing committed revision supplies the result. The request is not sent
again. If no commit exists, the original expected revision and before document
must still be current before the same request may proceed.

The assigned-key postimage is derived with the original mapped_tables,
effective_values and KEY semantics, including excluded rows and the exact
appended note. Calling allocate_keys to discover whether it previously
committed would itself change the review, so recovery does not do that.

A new unrelated current review is preserved. The runner stops before a pending
mutation whose original expected revision no longer describes the current
saved review.

### Delayed response and later typing

The held route has explicit completion/rejection promises, bounded fetch and
release deadlines, and unconditional release and unroute cleanup. A failed
fetch cannot leave the receiving process waiting on an unresolved promise.

The first committed note is retained even if the process stops before its
typing observation is published. The later note is completed through its
original saved request. If the observation itself is absent, the runner
records a separately numbered observation pair: save an explicitly labeled
temporary note with the real delayed response, then restore the exact final
review note. An interrupted pair is restored before a new numbered pair is
started. No committed POST is replayed and no missing observation is claimed
as measured.

### Queued archives

Each queue request retains the original pre-request job IDs, request body and
selected source/review. The accepted job ID is retained from its actual HTTP
response or uniquely reconciled from the original persisted job journal. An
ambiguous result is preserved for reconciliation rather than guessed.

A restart of the maintained server marks old QUEUED/RUNNING jobs INTERRUPTED.
If the original ZIP exists, the bridge validates and reuses that exact file,
even if the terminal response or sidecar publication was interrupted.

For a native ZIP whose sidecar was not published, the bridge reconstructs the
expected member descriptors from the original package_rows result, original
field order, CRLF CSV writer and retained assets, then calls the maintained
verify_zip. It records a separate verification receipt; it does not invent or
replace an original sidecar.

If an original INTERRUPTED job has no final ZIP, the bridge first requires the
original application server to have drained. It then invokes the same original
build_package or export_workspace function with the exact already-published
output path and original selection. It preserves operator-jobs.json and saves
a separate completion receipt. It does not create another queued job or a new
timestamped output. A failed, conflicting, corrupt or ambiguously owned output
is retained and reported.

### Downloads and PNG capture

The browser download must match the original queued archive's exact length and
SHA-256. Existing downloaded bytes are checked and reused. A missing download
receipt can be reconstructed from that same original queued file.

A PNG capture records its exact pixel-file descriptor and observed viewport
metrics before publishing the final filename. If the process stops in that
gap, the next invocation publishes the original captured bytes; it does not
redraw different pixels over the first capture. The PNG type is explicit, even
when a temporary filename ends with a receiving suffix.

### Cold receiving and final drain

The first complete export remains the source of the original received
workspace. The maintained receive function can reopen that same archive while
preserving its already received state. The runner never creates a replacement
export merely to obtain a new receiving path.

The output has one held kernel lock for the receiving owner. Native children
carry an operation/output-specific marker; an interrupted continuation checks
and drains only its own retained process family. CLI results use closed
stdout/stderr descriptors and bounded child termination.

A completed application/drain candidate is retained before the final control
lock is released. If publication of the final result is interrupted, the next
invocation verifies that candidate and its files, confirms the original
processes are inactive and publishes the same result. It does not start a new
browser journey in that final gap.

## Outputs and their meaning

The final machine-readable result is:

    browser-receiving-result.json

Its schema is commons.aviary.complete-browser-receiving.v2. PASS means the
complete browser/data-flow assertions succeeded and all owned application
processes, browser resources and control children were drained before final
publication. A failed invocation retains its own runs/<id>/failure.json and
all earlier completed requests/outputs. It never replaces a completed PASS.

The two primary browser-downloaded artifacts are:

    USGS_Aviary_Native_Package.zip
    USGS_Aviary_Complete_Workspace.zip

The complete export contains the actual application, original workspace,
source, saved review, native package and handoff manifests. The received copy
is retained under received-public.

Four PNGs remain in the producing workspace for actual local visual review:

    aviary-public-desktop.png
    aviary-public-mobile.png
    aviary-original-migration-desktop.png
    aviary-original-migration-mobile.png

Their hashes and viewport checks are retained in the result. Independent image
inspection remains explicitly PENDING until the actual PNGs are opened and
reviewed. DOM checks alone do not claim visual acceptance. Keep pixel files
available while that inspection is performed; use the requested artifact
selection for the final application/workspace handoff.

The source publication and V8 syntax check are complete at preparation time.
They do not represent a browser PASS. The actual producing owner will retain
the resulting native receipt, reviewed images and saved artifact identities
from the single original continuation.
