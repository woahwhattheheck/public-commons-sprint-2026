## Command identity, interruption and source history

Before creating a native command, the producer publishes its exact request and
an immutable attempt bound to exclusive stdout/stderr inodes. An inherited
pipe reports the child's own procfs host identity, namespace PID, parent,
boot/start time and exact bootstrap/target command digest. The held Popen
handle owns waiting and termination; host PIDs are observations, not substituted
handles.

The parent retains the child's dispatch binding before releasing START. Every
acquired child and inherited descriptor is drained or closed on an ordinary
failure. Terminal command results and their exact stdout/stderr hashes are
published before log promotion.

If a parent stops after a successful terminal result but before result.json or
log promotion, the same command reuses that retained success and promotes the
original logs. It does not start a second browser or collector. A known failed,
drained command may resume the same application workflow. An unresolved attempt,
or a legacy orphan log without its process/terminal proof, remains undispatched
and is reported as requiring reconciliation.

The initial producer file remains unchanged. Hash-named selected producers,
the two earlier source bodies, full reconstruction input, guide and exact
source-adoption records are retained under producer-source. The final handoff
includes that directory and all command requests, attempts, process/dispatch
records, terminal results and logs.

Before visual review, the producer saves an exact checkpoint containing the
current application, public source/workspace, browser receiving files and cold

are retained only in the original private recovery checkpoint. Its phase is

retained with the checkpoint.

Four PNGs are QA evidence. Their exact private and available shared paths plus
hashes are emitted. The private recovery checkpoint preserves those exact image

all final customer delivery ZIPs and reports; original public-source image
assets remain included as source material.

Inspect the actual four images. Then send the exact emitted response shape:

    {
      "action": "complete-visual-review",
      "summary": "Actual findings from the four displayed images",
      "images": [

          "name": "THE_EMITTED_ORIGINAL_NAME",

an accepted response. The producer can return a bound original PNG to the

It never generates an automatic ACCEPTED decision.

A revision 2 private checkpoint restores all four exact PNGs before visual
inspection resumes. It checks their descriptors against the original browser
result and every actual archive member. Original revision 1 pixel-free

producer reports that precise missing evidence instead of inventing acceptance

## Resume an actually saved checkpoint

This option accepts an already-authorized local copy of a checkpoint created by
this producer. It makes no remote file transfer or sharing change.

    python3 -B complete_aviary_delivery.py \
      --input aviary-delivery-input.json \
      --restore-checkpoint original-checkpoint-selection.json

The selection JSON contains exactly:

    {
      "path": "/actual/already-authorized/local/checkpoint.zip",
      "bytes": 123,
      "sha256": "ACTUAL_FULL_SHA256",
      "file_id": "ACTUAL_RETURNED_FILE_ID",
      "library_file_id": "ACTUAL_RETURNED_LIBRARY_FILE_ID",
      "saveReceipt": {
        "...": "THE_COMPLETE_ORIGINAL_EMITTED_SAVE_RECEIPT"
      }
    }

The complete saveReceipt is the providerReceipt field of the checkpoint result,
also emitted as saveReceipt with RECEIVING_CHECKPOINT_SAVED. Keep its complete
original fields. Placeholder values are not accepted evidence.

The restore holds one original archive descriptor, validates every unique
regular member against DELIVERY_MEMBERS.json before publishing any file, binds
the manifest to this original root/source/workspace/operation, and reuses exact
existing prefix files. It also restores the original checkpoint's save receipt
at its original source pathname. Reopening that checkpoint does not upload it
again. A completed browser checkpoint is reused even after later visual
inspection advances the workspace.

The checkpoint requires the two original accepted archives to remain available
at their original authorized locations. It contains their exact identities and
restoration manifests rather than duplicating their completed receiving.

On a caught failure, the producer first verifies that its recorded commands
have drained. It retains the exact failure and attempts one
INTERRUPTED_RECEIVING checkpoint using the same canonical save route. If a
command remains unresolved or the save fails, the output explicitly reports
that the checkpoint was not saved. It does not claim success or redispatch an
unknown command.
