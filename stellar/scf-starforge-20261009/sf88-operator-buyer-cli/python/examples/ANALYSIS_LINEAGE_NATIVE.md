# Continue an original Analysis publication through Lineage and restore

This programme receives one **already completed Analysis workspace backup** and one original completed job. It reviews that job's actual dependency closure, freezes a publication plan in the original Analysis database, sends the exact event array to the maintained OpenLineage producer, and receives both applications from their original portable archives.

It continues the selected Analysis operation. It does not create another source acquisition, response import, query, model fit, or workbook. The only new Analysis jobs are the reviewed lineage publication and the original whole-workspace export.

Keep the complete selected repository layout, including the SF88 Python workspace and the SF30 openlineage-workspace application. A collection of Python leaf files is not a complete runtime: the original Runtime starts the Node bridge, which imports the original LineageClient.

## Select the original completed input

Use the original Analysis **Backups** workflow to download its complete workspace.zip. Retain the actual download's SHA-256. Choose the original completed import, response-import, query, query-export, or workbook job whose history is being handed over.

For a document research customer, use the complete backup returned by the existing Research → Analysis → workbook continuation. Preserve its original capture, import, query-export and workbook IDs. This programme consumes that result; it performs no further paid or managed-provider request.

The original archive receiver verifies every member and restores the same workspace identity. The programme records the selected backup, full source hashes, actual runtime executables and original root job in operation.json before invoking the browser. A later call must use that exact selection.

The receiving host needs:

- Python compatible with the installed stellar_forge_buyer package and its original Analysis dependencies.
- Complete selected public source in its original repository layout.
- The original installed Node runtime, Playwright package and compatible Chromium executable.
- The original collector application's dependencies. Its own startServer, producer, client, export and bundle receiver are used unchanged.
- One existing private temporary directory. On Linux, --temporary-root /dev can place Chromium's temporary profile in the same foreground's private mount. The operation directory, original source, journal, application state, reports and archives remain at their durable original paths.

Use the maintained resource owner to reserve the measured source/input/output growth and the combined browser, Python, Node and storage memory. Continue an existing resource record through its own liveness and recovery controls.

## Invoke the complete continuation

Run the following from the selected repository. The variables identify actual retained files and IDs; retain their values with the existing operation.

~~~sh
python -B \
  stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/examples/analysis_lineage_native.py \
  --directory "$LINEAGE_OPERATION_DIRECTORY" \
  --analysis-backup "$ORIGINAL_ANALYSIS_BACKUP" \
  --backup-sha256 "$ORIGINAL_BACKUP_SHA256" \
  --root-job "$ORIGINAL_COMPLETED_JOB_ID" \
  --checkout "$SELECTED_REPOSITORY" \
  --node "$INSTALLED_NODE" \
  --playwright "$INSTALLED_PLAYWRIGHT_MODULE" \
  --chromium "$INSTALLED_CHROMIUM" \
  --temporary-root "$PRIVATE_TEMPORARY_ROOT" \
  --operation-id SCF-ANALYSIS-LINEAGE-B9D2-20261012
~~~

The first directory must be absent or empty. On interruption, pass the **same directory, operation name, source selection, backup, root job and runtime paths**. The selected source hashes are part of the request. Resolve source changes explicitly before accepting a different runtime; the programme will not silently change an in-progress operation.

The Python coordinator owns a private file lock and passes it to its browser child. It records the browser process before waiting, and its child-retirement scope includes publication of that process record. A failed journal write therefore still retires the actual child. If a host or transport disconnects, reconcile the original resource record and process family before re-entering the directory. A historical PID alone is not proof that a process is dead.

The programme's --operation-id is its application receiving identity. When a maintained worker is required, use that worker's original operation, records directory, liveness checks and same-record continuation. This script does not create its own capacity queue.

## What the one business journey does

The publish browser starts the original Analysis server and OpenLineage collector. It reads their actual startup records, verifies the expected workspace identities, and configures the Lineage connection on the server. Token contents remain in a private token file and are excluded from the browser journal, plan, portable envelope and stdout.

The browser uses the product controls:

1. Select the original completed job and review its native closure with SQL text disclosure turned off.
2. Choose the actual configured collector, supply the title and note, and save the immutable plan.
3. Capture the actual successful plan-save response and discard its browser reply once. Recover the saved plan by the same original request ID through the existing continuation control.
4. Download and verify the exact frozen events.json before publication.
5. Arm one loss of the **actual original producer's successful HTTP acknowledgement**, bound to the exact operation key and event source digest.
6. Publish through the original Analysis job and Node LineageClient. The collector commits the real source and retained operation before the one response is lost.
7. Read the same interrupted publication, restart the original collector workspace, and explicitly continue the same Analysis job with the same source bytes and operation key.
8. Verify the native retained receipt, source digest and event count. The original producer's replay resolves the committed request.
9. Download the complete publication handover and native evidence, and capture the desktop and 390-pixel mobile page.
10. Export and receive the collector with its original application bundle, verifying its unchanged workspace, event source and replay identity.
11. Close the original Analysis browser/server, run the original full workspace export, and restore that exact archive through the maintained receiver.
12. Open the restored Analysis Lineage page without collector configuration, verify the accepted receipt, download the identical publication handover, and retain the restored desktop/mobile views.

The programme distinguishes an actually discarded response from a committed save discovered during process recovery. ACTUAL_REPLY_DISCARDED is recorded only after the browser discarded the captured response. If a saved plan is found but no discard receipt was retained, the report says ORIGINAL_SAVE_RECOVERED_WITHOUT_DISCARD_RECEIPT.

A collector acknowledgement is also an observed result. The helper retains the actual native successful response and the exact source/key before dropping it. The final result includes that retained observation rather than inferring acceptance from a timeout.

## Retained action and file recovery

The browser journals the exact native POST body before allowing it onto the network. It also records the application's own saved browser journal. On a fresh browser profile, it reconciles any newer captured route request into that original browser journal before loading the page. This covers a process loss after the native request was captured but before the browser journal was copied back.

If a publication request was retained but the original Analysis job was never admitted, **Continue original publication** sends that same request ID. If it exists, the programme follows that job. A complete accepted receipt is reused.

Plan publication and collector actions have separate immutable identities. Collector helper actions retain their request and result before replying. A re-entered action reads that exact result. The helper preserves the publication key, event digest and original exporter identity.

Downloads and screenshots pass through a retained CAPTURED stage before their final filename is published. If the process ends between those steps, the original bytes and digest are used on continuation. An existing complete screenshot is verified and reused.

Browser and child-process cleanup runs independently of journal persistence. An ENOSPC failure while retaining an outcome remains the operation's failure, while the actual owned processes are still retired.

The original collector startup file may report a new port after restarting on the same numeric loopback address. The reviewed host and scheme remain fixed, and both Python and the bridge enforce that scope. A different origin requires another reviewed plan. Reconcile an uncertain earlier publication at its original destination first.

## Original collector control helper

The source-native analysis_lineage_collector.mjs helper starts the maintained application and accepts JSONL requests on stdin:

~~~json
{"id":"retained-control-id","action":"status","args":{}}
~~~

Its ready envelope contains the original operation ID, safe application identity, actual startup-record path and private token-file path. The token value is never returned. Every response preserves the exact request id and returns {id,ok,result} or its explicit error.

Supported actions are status, arm_loss, restart, verify, export_restore and close. The loss arm binds the original producer operation ID and source SHA. Verification and export/restore additionally bind the retained event path, source name, source URL and event count. The helper uses the actual startServer, LineageClient.exportWorkspace, downloadExport, verifyBundle and receiveBundle interfaces.

Do not invoke the helper independently while the original programme owns its collector directory.

## Scope of the result

A successful report proves this local source-native product path: original Analysis history → reviewed native event publication → actual collector HTTP/replay → original portable application and workspace receiving. It does not assert a managed-provider execution, paid purchase, competition submission or production remote deployment.

Until the selected host returns COMPLETE and the original files are verified, this packet is prepared source. Use the actual result and artifact hashes when reporting execution.


## Original MCP handover continuation

The same browser programme also calls `analysis_lineage_mcp.mjs` after the desktop/mobile captures, closing its Chromium context first. The original Analysis server and selected collector remain under that programme's ownership. There is no second native operation and no new query, workbook, publication or paid request.

Provide the complete installed original MCP source closure in the selected checkout, including `stellar-forge/mcp-paid-agent`, `stellar-forge/mcp-merchant-operator/retained-download.mjs` and their actual relative imports. The native coordinator records the selected server, dispatcher, Lineage helper/schema, saved-file reader, download adapter, original transfer engine and initialization helper hashes before the operation starts. Use the same Node executable as the selected original MCP package.

The publication phase registers the already-running Analysis directory through `createNativeAnalysis.register` and starts the original loopback MCP HTTP server through its maintained in-process operator interface. Its private bearer token stays in the receiving directory; it is absent from reports and command-line arguments. The original server's ordinary approve/sign interface is configured with the same refusing functions used by the native Analysis CLI. All exercised tool requests use the original Analysis action.

The MCP caller reads the accepted plan and publication, then repeats the exact saved plan and publication request bodies. It verifies that the same original IDs reopen as complete. It reviews the native seven-file index and checks that its handover bytes/digest match the browser's already retained handover.

The first download deliberately stops only after the maintained transfer engine has fsynced a real downloaded chunk and persisted its prefix digest. The exact interruption progress is saved before the deliberate stop. The caller closes the original MCP server, starts it again over the same private alias/cache state, and resumes the same file directory with the same plan/index digests. An interrupted carrier instead reopens those same records; it never allocates replacement plan or publication IDs. If the original download was already complete before its stage receipt was saved, the result names that actual recovered completion instead of claiming a newly discarded response.

After all seven files are verified, the caller closes MCP and reopens the complete handover through the SDK's offline path. It verifies all seven original files and `lineage-download-index.json` under the maintained download lock. The cold-restored browser phase repeats the read/download/offline continuation against the original restored Analysis workspace with no configured collector, preserving its accepted source and publication.

Each phase stores `mcp-publish/` or `mcp-restore/` beneath the same original receiving directory, with a frozen selection, exact request journal, private operator/server state, resumable handover files and final result. The browser result embeds the original MCP receipt and file records. The top-level original native result therefore includes the complete source/workbook/collector/archive/restore operation and this agent handover; the receiving programme does not create an independent source-only success claim.
