# Native MPP customer delivery

The customer handoff turns a configured Starforge merchant into a usable Node, TypeScript and Python integration. It publishes the actual offers and their atomic payment terms, exports a complete customer directory, and runs purchases through the original native MPP buyer, SF36 spending governor and SF86 reconciliation.

The merchant owns its configured application routes. The customer package owns the public contract and typed operation names. The installed maintained package owns request construction, native challenge review, signing, reservation, response recovery and accounting.

## Merchant delivery

Configure the merchant through the [native MPP workspace](../README.md). The **Customer handoff** tab displays its declared offers and exports these downloads:

| Download | Contents |
| --- | --- |
| Customer package | One JSON bundle containing the contract, OpenAPI document, Node client, TypeScript declarations, Python client and fixed Node bridge, examples and installation guide |
| Contract | Merchant origin, realm, profile revision, offer IDs, HTTP methods and paths, exact network/token/recipient/amount/decimals, request capabilities and pinned native versions |
| OpenAPI | OpenAPI 3.1 application endpoints, response semantics and dynamic native MPP authentication |

The running listener publishes `GET /_mpp/contract` and `GET /_mpp/openapi.json`. The download uses the listener's active profile when it is running, or the saved merchant profile before startup. The console includes the selected profile revision in the download request and checks it again on the server.

The contract's profile revision is the merchant's existing normalized configuration digest. Its public fields contain the offer terms. Resource bodies, local application paths and environment-variable names remain in the merchant configuration.

The same operations are available from the maintained CLI:

~~~sh
starforge mpp customer-contract /private/merchant-workspace
starforge mpp customer-openapi /private/merchant-workspace
starforge mpp customer-export /private/merchant-workspace /private/customer-handoff
~~~

The output directory must be new and have an existing private parent. Stop the operator workspace before using a separate CLI process on its directory.

## Receive a downloaded package

Install the maintained Starforge archive that contains the customer API. Receive the original JSON download through that installed CLI:

~~~sh
starforge mpp customer-receive /absolute/downloads/mpp-customer.json /private/customer-handoff
starforge mpp customer-inspect /private/customer-handoff
~~~

Receiving validates the public contract, the fixed twelve-file list, byte lengths and SHA-256 digests. It regenerates the Node/Python companion code and examples from the installed templates before writing the new directory. Every generated file is written privately, synced and linked into place once. A retained manifest records the original contract and file identities.

After a process interruption, inspect and resume the original destination:

~~~sh
starforge mpp customer-inspect /private/customer-handoff
starforge mpp customer-resume /private/customer-handoff
~~~

Resume fills missing files with the original generated bytes. A changed file produces a concrete conflict. Keep application code and `customer.json` beside the generated files so the original source remains usable for recovery. Inspect reports `COMPLETE`, `WRITING`, `INCOMPLETE` or `CHANGED` and the state of each file.

## Install the customer

The customer requires Node 22.16 or later, Linux with flock, and Python 3.11 or later for the original spending governor. Install the maintained archive into the generated directory. That directory has its own package metadata, Node entrypoint and TypeScript declarations.

~~~sh
cd /private/customer-handoff
npm install /absolute/path/to/starforge-merchant.tgz --ignore-scripts --no-audit --no-fund
./node_modules/.bin/starforge mpp runtime-template /private/mpp-dependencies
npm --prefix /private/mpp-dependencies ci --ignore-scripts --omit=dev --no-audit --no-fund
./node_modules/.bin/starforge mpp init /private/mpp-customer-workspace
~~~

The native dependency graph stays isolated and exact: `@stellar/mpp 0.7.1`, `mppx 0.6.29` and `@stellar/stellar-sdk 15.1.0`. The runtime template copies its maintained manifest and lockfile.

Copy `customer.example.json` to `customer.json`. Configure the actual payer, private workspace and dependency paths, existing SF36 ledger/policy and Python executable, actor/service, and the environment-variable name holding the payer secret. Review every per-asset token and network-fee limit. The generated limits start at the largest declared price for each network/token pair.

The original operator host supplies its existing SF36 consent, audit and operator keys. A fresh purchase is reviewed in the controlling terminal and reserves the exact accepted terms in that ledger.

## Node and TypeScript

The generated client exports `contract`, `source`, `initialize(configuration)` and `connect(configuration)`. Offer IDs are a TypeScript literal union generated from this contract.

~~~js
import { readFile } from 'node:fs/promises';
import { connect } from './merchant-client.mjs';

const configuration = JSON.parse(await readFile('./customer.json', 'utf8'));
const customer = await connect(configuration);
try {
  const purchase = await customer.prepare('report', {
    purchaseId: 'report-20261011-001',
    query: { edition: '2026-10', region: ['north', 'south'] },
    json: { groupBy: 'region' }
  });
  console.log(await purchase.inspect());
  await purchase.execute();
  const result = await purchase.result();
  console.log(result.receipt, result.accounting);
  await purchase.save('/private/results/report-20261011-001.json');
} finally {
  await customer.close();
}
~~~

Use the actual offer ID and application fields from the merchant. The example above is a POST offer. GET offers accept query fields and have no JSON body. Query names are ordered deterministically; repeated values retain their supplied order. Both languages use the original Node request builder for the final JSON bytes.

`prepare` captures the merchant's actual native 402 challenge. It limits the amount to the exported offer price and the customer's own asset limit, then checks the native challenge scope against the exported merchant profile, offer ID, method, full URL and exact body digest. A changed merchant profile requires a current contract before a fresh purchase can proceed. Purchase history marks that interrupted preparation as `CONTRACT_REVIEW_REQUIRED` with the exact mismatch code; earlier valid purchases remain available.

`execute` opens the original governor review in the launching terminal. Successful delivery returns the original stored HTTP response, native payment receipt and accounting result. A pending delivery remains available through inspection and recovery.

## Python

The generated Python module uses only the standard library. Its fixed Node bridge invokes the same installed customer API and original payment implementation.

~~~python
from merchant_client import Customer, CustomerError

customer = Customer('/private/customer-handoff/customer.json')
purchase_id = 'report-20261011-002'
try:
    purchase = customer.prepare(
        'report',
        purchase_id=purchase_id,
        query={'edition': '2026-10'},
        json_body={'groupBy': 'region'},
    )
    print(purchase.inspect())
    purchase.execute()
    result = purchase.result()
    print(result.receipt, result.accounting)
    purchase.save('/private/results/report-20261011-002.json')
except CustomerError as error:
    print(error.code, error.purchase_id)
    raise
~~~

The bridge exchanges bounded JSON through pipes and keeps the original `/dev/tty` operator interaction available. The Python client reopens its workspace for each operation; the Node client owns its workspace until `close()`. Each workspace has one owner process.

`Result.bytes()`, `text()` and `json()` decode the saved response after validating its byte length and SHA-256. The result also exposes `receipt`, `transaction`, `accounting`, `contract_sha256`, `offer_id` and `sha256`. An interrupted prepare retains the supplied purchase ID in `CustomerError.purchase_id`.

## Reopen the same purchase

Use a stable ID for one intended purchase. After a response interruption, reopen that ID:

~~~js
const customer = await connect(configuration);
try {
  const purchase = customer.purchase('report-20261011-001');
  console.log(await purchase.inspect());
  await purchase.resume();
  await purchase.finalize();
  const result = await purchase.result();
  console.log(result.transaction, result.accounting);
} finally {
  await customer.close();
}
~~~

Python uses `customer.purchase(original_id)` and the same method names. Resume uses the original saved native challenge, approved request, reservation and signed credential. Finalize observes the original transaction through SF86 and reconciles its original SF36 accounting row.

Calling prepare again with the same complete request reopens its saved preparation. Reusing an ID for different inputs, configuration or contract raises `MPP_CUSTOMER_PURCHASE_ID_ALREADY_BOUND`. After accepting a new customer package, `purchase(original_id)` still uses the contract and request retained with that earlier purchase on the same merchant origin.

`customer.list({offset, limit})` in Node and `customer.list(offset=0, limit=50)` in Python enumerate retained purchases, including interrupted preparations. `refresh()` fetches the live public contract and reports added/removed offers and exact field changes. It leaves the saved contract and purchases intact.

## Maintained API

~~~js
import {
  merchantContract, contractOpenAPI, buildCustomerRequest,
  createCustomerBundle, receiveCustomerBundle,
  initializeCustomer, connectCustomer
} from '@tokenjunkielabs/starforge-merchant/mpp/customer';
~~~

The maintained export includes TypeScript declarations. A server can generate and deliver a public bundle with `createCustomerBundle({profile})`, or a receiving operator can use `receiveCustomerBundle({bundle, directory})`. Public contract fetching uses the existing SF31 HTTPS transport and the customer's explicit proxy configuration when supplied.

OpenAPI describes dynamic `Payment` authentication and the native 402/receipt headers. The actual challenge is issued for each exact request by the original published SDK.
