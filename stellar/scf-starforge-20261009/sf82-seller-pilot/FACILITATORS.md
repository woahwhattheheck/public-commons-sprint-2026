# Change a retained merchant’s payment facilitator

Use a release that is already in the original SF82 store, read a configured
facilitator’s actual native capabilities, review every generated payment
alternative, and stage that change with the same merchant source. The existing
release comparison, selection, startup, shutdown and rollback controls complete
the change. You can operate it in the release console, from the CLI, or through
the same merchant MCP endpoint.

This workflow uses the official x402 SDK 2.28.0 HTTP facilitator client, original
SF30 route factory and Stellar requirements builder. The native review includes
the provider’s effect on payment fields such as `extra.areFeesSponsored`. A
provider that cannot initialize every retained payment option returns an
incompatible review. Its release cannot be staged from that review.

## Declare your providers

Create a host configuration such as `/private/merchant/facilitators.json`, using
the real HTTPS endpoints you operate or have selected. Replace the illustrative
addresses below before reviewing them:

```json
{
  "schema": "stellar-forge.seller-facilitators.v1",
  "providers": {
    "primary": {
      "label": "Primary facilitator",
      "url": "https://facilitator.merchant.example",
      "timeoutMs": 5000
    },
    "replacement": {
      "label": "Replacement facilitator",
      "url": "https://replacement.merchant.example",
      "timeoutMs": 5000
    }
  }
}
```

Declare 1–16 aliases. Aliases use 1–64 lowercase letters, digits, underscores or
hyphens. Endpoints follow the original merchant’s credential-free HTTPS model;
an explicitly selected local development provider can use
`"url": "http://127.0.0.1:PORT", "allowLocalFacilitator": true`.
`timeoutMs` is the SDK read timeout, from 1,000 to 30,000 milliseconds. The
original SDK’s HTTP retry behavior still applies. Runtime requests keep the
original merchant client settings. The host selects these endpoints; browser
and MCP requests select aliases from this file.

Use your original facilitator profile to select its accepted native payment
flows. The maintained [native facilitator configuration](../native-facilitator/README.md)
supports authorization, upfront, or both. This release workflow reads the actual
advertised capabilities and retains the merchant’s original payment choices.
When the selected supported kind declares `extra.paymentFlows`, the review and
original native startup require every SDK-generated requirement to belong to
that profile. The SDK resolves the flow, including its default. Providers that
omit this optional profile keep the ordinary native SDK behavior.

## Review and operate in the existing console

From the full source checkout with Node 22+ and the original native SDK
dependencies installed:

```sh
node stellar/scf-starforge-20261009/sf82-seller-pilot/release-cli.mjs console \
  --store /private/merchant/releases \
  --facilitators /private/merchant/facilitators.json \
  --port 0
```

Open the printed private operator URL. The console follows this sequence:

1. Select a prepared release in **Prepared releases**. In **Payment
   facilitator**, choose a configured provider and a new release ID.
2. Select **Review provider and native terms**. Read the original declarations
   beside the complete generated alternatives. The review includes amounts in
   atomic units, assets, networks, destinations, timeouts, all native extra
   fields, and the number of alternatives. Expand the actual provider
   capabilities if needed.
3. Select **Stage reviewed release**. Staging checks the original selection
   generation, source digest, host endpoint definition, current supported
   response and generated payment arrays. It copies the verified retained
   source into the original store under the new ID and saves the full review in
   that release’s metadata.
4. Read the original release comparison, including **Reviewed native payment
   requirements**. Select the release, then use **Start selected** or **Restart
   selected**. Selection and running state remain separate in the original
   console. A restart drains this console’s original seller before starting the
   selected release.
5. Reopen the same console and store when you return. The staged review remains
   in release inspection and comparison. **Select previous release** followed
   by the original restart returns to the retained earlier source and runtime.

The new release keeps the original compiled offers, service configuration,
response snapshots and native source metadata. A retained Python, DuckDB, S3,
MySQL, RPC or SQLite release keeps its original launcher and package checks.
Mutable readiness, process and control files are regenerated by that launcher.
Existing external application dependencies and host configuration references
continue to follow their original source family’s lifecycle.

### Startup checks the reviewed terms

Before the selected native server becomes ready, the original SDK reads its
configured facilitator and generates the current requirements. The original
SF30 factory compares every route’s complete array with the retained review.
If the generated values or number/order of alternatives changed, startup fails
with `FACILITATOR_REVIEW_CHANGED`. The original launcher closes its failed
startup; it does not activate the changed terms or select another provider.
Review the current provider into a new release, or use the original rollback.

The startup comparison concerns the generated payment requirements. An unrelated
additional supported network or changed provider signer listing does not force
a new release when the original SDK generates the exact reviewed terms. The
full supported response remains the dated observation saved with the review.
Actual request verification and settlement still use the original configured
facilitator and SDK. A successful capability review or startup does not itself
send a payment.

## Operate from the CLI

These commands use the same store and helper as the console:

```sh
SCF_RELEASE_CLI=stellar/scf-starforge-20261009/sf82-seller-pilot/release-cli.mjs
SCF_RELEASES=/private/merchant/releases
SCF_FACILITATORS=/private/merchant/facilitators.json

node "$SCF_RELEASE_CLI" facilitators \
  --store "$SCF_RELEASES" --facilitators "$SCF_FACILITATORS"

node "$SCF_RELEASE_CLI" facilitator-review \
  --store "$SCF_RELEASES" --facilitators "$SCF_FACILITATORS" \
  --from merchant-v1 --id merchant-provider-v2 --provider replacement \
  --out /private/merchant/provider-v2-review.json

node "$SCF_RELEASE_CLI" facilitator-stage \
  --store "$SCF_RELEASES" --facilitators "$SCF_FACILITATORS" \
  --review /private/merchant/provider-v2-review.json

node "$SCF_RELEASE_CLI" diff --store "$SCF_RELEASES" --to merchant-provider-v2
```

The review output file is created once with private permissions. Inspect its
`compatible`, `nativePayments`, `supported` and `proposed` fields before staging.
Use the exact current `generation` returned by the original diff/status command
when activating:

```sh
node "$SCF_RELEASE_CLI" activate --store "$SCF_RELEASES" \
  --id merchant-provider-v2 --expect GENERATION --reason 'Reviewed provider change'
node "$SCF_RELEASE_CLI" run --store "$SCF_RELEASES" --expect NEW_GENERATION
```

Replace both generation placeholders with the actual numbers returned by those
commands. The original `run` stays in the foreground and Ctrl-C closes its
seller. To inspect or recover the prepared result after a lost stage reply:

```sh
node "$SCF_RELEASE_CLI" inspect --store "$SCF_RELEASES" --id merchant-provider-v2
node "$SCF_RELEASE_CLI" facilitator-stage \
  --store "$SCF_RELEASES" --facilitators "$SCF_FACILITATORS" \
  --review /private/merchant/provider-v2-review.json
```

Repeating that same completed review returns the already verified release,
without another provider read or another copy. A different review or source
cannot take over the same release ID. If the first stage never committed,
staging requires the original reviewed generation and a fresh matching provider
read; make a new review when either changed.

## Use the original merchant MCP endpoint

Add the host-only field below to an existing merchant MCP configuration. A
relative path resolves from that configuration’s directory:

```json
{ "facilitatorConnection": "./facilitators.json" }
```

Keep the existing schema, release store, source aliases and other fields. For a
new ordinary merchant initialization, `--facilitators PROVIDERS_JSON` writes
the same connection. Reopen the original MCP endpoint to load a changed host
profile. The tools are:

| Tool | Input | Result and next action |
| --- | --- | --- |
| `merchant_facilitators` | `{}` | Host-configured aliases and endpoints. |
| `merchant_facilitator_review` | `provider`, retained `releaseId`, new `id`, optional `label` | Full native requirements and current-session review `id`. |
| `merchant_facilitator_stage` | `reviewId` | Original retained release and `reused` flag. |

Use the existing `merchant_inspect`, `merchant_compare`, `merchant_activate`
and original start/restart tools for the returned release. Their source digest,
selection generation and owned instance checks still apply. Reviews awaiting
staging belong to the current MCP session; a reopened session creates a new
review. A committed release and its complete review remain inspectable by the
same retained release ID after a lost reply or endpoint restart.

The MCP and console each drain their in-flight provider reads when closing.
The original process owner controls an active seller. Open the store in a new
operator after closing its current owner; do not run competing release managers
against the same merchant.
