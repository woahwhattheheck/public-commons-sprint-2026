# Merchant onboarding workshare

## Offer: one paid HTTP service, fully receivable by an agent buyer

**Proposed fixed fee: US$1,500. Delivery allowance: five working days after the service, customer task and authorized test account are available.** This is a prospective implementation quote. The reusable receiving software in this directory is the starting product.

The customer gets one existing HTTP service connected end to end: an original discoverable listing; a concrete useful task; exact request and payment terms; a customer-readable review; the existing Stellar Forge buyer's preparation and portable operation; and a receiving walkthrough another operator can complete. The work uses Rialto's original discovery and facilitator interfaces and the original buyer's payment engine.

The best buyer is a small API or agent-tool business that already has a working service and wants a buyer to discover it, understand what a paid request returns, and complete that request without a bespoke integration discussion each time. An existing Rialto seller or a service actively integrating Stellar payments is a direct fit.

## First useful demonstration

Choose an actual HTTP resource from the fully captured original catalogue. Select a task that a customer would otherwise do manually or with an existing tool. Write a concrete useful-output requirement before paying: for example, the exact records, file, fields or computation the task needs, based on the service's own documentation.

Keep the demonstration to one original customer intent and one original native operation. Retain the full response and native result location. Evaluate whether the returned output satisfies the stated task, then let a second operator receive and reopen the same operation. That receiving step demonstrates the practical benefit: a useful paid request becomes portable and reviewable.

A catalogue entry, a code integration and a successful preparation are distinct stages in the customer journey. Record the actual completed stage in the customer account so follow-up is useful.

## Customer intake handled by engineering

Engineering retrieves the public service description, original listing, original API schema and publicly available examples directly. The first customer conversation should resolve business questions:

1. Which recurring task should the paid service perform for this buyer?
2. What complete output makes that task successful?
3. Which existing service and authorized environment should the first delivery use?
4. Who will operate the receiving workflow after handover?

Private credentials or approvals required by the customer's actual service should use their existing secure channel and original authorized operator. An unavailable crawler is an internal source-retrieval task.
