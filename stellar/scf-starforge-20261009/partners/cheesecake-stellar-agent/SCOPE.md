### Choose the task and its next useful use

The three supported read products serve different application decisions. Select
the real request and consuming screen, process or agent action for each product
included in the agreed use case.

| Product | Application work to finish | Retained request and useful continuation |
| --- | --- | --- |
| `getTransaction` | Resolve the selected transaction for a support view, payment-status workflow or agent task. | Keep the exact transaction request, source network and complete original response. Reopening this response uses its original intent; a later transaction is a separately selected request. |
| `getEvents` | Feed the selected application event history or watcher with the agreed event pages. | Preserve the actual filters, ledger range and returned cursor. The original reference's second event page is a distinct reviewed request. A fresh page follows the customer's useful processing cadence and its selected terms. |
| `getLedgerEntries` | Refresh the selected application state from its original ledger keys. | Preserve the exact LedgerKey/XDR request and complete response before mapping the fields the application needs. A later state refresh has its own reviewed request and observation. |

The receiving engineer identifies what the application can do once these
results arrive, who will use them and what event makes the next paid read
valuable. Save one concrete follow-on task with the original workorder. This
provides a practical continuation after the first handover.

For an agreed remote MCP selection, keep the same application workflow and
choose the precise provider resource, tool and canonical arguments in the
private `remoteMcp` configuration. The application intent maps to its original
quote UUID. Source selection stays in the host configuration; an agent selects
the declared request rather than supplying a replacement endpoint, payer or
signer.

### Bind the receiving environment once

The workorder and private installation retain these inputs together:

| Input group | Decision owned by the receiving application |
| --- | --- |
| Source and useful output | Selected application release/lockfile, exact merchant handoff and request bodies, expected response meaning, destination that consumes the result, provider access and supported history. |
| Public purchase terms | Approved merchant origin, network, asset, recipient, integer atomic price, deadline and the applicable discovery/offer selection. |
| Application authority | Stable application and tenant-qualified subject, existing authenticated session, current grant lookup and revocation source, plus the actions that lookup authorizes. |
| Financial owner | Existing native operator/profile or generated MCP operator module, canonical aggregate policy/ledger, original signer reference and host-controlled key environment. |
| Receiving and operation | Existing deployment route, private configuration/state paths, HTTPS exposure and access control, receiving engineer, agreed backup destination and recovery ownership. |

Connect the trusted `authorizationModule` or embedded `authorize` callback to
the customer's current grant service. The application checks that authority on
operations and again before native execution. Native payment approval and
aggregate spending remain with the selected original buyer. The completed
integration uses both decisions: permission to perform the application task
and the buyer's approval to spend for that exact request.

Use the installed `stellar-application` initialization and original Applications
entry with the same configuration on restart. Retain the selected source,
handoff, subject and request identities in the private state. Changes to an
application or request selection are reviewed through the original setup rather
than silently rebinding work already accepted.

An application already using the maintained API-pass customer can attach its
original workspace through the installed `merchant-api-pass` client and generated
MCP settings. Its purchased pass, request, approval, queue and complete response
exports remain in that customer workspace. Select the existing customer path
that matches the agreed product. The [API-pass guide](../../../../stellar-forge/mcp-merchant-operator/API_PASS_WORKSPACES.md)
defines that connection and its retained operations.

### Six-day implementation and receiving sequence

The sequence starts with the complete agreed inputs described above and the
original commercial kickoff. It allocates the existing delivery window.

| Delivery day | Complete implementation outcome |
| --- | --- |
| 1 — Join the real application | Reopen the selected source and merchant handoff on the receiving environment. Connect the existing authenticated-subject and grant lookup. Record the exact request/result mapping and deploy the selected native operator through its original setup. |
| 2 — Finish the paid task | Connect the application's action to native review and explicit execution. Feed the complete original response into the selected application behavior, preserving its source types, binary/XDR content and event continuation. |
| 3 — Review with the receiving engineer | Conduct the first consolidated review on the customer's useful task. Correct the actual authorization, request/response and operator-flow differences; retain the resulting selected source and configuration. |
| 4 — Continue interrupted work | Exercise the relevant lost-response, canceled approval, revoked grant and restart paths through the original request. Complete source/terms change review and resolve the same retained purchase or delivery outcome. |
| 5 — Transfer operation | Deploy through the customer's normal route. Have its authorized maintainer reopen the saved work, consume the complete output and perform the agreed recovery or rollback. When complete encrypted project receiving is selected, use the original snapshot and receiver described below. |
| 6 — Accept and hand over | Complete the second consolidated review, finish the agreed corrections and conduct the included 60-minute engineering handoff using the actual receiving installation. Record accepted outputs and the remaining in-scope correction route in the original case. |

The engineer continues the same task after an interrupted response. Status and
recovery first inspect the original intent, native attempt and quote; native
settlement reconciliation uses the original network/transfer observer. A settled
purchase with incomplete delivery continues its result or fulfillment step. A
fresh useful task gets a new reviewed request after the current state is known.

Cancellation while awaiting native approval propagates to that approval.
Revoked application authority is resolved through the customer's current grant
service. Reopening retains the original financial reservation and result state.
The receiving operator should be able to explain and perform these actions
from the same application view used for ordinary work.

### Deliver complete usable results and operating ownership

Acceptance follows the selected application task through the real receiving
host. The application must consume the complete selected response and make the
agreed result usable to its operator. Downloads and MCP reads retain the same
response identity; a bounded preview is a viewing convenience. For event
continuation, the operator reviews and consumes each selected page and keeps
the returned source cursor with that page.

The handover includes the selected application source, configuration and
environment-variable names, original merchant handoff, request and review
identities, native attempt/outcome, complete response and the operating guide.
The customer supplies wallet/provider credentials through its normal host
environment. Existing authorization and signer modules stay under the
customer's source and custody.

When encrypted project handover is selected, drain active application work and
capture through `project-snapshot` or the running application's Project view.
Receive the complete encrypted bundle with `project-verify` and
`project-receive`; the receiving engineer can immediately read/export the
captured useful results. Review original destinations before choosing either
canonical restoration or attachment to the current host.

Restoration preserves the original application identities and complete shared
financial history. Current-host attachment verifies that the captured journal
remains part of the current history and retains later legitimate work. The
receiver's archived reviewer and the original live application use their
respective configured subjects and current authorization. Live continuation
keeps the original bound application identity and original spending owner.

The maintainer completes one relevant support case using its retained
operation, observed failure, source and repair. Record the time to usable
output, active integration/correction effort, waiting time, recovery time and
the result accepted by the receiving engineer in the original workshare.
Separate active engineering from elapsed waiting so later fixed-scope work can
be priced from the actual effort. The original invoice dates, two review
rounds and ten-business-day defect-correction terms below govern delivery.
