It performs HTTP discovery, conditional update, ETag readback, history and search, with complete request/response files. Each operating result states this source and endpoint classification. A client installation uses its own selected connection, discovery, authentication and actual receiving records.

## Run the complete operation

From the SF30 SDK directory:

~~~sh
python fhir_referral/operate_receiving.py \
  --source-root /absolute/source/stellar/scf-starforge-20261009/sf30-seller-sdk \
  --output /absolute/private/gravity-native \
  --examples /absolute/originals/examples.json.zip \
  --definitions /absolute/originals/definitions.json.zip
~~~

Optional --workspace names an existing selected private directory; its default is OUTPUT/workspace. Optional --node selects the installed Node executable. SF30_REFERRAL_NODE and CODEX_PRIMARY_RUNTIME_NODE are accepted existing runtime selectors.

Keep the original output and inputs when continuing. RECEIVING_JOURNEY.json retains the input binding, stable request UUIDs, phase identities and saved results. The operation holds its own receiving lock. A completed phase is reused from its retained output; an incomplete phase reconciles its original saved native records. Start one writer for that exact output/workspace.

## What the operation carries end to end

### 1. Original archives and source graph

The operator retains the complete examples archive, all original JSON members, the full definitions archive and its member index. It creates the native source from the declared original example members and explicit reference-base assignment, then selects the published fulfil/order Tasks and their related original resources.

Native source identities preserve the resource document, JSON Pointer, lexical JSON, original source/member hashes and qualified references. The operating record retains the full source and graph IDs.

### 2. Four topologies and all review rows

The driver saves explicit direct, direct-light, intermediary and intermediary-light configurations, including source/target/intermediary roles and recipient-server ownership. It adopts all 57 requirement rows and 24 field rows into the native review, retains the reviewed dispositions and source citations, and freezes the selected cohort assessment.

The queue and its complete field detail preserve Task status, requester/owner, focused ServiceRequest, subject, outcome, Consent and unresolved source relationships. Scoped operating decisions name the selected purpose and responsible actor.

### 3. Reviewed correction and comparison

The operation selects an original accepted Task, saves an exact correction preview, reads it back, and applies that original preview/hash to produce its in-progress successor. The full predecessor source, correction patch and qualified resource map remain available.

The successor is assessed and compared with the original edition. The result retains both original and corrected source/edition/assessment IDs and the selected logical Task identity.

### 4. Actual conditional HTTP exchange and monitoring

The published-example server loads the retained original resource bodies on an ephemeral loopback port. Native discovery reads its actual capability statement. The selected update retains the original server preimage and ETag, sends its conditional request, then saves the actual response and complete readback.

Reopening the completed operation uses its original UUID and saved native result. A stale preimage is returned for review. Instance history uses its supported _since selection and advertised history-instance capability; Task search uses the selected search filters. Both retain complete HTTP pages and native acquisition records.

History and search remain distinct requests. An instance-history request rejects until, owner, requester and status selections that do not belong to that history route. Every monitoring request binds its selected connection and discovery.

### 5. Complete HTTP custody

After the original fixture server closes, the operation receives its complete request/response journal and every corresponding file in Gravity_Complete_Original_HTTP_Exchange.zip. Source classification, origin, request methods, conditional headers, status and body identities remain inspectable.

### 6. Native dataset and customer receiving

The original SF30 mapping and dataset engine projects source resources with their original keys and unchanged resource JSON. The driver builds the original and corrected datasets, runs their native query and comparison, and receives the complete customer packet into a fresh destination.

The original-to-corrected projection records the concrete changed row and keeps every other source row. The result preserves plan/build/artifact identities and the full receiving files.

### 7. Original merchant and buyer edition

The original eLTSS merchant/customer adapter joins the SF30 and SF88 engines. The operation prepares the dataset merchant, reads its actual offer and native 402 challenge, saves/reopens the same original buyer configuration, publishes the corrected dataset with the existing expected-snapshot/revision guard, and retains the successor offer and buyer preparation.

These are native source, seller, buyer-configuration and edition operations. The retained result identifies their actual selected payment configuration and HTTP outcome.

### 8. Frozen handoff and actual receiving

The operation freezes the original source, selected edition, review, assessment and complete native workspace into Gravity_Complete_Referral_Handoff.zip. Repeating the same full handoff input returns its saved handoff and verifies the same complete files before returning.

A fresh receiver imports the complete handoff, reopens its retained source and assessment, and records the receiving result. Repeating that same receipt reuses its saved identity. The handoff includes readable HTML/CSV alongside complete machine-readable originals.

### 9. Whole editable restoration

The operation exports Gravity_Complete_Editable_Workspace.zip, imports it into a fresh private directory, reopens the original UUID, and compares all retained referral/native records and source files. The native dataset and complete artifact bytes are checked after restoration. Repeating the import reuses the same selected original workspace.

The editable archive is the portable continuation artifact. Copy the unchanged original operating record with it; a later browser or connected receiver can select the received directory explicitly while preserving the original record and UUID.
