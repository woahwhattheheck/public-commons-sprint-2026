# One complete publisher native journey

The original input selects one workspace, runtime, source release, operator and receiver. The caller performs the complete workflow and preserves its original per-phase request before each dispatch. It starts no scheduler and installs no environment implicitly. Use the same original operation and directory after an interrupted execution.

## Prepare one real runtime

Reuse verified installed components when available. The Python environment must already contain the exact publisher-compatible dependency set. A new explicitly chosen environment can install the reviewed package's `native` extra:

```sh
/absolute/python -m venv /absolute/private/native-environment
/absolute/private/native-environment/bin/python -m pip install '/absolute/reviewed/groundwater[native]'
/absolute/private/native-environment/bin/python /absolute/reviewed/groundwater/examples/prepare_runtime.py --directory /absolute/private/prepared-runtime
```

The preparation helper retains an original request and calls the unchanged bundled FloPy `run_main` for MODFLOW6 release 6.8.1's `mf6` and executables release 29.0's `mf2005dbl`. It does not use the old MF6 in the latter archive. The executable bytes, pinned versions and complete installed Python closure define the runtime fingerprint. Full version-probe output and return codes remain separate observations: the legacy Fortran EOF diagnostic contains process IDs and memory addresses that change between otherwise identical probes. Keep downloads and binary source provenance with this original runtime.

Select an existing Node, Playwright module and Chromium executable for the browser. The caller uses those paths, `--disable-dev-shm-usage` and its own private browser temporary directory; it does not install another browser.

## Run the one original operation

Copy [publisher-input.example.json](publisher-input.example.json) to a private original input. Supply actual paths and the complete reviewed source head. The work directory must be outside both the application directory and any parent Git checkout.

```sh
/absolute/native-environment/bin/python -B /absolute/reviewed/groundwater/examples/run_publisher_workflow.py /absolute/private/publisher-input.json
```

The caller:

1. Retains its complete application manifest and exact input, initializes one original UUID and creates one labelled publisher project.
2. Captures all fourteen original publisher files and records the actual configured runtime.
3. Reviews the source discrepancies and runs the unchanged publisher baseline, including both actual solvers and original plots/assertion.
4. Creates and reviews a metadata-only child declaring legacy feet/seconds, then runs both solvers as the compatible reference.
5. Retains a complete ZIP of files actually generated by the unchanged native run.
6. Starts the original loopback operator and drives its real browser forms. The UI recovers or imports that exact generated native package, records an attributed inspection of its unchanged native references, and preserves the original source and baseline edition; reads the unchanged source/result; authors a 4e-8 recharge child from the compatible reference; reviews, queues and executes it; reads the actual scientific comparison; freezes all three original runs; delivers and records a named package decision; then creates a stopped full backup.
7. Independently inspects/receives the exact report, checks its delivered bytes and restores the complete backup into a new destination.
8. Reopens every original native result and committed request, then uses the restored operator to inspect the same result, report and original history.
9. Drains all owned browser/operator/native children before creating `output/native-result.json`.

The baseline retains the executable/prose recharge discrepancy and actual legacy metres/days declaration. The driver never labels that baseline a compatible physical comparison. The metadata reference and recharge scenario are explicitly attributed technical examples, not customer recharge estimates or a calibrated site model.

Only known source findings have supplied example dispositions. A new blocking, listing, budget or numerical finding stops for actual named review. It is not automatically approved. Exact original binary results remain authoritative.

## Original request recovery

The parent stores each original request in `requests/<phase>.json` before dispatch. It reads the native operation first on replay and uses the same ID, expected version and payload if the commit is still absent. If that exact execute request committed but its queued run has no dispatch, replay continues the same native side effect under the original run lock. It does not replay a dispatched or completed attempt. The browser likewise binds one phase and its exact pending UI request in one private publication before permitting the network request. A lost response is recovered through the original operation endpoint. A missing source file or differing original request stops the continuation.

The core retains native run identity across all attempts. The default caller does not repeat an interrupted dispatched attempt. If the operator has inspected the actual stopped attempt and approved continuation, supply its actual ID:

```sh
/absolute/native-environment/bin/python -B examples/run_publisher_workflow.py /absolute/private/publisher-input.json --retry-run ORIGINAL_RUN_ID
```

This option applies to the parent-owned baseline/reference runs. A browser-owned interrupted scenario uses its retained UI **Continue original run** and explicit retry selection; do not create another scenario or queued run. Continue the same private browser journal after resolving that original run. Cached browser phases verify their original operation IDs and outputs before returning.

`--phase prepare` stops after the native baseline/reference and writes `browser-handoff.json`, with no live owned solver. `--phase complete` consumes an already completed `output/browser-operate-result.json` and performs independent receiving/restore. The normal `all` command owns those phases together. These modes are continuation boundaries of this same operation, not separate jobs.

A timeout leaves the actual original run pending. A completed run/report whose frozen bytes disappeared is reported unavailable. Neither recovery path generates fresh outputs under a completed identity.

## Continue after a reviewed application correction

An existing journey retains `journey-input.json`, its exact configuration and every queued run's frozen source. To continue it with a reviewed caller or launcher correction, supply `--source-revision /absolute/source-revision.json`. The record must contain:

- `schema: "starforge.groundwater-journey-source-revision.v1"`, the original `operation_id`, and `initial_input_sha256` computed with the application's `digest` over the original journey input.
- The complete current `application_files` inventory and its `application_sha256`, plus the actual reviewed 40-character `source_head`.
- The original operator's `actor`, a concrete `reason`, and timezone-qualified `created`.

The caller verifies these against the original input and current complete application, then retains the new selection in `application-revisions/<application_sha256>.json`. Subsequent continuation can use that same retained revision. The original input is not replaced. The handoff and native result identify both the initial and current application and include the source revision.

Legacy runtime records remain immutable. Their entire original fingerprint is validated before removing only the volatile version-output and probe-exit fields for comparison with current executable/dependency content. A changed binary, dependency file closure, version or interpreter remains a real mismatch. A reviewed current launcher can therefore start a never-dispatched original worker without changing that worker's scientific source, request or run ID.

## Actual deliverables

- `output/native-result.json`: complete source/runtime/run/browser/receiving/restore result after drains.
- `output/browser-operate-result.json` and `browser-restored-result.json`: actual operator requests, selected IDs and screenshot hashes.
- Original screenshots under `output/`, with no overwritten historical captures.
- The complete report ZIP and manifest named by the result.
- The full workspace backup named by the result; preserve it in the approved durable delivery destination during the same producing lifetime.
- Original logs, private input, phase requests, exact native attempt trees, independent report receipt and restored workspace.

The result distinguishes actual model completion, technical review, file delivery and the named example-package acceptance. Tethys needs an existing configured portal and account; the separate [portal receiving continuation](../TETHYS.md) consumes this exact backup and never reruns a solver. Source publication or syntax validation does not establish portal or solver completion.

## Original browser detail navigation

The browser continuation selects the saved project through the operator control and waits for that choice to be retained. Project selection intentionally returns the UI to the page inventory. The caller then reopens and reloads the exact source, edition, run or report route, verifies the selected project and original workspace, and checks that the requested record is rendered before it interacts with that detail. Reloading avoids a late project-selection refresh replacing the requested detail. The same sequence is used in the restored-workspace pass.

This is a read-only navigation correction. It preserves the original browser journal, phase requests, operation IDs, queued worker and completed native outputs. An existing journey adopts the complete reviewed source through the source-revision mechanism above; it does not replace the initial input or create another model run.


## Continue the original saved native-package import

If the old reader reported a `BAS6` unit number as a missing path, preserve the generated ZIP, saved source/edition and original browser import request. Install the complete reviewed application through the source-revision mechanism above. Run the same original input, directory and journal. The caller recovers the committed native-package-import phase, then uses the visible **Inspect retained native references** form for the new native-package-reference-inspection phase.

This phase binds the original source and ZIP hashes, unchanged selected namefiles, current reader and exact inspected basis. It verifies that the original source and its editions did not change. An actual missing required input still stops the continuation. The baseline and reference results are read from their existing completed runs; this inspection starts neither solver.

An already saved browser-handoff.json and browser-operate-input.json remain exact. The parent validates their unchanged data, paths and selected original identities, and records the current source context separately under browser-handoff-revisions. The final native result identifies the current application source and the original browser handoff source separately. It does not rewrite an old phase payload to carry the new reader.

The stopped backup carries the original import, all reference inspections and their operations. Independent restore compares the original source and inspection basis, then the restored browser displays that same source inspection alongside the original report and native results. A previously complete browser result remains an immutable completed result; it is not recaptured solely because a newer reader is installed.


### Completing a retained browser result

The publisher keeps native file-access descriptors in their original form while reading the backup and report. At the JSON handover boundary it validates each complete file again and records its absolute path as text with the unchanged filename, byte count and SHA256. The same projection is used in `restored-browser-handoff.json` and `native-result.json`; native `Path` objects are never embedded in these JSON artifacts.

If the original operator browser has already written a complete `browser-operate-result.json`, continue the same input/work directory with the publisher's existing `--phase complete` option and, for changed installed caller source, the original attributed `--source-revision` record. This verifies the completed native runs, exact report and backup, finishes the original independent receiving/restore and runs the same restored-browser phase. It does not queue another scientific run or create another report/backup. Existing restored handoff and input files remain create-only, and their exact original IDs and archive identities are checked on replay.
