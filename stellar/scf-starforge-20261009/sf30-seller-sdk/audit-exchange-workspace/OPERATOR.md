# Audit Exchange operating guide

Audit Exchange keeps a complete building audit document, its validation choices, and the work performed against each revision in one local workspace. The operator interface opens the server for that workspace. Every XML change creates a retained revision; reviews, explicit links, projections, analyses, and saved editions stay attached to their original source identities.

## Open the workspace

Start the installed Audit Exchange application with its original workspace directory. Open its local server URL in a browser, enter the server URL in **Open workspace**, and connect. A known workspace ID can be entered to pin the connection before its first read. Use the exact local URL announced by the running application; the default address is `http://127.0.0.1:8769/`.

The connection bar shows the workspace name, complete workspace ID, and current version. Enter the operator name that should appear on saved changes. **Refresh workspace** reads the latest version and preserves the revision currently being inspected. A later source revision does not silently replace an open historical revision.

The left navigation covers the complete workflow:

| Section | Work performed |
| --- | --- |
| Workspace | Inspect retained sources, review workload, installed schemas and profiles. |
| Source documents | Import complete original XML bytes and see each source's current revision. |
| Inspect and correct | Browse entities, exact fields, local references, time series, validation, and the complete XML. Stage an atomic group of corrections or replace a complete document. |
| Compare revisions | Compare full field values and reference changes between two retained revisions of one source. |
| Saved editions | Save and reopen a complete workspace selection with its source revisions and related work. |
| Review work | Assign and maintain reviews tied to one source revision and, optionally, one entity. |
| Related workspaces | Save explicit source-bound links to Haystack, LDA, and turnover records. |
| Native analysis | Preview one actual reading stream, supply its weather data, and run the installed native processor. |
| Turnover tables | Select actual source entities, inspect all eight table projections, and export their complete CSV files with the original XML. |
| Export and receive | Retain complete XML, review, workspace, or editable application packages; receive a complete exported case. |

Tables show every retained row through **Previous** and **Next** controls. The range above each table states the displayed range and full row count. Filtering searches the complete source result in the browser. Source detail, export, and receiving operations use full documents and complete packages.

During a foreground action, forms keep their submitted values until that action returns. This prevents a saved response from clearing a newer unsent edit. Background analysis status refreshes preserve editable forms, selected streams, and drafts.

## Import original XML

In **Source documents**, choose or drop one complete XML file. Review its filename, byte count, and SHA256. Enter a useful source name, select the installed schema, choose any applicable validation profiles, and add an import note.

**Import source** saves the complete original bytes and creates the first source revision. The interface opens its validation result. The document's declared version and the schema selected for validation are displayed separately. Each revision retains the selected schema and profile list, the source hash and byte count, the operator, and the note.

Validation diagnostics belong to the recorded revision. They remain available while you inspect and correct the document. The XML export retains the complete selected document, including revisions carrying diagnostics.

Import another file as a new source when it represents a distinct audit document. To continue an existing source, open its current revision and use **Replace with a complete XML revision**. Replacement preserves every earlier revision of that source.

## Inspect complete source structure

Open a source and revision in **Inspect and correct**. The context panel shows the exact source and revision IDs, XML hash and byte count, declared version, selected schema, selected profiles, and revision note.

**Entities** lists the source's own structure. Search by label, XML ID, XML kind, semantic kind, or path. The semantic-kind filter uses the native model's source-location classification to select physical buildings, systems, and other classified entities. The complete table keeps the original XML kind visible separately. Selecting an entity shows both kinds, its exact key and structural path, facility and building associations, and field count. Use **Show fields** to inspect its own values, **Create source-bound review** to record review work, or **Add related workspace** for an explicit external record join.

**Fields** shows text and attribute values as exact strings. Blank strings are visibly identified. Long values remain available in their cells. Structural paths and expanded attribute names come from the native parser. Preserve these supplied identities when using the client API.

**References** shows each source-local XML ID reference, its original target ID, resolution state, and unique local target where one exists. A related record in another workspace has its own explicit sidecar link.

**Time series** retains the source's literals for start, end, value, interval, reading type, and units, together with its building, scenario, resource, entity key, and path. Open a source-stream cell to inspect the complete native row, including its stream key, phase, peak type, quantity, flow direction, interval duration, original resource/weather identities, and units source path where those fields are supplied.

**Complete XML** displays the full parsed text. **Copy displayed XML text** copies that full text to the clipboard. **Export this complete XML revision** downloads the server's complete retained bytes with hash verification.

## Save an atomic group of field corrections

Open the current revision of the source. Historical revisions remain available for inspection, comparison, reviews, analysis, and export; **Open current revision** deliberately changes the editing context.

In **Fields**, select **Stage correction** beside an editable field. Review its exact path, kind, expanded attribute name, and current value. Enter the proposed value, including its intended whitespace and blank characters, then add it to the correction draft.

Repeat for every related field. The draft shows each full path and before/after value. Remove a staged correction to omit it from the group. For an XML ID change, stage the corresponding reference changes explicitly when those references should follow the new ID.

Add a revision note and choose **Save all corrections as one revision**. The request includes every original expected value and the original revision ID. The native workspace applies the group atomically, validates the complete resulting XML with the selected schema and profiles, and returns the new revision.

A changed source revision or changed expected value produces a conflict with the current workspace state. Review that current source and prepare a fresh correction after closing the refused request. The original draft and request remain available for inspection.

Correction drafts are retained per workspace, browser tab, source, and revision. Navigation saves the current draft before opening another context. An explicit **Clear correction draft** action asks before replacing staged work.

## Record schema and profile selection

Open **Validation** to inspect the full XML schema diagnostics and every selected profile's diagnostics. Each diagnostic shows its code, message, severity, source path, and available line or column.

To choose another installed validation schema or profile set, select it in **Record a validation selection**, add a note, and save. This records a new revision against the complete current XML with the selected validation choices.

To save a replacement document, open **Complete XML**, choose the full replacement file, review its hash and byte count, select its validation settings, and save. The expected current revision binds the replacement request to the source you reviewed.

## Compare revisions and save editions

**Compare revisions** uses the source currently open in the inspector. Select the before and after revisions and compare their complete structures. Added and removed fields remain distinct from changed fields. A blank value remains distinct from an absent field. The comparison shows exact before/after values and the complete reference changes.

A **saved edition** records the current workspace selection and its associated reviews, links, and analysis runs. Give it a name and note. Reopening an edition shows the exact source revision IDs and hashes it retained. Opening a source from that table opens the saved revision directly.

Use an edition's **Export edition review** action for its recorded review context. **Export complete workspace with this edition** retains the complete workspace history and identifies the selected edition in the export request.

## Maintain assigned reviews

Open the relevant source revision, then create a review for the document or a selected entity. Record the title, status, note, assignee, due date, and evidence links. Each evidence line has this form:

~~~
Audit scope | https://example.org/original-scope
Equipment documentation | https://example.org/equipment-documentation
~~~

The permitted statuses are **open**, **investigating**, **resolved**, and **accepted**. Reopening a saved review opens its exact source revision before filling the form. Changing or saving a later XML revision leaves earlier reviews attached to the revision they assessed.

The review table can be filtered by status or searched across its title, note, assignee, and source name. Saving an existing review uses its existing review ID. **New review** prepares a separate review on the current source context. Replacing an unfinished review form with another saved review requires a deliberate choice.

## Join related workspaces

In **Related workspaces**, select the source entity, target kind, target workspace ID, and complete target record ID. Add a note that explains the relationship, then save.

Supported target kinds are **Haystack**, **LDA**, and **Turnover**. This explicit sidecar records the relationship at the selected audit source revision. The join table shows both ends' original identifiers so another operator can open the intended records.

Open an existing row to edit the same link ID. **New link** starts a separate relationship. The UI preserves an unfinished form until you deliberately replace it.

## Run native analysis with actual selected readings

Open the audit source revision to analyze. In **Native analysis**, select the building, scenario, resource, reading type, units, and source stream in order. Available downstream choices come from the actual time-series records in the selected source revision. The source-stream choice displays its original phase, peak, quantity, flow, and interval details where supplied. Its exact stream key is carried through preview and the retained native analysis request so separate recorded streams within one resource remain distinguishable.

When readings have no source-recorded building association, the Building control requires an explicit choice from the source's actual native Building entities. The view labels that choice and retains the original empty associations. Source-linked readings retain their recorded building bindings.

Choose **Preview the complete selected readings**. Inspect every selected reading, the full source selection, available diagnostics, and the native processor profile. The source's literal units and reading types remain visible. Total, peak, cost, and other streams keep their original resource and reading identities. Native energy modelling requires a complete, unambiguous Total-energy selection; preview diagnostics identify source conditions that need correction.

Choose the actual weather CSV for the analysis, review its filename, complete byte count, and SHA256, and record the weather source or acquisition reference. Use the recorded time and weather controls to enter:

- The original source's IANA timezone when its timestamps omit an offset.
- The acquired weather's IANA timezone when its timestamps omit an offset.
- The actual observed temperature units, Fahrenheit or Celsius.
- The acquired weather interval: 15 minutes, hourly, or daily.
- The meter interval when it needs an explicit selection; otherwise the native processor reads it from the original selected measurements.
- One or more of the actual native models: Mean, SLR, 3PC, 3PH, 4P, 5P, HDD, CDD, HDD-CDD, TOW, and TOWT.

An explicit timestamp offset remains authoritative. A timezone choice describes the supplied observations; record any necessary source interpretation in the analysis note and acquisition reference. The native processor validates actual time alignment, contiguous coverage, units, and each model's applicability to the selected meter interval before retaining its result.

**Complete native model options** contains the same JSON object edited by those controls. Changing one control preserves the other options. Editing valid JSON refreshes the controls. Keep advanced choices there, including `weatherColumns` mappings for `time`, `temp`, optional `end` and `station`; exact `baseline`, `reporting`, and `normalization` start/end periods; `modelArguments`; `endPolicy`; `lastEnd`; `balancePoint`; `confidenceLevel`; `allowNegativePredictions`; `seed`; `timeoutSeconds`; and `weatherMissingValues`. Weather units and interval need an explicit value. Omitting `models` requests the full eleven-model catalog; each model's returned outcome describes its actual applicability and fit.

**Run with these readings and weather** retains the complete selection and original weather bytes before submitting the native operation. The first committed result identifies the queued analysis. The server then runs the selected native processing in the background and retains its status, diagnostics, full input identity, and full output files in the workspace's analysis history. Retained summaries show the exact source selection, reading count, original model options, and weather metadata.

While the Native analysis view is visible, queued and running analyses refresh automatically. The selected run's result and output links update as the work progresses; unfinished forms, staged corrections, source selection, and weather selection stay in place. Switching away or hiding the tab pauses these status reads. Reopen the view or use **Refresh workspace** to read the current retained outcome.

For a retained `needs-runtime`, `needs-input`, or `failed` outcome that the native processor marks `metadata.terminal: false`, **Resume the same native analysis** continues the original analysis ID after its reported external or runtime condition is repaired. The original readings, weather, model options, and completed model files stay with that operation. Enter a continuation note; the workspace retains the preceding diagnostics, outputs, and metadata in its continuation history before requeuing the same inputs. A changed source, weather file, or model configuration is a deliberate new analysis.

Recovering an earlier committed request returns its original recorded result. An analysis request's original result can be the queued response; the UI joins its analysis ID to the current retained run so its later native outputs remain available. Replaying a resume request likewise recovers that original continuation without issuing another one.

Each output is downloaded from the connected workspace's retained file route. The client verifies the supplied complete byte count and SHA256 when that output provides them.

**Preview all turnover tables** returns all eight exact table names from the installed projection, their complete rows, mapping diagnostics, source and revision IDs, and selection hash. Review every applicable table and diagnostic.

## Recover the original request

Each mutation receives a UUID, the original workspace version, and complete inputs. The browser retains the complete request transactionally before sending it. A small workspace marker identifies the one pending request across tabs; complete XML, weather, and case bytes remain in the retained browser record.

If the response is lost, the **Retained original request** panel identifies that request. Choose **Recover original request**. The same UUID, original version, action, and complete inputs are submitted again. The server returns the original committed result even when the workspace has advanced since that request.

**Download complete request** saves a complete JSON copy, including original file bytes. To reopen that copy in a later browser session, first connect to the original workspace, expand **Open an original request file**, and select the file. Its workspace identity must match the connected workspace. Recovery then uses the original request.

A definite server refusal remains visible with its code and details. **Close refused request** ends that local pending item so you can inspect the current state and prepare a new change. An uncertain response stays attached to its original request until recovered.

The server connection is pinned by workspace ID. Actions and downloads carry that identity header. A server that changes to another workspace is rejected by the client. To work on another workspace, open it deliberately through the connection form.

Browser draft or request storage errors are shown before an unretained mutation is sent. Keep the current tab available while retaining or downloading that original work.

## Use the typed client

The standalone `client.mjs` has browser-compatible code and complete JSDoc types for sources, revisions, fields, references, time series, validations, reviews, links, analyses, projections, exports, and every action input/result.

Connect to the same server:

~~~javascript
import {AuditExchangeClient} from "./client.mjs";

const client = new AuditExchangeClient({
  baseUrl: "http://127.0.0.1:8769/",
  workspaceId: originalWorkspaceId
});
const state = await client.connect();
const serverIdentity = await client.identity();
const detail = await client.read("source.get", {
  sourceId,
  revisionId
});
~~~

Prepare and retain an exact mutation envelope before execution:

~~~javascript
const request = client.envelope("source.patch", {
  sourceId: detail.source.id,
  expectedRevisionId: detail.revision.id,
  patches: [{
    path: originalField.path,
    kind: originalField.kind,
    ...(originalField.attributeName
      ? {attributeName: originalField.attributeName} : {}),
    expected: originalField.value,
    value: correctedExactString
  }],
  actor: operatorName,
  note: revisionNote
}, {expectedVersion: state.version});

// Retain this complete JSON in the caller's durable operation record.
const result = await client.execute(request);
~~~

After a lost response, execute that same retained request without changing its UUID, version, or inputs. Read calls use `client.read(action, inputs)`; mutations use `client.envelope` followed by `client.execute`. The client performs one HTTP attempt and reports transport uncertainty through `AuditExchangeError.outcomeUnknown`. `client.identity()` reads the pinned running application's instance and original workspace identity.

For a retained export:

~~~javascript
const exported = await client.read("export.get", {exportId});
const file = await client.download(exported);
// file.bytes is the complete verified Uint8Array.
// file.name, file.mediaType, and file.sha256 identify the received output.
~~~

`analysis.run` commits a queued result with an `analysisId`. Read `workspace.get` and find that same ID in `state.analysisRuns` to follow its retained native status and complete outputs. Replaying the original request recovers its original queued receipt; it does not start another analysis.

The browser's file helpers are `auditFileBase64(file)`, `auditSha256(bytes)`, and `auditRequestId()`. The complete action catalog and exact DTOs are documented in the client source. All supplied structural locators and native field literals should be passed unchanged except for explicitly proposed corrected values.

### Continue and preserve the whole case

Use the same application, operation directory and complete input JSON after an interruption. The operation lock, immutable source cohorts, original request files and completed stage records keep the existing workspace and effects. Every recovered mutation retains its original request ID, expected version and complete inputs. Browser recovery uses the original request file if browser storage is no longer available.

A native analysis whose retained metadata permits runtime recovery can continue after the actual reported condition is repaired. Add `--resume-analysis REPAIR_LABEL` to record that continuation against the same analysis ID and immutable original inputs. A deliberate application correction uses `--adopt-source`; the driver retains both complete source generations in the same case.

The final case contains the original input files, source cohorts, all three native workspaces, full request and response files, browser recovery records, source models, projection, consumer result, observed weather, native outputs and complete exported application/workspaces. Each captured archive includes a complete member manifest and is reopened to verify every member's bytes and SHA256. The original operation's `-latest-archive.json` pointer identifies the complete retained archive beside the case directory. Preserve that archive with the operating deliverables.
