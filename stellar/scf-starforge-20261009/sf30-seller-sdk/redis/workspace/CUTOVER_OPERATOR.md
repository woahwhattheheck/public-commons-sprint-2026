# Redis / Valkey cutover operator

The cutover operator opens the existing paired receiving directory. It edits the complete shared application contract, reviews both actual deployment profiles, receives both original commissioning operations, shows their full differences, and prepares a complete customer handover. Each source correction can retain its parent as a new receiving edition.

The browser and CLI use `cutover-workspace.mjs`. Receiving uses the original `receiveRedisCutover`, original Redis authoring workspaces and their saved native operation records. The SQLite workspaces, source profiles, package files and candidate release remain the original product objects.

## Open the installed product

Use the `redis-applications` source selection and its maintained runtime installer, described in [the complete installation guide](../../../distribution/selections/REDIS_APPLICATIONS.md). The Redis contribution registers these original commands:

| Command | Purpose |
| --- | --- |
| `redis-cutover` | Original complete input review, creation, receiving and cold comparison |
| `redis-cutover-operator` | Full browser operator, saved editions, operation recovery, difference paging and handover export |
| `redis-commissioning` | Customer commissioning within an individual original Redis workspace |
| `redis-customer-export` | Complete generated-client response export through the original buyer |

Open a new private receiving directory with a complete original input:

~~~sh
starforge redis-cutover-operator open \
  --directory /srv/customer/redis-valkey-cutover \
  --input /srv/customer/approved-cutover.json \
  --port 8440
~~~

The command prints `REDIS_CUTOVER_OPERATOR_READY` and its actual `operatorUrl`. Open that address. The original loopback HTTP host uses its existing origin checks and private workspace token. Source credentials come from the process environment named by the approved source profiles.

Reopen the same directory without another input:

~~~sh
starforge redis-cutover-operator open --directory /srv/customer/redis-valkey-cutover --port 8440
~~~

Use the same browser origin and port to retain that browser's complete local draft and unresolved request. The native files remain available independently of browser storage. A stopped host closes its original workspace owners. Reopening then uses the saved native operations and completed source files.

The selected source also supports direct Node entry:

~~~sh
node source/stellar/scf-starforge-20261009/sf30-seller-sdk/redis/workspace/cutover-operator-cli.mjs open \
  --directory /srv/customer/redis-valkey-cutover --port 8440
~~~

## Review the whole contract

The **Contract & sources** view provides the complete source, rather than an excerpt of the plan:

- Baseline and candidate connection setup, including standalone, Cluster, Sentinel, REST and supported deployment-profile fields.
- One shared set of read queries, merchant routes and payment terms.
- The source consistency reference and responsible receiving operator.
- Every customer example, its input, expected columns/rows, page/row budgets and complete-page requirement.
- One ordered, multiset or set comparison rule per example.
- The optional candidate release selection and original comparison byte budget.

Shared queries, routes, payment and examples are edited once and applied to both original source inputs. The deployment editors retain their independent connection identities, namespace, environment references, TLS authorities and public certificates. The complete JSON import/export also preserves supported fields outside the visible summaries.

**Save complete draft** records a request ID and the exact previous draft SHA256. A concurrent save must match that preimage. **Review complete contract** validates the saved profiles and original commissioning contracts, then binds a review digest to the complete canonical input and both actual draft/bound file hashes. The original paired writer checks those same preimages before the first receiving selection becomes bound.

Viewing and editing saved source work can proceed without opening a live database connection. Receiving and previewing use the selected deployment and actual process environment. Required names and immutable source identities remain visible; secret values are supplied through the customer's existing environment.

Once an original receiving input is bound, its complete input remains readable. Use **New edition** to change its source, acceptance examples or comparison rules. Repeating its original receiving IDs returns their retained observations.

## One browser editing owner

The browser uses the existing local draft store for the complete draft, invalid raw form fields and exact pending request. A Web Lock gives one tab editing ownership for the receiving directory before any shared-store write.

Other tabs can inspect saved results, pages and files. Their forms and mutating actions remain read-only. Close the original editing tab, then select **Take editing control** in a viewing tab to read the retained full draft and original request. A browser without Web Locks provides the read-only view.

This ownership is specific to local browser intent. The native directory writer and exact source preimages still govern separate CLI or operator processes. A concurrent source change returns the actual conflict while preserving the original draft for review.

## Receive and continue

The **Receiving** view exposes four original operations:

| Action | Result |
| --- | --- |
| Create workspaces | Create or recover both original source workspaces without a live receiving pass |
| Receive both deployments | Execute the original customer examples and all selected native pages, prepare accepted packages and compare the pair |
| Compare saved results | Read every original retained source page and customer file; both database servers can be stopped |
| Continue original operation | Reattach or resume the same retained phase and original native operation IDs |

**Pause** applies to the attached original operation. It finishes the current retained native step, then closes the owning workspace before stopping. Continue reuses the same requests. A cold progress record that still says running is displayed as retained running; the original writer determines whether another live process owns it.

Before sending a mutation, the browser saves its exact arguments. If the reply is lost, **Read original outcome** reconciles those arguments against native state. **Continue original operation** uses that same request. Returning to review preserves the actual source/error and does not replace an uncertain native request with a new one.

Each receiving result keeps complete native observations. Missing continuation after a declared source limit, an incomplete final Set cursor, a page budget ending before completion, or another failed source requirement preserves that native outcome for review before package/stage acceptance. A matching prefix cannot substitute for the full selected source.

**Open baseline** and **Open candidate** open the original authoring workspaces with their immutable workspace/profile bindings and setup origin. Their normal source and commissioning editors remain available. Starting another paired operation closes those attached authoring owners first. **Close authoring windows** also releases them explicitly.

## Corrected receiving editions

**New edition** copies the complete reviewed contract and assigns new paired and per-side setup/receiving IDs. Its origin retains the exact parent operation, input, result and the operator's note.

The parent stores one original creation request before creating its child directory. If creation stops after any of its original filesystem writes, the same pending creation remains in history. **Continue edition** uses those exact saved arguments, including when browser storage was lost. Its completion preserves an already edited child draft. Completed child-origin receipts remain reusable after the parent creates another edition.

The edition list pages through up to 1,000 retained editions. Opening a prior edition preserves its original observations. A following draft becomes a live receiving pass only after its complete new source is saved, reviewed and explicitly received.

## Complete differences

The **Differences** view keeps column mismatches, customer expectation results, row counts and the declared comparison rule visible together.

- Ordered comparison retains each changed position and duplicate value.
- Multiset comparison retains removed and added rows with their counts.
- Set comparison retains membership differences and the original native scan pages.

The pager hashes the entire original difference file and builds a compact sparse offset index. It returns only the requested full entries, with a 2 MiB response budget. It does not retain all row bodies in the operator process. A single larger entry is identified with its full size and remains available in the complete file download.

Each original difference file has its retained SHA256. Paging and downloads verify the held original file identity. Downloads expose the full length and digest, support an exact byte range, and leave large rows intact.

## Complete handover

After original receiving, **Prepare complete handover** reopens both original workspaces and verifies their complete native page chains, expected results, difference files, generated customer files and original release selection.

The ZIP contains:

| Member | Complete contents |
| --- | --- |
| `cutover-input.json` | Approved paired input for original customer receiving |
| `selection.json` | Exact original bound selection and input digest |
| `result.json` | Exact retained paired outcome |
| `baseline/` and `candidate/` | Original receiving report, commissioning input, source revision and every full native preview in JSONL |
| Each accepted side's `customer/` | Whole generated client, OpenAPI, manifest, types, metadata and guide from its original prepared package |
| `differences/` | Every complete original comparison file |
| `manifest.json` | Every preceding member's byte count and SHA256 plus the original pair identity |

The handover uses the maintained streaming archive writer: at most 64 MiB compressed, 512 MiB expanded and 128 complete members. Preparation retains its original PREPARING/PREPARED/READY record. Publication uses create-only linking, full-file verification and directory synchronization; the same operation recovers an interrupted final publication. An existing READY archive is verified and reused.

The browser verifies the complete received ZIP bytes before offering its download. The CLI can resume a verified prefix of the same original file:

~~~sh
starforge redis-cutover-operator export \
  --directory /srv/customer/redis-valkey-cutover \
  --kind handover --output /deliveries/redis-valkey-handover.zip
~~~

Keep the original output path to resume. A complete byte-identical output is reused. The CLI compares every existing stage byte before appending; a different complete file or prefix returns the original mismatch without replacement. The same export command supports `--kind input` and `--kind difference --check ORIGINAL_EXAMPLE_ID`.

## CLI and programmatic operation

The complete command help names all supported arguments:

~~~sh
starforge redis-cutover-operator --help
starforge redis-cutover-operator status --directory /srv/customer/redis-valkey-cutover
starforge redis-cutover-operator history --directory /srv/customer/redis-valkey-cutover --limit 25
starforge redis-cutover-operator review --directory /srv/customer/redis-valkey-cutover
starforge redis-cutover-operator start --directory /srv/customer/redis-valkey-cutover --mode receive --review-digest ACTUAL_REVIEW_SHA256
starforge redis-cutover-operator continue --directory /srv/customer/redis-valkey-cutover
~~~

Use the actual digest returned by Review. `--edition ORIGINAL_CHILD_ID` selects a saved child for status, review, save, start, continue, difference or export. Save requires its original `--request` and `--expected-draft` SHA256 (or `none` for the absent first draft). New-edition requires the selected parent canonical input SHA256 and an explicit operation/request/note.

~~~js
import {openRedisCutoverWorkspace} from './cutover-workspace.mjs';
import {startRedisCutoverServer} from './cutover-server.mjs';

const workspace = await openRedisCutoverWorkspace({
  directory: '/srv/customer/redis-valkey-cutover',
  environment: process.env
});
const server = await startRedisCutoverServer({workspace, port: 8440});
// Open server.operatorUrl. Closing the server closes its original workspace owners.
await server.close();
~~~

The model also exposes `state`, `progress`, `history`, `save`, `review`, `start`, `continue`, `pause`, `wait`, `newEdition`, `difference` and `file`. `file` returns the verified original handle, full identity and async byte stream; close that handle after use.

## Full native browser receiving

The existing [physical Redis-to-Valkey programme](NATIVE_CUTOVER.md) can include this complete operator through `SF30_REDIS_CUTOVER_BROWSER=1`. It uses the same two original receiving operations, same real Redis snapshot and Valkey process, six products and original customer application exports.

The conditional flow covers complete input editing, exclusive browser ownership and cold tab handoff, Save/Review/Receive, an admitted original request whose response is lost, same-request continuation, actual ordered/Set differences, both original editors, cold comparison after the native engines stop, whole archive/member verification, existing-file CLI export, and a saved/reopened following draft. It adds no second physical pair. Use the same installed source and original equipped Playwright/Chromium selection described in the native guide.
