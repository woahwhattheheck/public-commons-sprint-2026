# Approved Central periods in PostgreSQL

This component carries an existing Central commissioning delivery into the original PostgreSQL receiving operator. An operator selects an issued dataset for each reporting period, inspects the complete approved CSV projection, saves a SQL mapping review, imports its immutable edition and exports a full period comparison. The same authenticated Central application retains each original request, source approval, native result and report file.

The complete source, accepted Central captures, issued exports, original row and repeat-parent keys and existing PostgreSQL warehouse remain the operating authorities.

## Required original product

Use the complete Central source with its trusted Store callback and authenticated server extensions. Install the full odk/commissioning/ contribution with its original two-period definitions and native delivery. Its current source includes the archive-revision and baseline-review repairs from PR2116, head534215098c2133d55bb25034d6788ae75dcb86cd.

The selected Python interpreter contains the original stellar_forge_buyer package, optional Psycopg3 driver, current Central intake and period-report modules, and maintained processes.run_owned. The full PostgreSQL guide is sf88-operator-buyer-cli/python/POSTGRESQL.md. This component invokes that installed CLI using structured arguments. The original command opens the configured database and private operator workspace.

The Central Store runs on its original Linux/Node24 host with util-linux flock. A managed host mounts Warehouse on its existing listener. A direct operator first closes the current owner, then opens that same workspace through the direct source entry.

## Host profile

Create a mode-0600 JSON profile file in a private host directory:

~~~json
{
  "schema": "stellar-forge.central-warehouse-profiles.v1",
  "profiles": [{
    "id": "reporting",
    "name": "Reporting warehouse",
    "workspace": "/private/postgres-reporting",
    "connectionEnv": "SF_BUYER_POSTGRES_DSN",
    "schema": "sf_received",
    "python": "/private/venv/bin/python",
    "timeoutSeconds": 3600
  }]
}
~~~

connectionEnv names the existing environment variable holding libpq connection settings. Its value stays on the host. workspace is the current private Python operator directory, separate from the Central source workspace. python selects the interpreter containing the installed package. Set expectedWarehouse when the original warehouse identity is already known.

The host initializes an empty dedicated SQL receiving schema through the existing command when that is the intended database setup:

~~~sh
/private/venv/bin/python -m stellar_forge_buyer.postgres_cli \
  --connection-env SF_BUYER_POSTGRES_DSN --schema sf_received init
~~~

An established warehouse reopens with its existing schema and identity. The browser's **Open existing warehouse** calls original status, then retains its actual warehouse ID in the Central Store. Later reviews, imports and reports pass that identity to Python. Moving a host profile to another database requires an explicit new profile identity.

## Complete operator workflow

### 1. Open the existing warehouse

Select the host profile and choose **Open existing warehouse**. Read the actual PostgreSQL warehouse ID and SQL schema. This records its first identity or reopens that same identity. Each later source review, import and report uses the retained warehouse identity.

### 2. Select a delivered table and period

Choose the original commissioning delivery and **Approved table and period**. Select **Retain approved export**.

The delivery already contains the native dataset export. Approval preparation verifies its exact original records and all complete export files, preserving:

- Workspace ID and commissioning definition/source references.
- Period label, plan ID and exact capture scope.
- Complete capture, whole-capture hash and the accepted review that issued this export.
- Actual project, form, table and repeat-parent relationship.
- Dataset/export fingerprints, table-edition identity and row count.
- Explicit approved source fields and native key paths.
- Exact physical CSV declarations, dictionary identities and every file's bytes/hash.

An immutable issued export retains its issuing review when a later review exists. A later source correction is selected through its own original delivery/export.

The approval carries a relative exportRoot and relative member paths. Python receives the current Central directory separately, so a portable restore resolves its own original export files.

Open the saved approval to inspect its complete binding and download the exact approved CSV, dictionary, approval or other retained native export members.

### 3. Inspect and review SQL

Choose **Inspect for SQL**. The original Python operator verifies the full approved CSV and dictionary, then inspects all rows. The browser displays a five-row preview with the complete retained inspection and source metadata.

Review every SQL name, type and nullable setting. Every approved physical column stays present. Original row-key columns remain explicitly selected in native order and nonnullable; the repeat-parent field remains its own approved column. Save a **SQL review** with the operator's reviewer name and note.

Supported types are the original operator's text, boolean, bigint, numeric, double precision, date, timestamp with time zone and json. The original mapping validates every conversion. Source semantics and SQL aliases remain separate retained values.

Each Central field has its value column plus a matching _state string column. States are value, null or missing. The native exporter keeps Int64 and Decimal as exact text; the SQL review makes further typed conversion explicit. The approved CSV is the receiving data. Complete rows.jsonl, original pages, XML and media stay in the original private capture/export and portable workspace.

The application retains the native review ID before calling Python. central-review --review-id reopens that exact immutable review after a lost response. Changed source, mapping, reviewer or note uses a new review request.

### 4. Receive the full edition

Select the saved SQL review and choose **Import complete edition**. The original PostgreSQL operator receives every approved row into one immutable version, retaining its exact source, mapping, dictionary and manifest.

The request ID is saved before invocation. A closed browser, interrupted response or restarted source application reopens that same original operation. The native transaction and request journal determine whether the edition is committed. Completed editions remain available.

### 5. Export the complete comparison

Select period0 and period1 imports for the same commissioning definition, project, form, table and warehouse. Enter a title and choose **Create full period report**.

The original report operation receives the actual immutable version IDs and period labels. It reads one consistent database snapshot with server cursors and writes both full datasets, every added/removed/changed row, exact dictionaries, mappings, manifests, SQL and an offline HTML report into its complete ZIP.

The bridge receives the fixed original artifact using its returned bytes and SHA-256, retains it as a native Central resource and provides **Download full period report**.

Comparison follows the actual row keys. Distinct submission cohorts can contain different original row IDs; added/removed counts retain that meaning. Cross-form or business-entity reconciliation uses its explicit customer identity agreement.

Repeat tables are separate outputs with their own row and parent columns. Prepare, review and import every selected root/repeat output. Pair the same original table's two periods for each complete report.

## Saved operations and recovery

**Saved operations** lists original ID, action, table/period, state and row count. Open an operation for the exact selection, complete native result and full stdout/stderr. Select **Resume original request** for interrupted work.

Before dispatch, the browser retains the exact request body. A lost response leaves **Reopen original requests** on the same origin. Reopening reuses that original body/ID. Completed operations return their saved result.

The original Store serializes this extension's operations. A storage error identifies the need to close/reopen the same workspace. Existing native transactions, content retention and record revisions own publication.

Python's maintained run_owned supervisor owns the CLI and all descendants. invoke.py holds a parent-lifetime descriptor; losing the Node owner unwinds that same command tree. Command timeouts return after native cleanup. Complete stdout/stderr are retained as native resources. A command JSON larger than16MiB remains available as its complete download and is identified as exceeding the browser result view.

Imports/reports keep their original Python request journals. A SQL review retains its explicit review ID. The report stays in the private Python profile and its complete verified bytes are also retained in Central for download and portability.


## Composition for the original owner

Retain every file in odk/warehouse/. Dependencies are original odk/analysis.mjs, store.mjs, workspace.mjs, server.mjs, commissioning/, odata/state.mjs, the native dataset semantics validator and the complete installed Python product.

Compose through the original trusted callback:

~~~js
import { createCentralWarehouse } from './warehouse/model.mjs';
import { createWarehouseExtension } from './warehouse/extension.mjs';

let warehouse;
const workspace = await openCentralWorkspace({
  directory,
  extend: ({workspace, store}) => {
    commissioning = createCentralCommissioning({workspace, store, connection});
    warehouse = createCentralWarehouse({workspace, store, profiles});
  }
});
const extensions = [
  createCommissioningExtension({workspace, commissioning}),
  createWarehouseExtension({workspace, warehouse})
];
// Supply extensions to the one original createCentralServer call.
~~~

The original server mounts assets after Host/Origin checks and calls extension handlers after bearer authentication. The extension handles only its own /api/warehouse/ routes; original field, commissioning, publishing and download handlers retain their entry points.

Close in order: HTTP listener; await warehouse.close(); await commissioning.close(); await workspace.close(). A borrowed Store/listener remains owned by its original host. Direct single-owner forms are openCentralWarehouse and serveCentralWarehouse.

New native record kinds are warehouse-profile, warehouse-approval and warehouse-operation. Approval JSON, mapping/selection inputs, full command output, results and report ZIPs use the original resources table and content-addressed sources files.

The original Central archive includes its full SQLite snapshot, every referenced source body and native output. Create the next original workspace backup after warehouse operations to carry the new records/resources. Restore through the original archive API and configure the receiver's current private PostgreSQL profile. The approval's relative paths resolve under that restored source workspace, and report downloads reopen by retained source hash. The PostgreSQL warehouse and its own native operator profile retain their original database/receiving authority.
