## Run on an existing Linux worker

Keep `run-native.py`, `source-map.json` and `source-assets.json` together. Select the installed Node, Chromium, Playwright and application dependency paths on the worker. Keep the same persistent receiving directory on every continuation. The helper installs the exact original source into a separate writable work directory and places the Chromium profile there. Cases, native requests, completed phases, customer files and both workspace profiles remain in the persistent receiving directory.

```sh
python3 run-native.py \
  --source-packet source-map.json \
  --source-assets source-assets.json \
  --directory /absolute/persistent/merchant-workflow-receiver-24ea \
  --work-dir /absolute/writable/workflow-receiver-work \
  --node /absolute/installed/node \
  --chromium /absolute/installed/chromium \
  --playwright-module /absolute/installed/playwright/index.js \
  --node-modules /absolute/installed/node_modules
```

Adding `--inspect` reads the original baseline and recipe checkpoints, completed results and active owner without launching a child. It verifies the exact packet before reading the operation and does not require those executables to be available.

The helper uses one inherited flock on the original receiving directory. Runtime identity includes the host, boot ID, PID namespace and original process start time. Signals reach the owned native process group; an interrupted output consumer leaves private logs and completed native records intact. Original source files and runtime records are written atomically. If an invocation-local browser profile has disappeared, recovery replaces its dangling link only after matching the original saved runtime custody.

### Customer journey

The merchant creates one recurring series bound to the original installed
recipe edition. The first period is planned and started in the actual Console.
After the server accepts that start, the browser loses its response and uses
**Continue original action** to recover the same native run. The second period

The customer receives both native deliveries through the existing customer API.

reopens both customer archives and the retained offline handover, confirms the

### Native output transfer

### Reopen the shipped customer workspace

After a complete native case, the runner keeps the original receiving directory
as a private sibling backup, extracts the exact shipped archive at its recorded
receiving path, restores the original configured source inputs, and invokes the
same completed native entry. Both Console workspaces start through the real
merchant launchers on fresh loopback ports. A fresh private local token is
created when the restored directory has no token.

The restored operation reads all 31 original merchant, recipe and recurring
calls, the same two completed periods and installation editions, all four
six-file customer deliveries and the thirteen-file recurring handover. The
original completed reports remain unchanged. The separate
`workflow-series-reopened.json` and full reopen output are retained in the readable
customer delivery summary beside the exact archive that was reopened.

To receive a previously delivered archive on an equipped worker, select the
source packet and original paths recorded by its manifest:

```sh
python3 run-series-native.py \
  --source-packet series-source-map.json \
  --restore-archive merchant-original-native-artifacts.tar.gz \
  --directory ORIGINAL_RECEIVING_DIRECTORY \
  --work-dir ORIGINAL_WORK_DIRECTORY \
  --node ACTUAL_NODE --node-modules ACTUAL_INSTALLED_NODE_MODULES \
  --chromium ACTUAL_CHROMIUM --playwright-module ACTUAL_PLAYWRIGHT_MODULE
```

The work directory and receiving directory have separate locations. The runner
preserves an existing receiving directory before extraction and resumes the same
saved archive phase after interruption. Original operation locks remain with the
controller and its child throughout the archive exchange and reopen.

`ORIGINAL_NATIVE_OUTPUT_READY` reports the exact bundle size, SHA-256, native
exit code and archive restoration phase. The readable
`merchant-native-customer-delivery.md` is produced on every receiving host.
The held receiver remains available for complete output transfer. Each
newline-delimited command
`{"op":"read-bundle","offset":0,"length":8192}` returns a base64 chunk at the
requested byte offset; advance by the returned byte count until the complete
bundle is preserved and its reported digest matches. Send
`{"op":"close"}` after transfer.
The standalone command saves its outputs and returns the native exit status.
The held receiver continues accepting file-transfer and close commands for the
original operation.

A managed receiving session can include the complete current Library upload helper
and its two companion modules as `payload.libraryHelpers`, or pass their existing
directory through `--library-helpers`. The receiver writes
those original helper bodies together in a private directory and submits one
closed-stdin batch for the customer archive and a readable native delivery
summary. It retains each returned file identity for the original operation.
The held receiver keeps the complete original output-transfer interface available
until the receiving owner finishes preserving the produced customer files.
