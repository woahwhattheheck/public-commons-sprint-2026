# Source Updates: scientific report and editable Study

Choose the actual completed source update in **Source Updates**. Enter a report source title and the scientific reason for replacing its inputs. **Prepare scientific report source** runs through the existing operator task queue. Its saved source appears below the form when that operation completes.

**Open this report source** opens Scientific Reports with this source as the explicit selection. **Add to current report** appends it to the existing ordered selection. The original composer retains title/order, preview, render, interrupted-operation recovery, saved editions and report downloads. From its completed edition, use the original Customer review action and the original editable Study exporter.

## What the source retains

The source is a normal imported document with role OBSERVED_CONTEXT. Its companion tree contains:

- The original immutable plan in its original edition or roots format.
- A scientific snapshot of both source collections, their body and companion descriptors, all original and successor native selections, actual completed target stages, runtime/version provenance, native artifacts and exact retained comparisons.
- The original checkpoint at this capture, kept separately from scientific identity.
- The immutable capture identity and scientific rationale.

Actual output bytes are checked before capture. The compact report shows source differences, saved mappings, per-model completed/reused stage provenance, output units, comparison availability and the original sum_change on common finite raster support. Exact IDs, input signatures, source metadata, artifact hashes, native spatial checks and coverage details remain in the linked scientific snapshot.

A sum_change is a successor-minus-original modeled output difference over finite cells of the aligned native raster. It is not automatically a reporting-area subtotal or an intervention benefit. The report retains excluded original-only and successor-only support where the original comparison recorded it. Original legacy run-level version provenance stays labeled when model-stage provenance is unavailable.

Changes to checkpoint timestamps, request history and the already_complete execution label do not change the scientific source identity. Repeating the same preparation reopens its exact retained source. Different scientific inputs, rationale or producing implementation produce a separate immutable capture.

## Editable receiving

A same-project Study follows the report source back to the original imported collection, original plan, both source editions, all selected native profiles/scenarios/grids/runs and original comparisons. The original Study closure retains their full scientific members once. It also retains the current coherent checkpoint of the same plan, under that plan's original writer lock.

The report's earlier checkpoint is an immutable companion. The current editable checkpoint is a separate original workspace record. Later valid continuation therefore preserves progress without changing the captured report. The edition engine uses source-refresh/PLAN/state.json; the roots engine uses source-refreshes/PLAN/state.sqlite3 and its original DELETE-journal database. Both use their own .refresh.lock.

An imported source from another project retains its original recipe and companions as external scientific evidence. It does not silently invent editable local plans or native results.

Distinct refreshed profiles retain distinct scientific review histories. Preparing a report source does not copy an earlier profile's review status or create a customer response.

## Install into the current application

Keep the complete received Source Updates source in its own application-root directory, beside the existing application. The current installer retains its original state/preimage journal and shared extension-install lock.

~~~bash
python "$SOURCE/install_source_refresh.py" --application "$APP" --source "$SOURCE"
~~~

Restart the existing operator server, then reload its browser page. The installed current application supplies the original Scientific Reports, Customer review and editable Study modules.

The installer copies the owned Source Updates implementation before its entrypoints. It adds only three guarded joins to the shared original consumers:

1. native_versions.validate_run_comparison delegates records with source_refresh_context to the source-update comparison reader. Ordinary comparison identities follow their existing code.
2. scientific_report_study_transfer includes the typed source-refresh report source.
3. study_transfer captures the original plan writer lock while staging this lineage.

The exact before/after joins are retained in source/source-refresh-report-integration.json. Independent owner edits outside those joins are preserved. Unknown or ambiguous joins stop before mutation and name the actual file to compose.

The host supplies openScientificReport with explicit selection_mode replace or append. Source Updates keeps working in its standalone view; its retained report sources are also immediately listed in the full Scientific Reports composer. The receiving-water impact button delegates to the independently owned receiving-source-impact extension when the original host supplies openExtension.

## Actual receiving course

Use a completed real Source Updates plan from the current original workspace. Save this operator-selected input as a JSON file:

~~~json
{
  "plan_id": "ACTUAL_RETAINED_PLAN_ID",
  "title": "Scientific source update",
  "rationale": "The actual scientific reason for replacing these retained inputs.",
  "notes": []
}
~~~

From the installed application root:

~~~bash
cd "$APP"
"$PYTHON" -B -m source_tools.receive_source_refresh_report \
  --workspace "$WORKSPACE" \
  --selection "$SELECTION_JSON" \
  --output-dir "$OWNED_OUTPUT"
~~~

An optional --review-selection file uses the existing title, purpose, requirements and notes contract. The default creates questions about the actual source replacements and native evidence. It never generates reviewer answers.

The receiving command captures the actual update, prepares and renders through the original composer, creates and exports an original customer review, exports the selected report/review as an editable Study, restores that archive into a fresh directory and checks the actual report source, saved edition, review request, selected Study identity and editable original plan. Progress is retained after every phase. The same output directory continues the same admission and verifies retained exports; it cannot be reused for a different scientific selection.

Keep OWNED_OUTPUT outside both Workspace and application. All generated bytes, actual source IDs, review/report/Study IDs and restore paths are recorded in receiving.json. The command starts no native NDR or SDR solver.

## Producing-peer product inspection

On the same installed application and real workspace, operate the populated Source Updates form at desktop and narrow widths. Prepare the source, open it alone, append it to an existing report without losing that draft, inspect the actual generated report and its original source links, open the original review, and cold-reopen its editable Study.

Look at the actual screenshots and rendered HTML/PDF, including long source labels, runtime provenance, change units, unavailable comparisons and tables. Correct human-visible errors before presenting the result. Layout measurements alone do not replace looking at the outgoing product.

## Original comparison recovery

The previous cross-edition builder reused its comparison-ID variable while counting coverage. The corrected builder uses a dedicated coverage_key. For that exact known predecessor only (id equal to neither_valid_cells inside its correct digest directory), the existing retry validates the complete original cohort, context, support/output/difference hashes and coverage before repair. It retains the original malformed JSON in a hash-named history file and publishes the original digest ID atomically. Every scientific raster remains unchanged. Other mismatches remain descriptive failures.


## Receive the complete report flow in the actual browser

The existing browser course can open a saved update directly. This mode leaves its native cases in their current state unless you explicitly supply --run-models. Use a completed original plan for the scientific report course:

~~~bash
cd "$APP"
node source/run_source_updates_browser.mjs \
  --url-file "$PRIVATE_OPERATOR_URL_FILE" \
  --workspace "$OPERATOR_WORKSPACE_KEY" \
  --plan-id "$ACTUAL_COMPLETED_PLAN_ID" \
  --report-selection "$ACTUAL_REPORT_INPUT_JSON" \
  --transfer --video --output "$OWNED_BROWSER_OUTPUT"
~~~

Use --plan-id instead of --from-collection, --to-collection, --mapping or --title. The original from/to mode remains available when the actual task is to prepare and explicitly execute a new source update. --expect-reuse still requires --run-models and verifies the actual saved per-model reuse receipts.

The browser input uses the actual source rationale and optional existing report choices:

~~~json
{
  "plan_id": "ACTUAL_COMPLETED_PLAN_ID",
  "title": "Actual source update report title",
  "rationale": "The scientific reason for this retained input change.",
  "notes": "",
  "report_title": "Actual composed report title",
  "append_to": []
}
~~~

plan_id is optional in this file and, when present, must match the opened plan. notes is one optional text note (or a one-item string list), matching the existing form. append_to may contain the actual existing {source_collection_id,source_id} choices to keep before the new update chapter. Leave it empty for a source-update report on its own. The driver selects only saved sources returned by the original composer; it creates no scientific observations or reviewer answers.

The course fills the real source form, submits its original queued operation, downloads the retained identity, opens the prepared source with explicit replacement, and then exercises Add against the operator-selected ordered draft. It verifies that Add keeps the title/order and does not duplicate the source. It prepares the actual preview, renders or reopens the existing edition, opens the original report viewer at desktop and 390-pixel widths, and downloads every original report member and its complete ZIP. Downloads stream to disk and are checked against the actual provider's byte counts and SHA256 values.

With --transfer, the same original Workspace archive includes that report source and edition. The browser restores it through the existing operator, reopens the actual source and report, and compares all retained report file identities. It also keeps the earlier original-to-restored workspace race receiving course. The source-update report CLI above separately follows the smaller editable Study and Customer review closure.

journey.json retains actual operation/result IDs, source choices, downloaded identities and saved screenshots. The producing peer must open and look at the desktop/narrow operator and report screenshots, plus the downloaded HTML and PDF, and operate the resulting product. The recorded geometry and completed browser commands do not replace that visual inspection. Correct visible defects before using the report or recording the demonstration.

For the current Upper Savannah demonstration, use the actual original geographic shapes, 30 m source edition, upstream model domain versus South Carolina reporting area and utility focus provided by the responsible model owner. Explicitly simulated physical inputs stay labeled. A source-update difference describes the effect of changed inputs; use the saved baseline/restoration/matched-control comparisons to discuss management effects. Annual nitrogen/phosphorus mass reaching streams, sediment units, and any separate intake/concentration calculations retain their distinct scientific meanings.
