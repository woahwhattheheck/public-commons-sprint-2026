# Utility Monitoring decisions with original source context

The existing Monitoring export now carries the selected utility's original source evidence beside the actual saved design. Open a feasible utility plan or a saved campaign in Monitoring and use its existing HTML or field-package export. Use the existing saved Monitoring report-source action to include the same explanation in an ordered scientific report, PDF, Markdown export and scientific briefing.

The producer only attaches utility context when a completed original utility preparation identifies the exact saved network. Regional or independently prepared Monitoring networks retain their existing report behavior. No new network, design, station assignment or field event is generated by exporting.

## Read the decision

The report begins with the existing saved plan, costs, calendar and field history. Its appended utility sections show:

- The original whole-HUC utility choice and its saved source/export identity.
- Target overlap, selected search areas and actual covered catchments from the saved design.
- Historical source station membership beside the network's native geometry assignment.
- Verified-outlet status, explicit existing-programme credit and actual campaign station choices.
- Original sampled records, dates, method/activity/unit distinctions, detection states and Information Only records.
- Regional nutrient and flow context with its original geographic and quantity scope.
- The relationship between the source report's 303-record topology and the supplied 217-polygon Monitoring graph.

ARJWS and Pioneer use their original independent utility selections. Their target areas and observation counts are not added across utilities. The original utility report and full relative source members are included in the native field package.

### What area coverage means

For these utility preparations, the network target weight is the area of the original utility footprint intersecting each original catchment in EPSG:5070, divided by 10,000 to obtain hectares. The report labels this quantity **target overlap (ha)**. Its covered and total values come directly from the saved solver result.

The network also retains geodesic catchment area in square kilometres, calculated on WGS84 geometry. The report labels that quantity separately. It never converts the reported geodesic area into the solver's projected overlap weight.

Local versus upstream coverage is the exact saved plan choice. A contextual catchment outside the original utility selection may be selected by an explicit design; the report lists that choice and preserves its actual target weight. The report does not impose a new catchment exclusion rule.

The source-area objective measures planning coverage. It does not estimate E. coli concentration, annual nitrogen/phosphorus/sediment delivery, removal, detection probability or monitoring effectiveness. Native model quantities, where used elsewhere, retain their own units and support.

### Historical stations and actual programme choices

Each station row keeps these distinct fields:

| Field | Meaning |
|---|---|
| Original membership basis | The original utility observation selection, including a publisher HUC8 criterion where that was the source method. |
| Original matched HUC12 | The original source analysis's HUC12 association, if present. A missing association remains missing. |
| Native HUC12 and assignment | The actual saved Monitoring network's point-in-polygon result or explicit retained assignment. |
| Verified outlet | The native network's explicit outlet evidence; historical presence does not establish this. |
| Explicit existing credit | Membership in the saved design's existing_station_ids. |
| Planned visit IDs | The saved campaign's station bindings, or an original plan station field if present. |
| Effective visit IDs | The latest retained field event's station when an event exists; otherwise the planned campaign station. |
| Original summary | Original cohort counts, dates, activity types, method/units and source comments. |

An original station inside a HUC does not automatically receive existing-programme credit. Catchment polygons remain search areas; only actual retained source points identify station locations.

A station on an unresolved boundary remains in the network's assignment findings. Per-catchment inventory is unavailable when the original microbial station source was not selected; it is not replaced with zero. A native assignment that differs from an original HUC association remains visible in the JSON and station CSV.

A field event can identify a different station than the planned campaign binding. Both lists are retained. An event without a station does not silently inherit one for the effective-station column.

### Observation interpretation

The report reproduces the utility's original sampled cohort, including unique sampling dates, annual station sets and observed months. Detection states and Information Only rows stay explicit. Source concentration units and reporting-limit units are both retained. No calendar-year mean or annual load is inferred from irregularly sampled dates.

The complete original station/year/method/activity/unit groups remain in selected-watersheds.json and the original source files. Regional nutrient and daily-flow context stays regional; the report does not silently select it as a utility-only measurement series.

## Download and reopen

### Native HTML

The ordinary HTML export appends the source and planning explanation directly. It has no relative links to files absent from that single-file download.

### Native field package ZIP

The original Monitoring ZIP retains its existing plan, network, calendar, events, source geometry and exact source companions. Each utility context adds:

- utility-context/<context-id>/context.json — exact original utility choice, observation context, saved plan explanation and station/catchment joins.
- preparation.json — the retained original preparation record.
- catchment-context.csv and station-context.csv — human-readable joined tables; source IDs remain text.
- report.html — a standalone offline utility decision report.
- original-report/ — every ordinary file from the existing utility export, at its original relative path.

Open the package's root report.html or the utility-specific report.html after extraction. The original source briefing can follow its own relative source links. The original nested utility packet is already present among native source companions; the report directory reuses its ordinary members to avoid requiring a second extraction.

CSV fields that spreadsheet software could interpret as formulas are quoted as text. The retained JSON and original files preserve the original values without this display adjustment.

### Saved scientific report source

The existing Monitoring report-source producer first verifies the entire native ZIP manifest and all member hashes. It then verifies the utility context against the exact plan, network, original preparation, utility selection and campaign calendar before adding ordered scientific sections.

Its source links point to retained native members. The same source package remains available to the existing report editor, PDF/Markdown generator and scientific briefing workflow. Original report directories and prior saved source editions remain unchanged. A changed producer/helper source creates a new saved report-source identity.

The existing budget-comparison report path remains available. This change preserves its producer and selection semantics.

## Source and API contracts

model.utility_monitoring_report.contexts(workspace, plan, network, visits) reads completed original utility preparations for the network. It verifies the existing utility export and all original files, and derives only presentation joins from already saved records.

The context identity binds the Workspace, plan, network, preparation record, original utility export files, exact actual calendar and helper implementation hash. A separate record digest covers the complete retained explanation.

read_bundle(archive, manifest, plan, network, campaign, events) is called only after the native report producer has verified every ZIP member. It validates the context's original source links and reconstructs the exact native calendar from the saved campaign revision and event history. Older native archives without utility members remain readable.

scientific_sections(records) returns the current ordered SourceReports paragraph/table/link block format. It does not solve, change field history or reclassify original observations.

The existing native API is unchanged:

    from model.monitoring_workspace import MonitoringWorkspace
    monitoring = MonitoringWorkspace(workspace, export_root=output_directory)
    report = monitoring.export(plan_id=actual_saved_plan_id, format="html")
    packet = monitoring.export(plan_id=actual_saved_plan_id, format="bundle")

For a campaign, provide campaign_id and expected_revision_id instead of plan_id. The current campaign revision is checked by the native exporter.

The existing report source API is also unchanged:

    from model import monitoring_report_source
    result = monitoring_report_source.prepare(
        workspace, {"plan_id": actual_saved_plan_id})
    # Or {"campaign_id": actual_campaign_id,
    #     "expected_revision_id": actual_saved_revision_id}.

Supply the resulting source reference through the existing saved scientific report workflow.
