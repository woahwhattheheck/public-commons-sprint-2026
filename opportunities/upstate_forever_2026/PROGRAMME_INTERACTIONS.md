# Conservation studies in Run programmes

This component continues the existing conservation-combination design through the application’s retained native programme. It adds no second execution controller.

## Operator workflow

1. In Conservation combinations, open a saved plan and choose **Use in run programme**. The same picker is available in **Run programmes → Use conservation study**.
2. Review the baseline, grid, scientific profile, native models, ordered actions and complete case count. The preview reads existing selections. Saving prepares the original coalition selections and creates a programme binding those run identities.
3. Continue the programme through its existing queue. Pause, continuation, completed-stage reuse and native logs remain the existing programme operations.
4. Once every case completes, the programme reconciles the study attribution using its original retained run bindings. If report reconciliation needs attention, **Reconcile study attribution** resumes that part without replacing the run selections.
5. **Attach completed attribution** connects a previously completed study result to a programme with the same native baseline. The adapter verifies retained selections and artifact hashes, retains previous link editions, and rebuilds the programme catalogue.

## Scientific interpretation

The programme’s original comparison columns remain alternative minus baseline. The conservation study’s benefit columns are baseline minus combination export, so a positive benefit means lower export. They appear in a separate report section.

Every study retains common support across all its coalitions and selected metrics. Summary rows report baseline and combined exports, combined benefit, summed allocations, efficiency residual, combined nonadditivity, and higher-order remainder with the original units and geographic support. Action rows retain standalone benefits, Shapley allocation and any permutation sampling standard error. Pair rows retain the original pair benefit and pair nonadditivity.

Permutation sampling standard error describes variation across sampled action orders; model and source uncertainty require the corresponding scientific analysis.

The programme’s JSON, Markdown and artifact catalogue carry the same retained study identities, complete tables and original GIS/CSV/report files. The browser initially renders at most 300 rows per table and retains complete rows in the downloadable result and source view.

## Verification

Executed browser checks cover module grammar, stale-workspace preview and submission, escaped titles, signed native units, and a large study’s full case count despite a shorter visible preview. Native receiving runs use the existing shared compute follow-through with the actual retained workspace and native engine.

## Exact original native-run adoption

The existing upstate.compute-programme-selection/v1 run rows accept the optional
native_run_id field. It is a full original 64-character run ID, mutually exclusive
with source_runs (completed-stage assembly). The row still selects its actual
profile_id, scenario_id and model scope; the programme's grid_id remains explicit.

The programme inspects that original run, verifies its selection digest, grid,
profile, scenario and resolved models, and retains the complete original
selection verbatim. This includes the version originally requested. It reuses
the saved run during programme creation instead of synthesizing a new selection
under the currently installed version.

Prepared, interrupted, partially completed and complete original runs are all
eligible. Programme execution still calls the original Workspace.run on the same
ID, under the same run and batch locks. Existing completed-stage checks, original
artifacts, actual native runtime validation, cache reuse and recovery journals
remain with that runner. Adopting a run does not assert that it has completed or
that its outputs are compatible with another run.

Conservation-study adoption supplies native_run_id for every exact retained
coalition. Nonempty coalition selections may differ from the original baseline
only in their exact generated scenario and requested invest_version declaration.
The original baseline ID/selection, composed mask sources, action order,
grid/profile, model scope and saved case selection/digest remain exact. Completed
comparisons and attribution continue to validate actual executed native-stage
versions with the maintained native version/cohort service.

Repeated adoption also recognizes an earlier programme whose exact selection
differs only by omission of native_run_id from every row, provided all original
coalition run bindings still match. It reopens that immutable programme and its
existing queue/history. The same predicate applies when synchronizing completed
attribution; no legacy programme record is rewritten.
