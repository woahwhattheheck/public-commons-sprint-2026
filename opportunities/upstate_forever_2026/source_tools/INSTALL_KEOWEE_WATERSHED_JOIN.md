# Install the Keowee, watershed and scientific setup workflows

This installer applies the cumulative native profile, watershed receiving and scientific setup review work to an existing Upper Savannah application. It composes the two maintained Python entrypoints and original Conservation browser in place, installs the complete scientific setup backend and operator desk, and retains the exact Keowee 1.0.2 source profile.

## Source and receiving application

Use an exact checkout of this installer's publication in public-commons-sprint-2026. Its complete implementation is the cumulative PR2916, PR2939 and PR2996 edition, commit 334c35b62d2555cc61a90863a0cf238b800f22a9. The application directory is opportunities/upstate_forever_2026. Later source checkouts are also usable when their package files match the published source manifest.

The source checkout contains the final 28-file implementation: native profile adapter/scorer and its original Greenwood receiving files, the regional receiving command and guide, the maintained completed-watershed receiver, the readable source-method view with its asset-only descriptor and original browser join, and all ten scientific setup backend, source schema, receiving and operator desk files. The installer and this guide make 30 package members. The source manifest records every exact byte count and SHA256, all three complete edit ledgers, and the nine original Keowee profile members from PR2742.

The receiving application must already contain the original Workspace and portable engine, the maintained Conservation workflow and native Keowee method definition, the regional watershed report/export provider, and the current shared operator extension host, and the original customer review engine. The installer checks their actual APIs, including the review/export operations and original grid/profile/scenario selectors. It updates model/keowee_priority.py, operator/receive_watershed_context.py and operator/web/conservation.mjs through the recorded edits. Their respective original preimages are:

An existing source file may contain additional owner work. The installer composes each unique original block while preserving all bytes outside the recorded integration edits. It also accepts the already integrated source and interrupted installations.

## Install

Run with the receiving application's Python environment. SOURCE is the new application source checkout, and APP is the existing receiving application:

```bash
python -B "$SOURCE/source_tools/install_keowee_watershed_join.py" \
  --application "$APP" --source-root "$SOURCE" --dry-run

python -B "$SOURCE/source_tools/install_keowee_watershed_join.py" \
  --application "$APP" --source-root "$SOURCE"
```

The planning invocation returns the actual changed files, exact resulting hashes, source policies and current native API hashes. The installation invocation performs the same preparation under the existing application/.locks/extension-install.lock.

All package files are checked against the source manifest. Python is compiled without executing imports, JSON is parsed, and all three full edit ledgers must reconstruct their exact published source from their original preimages. The installer stages and flushes the complete receiving plan before any application source is published.

The original nine-file Keowee profile is required. Exact existing members are retained. Missing members are copied from the new checkout only after their bytes match the recorded original profile. A different existing profile member is identified by its exact path so its source edition can be reconciled.

Implementation dependencies and source bindings are published before the modified entrypoints. The new method-view and scientific setup modules are present before the original Conservation browser is changed. Both extension descriptors are published after every implementation member; the scientific setup descriptor is the final registration. When Node is available, the staged JavaScript modules are also parsed with node --check before publication. The source manifest is published last. Missing files use atomic no-clobber publication; updates compare the captured current bytes immediately before replacement. The shared installation lock coordinates with the existing extension installer. A changed or ambiguous owner block is reported without replacing it.

The installer also retains itself, its manifest and this guide under source_tools, which is included by the original application backup engine.

## Continuation

Repeat the same installation command, keeping the same published source checkout, after an interrupted operation. Completed leaves are reused, and known earlier profile-adapter, scientific setup and installer files are upgraded through their recorded hashes. The three shared entrypoints reverse recognized integration edits in reverse order and replay the exact source ledger. This handles the atomic receiving-file recovery join nested inside the earlier legacy-record join.

The second successful invocation returns already_installed when the current application already contains the same integration. Concurrent owner additions outside the integration blocks remain in the composed files, so their resulting SHA256 may legitimately differ from the canonical whole-file postimage recorded in the checkout.

## Receive the actual studies

Use separate writable receiving directories outside the application and existing Workspace. Run the native source-profile workflow from the installed application root:

```bash
cd "$APP"
python -B -m source_tools.keowee_profile_receiving \
  --workspace /actual/owned/receiving/keowee-profile
```

It imports the retained original Greenwood parcel, prepares and builds the published land-protection study, saves an explicit source selection, and reopens its original source, study and plan.

The complete regional data edition was merged in PR2861. Its manifest under SOURCE/source/water_context/20261013/complete-sources.json retains the original completed ZIP and all context companions. The native receiving command can import that manifest directly from the source checkout:

```bash
python -B source_tools/receive_watershed_edition.py \
  --application "$APP" \
  --manifest "$SOURCE/source/water_context/20261013/complete-sources.json" \
  --output /actual/owned/receiving/watershed
```

It uses the maintained original completed-result receiver, opens the saved report and HUC records, runs the current JSON/CSV/brief selection exporter, and performs original portable backup and independent project reopen. The per-phase result is written to receiving-result.json. Both commands operate through the original scientific Workspace.

The installer result prints these receiving commands using the actual application and source-checkout paths with shell quoting. Its Keowee command changes into the application before importing the native module. Replace `/actual/owned/receiving` with the writable output directory used by the existing receiving operation.

## Capture the actual scientific setup for review

Open **Scientific setup** in the updated operator. Select the existing project grid, parameter profile, baseline and alternatives; state the scientific question, domain rationale and proposed validation. Preview displays source editions, selected areas, prepared inputs and review findings. Retain the setup to capture the actual raster headers and original companions and create its normal customer review. Review decisions continue in **Customer reviews**.

For the existing accepting-host operation, start with its actual prepared Workspace. These commands run from the installed application using the same native interpreter that runs its scientific modules:

```bash
cd "$APP"
"$PY" -B -m source_tools.receive_scientific_setup \
  --workspace "$WORKSPACE" --catalog \
  --output-dir "$OUT/setup-catalog"

"$PY" -B -m source_tools.receive_scientific_setup \
  --workspace "$WORKSPACE" \
  --selection "$OUT/setup-selection.json" \
  --output-dir "$OUT/scientific-setup"
```

The first command writes setup-catalog.json with the actual saved grids, profiles, scenarios, source collections and observations. Prepare setup-selection.json using those retained IDs and source/scientific-setup-selection.schema.json. The operator can capture the same selection through its form. Requested resolution and alternative count are compared against the actual selected project; the resulting specification retains any difference for scientific review.

The second command retains the exact original selection bytes, captures original native objects and companion paths, imports the setup as an ordinary source collection, exports its original customer review, transfers the complete Workspace and reopens the actual grid, parameter profile, baseline, alternatives, sources, observations and review head. A resumed invocation retains its original operation and checks the existing archive bytes before reuse.

Existing Gura receiving operations may already retain their selected object IDs in gura-receiving/gura-receiving-state.json or in source/receiving.json and source/programme-selection.json inside the original workflow capsule. These provide the native inputs for a catalog request; use the actual Workspace associated with those records.

The installer output includes both catalog and selection receiving commands. Every emitted command uses the same Python executable that invoked the installer, with shell quoting for interpreter, application and source paths. Replace the displayed example Workspace and output paths with the existing receiving operation's paths.
