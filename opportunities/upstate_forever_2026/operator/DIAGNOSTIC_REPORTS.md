# Scientific interpretation in an ordered report

A saved Scientific interpretation can become a section of the original scientific
PDF and client report. The source is the exact committed analysis revision shown
on screen. Its complete original tables, HTML, source wrappers, analysis manifest,
support masks and available analysis ZIP travel as native source companions.

## Operator workflow

1. Open **Scientific interpretation**, choose the saved analysis, and inspect its
   results state, common support, matched effects and observation coverage.
2. Choose **Use in scientific report**. The dialog identifies the report revision
   and its complete or partial results state.
3. Choose an existing delivery to retain its native runs, map settings and ordered
   scientific sources, or choose a new report. Prepare the report source.
4. The original task queue retains the operation. On completion, choose
   **Open prepared report form** in the saved task. If the request completed
   immediately, the same form opens directly.
5. In the original delivery form, review the native baseline and alternatives,
   report order, contact details and map settings. The diagnostic source is
   appended once. Build through the existing delivery action.
6. Open the scientific PDF and client report, then download their editable
   workspace and source companions. Existing report sources remain in their
   selected order.

A partial saved diagnostic is a usable working report. Its report sections show
the missing native members, incomplete shared support, inactive model families,
observation omissions and unavailable full-cohort scores. Report preparation does
not change these results or declare the scientific assumptions approved.

## What the reader receives

The scientific and client reports contain the same original selected revision:

- The analysis question, original grid, baseline, reference profile, explicit
  design and completed/expected run counts.
- Per-metric common valid-cell support and native model applicability.
- Matched alternative-minus-baseline response, profile effects and interactions.
- Scenario response minimum, median and maximum within each structural group.
- Average tied ranks, fractional top-k design frequency and complete candidate
  coverage.
- The authoritative expected observation roster, omitted observations and missing
  or inactive profiles.
- Separate tables for complete expected-cohort fit and the explicitly shared
  observation subset.
- The original native run matrix, recorded issues and source stamp.

Annual nutrient masses are kg/year and sediment masses are metric tonnes/year.
The diagnostic's canonical response is alternative minus baseline; a negative
value indicates lower export. A positive reduction elsewhere uses the opposite
sign. Sampled parameter spread and top-k design frequency describe the cases
evaluated. They are not confidence intervals or event probabilities. Zero shared
cells leave mass unavailable rather than implying zero export.

All numerical rows remain in their original precision in the accompanying CSV
and JSON. Full report tables are retained without selecting a favorable subset.

## Saved revisions and recovery

The queued request includes both the analysis ID and exact report SHA-256.
During first capture, the producer holds the original diagnostic writer lock,
verifies the committed raw report and each original artifact descriptor, copies
the full member set, and publishes one complete capture. It does not serialize
the operator's decorated or changing task view as scientific evidence.

Once the complete capture exists, repeating the request uses those exact retained
bytes even if the original partial analysis later completes under the same
analysis ID. The new report SHA identifies a separate report revision. Earlier
sources and deliveries remain readable.

The original operation ID handles a lost acknowledgement. Reopen the saved task
to continue to the report form; do not create a new scientific analysis simply
to recover the report source. A process stop during copying leaves no committed
capture; retry uses the original descriptor checks and either completes the same
revision or asks the operator to reopen the now-current report.

Source registration uses the original Workspace content-addressed collection.
Complete workspace backup and original restore retain the imported source and
its companions. Delivery archives retain the exact selected scientific source
through the existing observed-context consumer.

## Command line

Run from the current application with its installed scientific Python:

`python -m model.diagnostic_report_context --workspace WORKSPACE --diagnostic-id ANALYSIS_ID --report-sha256 REPORT_SHA256`

Optionally add `--delivery-id DELIVERY_ID` to append the analysis to that
delivery's existing ordered sources and native selection. `--prepare-only`
retains the complete source packet without importing it and cannot be combined
with a delivery ID.

The command returns the original source collection/document IDs, immutable
report identity, manifest and recipe descriptors, and prepared native delivery
selection. `diagnostics.report.prepare` exposes the same operation through the
original authenticated queue. Actual report publication remains the maintained
`delivery.build` workflow.

## Source installation and receiving

This component belongs to the original registered Scientific interpretation
desk. From a complete decoded source directory, run:

`python operator/install_diagnostic_reports.py --application CURRENT_APP --source SOURCE_APP`

The installer checks the exact known predecessors, parses every changed Python
module and checks JavaScript when Node is available, retains changed source
history, and installs only this component's leaves. It keeps the current
ExtensionRegistry and original queue. A current repository checkout already
contains those same files.

On the existing receiving host, reopen the same original application and
Workspace. Use an actual saved diagnostic report ID/SHA, prepare its source,
complete the report form, then inspect the PDF/client sections and original
companions. Back up and restore through the original operator and reopen the
same source and report. The expected identity is the same original project,
analysis ID, report SHA, source collection and document ID; further scientific
runs or new report editions can then continue independently.

## Selected editable studies retain the scientific lineage

When a completed delivery containing this source is included in a selected-study
archive, the original transfer resolver checks the exact retained recipe and raw
report companion. A same-project source adds the original Scientific
interpretation and its existing typed native-run, grid, parameter, land-cover
and observation dependencies to the archive. The original saved report capture
also travels when present, so a historical partial report can be prepared again
after its live analysis has advanced.

The report's copied bytes remain the selected report revision. A newer live
diagnostic report under the same immutable analysis identity can travel as
editable working state alongside that historical source; it does not replace
the report's pinned companion.

Reports imported from another project keep their exact source and companion
bytes and are recorded as external-project scientific evidence. The resolver
does not interpret their IDs as local native records. This preserves the
distinction between imported scientific evidence and editable local analysis.

The study preview lists the required original analysis and native records before
export. Its immutable transfer identity includes the typed scientific report
source mapping. Receiving checks that each retained mapping is preserved while
allowing subsequent scientific work and additional report sources. Archives made
before this lineage extension retain their original receiving contract.

Use the original **Transfer study** workflow on the relevant saved study or
completed Decision delivery. Inspect the dependency preview, export the editable
study, restore it into a separate original workspace, and reopen both the exact
report source and the original analysis. For this updated source edition, the
same `operator/install_diagnostic_reports.py` installer includes the native
lineage helper and guarded current study-transfer join.

## Producing-stage compatibility in the report

Current diagnostic reports record the actual completed producing-stage versions
for each native run and per-metric shared support. The report source copies those
fields unchanged and renders their compatibility state and explanation. NDR
compatibility governs nitrogen/phosphorus; SDR compatibility governs sediment.
An incompatible selected model family stays visible as unavailable, with its
full expected membership. Other compatible metric cohorts can still be read.

Observation tables keep the expected and shared source counts even when
cross-profile fit is unavailable because of producing-version differences.
The report shows the original score state and reason beside the separate
complete/shared-cohort values. Older saved diagnostic reports remain readable;
they do not acquire invented execution-version metadata.
