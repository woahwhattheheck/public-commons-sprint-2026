# Maintained Haystack distribution receiving

This programme produces an installed Haystack turnover product from the complete reviewed source cohort. It uses the maintained distribution builder and installer, opens the complete delivered workspace through the registered Applications lifecycle, reads that same live workspace through the registered Merchant provider, and saves the entire operation.

The work is one continuation. Keep its input file, operation ID, source snapshot, runtime installation, native receiving directory, saved application, and original launch request together. Its progress records refer to actual original operations and their retained results.

## Prepare and run the original operation

The accepting owner chooses the existing checkout path, its full reviewed base commit, and the original receiving directory. The example below uses illustrative absolute paths; use the paths actually retained by that accepting owner.

~~~sh
node --experimental-vm-modules --no-warnings PREPARE_INPUT.mjs --cohort /work/haystack-source-cohort.json --repository /work/tjlabs-stellar-merchant-workspace --source-commit a7629861dd3c1b9adfebbe5bf1b88bd5a82eb14d --directory /work/haystack-distribution-6804 --receiving-directory /dev/shm/6804-haystack-native-20261012/operation --operation-id HAYSTACK-DISTRIBUTION-6804-20261012 --out /work/haystack-distribution-input.json
~~~

The input preparation reads the complete cohort, checks all 43 source paths and Git blob identities, resolves the explicitly supplied paths, and retains the complete input atomically before publishing its original filename. Repeating that command accepts the same saved bytes.

Launch the complete programme:

~~~sh
node --experimental-vm-modules --no-warnings DISTRIBUTION_RECEIVING.mjs /work/haystack-distribution-input.json
~~~

The first call prints progress as complete JSON lines. Long original commands retain their stdout, stderr, worker process record and actual exit result under the operation's commands directory. The original distribution builder also retains its own source-acquisition and packaging progress.

Continue after a process or transport interruption by invoking the same command with the same input file. The Linux lock reports when that original operation still has a live owner. Completed command results and product stages are read before further work. A successful long native command can retain its own outcome even if the caller loses its response.

When the original RECEIVING operation already exists, transfer that directory from its actual owner before the installed-distribution leg starts. Supply it through --receiving-directory. The runner compares the complete original application inventory, upstream file identity, saved native result and delivered package against the installed source. A completed native journey is reused. A partially completed original journey follows its existing saved requests and checkpoints.

For a fresh whole operation whose native journey has not started elsewhere, omit --receiving-directory. The runner creates that original journey under its own native-receiving directory.

## Complete operating sequence

### 1. Retain the exact source snapshot

The programme retains its own source, the full input packet, and the native command worker. It acquires the original operation lock and records an invocation.

It resolves the maintained base commit, captures each target path's original Git blob and mode, writes all 43 postimages to its private Git object directory, and creates a deterministic commit using the original retained operation timestamp. The source snapshot records the base commit, composed commit, tree, before/after blob identities, full byte counts and SHA-256 values.

The runner captures the complete original builder and installer import closure from that Git snapshot into its bootstrap directory. It uses the native JavaScript parser to enumerate static module requests, retains the original Python unpacker, and checks the reviewed maintained entry points against their exact source pins before execution.

### 2. Build the maintained selected distribution

The original builder receives the explicit source commit, selection haystack-turnover and original output directory. It parses the selected source declarations, follows actual native imports and browser manifests, and packages the original complete source.

Its native build state handles interrupted source acquisition, materialization and packaging. A retained completed archive is reused through the builder's own receipt. The runner records the complete PACKAGED result and checks the actual saved archive SHA-256.

### 3. Install the complete product

The original installer prepares an isolated runtime directory from that exact archive and resolves the source-selected dependency profile. It then performs its actual installation and inspects the READY runtime, original source and selected module graph.

An interrupted installation resumes in its existing prepared directory. If source preparation itself stopped before completing its plan, the original installer recovers that retained preparation into a new directory under the same task. The earlier preparation remains available and the operation records the relationship.

The programme reads the installed distribution manifest and actual source-owned registrations. Every one of the 43 source postimages must be present in the installed manifest and match its full original bytes. It then runs the installed source, registrations, doctor, Haystack help and Merchant-provider inspection commands.

### 4. Continue the original complete application journey

The installed application's original RECEIVING.mjs supplies the full native product operation. Its own retained journal preserves source intake, exact review and delivery requests, saved editions, full reports and complete receiving.

When the original completed result already exists, the runner compares its complete application inventory against the installed portable application files. The portable application contains the complete independent local product; the four maintained integration modules stay in the distribution that owns those APIs. The complete 43-file distribution remains retained alongside it.

The full delivered workspace is reopened through both the installed Haystack CLI and the independently received CLI. Both must return the same workspace and state. The installed command exports every selected record into one complete JSON register.

### 5. Register and launch through Applications

The programme creates or reopens its actual Runtime workspace and attaches the READY distribution. It prepares a complete application review for the received Haystack workspace, saves that review with an original request UUID, and lets the maintained owner adopt the runtime's complete release.

It observes the original adoption operation until that release is connected. It then obtains the actual start review, retains the full launch request, and starts the application through the maintained worker.

The managed application must announce its actual private listener through the original one-line startup record. The original observer binds that record to the application, operation, runtime and workspace. The runner opens that exact listener, reads the complete workspace identity and verifies the full retained original source bytes.

The selected workspace is served on literal loopback with port 0. The operating system chooses the free port and the actual startup record supplies it.

### 6. Operate the registered Merchant provider

The programme creates a complete host configuration pinned to the same workspace ID, the original startup file and the retained Charlie source alias.

It invokes the installed merchant-providers initializer through the original Haystack provider registration. It opens the resulting native Merchant configuration, resolves the source-owned registry, constructs that registered provider and reads the full workspace through its actual tool catalog.

Every source record is read through the returned page cursor at the same selected revision. The complete register is saved as a file with all native typed values, including signed zero. The provider closes its borrowed clients, and the original live application remains available for another status read.

### 7. Stop through the original owner and preserve everything

The programme stops the same saved application run through Applications, follows its original outcome, and reads every page of its saved run history. It retains the complete Runtime workspace state, command output and original request identity.

The final result records the composed source commit, exact archive, READY runtime, original native operation, received workspace, application and launch IDs, all stage results and all saved requests.

The archive helper publishes its original inventory and final archive pointer from a fully written and synchronized private candidate. A resumed operation reads complete published bytes or discovers its already-complete capture.

The archive helper then captures the complete task directory and the original native receiving directory if it lives outside the task root. It includes the source cohort, private Git objects, captured original bootstrap, complete distribution archive, prepared runtime, original application sources, workspaces, saved requests, native outputs, complete editable delivery and Applications history. The original ephemeral startup connection files can be regenerated by their owning applications.

Every saved regular member is checked against its full byte count and SHA-256 in the archive inventory. Each ordinary file is retained as complete bytes, including any source files that shared an inode in the native directory. The actual resulting archive and its full inventory have separate durable receipts beside the original task directory.
