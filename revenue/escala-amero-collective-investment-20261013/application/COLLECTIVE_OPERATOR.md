# Collective investment operator

The application carries the complete programme from original observations through a reviewed payout plan, prepared provider operations, payment reconciliation and an editable handover. The interface uses the same native commands as the command line and keeps original request identities when a response is interrupted.

## Open the workspace

Start the supplied server against the selected private workspace and configuration using the root operations guide. Open its actual local address and enter that workspace's operator token. The browser stores the token for this tab. Provider credentials remain in the host configuration.

The header shows the current workspace identity, revision and dispatch setting. Connection cards identify the provider, tenant, environment and selected endpoint. These identities travel with every prepared operation. Refresh reads the same workspace; an unexpected workspace change stops a retained request from being sent to a different store.

The supplied Escala interface is derived from the company's published collective-investment API mock. The connection and native source record preserve the selected compatibility and original source designation. Use the customer's selected deployed service and authorized account for actual operations.

## Save a programme

Open **Programmes** and select the tenant, community and fund. Add the complete original project, proposal, milestone and SDP distribution-wallet IDs relevant to the review. Select the exact Escala, SDP and Horizon connection aliases and a period whose timestamps include explicit offsets. Start is inclusive; end is exclusive.

Saving creates an immutable edition. Open a saved programme to use that edition throughout the operator, edit it into a new edition, record a review decision or create a reconciliation. Earlier observations and reports retain their selected edition.

The native method contract is shown beside the editor. The complete selection is visible in the saved record, including its original supporting sources. A display name never substitutes for a provider identity.

## Capture original provider records

Open **Prepare provider operation**. Choose the connection and action, enter the original path/query/body fields and attach any exact retained source versions used by the request. Guided fields come from the selected provider schema; the complete request editor retains the original JSON spelling. Financial amount strings and issued numeric types stay in their original units.

Preparing saves an operation for review. Open that operation to see its exact request, selected connection, evidence and source catalogue. Use **Run prepared read** for an original read. **Collect all pages** creates a source collection and continues its original provider cursor.

Original records are available in **Original registers**. Each record has its current retained version, earlier versions, full original observation and source identity. Select an exact version for a plan, decision or reconciliation. A provider's original status and the reconciliation's evidence state have separate labels.

If complete provider responses or instructions have already been acquired, use **Source files** to retain their original bytes. The upload retains the file before applying its source projection. The independent file intake also supports original multipart instruction files. An imported response keeps its complete-body declaration, original request parameters, HTTP status and observation time.

## Continue original Stellar account observations

Open **Settlement streams**, choose the original Horizon connection and account, and select a starting paging token. Zero selects the earliest available account history; an exact saved token continues that original position. Attach the selected programme edition when this account belongs to its reconciliation.

Start the supplied native settlement-stream worker on the existing host using the operations guide. The operator shows its process state, retained event count and committed cursor. Pause or resume the selected stream explicitly. Each complete original event is retained before its durable cursor advances. Interrupted connections resume the saved position. A continuous stream remains distinct from a completed period collection.

## Prepare a milestone payout

Open **Payout plans** and select the programme edition. Pin the original milestone, optional proposal, all approval/evidence/treasury versions and the SDP distribution wallet and asset. Select the actual recipient wallet when the chosen registration method requires it. Registration contact and verification fields use the selected SDP values.

The recipient editor retains every row, in order. Each row includes an original ID, an exact decimal amount string and paymentID. Supply the original email, phone, wallet address, wallet memo and verification value required for that registration method. Move or remove rows explicitly. The full JSON editor retains additional original fields.

When editing complete JSON, reopen it in the row editor before changing individual cells. This prevents an older grid from replacing newly pasted instructions. Invalid or unfinished text remains available to correct. Save and preparation validate the complete current rows.

Saving a plan produces its exact native CSV, selected source pins, totals and preparation findings. Read all findings and download the complete instructions. Edit a saved plan into a new plan when its recipients or source basis change.

The registration contact selector uses the original SDP API values: EMAIL, PHONE_NUMBER, EMAIL_AND_WALLET_ADDRESS and PHONE_NUMBER_AND_WALLET_ADDRESS. Recipient CSV fields retain the original `email` and `phone` column names.

To start from an existing recipient file, select the complete original SDP CSV and choose **Retain and open complete CSV**. The original UTF-8 bytes are retained as a source file through the existing request journal before all rows are opened. Quoted fields and embedded newlines remain complete; the original file stays available after editing the plan. The importer uses the exact published column names and preserves every amount as text. Its retained file ID travels in the plan draft and saved immutable plan. The saved plan exposes the complete original intake alongside its generated instructions and definition; editing it into another plan preserves that source selection.

### Provider stages

The saved plan exposes three explicit stages:

1. **Create SDP draft** prepares creation of the disbursement on the selected original distribution account.
2. **Attach original recipient instructions** selects the exact retained SDP disbursement version and prepares its full CSV upload.
3. **Change disbursement status** selects that same original disbursement and the requested status. STARTED begins payment processing; PAUSED and CANCELED use the provider's actual transition rules.

Each stage prepares one operation. Open that operation, review it and use its dispatch control to send it through the configured provider. Saving a plan, a source association or a reviewer note does not start disbursement processing.

The native programme and source checks determine whether a plan is ready or needs review. The interface preserves the original observations. A tally result, attestation label or mock response does not become a newly inferred vote, signing authority or release.

## Record review decisions

Open **Review decisions** and select the exact subject version. Record a note, include/exclude decision, original relationship or payment allocation. Name a related version where appropriate, select proposed, accepted or rejected, give the reason and actor, and retain the original supporting source IDs. The latest accepted decision controls the reconciliation; a proposed or rejected correction preserves the preceding accepted effect.

An allocation selects an original SDP payment and an independently observed Stellar movement. Its amounts and complete unit binding preserve the actual asset, issuer, network, accounts and units required by the native model. The native model performs the exact arithmetic and source checks.

To correct a decision, open it and choose **Prepare a linked correction**. The new decision names the earlier one. Withdrawing a decision preserves that chain. Programme history, observations and reports retain their original editions.

## Reconcile and report

Create a reconciliation against one saved programme edition. Select exact resource versions, original source IDs and capture IDs when a particular frozen selection is required. The native result includes all supported community, fund, contribution, token, proposal, vote, milestone, evidence, attestation, release, SDP, receiver, asset, account, settlement, decision, total and finding registers.

The reconciliation view offers register selection, text search and original-state filtering. Its count shows displayed and total records. Expand a complete record to inspect every field, then use its original version/source/collection links. Filters change only the view. The complete saved result is retained unchanged.

Create a report from the selected reconciliation. The JSON contains the complete original edition. The CSV contains every register and the full original JSON for each row, plus the complete non-tabular scope. The standalone HTML contains every register, source basis, complete row and unchanged reconciliation. Provider state and derived evidence state remain separate. Open the HTML preview, download the complete files, and export the report delivery through the selected host destination.

## Unfinished forms and interrupted requests

The programme, payout plan, recipient JSON, decision, provider request, source, reconciliation, export and receiving forms retain their working values in this browser. Saved-plan preparation choices are retained by exact plan identity. Keep the selected workspace open while editing. The request journal binds each submitted command to the workspace, arguments, request UUID and original file hash.

If a response is interrupted, open **Request recovery**. Check the original host request first. A completed result restores the original view. A known workspace-revision conflict offers an explicit refresh and same-request retry. An uncertain provider outcome remains attached to its original operation for readback. The browser does not create a new payment to recover a missing response.

Keep the original uploaded file and request available until its result has been reconciled. The native journal is the durable command history; the browser stores the current tab's request and form continuity.

### Transfer the full browser working copy

In **Export & receive**, choose **Download complete working copy**. The JSON includes every unfinished form, raw recipient text, binding editor, saved-plan stage choice, view selection, retained original request, request history and full original uploaded file bytes. It excludes the session operator token.

Select that file in the same workspace, choose **Inspect working copy**, review its full identity and counts, then choose **Restore inspected working copy**. Restore adds missing original requests and preserves existing matching request histories. It retains the previous working view in the restore history before applying the inspected view. Conflicting original request identities stop the entire restore.

Imported requests appear in **Request recovery** and require explicit recovery. Merely opening or restoring a working copy does not send them. Keep the browser working-copy JSON with the complete native delivery archive; the native archive contains the application and host history while the separate browser file carries unfinished local forms. Workspace identity must match. Restore history remains part of later working-copy exports.

## Deliver and receive the complete workspace

Use **Export & receive** to create the full application, selected runtime, original workspace history, reports and source-file delivery. Download the complete archive from the recorded export. Prior exports remain listed.

Upload and inspect a complete archive or select its existing host directory and exact manifest. Receive it into a new destination. The received workspace is independent and retains its original provenance. Open it with its returned application/runtime/workspace paths, select the intended connections and review its dispatch setting before operating.

Use the supplied whole receiving course to open the exported application, inspect reports and original files, make a customer edit, export the return and reopen it through the original command identities. Keep the actual customer outputs with the original case.
