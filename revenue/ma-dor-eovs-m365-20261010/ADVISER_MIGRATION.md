# Adviser migration commissioning

## Purpose

This workspace helps an implementation team account for a CRM migration from the complete original exports through practical configuration reconstruction, independent target returns and accountable handover. It adds an adviser commissioning desk to the maintained Migration Workbench. The original file store, typed register mappings, reconciliation engine, operation journal, source downloads and complete portable receiver remain the working foundation.

The desk organizes work that often falls outside record migration: recurring task and event settings; workflow templates and active step relationships; note, task, email and report templates; original document versions or retained cloud links; staff attribution; workspace placement and visibility. The original migration team supplies and operates its own target import route. An accepted local review records a decision about the supplied evidence.

## 1. Retain the complete original intake

Use **Original file intake** to retain each complete CSV, JSONL or attachment. Keep the original backup, original table files, source documentation and export logs. A register projection selects CSV columns or JSON pointers from an original retained inventory; it does not replace that file.

Declare one exact scope and identity namespace, source or target role, capture time, complete/partial/unknown coverage and full/incremental scan meaning. The current engine retains raw strings, original values, row ordinals and file identity. IDs such as 001 and 01 remain distinct. Select text identity fields deliberately. Retain missing, null, empty and invalid values as their actual separate states.

Stage document binaries as original attachments as well as retaining their complete version inventory. Preserve each original contact/document identifier, version, filename, exact hash, byte count, location and visibility. A document inventory alone establishes metadata; the actual retained file provides its bytes. For an external cloud link, retain the original location and the real inspection evidence.

Customer source data, credentials, exports and workspaces belong in the selected private operating location. Repository source contains application code, public references and explicitly labeled authored examples.

## 4. Record complete reconstruction work

Open a programme's family rows. The table pages through every original occurrence and shows its current assignment. **Assign reconstruction** prepares the exact selected source reference. **Open current work** and **Continue this reconstruction** follow the actual current predecessor.

A work edition retains:

- Exact selected original dataset and row identities.
- The accountable operator, practical method, reason and optional due time.
- The full requested recurrence, workflow, template, access or document definition.
- Planned, in-progress, verified, deferred or explicitly accepted-omission status.
- Independent returned target rows, explicit source-to-target associations and exact field expectations for each association.
- Original operating evidence, named verifier and actual offset verification time.
- The full prior work edition and every affected source row.

Use original JSON values for expected JSON fields. The engine normalizes expectations with the same exact field type used by the original target projection. Decimal values should be supplied as exact decimal strings. Boolean fields require booleans. Timestamp fields require their declared offset. A missing or invalid expectation cannot prove a match.

A verified reconstruction requires an independent target observation at or after the original cutoff, usable source and target identities, matching typed fields for every explicit association, the real verifier/time and retained evidence. A verified recreated or archived document must also bind every selected inventory row to its actual original retained file. Use **link existing** only for an explicitly reviewed retained destination or external location supported by actual evidence.

To bind original document files, supply the complete list:

~~~json
[
  {
    "source_row_id": "the-original-projected-document-row",
    "source_id": "the-retained-original-binary-source",
    "sha256_field": "content_sha256",
    "bytes_field": "bytes"
  }
]
~~~

The source ID belongs to the same scope and namespace. Map the inventory’s original SHA-256 as a text field and byte count as a decimal field. The field names default to content_sha256 and bytes; use the explicit binding fields when the selected mapping uses other names. For nested JSON, select the exact original pointers. Both fields must contain usable original values, without a value-map replacement. The engine compares those values with the actual retained file identity and verifies the complete original object. A same-sized file from another version is rejected. Preserve the inventory’s original filename and version as well as the binary source filename; renaming an attachment does not establish version identity.

Every supplied document binding retains the original mapped values, selectors, normalized comparison and file identity. A verified recreate or archive-original assignment requires that binding for every selected document-version row. If the inventory lacks a usable original hash or byte count, keep the reconstruction open while obtaining the original inventory; a reviewed external location can instead use link-existing with its actual target and operating evidence.

For all families, supply explicit associations rather than relying on equal row positions or similar names:

~~~json
[
  {
    "source_row_id": "the-original-projected-person-row",
    "target_row_id": "the-independently-returned-person-row",
    "reason": "The original external identifier and reviewed target internal ID identify this person.",
    "expected_fields": {"record_type": "person", "source_external_id": "001"}
  }
]
~~~

The target_links list covers every selected source and target row before verification. Both sides must belong to the same register. Common expected_fields apply to each association; its own expected_fields explicitly override common values. This supports a multi-row assignment with different people, households or document versions without applying one record’s values to another. Every association retains both dataset IDs, original source key, returned target key, reason and effective expectations. Multiple associations require explicit separate entries and reasons; they do not merge or rewrite source identities. A source ID and a target internal ID may differ. Preserve the reviewed association instead of replacing either identifier.

Every successor must follow the actual current work for all selected rows. A multi-row assignment may be continued in selected subsets when work is split; those subsets keep their original history. A later choice cannot silently attach unrelated rows to an older assignment.

A deferred item stays open. An accepted omission requires its actual accountable decision maker and reason. This is an explicit acceptance of missing functionality, visible in the handover.

## 5. Reconcile actual independent returns

Import each complete target export through the original file intake. Declare its actual scope, namespace, capture time and coverage. Build the target dataset under the same reviewed register definitions, with the original target system.

Retain the real source-to-target identity mapping. A target internal ID and a source external ID serve different roles; do not assume that a newly created target record carries an original external key. Preserve both source columns before selecting a reviewed comparison key.

The original register rehearsal compares records, references and controls across the selected complete source and target populations. Every missing, unexpected, ambiguous, different or unknown finding stays available. Rehearsal comparison preserves changes across repeated returns. Reconstruction work uses selected target rows as exact evidence, while the native rehearsal still accounts for the full population.

For an actual update import, retain the selected account's original settings and backup: blank-ignore versus blank-overwrite, and merge versus replace for multi-value fields, are different operations. A reviewed source file or work record does not execute those choices on the external CRM.

## Module and source contract

adviser_workspace.py extends the original Store with immutable programme, work and release entities and one indexed projection of current work by original row. Mutations use original operation IDs, source checkpoints and project revisions. There is no second database or target CRM writer.

The read API exposes adviser.schema, adviser.list, adviser.programme.get, adviser.programme.rows, adviser.programme.assessment, adviser.work.get, adviser.work.history and adviser.release.get. The original HTTP /api/read and /api/operations routes remain the entry points. The same source-file download and complete portable receiver handle originals and handover.

Mutation payloads are advertised completely by adviser.schema. Common actor, expected_revision and operation_id fields remain the original workspace contract. Every accepted body retains its source and target identities, meaningful decisions and original timestamps.
