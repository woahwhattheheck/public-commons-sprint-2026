# Principal Operations

This operator is the working interface for the complete five-contract reference integration derived from Principal Protocol at `fe159e80561061fea9f7358b8ae15137eeacb0e4`. It keeps the original project's issuance and settlement purpose while making the added per-issuance accounting choices explicit in the contract guide.

## Complete operating journey

1. Open the existing native operator with its access token. The token stays in this tab's session storage. The native host retains signing material in the original Stellar key store.
2. Open **Configuration**. Enter the actual RPC URL, network passphrase, public source account, signer alias, installed CLI path/version/hash, Python path and all five deployed contract IDs with their WASM hashes. The guided fields update the complete configuration JSON; save the complete configuration explicitly. Incomplete drafts remain editable.
3. Use **Prepare operation** to read current wrapper/configuration, oracle sample, risk window, eligibility and account balances. Every original result remains in **Contract observations** with its selected action and native record. Integer parameters remain exact decimal text; amounts have seven decimals.
4. Prepare the native wrapper deposit and manager mint with explicit minimum outputs and original issue nonce. Inspect each saved plan, simulate it separately, then choose explicit invocation when the selected configuration enables it. An unresolved invocation retains its original native attempt; request recovery reads the original result before any further action.
5. Use **Issuances & settlement** to read the manager's actual `get_issue` result and account `balances`. Each issue preserves its own original backing, entry sample, claims and maturity. A shortcut retains its observed network and manager in the complete action draft; submission rechecks that binding. To prepare a new manually selected operation, explicitly start a new operation in the current configuration. PT and YT are internal issuance-scoped balances; separate issue IDs remain separate instruments.
6. Transfer the selected issue's claims or recombine matched PT/YT before maturity. Exact paired recombination returns the original locked SY proportion; complete recombination releases all of that issuance's shares.
7. At maturity read and lock the configured eligible oracle sample, settle the selected issue's actual backing and inspect its fixed budgets. The contract guide defines the accepted sample and shortfall policy. The operator displays actual underlying backing, PT/YT underlying budgets, redeemed claim units, paid underlying amounts and the original complete sample. Principal shortfall is denominated in USDC accounting units, with seven decimals.
8. Calculate a partial payout from that saved fixed budget if useful, then prepare an explicit native redemption with the intended account, destination, exact PT/YT amounts and minimum underlying output. The browser calculation uses exact BigInt arithmetic; the actual contract evaluates current balances, eligibility and state.
9. Retain source documents or original native outputs in **Original source files**, add working notes to their subject IDs and download the complete native workspace. Download the browser working copy to preserve unfinished fields, selected complete file bytes and original browser request history.
10. In **Export & receive**, inspect the complete native workspace file, including all original files, requests, history and application source. Use the installed CLI receive command to materialize a separate destination with its original workspace identity and execution disabled. Open and use the independently received workspace through the same native commissioning course. Reopen every outgoing attachment and original file in its ordinary viewer. Continue the selected original receiving operation and return concrete exceptions to this project's original sales thread.

## Source and interface

The installed action catalogue comes from the complete contract API. Each field follows the declared native type. Booleans remain booleans; i128/u64 inputs stay decimal strings. Public account/contract addresses and source hashes are explicit selections. The browser does not turn an observation into a claim about a different network, manager or time.

The original whitepaper describes a broader programme including markets, a router, frontend, mainnet and liquidity. This reference contribution implements custody, separate issuance claims, eligibility/risk/oracle joins, recombination, maturity settlement and operator handover. It uses zero reference fees and the selected administered oracle design described in the contract guide.

## Native request recovery

Before sending a command, the browser records its UUID, exact method/arguments, original workspace revision and full intent hash. The host receives the same original request envelope. On a lost response, **Request recovery** reads the original host record. A selected same-request retry retains the original UUID and body. Native external attempts have their own durable execution records; the host must reconcile an uncertain external submission instead of starting it again.

A saved complete response and a later workspace refresh failure are distinct outcomes. The accepted response remains in the journal. Changes to current workspace revision or configuration produce an explicit original response rather than silently modifying a prepared plan.

## Complete browser working copy

The browser journal uses `principal-operations-browser` and `principal.browser-working-copy.v1`. Export includes every local request and attempt, the complete current view, all unfinished form fields, complete selected source-file bytes and prior restore receipts. It preserves optional original metadata fields.

Choose **Inspect complete working copy** before **Restore inspected working copy**. Both require the same workspace ID. Inspection validates the entire envelope and original request/file identities. Restore atomically adds missing original requests, preserves existing same-intent request histories, saves the complete preceding view and replaces the selected view. Imported requests require explicit recovery. Inspection and restore do not invoke native transactions.

The prior full view can be downloaded from the restoration history. The source file itself remains downloadable before and after an import. A failed browser save leaves the complete in-memory view available for an explicit download while readable original journal records remain intact.
