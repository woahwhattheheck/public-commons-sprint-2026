# Berkeley / Clariti daily cashiering and receivables reconciliation

## Purpose and source boundary

This is the separate financial operating arm of the existing Berkeley/Clariti permitting project. It gives staff a complete local path from original daily reports through allocation, discrepancy investigation, correction, deposit review and a recoverable financial handoff. It extends the original project without changing its case-level `audit.mjs` contract, existing cutover decisions or proposed permitting workshare.

The controlling source meanings and exact locators are in `requirements-catalog.json`. The original issued [Addendum E, Q80](https://berkeleyca.gov/sites/default/files/documents/24-11661-C%20-%20Addendum%20E%20-%20Additional%20Vendor%20Questions%20and%20Second%20Extension.pdf) names daily accounts-receivable/permit comparison. The question uses AP wording, but the answer identifies receivables and future Tyler Munis ERMA. Keep this distinction in every label and source map.

[To-Be Appendix B](https://berkeleyca.gov/sites/default/files/documents/Appendix%20B%20-%20Rapid%20Workflow%20To-Be%20Business%20Process%20Maps_0.pdf) supplies Sessions16/21. These are historical proposed process maps, not current operational captures. Legacy FUND$/Accela references remain attached to their original edition. The December6,2024 Addendum E cover has a historical bid-date inconsistency; this proposed implementation arm creates no new procurement deadline.

The selected documents specify behavior rather than transaction schemas. Native report columns, tenant identities, amounts, account codes, event semantics, dates and final output formats come from the actual supplied export or agreed configuration. A neutral CSV generated by this tool must be labeled as its own handoff format until a receiving layout is actually supplied.

## A complete operator session

1. Select the financial population: department or division, actual accounting day/interval, source timezone, sessions, currencies and expected source lanes. Record which reports are final, partial, delayed or awaiting capture.
2. Retain each original permit, receivables, settlement or cashier export unchanged. Inspect its headers, native rows, observed time and declared coverage. Confirm a versioned mapping; preview its complete interpreted population before commit.
3. Reconcile the selected native transactions. Inspect exact requested/paid values, original IDs and lifecycle meanings; work unmatched, ambiguous and inconsistent rows directly from their source context.
4. Confirm payment-to-invoice/fee allocations where a report lacks a direct authoritative join. Keep partial allocations, unapplied remainder and reviewed one-to-many/many-to-one links visible.
5. Record proposed corrections and responsible parties. When an actual corrected report or external status arrives, retain it as a new edition, compare again and inspect what changed. Preserve the old financial close and decision history.
6. Prepare the daily packet from the exact selected population. Review tender counts, over/short, settlement observations, outstanding items, document references and the two distinct deposit reviewers.
7. Produce the configured receiving file or neutral financial handoff. Attach actual transmission and receiving/posting observations separately. A prepared file is never displayed as an ERP posting.
8. Reopen the same operating work or export it for another private installation, carrying the complete original files, mappings, allocations, source decisions, prepared packets, actual receipts and history.

The interface should make missing source facts editable through their appropriate source or interpretation controls. It should not require an invented successful outcome merely to inspect, export or hand over an unresolved day.

## Observation model

Maintain a source connection identity for each original system/instance/report family. Separate the lanes `permit`, `receivables`, `settlement` and `cashier`. A source can have several roles only when that relationship is explicitly declared; the same row cannot silently become independent corroboration of itself.

For every file retain its bytes, hash, filename, capture time, source identity, reporting interval, declared completeness, native schema or supplied mapping, and original row location. For every interpreted financial row preserve the original ID components as strings, the original values and the exact mapping edition. Long IDs must never travel through a floating-point number.

Support original scope independently of record content. A final empty report is evidence of an empty observed population; the absence of any report is not. A replacement capture must declare the exact scope it replaces. Other days, departments, sessions and sources retain their current pointers and full history.

A candidate interpretation may be incomplete and may contain errors. Preserve the raw row and actionable mapping problem. Reconciliation excludes it only with an explicit count and reason, leaving it available to the operator.

## Amounts and lifecycle semantics

The financial engine owns all arithmetic. Parse declared decimal or minor-unit input exactly. Preserve currency and scale; never sum different currencies, infer a missing amount as zero, or round a source amount without an explicit supplied conversion rule.

Requested amount, amount paid, fee, refund, returned amount and settlement net are different fields. A denial can have a requested amount and an absent paid amount; its source meaning must remain visible. A processor report's net settlement is not automatically the permit's gross receipt.

Each source mapping declares whether it describes a current state, an event stream, or separate cumulative snapshots. This prevents a voided current-state row and a distinct negative reversal event from reducing one payment twice. The exact native linkage, amount and effective date determine the selected interpretation; an unfamiliar status stays unresolved.

Distinguish these operational facts:

- A proposed fee or payment correction.
- A recorded authority decision.
- An observed fee void or payment void.
- An actual refund request and its external reference.
- An observed refund settlement.
- A returned-check or chargeback notification.
- A subsequent replacement payment.
- A separately observed permit/workflow state.

An internal approval or prepared adjustment does not itself mutate the external permit, processor or AR ledger. Do not import the source's automatic workflow requirement as an imaginary local posting.

## Identity and allocations

Use the source's declared native transaction identity, not a guessed combination of amount and date. Preserve duplicates and collisions for review. A corrected source version with the same identity supersedes only its selected source scope; it does not create another financial event.

A direct source transaction/invoice/fee reference can supply an authoritative match. Otherwise show the candidate relationship and retain an explicit allocation decision with:

- Exact source and receiving row identities and versions.
- Invoice, fee, permit or one-time-payment references as actually supplied.
- Allocated amount and currency.
- Allocation purpose, source reference and responsible actor.
- Reversal or correction linkage when applicable.

Allow split allocations and grouped receiving entries when explicitly supported. Do not force a one-to-one relationship on a partial-payment population. Prevent allocations above the available signed amount, ambiguous reuse of the same receiving entry, and hidden cross-currency or cross-day netting. Keep both original gross allocation and later reversal history.

Worked arithmetic illustration, not a Berkeley record: a supplied USD100.00 receipt allocated USD60.00 and USD40.00 has USD0.00 unapplied. A later supplied USD10.00 refund is a distinct linked event. Its interpretation can make net received USD90.00 while preserving the original USD100.00 allocation and explicit USD10.00 refund; it does not rewrite the old receipt to90 or silently subtract it twice.

Use the original permitting workspace's selected case crosswalk only through a pinned, explicit linkage. Its `paymentMinor` is a case-level compared field and cannot establish native transaction, settlement or refund facts.

## Reconciliation and investigation

Each completed comparison pins the selected source editions, mappings, declared scopes, allocation versions, rules and engine version. Keep its input fingerprint separate from its later reviewer decisions.

The operator must be able to inspect the entire population and filter at least by accounting day, department, source lane, session, tender, native transaction, permit/invoice/fee reference, lifecycle class and disposition. Show original row context beside normalized interpretation.

Useful native findings include unmatched source/receiving entries, duplicate native IDs, ambiguous joins, currency mismatch, requested/paid divergence, denial-state disagreement, unallocated or overallocated values, unmatched reversal/refund references, incomplete source coverage, unsettled timing differences, missing accounting identities and inconsistent session/count totals. Findings identify actual compared inputs; they must not claim external failure from a missing report.

A reviewer may explain an accepted difference, request correction, or retain an unresolved timing/source question. Review identity depends on the compared values and original editions. A material input change requires a current decision while making prior reasoning easy to inspect. Do not carry an accepted difference across a changed amount or different original transaction by matching only its label.

Totals retain their denominator: selected rows, valid interpreted rows, participating financial events, excluded rows, unresolved rows and coverage. Report by currency and scope. Unknown total or incomplete net coverage remains labeled, with the known subtotal shown separately.

## Sessions, cash and deposit review

A session has its actual cashier/source identity, accounting day, opening/closing observations, selected receipts, original reports and declared tender scope. A local review session is distinguishable from a source-observed cashier session.

Cash expected from retained receipts and cash physically counted are separate values. A blank count means not recorded. An explicitly supplied zero is zero. Over/short uses the selected count and expected amount under an explicit rule.

Prepare a deposit packet that binds the exact financial population, relevant supporting documents, declared cash bag/deposit/slip references, count observations and unresolved exceptions. Two distinct authorized staff identities must be attached to the same current prepared edition for the source-described deposit review. Preserve their observed approval time and evidence; an entered name is not a cryptographic signature or automatic proof of agency employment.

A later material source, allocation or count change creates a new packet edition. Existing reviewed packets remain intact and visible. The current daily decision can be open, prepared, reviewed, deferred, or otherwise explicitly modeled; none of these labels should imply a real Treasury deposit without an actual observation.

## Receiving output and actual receipts

A receiving profile defines the actual column order, encoding, separators, amount formatting, account-code mappings, source references and permitted records for a supplied receiving contract. Validate it against the selected population before creating immutable bytes.

Store prepared output identity and hash, source packet/version, layout/version and included row references. Give the operator a complete preview and download. A manual/partner transmission receipt references those exact bytes and preserves its reported outcome. If the external outcome is unknown, keep it unknown and reconcile later; do not automatically send again.

Readback is another original source capture, including reported rejection details or actual accepted/posting references. Its relationship to the prepared file does not make every emitted row posted. Compare the receiving rows and retain their complete statuses individually.

The tool's neutral exports must remain useful even when no production receiving layout or transport has been supplied. They are a financial workshare handoff, not an invented Munis import.

## Durable work and review boundaries

Persist all original sources and immutable input/decision editions in the selected private workspace. Writes require the current workspace revision; a stale edit reports the current revision and preserves the requested values for explicit refresh. If transport fails after a mutation, reopen the same request/result rather than duplicate its effect.

A release freezes the full chosen day/population, source manifests, mapping and allocation histories, analyses, selected reviews, original packet/receipt identities, complete data exports and operating instructions. Keep the prepared release state separate from any later reviewer receipt. A rollback restores selected working pointers while leaving all later historical observations accessible.

Portable receiving verifies exact artifact identities and restores a new private workspace without mutating its origin. Preserve original source IDs/versions and original environment provenance when local identifiers change.

## Product acceptance and delivery

The acceptance rows in `requirements-catalog.json` are the implementation contract for the complete workflow. They are proposed engineering acceptance criteria, not a report that City acceptance has happened.

The original permitting product continues to own case-level cutover decisions. This financial arm adds the separate transaction population and must deliver a usable staff interface, source/mapping controls, native arithmetic/reconciliation, allocation/correction workflow, deposit review, complete exports and recovery through one coherent application.

Delivery includes the full maintained source, exact source catalog, operating guide, editable configuration, retained input/output manifests, all original row data in the private operating package and the selected financial history. Public example data, if included by the builder, must be unmistakably identified as worked training input and kept separate from the operator's actual City/partner source observations.

No new quote, customer email, agency contact, payment movement or ERP production posting is created by this specification. The original Clariti relationship owner retains the commercial conversation; the new module can be adopted into that existing case once the complete product is ready.
