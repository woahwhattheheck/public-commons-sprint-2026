# Complete native Lab operator receiving

This launcher supplies the original native merchant and disposable checkout environment for the complete [Lab operator receiver](LAB_EDD_WORKSPACE.md#complete-original-receiving). It runs the saved McCampbell EQuIS4/EQuIS3 comparison through the real merchant MCP provider, original SF88 customer intake and checkout, original SF36 reservation, original file-job worker and full native result. The same output directory continues the same operation.

The retained business operation is `MCCAMPBELL-LAB-MCP-RECEIVING-9F77-20261012`. Its one job reference is `mccampbell-lab-mcp:2026.10`. The two complete public input archives, independent field choices and correspondence document are already part of the Laboratory EDD application.

## Run the installed source

Use the complete Laboratory EDD source selection containing this guide and both launcher files. The [standalone selection guide](../../stellar/scf-starforge-20261009/distribution/selections/LABORATORY_EDD.md) describes the maintained source and package installation.

From the repository or installed package's original `source` directory:

~~~bash
python3 stellar-forge/mcp-merchant-operator/lab-edd-native-receiving.py \
  --directory /absolute/private/lab-mcp-native \
  --node /absolute/existing/node
~~~

The Python executable must be the existing Python 3.10+ runtime. The selected Node must be Node 24 or newer with its native SQLite support. The original SDK closure uses `@x402/core`, `@x402/stellar` and `@x402/extensions` 2.28.0; the original SF88 buyer uses `@stellar/stellar-sdk` 16.3.0. Use the existing application dependency closure, including the original `re2js` dependency, and the host's existing `openssl` command. The launcher verifies the actual loaded core SDK against the maintained native factory version.

The directory must be canonical, private to the current user and on the actual receiving host. A process-wide file lock keeps one launcher on that same directory. The native merchant, customer workspaces and MCP owner retain their own original leases.

The full operation keeps both 500-result source families, both complete native output families, every editable table, the full comparisons, both independent customer desks and all result members. Declare at least 2,048 MiB for the complete operation plus the existing host's reserve, and 1,024 MiB of new ordinary-disk capacity plus reserve. These are receiving resource selections for the full graph; the original host performs actual admission. The default parent Node heap is 768 MiB and the application retains its original 768 MiB worker limit. No browser installation is required for this MCP path; approval uses the original SF62 browser broker through its authenticated native API.

The optional launcher flags are:

| Flag | Meaning |
| --- | --- |
| `--source-root` | Exact existing source root; defaults to the root containing these original files |
| `--timeout-seconds` | Complete process deadline, default 2,400 seconds; accepted range 300–7,200 |
| `--heap-mib` | Parent Node heap, default 768 MiB; accepted range 512–2,048 |

The existing native execution owner should run this one command through its maintained capacity/controller route. Preserve the operation and output directory when moving an undispatched request to an accepting equipped host.

## Full scientific and customer receiving

The launcher invokes the existing `receiveLaboratoryOperator` function. The function and all its source-model checks remain the same ones exposed by `starforge lab-edd-agent receive`.

The full source family contains 500 EQuIS4 result rows and 500 EQuIS3 result rows. It retains 614 current and 571 baseline physical records, 599 correspondence groups, all original identifiers, units, qualifiers and limits, and the exact saved independent field and correspondence choices.

The original receiver performs the complete workflow:

1. Verifies and uploads both source archives through the native file store, then reopens the original request.
2. Reads every physical row, issue and correspondence group through the Lab operator.
3. Exports and imports full CSV and TSV catalogues for both field-decision families and correspondence, comparing normalized documents and exact native bytes.
4. Saves the complete review, downloads its offline working directory and applies all five original native file slots.
5. Prepares the original request, reviews and approves the exact SF88 checkout, and receives the accepted native customer entry.
6. Uses the dedicated original worker to exercise a real customer watch/wait while the MCP owner closes, then reopens the same task and starts the worker.
7. Fetches the complete native result, interrupts and resumes that same transfer, and verifies every one of its 37 members.
8. Receives the original result ZIP into the independent customer desk, cold-reopens both owners and verifies the same source/result and payment identities.

The full baseline editable table exceeds the native 4 MiB decision slot. The existing operator parses that complete table into its exact source-bound JSON decision document before staging the original slot. The exported review retains every full table row.

## Continue the saved native operation

Run the same command with the same directory after a deadline, unavailable host or interrupted connection. The source marker, merchant configuration, payment policy and input identities must match the retained operation. Keep the source and selected runtime available at their original canonical paths.

The complete receiver's `receiving/checkpoint.json` retains its endpoint, request, field and correspondence review, apply intent, checkout, native customer, original wait task and partial download identities. Its retained same-endpoint transfer can resume after the original MCP owner closes. Every owner drains its original active task and held files before releasing its lease.

The wrapper updates the private merchant launch address after an actual listener restart and reuses the immutable original paid-job/source binding. Generated initialization files and actual customer/job records have separate retained directories. An incomplete setup is reconciled before any paid operation; a completed customer operation remains in its original workspace.
