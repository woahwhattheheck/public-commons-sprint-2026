## Pipeline Delivery Workbench: original Dagster/dbt customer operation and complete receiving

Pipeline Delivery Workbench turns an existing full customer dbt project into an operated, reviewable and independently received delivery. The operator retains the original source edition and operating criteria, runs the actual installed Dagster/dbt engine, examines every native result, records an accountable acceptance decision and gives the customer a complete editable release. The browser, Applications entry and customer agent operate the same original workspace and request history.

### The customer problem and useful output

A customer can receive SQL files, a task log or a successful exit code while still lacking the source edition actually run, the criteria used for acceptance, the native result population, the review decision or a reproducible working installation. That gap makes a recurring reporting or transformation service hard to review and hand over.

The workbench supplies one connected customer record:

- the complete selected dbt project and upstream/license/source-period references;
- a named project, immutable source edition, accountable operating contract and explicit native binding;
- an original request and Dagster run UUID retained before submission;
- full native manifests, node statuses, errors, timing, adapter responses, logs and original artifacts;
- a complete comparison for a useful later source/run edition;
- an accountable approve/revise decision bound to the actual outcome;
- an approved release, readable handover and complete editable customer ZIP;
- independently received source/runtime/project history with deliberate host-local operation.

A recurring job is a distinct approved source period or useful change/result. Retry, reconcile polling, a second file format, download ranges and reopening the same edition remain the same customer task. No purchase count or operated result is created by this chapter.

### Original native source and computation

The original source pins Dagster1.13.26, dbt-core1.12.5 and dbt-duckdb1.11.0. Preparation uses the actual released packages, preserves the selected Python/dbt invocation paths and retains every installed distribution and complete wheel. It then verifies a separate offline receiving environment against the normalized full installed payload/RECORD identity, selected package versions and actual Python binary/version/ABI/platform.

The integration does not replace Dagster or dbt with another evaluator. Original runner.py executes the actual native engine and retains its run identity and results. Managed DuckDB uses original per-run storage. External profiles remain explicit private host references whose identities are checked by the original native path; credentials are not copied into source editions.

Operating contracts preserve command, selection/exclusion, variables, thread count, dependency/catalog choices, full-refresh/fail-fast and every required node expectation. Criteria use native unique_id and accepted status strings. Missing native results remain missing, and a required unmet node cannot become accepted because other nodes succeeded.

The original limits are32MiB per edition file,128MiB per complete project and512MiB per compressed/expanded archive, with25000 archive members. A larger legitimate population needs an explicitly complete supported operation or partition. The product does not silently sample the customer's population.

The preparation result supplies actual applicationDirectory, programmeDirectory, runtimeReadyFile, Python/dbt invocation paths and runtime identity for both primary and receiving. A receiving host uses its returned paths. It does not relocate a source-host ready record or resolve a venv Python path into the base interpreter.

Applications reviews the exact private launch configuration and source/runtime selection, then owns the original Staff listener. The existing private capability remains local. Agent parameters never carry that capability. The original customer browser uses its normal local session mechanism.

The original Staff can deliberately select an independently received workspace. Selection is the complete root/receiving_id/workspace_id tuple, because received copies can preserve the same workspace UUID. New mutation requests retain that exact selection and the global workspace revision.

Applications Stop closes the observer/listener and drains its owned handles. Accepted native workers and their dbt children keep the original inherited kernel lease. Actual cancellation remains the explicit native action; closing the observer is not represented as cancelling the customer pipeline.

### Review, release and customer receiving

The customer sees the entire project source and native result population. Recent state summaries are followed by complete record/audit pages. Original file.read, run.log and run.artifact expose the exact source and retained native bodies.

A useful later edition preserves its source diff and native before/after manifest comparison, including changed fields and downstream dependencies. Review approval requires the original run to have succeeded and all required criteria to be satisfied. The saved decision identifies the reviewer, reason and exact outcome hash. Release creation binds that approved review, source, contract and outcome.

Two complete archive products serve different receiving needs. A workspace backup retains the whole original workspace and Dagster instance. A scoped client release keeps the selected project's source, editions, contracts, bindings, native runs/artifacts, requests, audit history and readable handover while excluding other clients and shared multi-client Dagster history. Both retain the complete original application source.

Each intentional export uses a stable original request ID. The original archive route follows the writer selected at actual dispatch; it has no expected-selection CAS. The full returned workspace/revision/archive receiving identity is retained. The archive's receiving ID is not confused with the current Staff receiving-directory selector.

Independent receiving validates every original member path, size and SHA, stages the complete workspace and records the actual receipt. HTTP POST /api/receive also immediately switches Staff to that received writer under the original native idle guard. POST /api/open separately switches among already-received and original workspaces; the standalone CLI receive only receives the archive. Reopening the same archive preserves later received edits. No native execution follows automatically. A future run requires an explicit host-local binding and customer request.
