## ClickHouse Acceptance Workbench: complete native table acceptance and customer receiving

A data migration becomes useful to a customer when its receiving operator can explain what was selected, inspect the complete transferred population, understand every acceptance difference and continue the same work after delivery. ClickHouse Acceptance Workbench joins those tasks through the existing Installation, Applications and Merchant interfaces. It preserves the approved source configuration, original native transfer and verification attempts, full typed exports, explicit consumer declaration and rollback, complete named packages and an independently received editable project.

This is TJLabs’ authored integration of the [complete original 54-file migration acceptance application](https://github.com/woahwhattheheck/commons/tree/4fd50b7f5a5744f1fdfdbe2e7ff0dba162863623/opportunities/altinity_clickhouse_application_workshare_2026/migration_acceptance). It operates existing approved ClickHouse source and target servers through the original HTTP worker. The original Altinity company case, F8256 sender and existing ClickHouse read-service merchant retain their ownership. The registration does not imply Altinity endorsement, a new customer agreement or an already operated customer deployment.

The source edition is explicit. The original [source manifest](https://github.com/woahwhattheheck/commons/blob/4fd50b7f5a5744f1fdfdbe2e7ff0dba162863623/opportunities/altinity_clickhouse_application_workshare_2026/migration_acceptance/SOURCE_MANIFEST.json) names 53 members plus its own file. The installed product keeps those 54 paths and all licenses. Its external original-source.json records the selected bytes and seven maintenance preimages/postimages: observer and workspace closure, Python isolation and complete child output, durable receiving phases, the active operator instruction and regenerated self-inventory. The planner, native SQL/RowBinary worker, comparison, consumer semantics and merchant-source derivation retain their original implementations. Additive Applications, agent, Installation and runtime-transfer files live outside the original workbench directory.

### A complete, approved population

The operator retains the entire altinity.acceptance-input.v1 document, with one to five source/target table pairs. Each pair selects the actual database and table, source and target account references, exact approved server versions, complete business columns, native types, key and sorting semantics, candidate engine, export bounds and source-period boundary. The source and target credentials are existing host environment references; tokens and passwords are absent from tool arguments and portable customer packages.

The [native plan compiler](https://github.com/woahwhattheheck/commons/blob/4fd50b7f5a5744f1fdfdbe2e7ff0dba162863623/opportunities/altinity_clickhouse_application_workshare_2026/migration_acceptance/commissioning/plan.mjs) retains every selected meaning. Candidate names begin commission_. MergeTree and ReplacingMergeTree are supported. ReplacingMergeTree requires a declared version column, logical primary key equal to ORDER BY, and explicit FINAL semantics for logical comparison. Unsupported nested types or delete/tombstone projections remain visible issues requiring separately commissioned source adaptation. A reviewer approves the exact ready plan before execution.

The complete export cap is selected per table, up to one million rows and 512 MiB. The worker detects an over-cap population and rejects it rather than silently sampling. Legitimate larger work needs an agreed complete partitioning and retained joins. Separate native reads do not establish cross-table transactional isolation; the customer supplies a real quiesced period, immutable snapshot or another approved source boundary, and source stability is observed during execution.

This selection provides a clear unit of customer work. A finance owner might request a complete agreed orders period; a catalogue owner might request a new schema edition with exact identifier and nullable-field handling. The real input period, table population, receiving operator and output are selected before pricing. Internal retries, upload chunks, pagination and additional export formats do not become additional purchases.

### A reviewable consumer transition

Cutover requires a ready comparison from the latest completed verify of the current approved plan and an explicit reason. It saves the complete table-binding JSON: source/target side, plan, job, comparison, table identity, native engine/columns, source boundary and observation. The exact previous declaration is retained for rollback.

The consumer endpoint exposes mode retained-native-export and liveQuery false. Its pages contain the actual typed rows from the selected completed job, with their source response path, byte count and SHA-256. The operator can inspect every row of every stream and tie the output to the saved binding snapshot. This is a precise review of the accepted observation. A new remote observation requires another deliberately selected original verification.

Rollback restores the previous retained declaration. It does not downgrade ClickHouse, drop candidate tables or silently reconfigure external customers. The engagement identifies the person responsible for changing real external consumers and records that separately. The final selected binding is chosen explicitly after the rollback path is demonstrated.

When a read-service handoff is commissioned, the [original merchant derivation module](https://github.com/woahwhattheheck/commons/blob/4fd50b7f5a5744f1fdfdbe2e7ff0dba162863623/opportunities/altinity_clickhouse_application_workshare_2026/migration_acceptance/commissioning/merchant.mjs) retains the complete stellar-forge.clickhouse-source.v1 source. Its literal edits name queryId, find, replace, expectedOccurrences and reason. Only the reviewed matches change; original parameters, limits and unselected queries remain. The derived source uses the accepted binding’s database and environment references, and its full change record retains both original and derived identities. nativeReviewRequired remains true. The existing ClickHouse merchant owner performs its own native Review/Stage/Activate and payment workflow.

### Installed Applications and exact agent recovery

The installed source/runtime preparation independently materializes primary and receiving application directories, verifies every selected original file and binds each to its actual canonical CPython interpreter and worker. The original engine uses Python’s standard library and approved external servers; customer preparation does not install a substitute database fixture. The deterministic tar.gz carries all selected source, source authority and transfer metadata. A receiving host selects and measures its own interpreter and obtains its own runtime receipt.

Applications Review/Save freezes the complete private launch configuration, original application directory, runtime receipt, auth actor, editable workspace and connection file. Start opens the same original application on loopback. The native runtime selection, source manifest and actual actor are checked when the Merchant attachment connects. The [original runtime contract](https://github.com/woahwhattheheck/commons/blob/4fd50b7f5a5744f1fdfdbe2e7ff0dba162863623/opportunities/altinity_clickhouse_application_workshare_2026/migration_acceptance/commissioning/runtime.mjs) remains the job authority.

Applications Stop drains its listener, observer work, archives, store and workspace lease. Accepted detached native jobs retain their original kernel lifetime. Explicit job.cancel requests cancellation; Stop alone does not undo a remote write. Reopen the same workspace to observe accepted work. A closing error retains the actual owner and handles until closure is confirmed.

The customer agent exposes 22 tools for the original interface: aliases and connection lifecycle; browser/info/projects and historical project reads; create/action and durable request recovery; resumable upload and declared-host source streaming; complete source/target connection declarations and consumer pages; full artifact retention, retained files, JSON pointers and exact byte-range reading. It preserves the original operator/viewer model. No substitute tenant or project-grant scheme is introduced.

Before mutation, the host saves the complete original actor, instance, request ID, expected revision and payload. A native commit may precede a later process launch, materialization or HTTP error. Recovery therefore reads the saved request and replays that identical original input. The original store returns its immutable outcome and current head separately. There is no fabricated request-receipt endpoint. A successful native response remains confirmed when a later local retention write fails.

Uploads and full retained files may reach 2 GiB, with original 8 MiB upload chunks and bounded 196,608-byte inline agent transport. Structured source/request/inspection JSON remains bounded at 32 MiB. Compact tool output points into the complete retained file; it does not replace it. Source, plan, replication document, comparison, observations, named handoff and original native files preserve complete bytes, hashes and filenames. Every disclosure rechecks the current original actor and installation; mutation history requires operator authority.
