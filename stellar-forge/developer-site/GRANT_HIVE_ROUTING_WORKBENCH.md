## Hive Routing Workbench: complete customer routing editions and independently received operations

Hive Routing Workbench adds a practical customer operating service to the existing Merchant, Installation and customer-agent product. A customer application owner can bring a complete GraphQL routing edition, run every agreed client operation on the original Hive Router, review a real configuration or schema change, select the accepted native attempt and deliver the entire editable workspace to an independent operator. The product retains the application configuration and original results needed to continue that service after the initial commissioning.

The underlying application is already substantial authored source: a Python HTTP operator, SQLite event history, complete edition intake, original native process ownership, whole client programmes, full comparison, review, cutover/rollback and complete source/workspace receiving. The installed composition preserves that original application and adds the existing Merchant Applications owner, a21-tool customer agent, exact request/effect custody, declared host inputs, native preparation and portable runtime, an Installation profile and a complete installed receiving course. The whole selected workbench remains64 source files, with explicit provenance for the original application and two maintained listener/display corrections. ### The customer job and complete output

A useful customer task is a real agreed routing release: initial commissioning of one application, or an authorized later configuration, schema, subgraph, authentication, persisted-operation or client-programme change. Its output is the complete accepted edition and operating handover, not a count of HTTP requests. The source owner, native operator, application reviewer and independent receiver remain named in the existing Workshare and Installation case.

The full input includes edition.json, the selected router configuration, complete supergraph, a hive-desk-operations/v1 document and every original supporting file. The customer specifies every operation's stable ID, method, path, body and expected business outcome. Private authorization values remain in the existing selected host environment; the retained source contains only the selected reference names. The programme includes expected authorization, validation and application errors alongside successful data. This matters when acceptance means preserving a deliberate security or business response rather than merely eliminating error messages.

The complete output carries the original and changed source editions; every native request and response; configuration and result review decisions; all comparison differences; native process attempts and logs; actual endpoint selections and rollback history; complete editable source; and independently received workspace/runtime. An operator can open a full response body, inspect its request and headers, download its exact bytes and explain the acceptance decision. ### An installed customer workflow

The operator first prepares or independently receives the selected original source/runtime. The router is the exact published Hive v0.3.4 Linux binary, with a host-matching x64 or arm64 selection. The preparation records actual Python and installed PyYAML6.0.3 dependency files. The returned applicationDirectory, python and runtimeReadyFile belong to that installation; a source-host receipt is not relocated to claim another runtime.

The existing Applications workspace reviews the complete private launch configuration, source and runtime before starting the original HTTP listener. It keeps the actual listener owner and request handlers until closure. The original native router is a separate accepted worker with its own inherited deployment lease. Closing Applications closes the listener; explicitly stopping a native deployment is an original native.stop operation followed by actual status/reconciliation. These distinct lifetimes preserve accepted work through a stopped operator view.

The five-pane application exposes Editions, Native deployments, Client programme, Cutover and rollback, and Delivery. An edition is imported as complete original files. Every selected configuration feature is reviewed with a concrete reason against the original Hive implementation. A changed edition preserves its parent and every original supporting file alongside the complete authored replacements. It is then prepared and explicitly started as the original native deployment.

The programme runs all agreed operations from the actual ready attempt. Each received result retains its whole original body, HTTP status/headers and original request. The reviewer accepts or requests changes for every operation. Complete baseline/candidate comparison preserves request/header/status changes, added/removed operations and every parsed JSON difference. Acceptance is tied to that actual programme revision and attempt.

Endpoint cutover selects a ready current native attempt supported by complete accepted reviews. Rollback restores a retained deployment that actually served the endpoint, using a programme from its current attempt. An earlier saved edition or old URL alone cannot establish live service. The maintained UI states clearly when a selection is stopped or belongs to an earlier installation and retains the original explicit Start and review workflow. [Native process ownership](https://github.com/woahwhattheheck/commons/blob/b3b6f57d92c8e704e789728576a3bd95caf40fe6/revenue/hive_application_workshare_20261012/hive_desk/native.py); [cutover and rollback](https://github.com/woahwhattheheck/commons/blob/b3b6f57d92c8e704e789728576a3bd95caf40fe6/revenue/hive_application_workshare_20261012/hive_desk/deployment.py); [original server](https://github.com/woahwhattheheck/commons/blob/b3b6f57d92c8e704e789728576a3bd95caf40fe6/revenue/hive_application_workshare_20261012/hive_desk/server.py).

### Customer-agent access to the same original application

The provider registers as hive-routing-workbench, with family/config hiveRoutingWorkbench and host input hiveRoutingWorkbenchConnection. Its21 merchant_hive_ tools attach to the actual Applications-owned listener. They expose complete original state and entities, action/request history, edition import/change, binary preparation, archive inspect/compare/export/receive and whole original file reading. They use the same Python controller and workspace as the operator UI.

The private host declares original edition directories with complete member hashes, exact published binaries, full archives and an owned root for new changed/received directories. The model selects an alias and expected identity; it does not invent a server path or runtime. Complete current state and original responses are retained as full files. Large inline displays point into those files. JSON pointer inspection supports complete structured access, and full byte reads preserve exact SHA, offset and retained reader identity.

This service preserves the original application’s real mutation semantics. Hive Controller does not offer a requestId/idempotency endpoint. The adapter therefore retains the exact host request, resolved input and before-state before dispatch. If the reply is lost, it can reopen the same closed response, prove a matching saved entity, safely repeat an unchanged original compare-and-save, or leave an explicit unresolved effect. It does not label every HTTP retry safe.

An original HTTP error may follow a partial native or filesystem effect. The full response remains retained and distinct from a recovered effect. A changed target, incomplete changed directory or ambiguous started GraphQL operation stays visible for reconciliation. The native programme's original started-row guard and inherited locks remain authoritative. The customer agent can therefore help an operator continue the original task without manufacturing a new purchase or silently repeating a side-effecting client request.

### Complete receiving and a useful later edition

The original workspace uses a full SQLite event chain and content-addressed source/result objects. Export freezes the actual database and includes every original object and every selected editable source file. Full inspection validates all ZIP member identities, the original database/event chain and object inventory. Compare classifies identical, incoming-forward, current-forward or diverged history.

Receiving always creates a new complete directory. It preserves current local work and the incoming edition independently. A receiver reopens source/ and workspace/ with the original IDs, reviews its own runtime and local native deployment, and runs the actual customer programme when commissioned. The agent export selects one create-only archive per retained request and supports complete independently received file custody. The installed runtime package is separate from the customer's project ZIP; both are necessary for an independently operable handover.

A later real customer release can retain an authorized changed edition, run its full agreed population and deliver another accepted workspace/archive under the same customer relationship. Internal transfer chunks, format variants, retries, reloads, repeated response pages and repeated downloads remain one customer task. Completed tasks, native settlements and actual delivered editions are recorded distinctly.
