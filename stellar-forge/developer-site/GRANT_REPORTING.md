## Grant reporting from original cases to received procedures

Grant Reporting turns an existing managed Grant Operations case and its complete Source Tables project into a reusable reporting procedure. The operator keeps the case's real work, invoices, cash, awards, deployments, purchases and outcomes, selects the reporting period, and prepares the original tools needed to inspect, report, export and hand over that work. A second operator can receive the complete procedure and its source material through the existing Grant case workflow. This gives a customer a repeatable reporting process whose source selections and later revisions remain inspectable.

The [complete creator and capture guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf-starforge-20261009/distribution/discovery/GRANT_REPORTING.md) documents the available implementation. The native capture source was merged in [Merchant PR1035](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/pull/1035). The implementation is available; the selected native capture and two-operator receiving remain pending with their original operators. Completion will be recorded from their actual case, saved results and receiving records. Reporting instructions, authored status, customer acceptance and observed financial transfers retain their separate meanings.

### Prepare one real reporting period

In the existing Command finder, the customer opens **Operating plans → Create Grant reporting plan**. They select the complete original Grant case JSON or native show response, the complete Source Tables project, and the installed toolkit's complete catalog. They enter the title, customer, period, owner and receiving notes, the reporting end date, and an optional start date. Omitting the start date retains cumulative reporting. The workspace, source-project, report-output and receiving-workspace paths refer to the actual operating host; choosing a file in a browser does not establish its native path. The Command finder address remains the selected loopback HTTP address with an explicit port.

The [original-input validator](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf-starforge-20261009/distribution/discovery/grant-reporting-input.mjs) retains the case ID, version, mode, plan ID, selected plan revision and full planning snapshot. The Source Tables project must belong to that plan. Its selected table editions, mappings, reviews, workbook selections and baseline remain present. A baseline that is older than the case's selected plan stays visible as an explicit difference; preparation does not silently rebase it. Catalog registration must include the existing Grant workspace, Source Tables and discovery commands. Changing to the current installed catalog is a deliberate selection, including removal of stale source-checkout context when appropriate.

Preview creates the [canonical Operating Plan](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf-starforge-20261009/distribution/discovery/grant-reporting-core.mjs). The plan contains the original case and source-review steps together with the existing reporting procedure. Its steps start planned and its recorded results start empty, ready for the operator to record actual work. The customer downloads the complete preparation JSON to retain entered values, full original files, catalog and preview together. Reopening that preparation keeps its plan identity and UTC creation time; copying it for a new period creates a separate preparation. JSON, HTML and Markdown handovers describe the same canonical plan.

### Capture and reopen the selected managed case

The [installed reporting command](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf-starforge-20261009/distribution/discovery/grant-reporting-plan-cli.mjs) supports a native capture from the original managed Grant workspace. The operator selects the actual case ID and, when required, its expected version; supplies the complete Source Tables JSON, report fields and catalog or selected source checkout; and chooses a new output directory. An optional procedure selection names the original actor, note, selected revision, preceding source and explicit source, table, edition and step links.

Use the existing private client binding and the selected case's actual ID and reviewed version for these commands. Replace the example absolute paths with the original input and destination paths. The complete report-fields JSON requires `id`, `title`, `asOfDate`, `receivingWorkspace` and `commandFinderUrl`; use the actual reporting date and current loopback listener. Optional `savedAt` retains a chosen UTC plan creation time, and `startDate` sets the beginning of the reporting period. The catalog argument selects the complete installed catalog JSON.

~~~sh
starforge grant-reporting-plan capture \
  --binding /absolute/private/original-client.json \
  --case "$GRANT_CASE_ID" \
  --expected-version "$GRANT_CASE_VERSION" \
  --source-project /absolute/inputs/planning-source-project.json \
  --input /absolute/inputs/report-fields.json \
  --catalog /absolute/inputs/selected-toolkit-catalog.json \
  --out /absolute/reports/period-01

starforge grant-reporting-plan capture-show \
  --directory /absolute/reports/period-01
~~~

Choose an existing parent directory and a new capture destination. For a toolkit loaded from its selected checkout, replace `--catalog` with `--source-root /absolute/checkout --selection PRODUCT`, using that installation's actual product selection. To prepare the subsequent case attachment during capture, add `--procedure-selection /absolute/inputs/procedure-selection.json` with the original reviewed procedure choices.

The [native capture implementation](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf-starforge-20261009/distribution/discovery/grant-reporting-native.mjs) reads the full selected case through the original client and binds the parsed case to its retained native bytes. It validates the same source project and catalog used by the creator, then rebuilds the canonical plan from those complete inputs. It reads the case again and checks the selected source files before completing the capture. A changed case, changed selected source or mismatched expected version requires reconciliation of that actual selection. Capture preserves the original case while producing a separate complete preparation for the subsequent save and receiving workflow.

A completed capture directory contains `reporting-preparation.json`, `grant-reporting-plan.json`, `grant-reporting-plan.html`, `grant-reporting-plan.md` and `capture.json`; an explicitly requested original procedure preparation adds `grant-procedure.json`. The capture manifest is written after the other outputs and binds their exact bytes. The client closes the connection or the service it owns before publishing completion, preserving any closure failure. An existing destination is not overwritten.

The customer can use `capture-show` to reopen the frozen capture without contacting the live case. It verifies the complete selected files and their hashes, reconstructs the plan from the retained preparation, and checks the case, source, plan and optional procedure bindings. Moving the directory does not rewrite the operating paths recorded inside it. An intended path or reporting-period change belongs in a new preparation. An interrupted directory remains available for diagnosis; the presence of some output files is insufficient to call its capture complete.

### Save, export, receive and return the procedure

The [original Grant procedure workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf_2026/sf47_budget_model/workspace/GRANT_PROCEDURES.md) saves an Operating Plan in the existing case as an immutable source edition. The operator supplies the real actor and current case version. The selected request identity and complete prepared input are retained before dispatch. After an uncertain response, the operator resumes that same request and checks its original result. The retained request ID, prepared file and operation directory keep that recovery tied to the original save.

Procedure links distinguish the selected case plan, case source, local original file and preceding procedure. Source Tables and native Installation or Customer Task Outcome selections retain their actual IDs and revisions, complete selected responses and explicit step relationships. A step marked complete by an author remains distinguishable from a native execution result. Opening an unchanged procedure retains its original plan; an actual edit creates a later revision while keeping earlier sources and history.

The [complete receiving workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/b2b6efba94ffb5876a5f207b1f84e6ebf8c2117a/stellar/scf_2026/sf47_budget_model/workspace/GRANT_PROCEDURES_RECEIVING.md) exports the original case, Operating Plan, procedure, native plan, selected tables and editions, readable HTML/Markdown, source links and manifests. Export checks the selected case version around its work and publishes only a complete verified selection. The independent receiver uses the existing Grant importer and retains its actual destination case and plan mappings. Returned changes create a later procedure edition with an explicit predecessor. Reopening the first edition and the returned edition must preserve their respective source selections and histories. Missing predecessors or conflicting chains remain unresolved until the original records are reconciled.

Customer acceptance therefore follows an observable journey: select a real case and report period; reopen the complete preparation; capture and verify the original selection; save the original procedure; export and independently receive it; make an attributed change; receive the returned edition; and reopen both histories. The original operation records establish which steps actually occurred. The receiving operator records the actual destination, changed edition, reopened history and customer acceptance in that original operation.
