## Catalogue Delivery Workbench: complete producer editions, native catalogue approval and independent customer receiving

Catalogue Delivery Workbench supplies a complete customer operating path from an approved producer edition to a reviewed catalogue resource, native contributor/reviewer decision and independently received working history. It joins the existing Merchant Applications, customer-agent provider, source distribution and Installation workorder. The original private application retains its CSV parser, Store, ApprovalStore, customer implementation model, provider client, request journals and archive readers. Newly authored public integration makes that application installable and usable through the maintained interfaces.

This is a reusable product offering within the existing grant programme. It leaves the canonical USD38,000, 400 engineering hours, 150-day delivery period, six funded packages and existing milestone/payment/acceptance rules intact. It does not create a seventh package or add a customer's commercial price to grant costs. Previously completed original development and actual prior customer/native work remain described as prior work; new integration and remaining operated receiving are identified separately.

### Customer problem and whole output

A catalogue operator needs more than a successful file upload. The delivered resource must contain the entire approved edition, preserve identifier and metadata meaning, survive a lost acknowledgement, and leave enough complete source/history for an independent colleague to continue. Where a native approval workflow applies, an editor's request and a reviewer's decision must be tied to the actual delivered edition and current native revision, with the original principal and provider operation evidence retained.

The workbench connects three existing useful screens. The delivery view retains complete CSV editions, targets, reviewed plans, jobs, readbacks, feeds and exports. The implementation view groups customer responsibility, deployment, resource/source bindings and full identifier comparisons. The approval view exposes actual native source and principal observations, revision-guarded notes, contributor requests, reviewer decisions and reconciled provider history. These use one original model and archive contract rather than disconnected demonstrations.

A complete customer edition includes the full approved source population and manifests, original reviewed destination baseline and protected metadata, actual delivered bytes and readback, native review evidence when required, the complete implementation profile, all source/native/request/review history and full export packages. Independent receiving must reopen the complete working result and preserve a deliberate local edit. A partial population, pending native operation or unobserved receiver remains explicitly incomplete.

The application is supplied through an external private authority with every original path, byte count and SHA-256. The managed process verifies the complete exact inventory before importing it. The public product contains generic new adapters, host registration, tools, guides and declarations; it carries no private customer source bodies, commercial documents, credential values or exact case source pins.

This separation preserves complete source receiving. It does not strip private leaves from an original edition and call the remainder complete. The authorized original application includes delivery, implementation, approval, static interfaces, native MCP, bridge and backend operating source. Its private source transfer carries every selected member and exact authority. Original operating archives remain separate. The implementation exporter intentionally filters some source suffixes, so its ZIP alone is not the full selected backend/application source. Each approval archive carries its complete review graph and delivered source; it is not silently assumed to be part of an implementation package.

Preparation makes two independent private source copies and observes the actual local CPython executable, version, ABI, relevant standard-library files and isolated package imports. The full command, stdout, stderr and closed import outcomes are retained. A source/runtime preparation receipt is not a native destination run. A receiving host observes its own runtime and verifies all source bytes; it does not relocate an old host's interpreter identity.

The public source witnesses at the end of this chapter bind the existing distribution, exact source selection, installed package, grant workorder and Merchant provider interfaces. They do not assert public redistribution rights for the private application or customer correspondence.

### Recovery and business meaning

Catalogue writes are not all interchangeable idempotent operations. The original queue identifies a job by its reviewed plan; source import reuses its complete content; native approval requests carry an explicit operation key and full body; implementation preparation is bound to its resolved profile. These stable original identities support their specific replay.

Other interrupted exchanges must remain uncertain until the original state is inspected. The installed journal records `HTTP_OBSERVED` only when it received a complete response. An HTTP400/409/500 can follow partial original effects. A missing response is not permission to reissue an export, restore, metadata action or provider request. The manager retains a dispatch marker and exact original request; the operator reads the original job/review and invokes its explicit reconciliation when appropriate.

The original native approval retry reuses the same saved provider operation and actor/source binding, and an APPLIED operation is returned as reused. Delivery retry and confirmation that a request ended remain explicit operator assertions; timeouts do not establish that fact. If concurrent exact calls produce both an observed error and a successful full response, the retained success is preferred while every observed body remains available. Hash filename order is not described as time order.

This prevents a transport attempt from becoming a new business edition or purchase. A distinct approved source period, population or customer output can create the next linked task. Download chunks, repeated receiving, reopening and exact retries remain part of the original result.

Combining them admits only identical shared base records, preserving both selected original review editions. The customer receives useful delivery, implementation and approval views, complete source/rows and full downloads. The agent reads the same original records and exact full artifacts. Onward export and independent receiving use the original archive readers and preserve later edits on replay. The final handover has an explicit artifact population and full member manifest, with the same closed candidate retained after acknowledgement loss.

The course exercises the actual customer workflow and validates the registered catalogue. It does not dispatch extra provider operations merely to count tools. Native writes, Docker/backend execution and human contacts remain with their original authorized owners.
