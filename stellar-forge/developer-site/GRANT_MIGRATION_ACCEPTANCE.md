## Migration Acceptance Workbench: complete native migration and independent customer receiving

Migration Acceptance Workbench gives an accountable customer operator one complete workflow from original data through native migration, exact comparison and business acceptance to an independently received application. TJLabs has already authored the reusable workbench and is integrating it with the maintained Merchant Applications, customer-agent and Customer installations interfaces. The funded opportunity is the remaining work needed to make a selected customer's real migration useful and operable: its sources, meanings, mappings, acceptance rules, runtime environment, accountable operators and full receiving.

The workbench uses the original dlt 1.31.0 extraction, normalization and load engine with its locked DuckDB runtime. It retains complete native pipeline state, schema, load packages, data files, logs and original attempt history. Typed parity checks every selected business row and multiplicity. A separate acceptance layer explains the business result through object keys, required fields, parent/child relationships and exact grouped controls. The operator's decisions remain attributable to the exact measured report.

The grant-facing name describes TJLabs' authored product. The original Definian source module names and schema identifiers remain unchanged so existing projects and receiving programmes retain their identities. That provenance is separate from Definian's company correspondence, commercial terms and any customer acceptance; it does not imply endorsement or ownership of this grant registration.

### A complete customer task

A migration task begins with the customer's whole agreed population and source authority. The Installation names its source owner, accountable merchant, independent customer operator, receiving host and engineer. It preserves the full original Workshare, source attachments, selected grant plan, commercial phases, funding assignments and payment authority.

The task can be a complete periodic finance-data migration, a corrected order and invoice edition, or an agreed migration of an existing integration configuration. Its source selection specifies every table and nested business object, full expected population, exact key/type/NULL semantics, cursor or bounded-backfill meaning, and any explicitly excluded scope. The independent expected data must be retained in full with its provenance. A few example rows cannot establish whole-population acceptance.

The operator receives the original CSV, JSON-array or newline-JSON files, with filename, acquisition reference, byte count and digest. The native pipeline input explicitly selects those source objects, resources, table names, mappings, primary keys, write disposition, incremental options and schema contract. Original Airbyte configuration can be retained and reviewed as part of migration planning; an uploaded configuration alone does not implement a live extractor. A customer live connector or external destination remains specific commissioned integration work.

The useful result is the entire accepted migration edition, including original source and expected data, complete actual destination observations, native state and attempts, measured business reports, decisions, selected consumer and independent application receiving. An interrupted request, a stage retry, a second report format or another copy of a handoff remains part of that original task.

### Source-native operation and honest recovery

The original native engine performs extraction, normalization and loading. Its selected ready receipt binds the actual interpreter, original source commit, dependency lock and installed runtime. The complete portable runtime is retained for independent receiving. Earlier closed native outputs remain immutable when a following job continues from their state.

Each project mutation binds the authenticated actor, original request ID, current project revision and full body. Upload continuation uses the original complete-file descriptor and committed byte ranges. A lost response is reconciled against that same saved operation. An uncertain native attempt retains its files and original state until the supported resume or explicit retry/adopt/abandon decision is made. Adoption requires a genuine original result.

This distinction matters to both the customer and the grant. A prepared Installation, compiled plan, queued native job or completed code review is not a completed migration. A source manifest or browser screenshot does not replace the original native result and complete retained files. Actual commissioning is recorded only after the relevant original operation has completed and its selected outputs reopen correctly.

The managed application retains the original workspace and runtime owner. Applications provides its reviewed prepare/start/stop path. The customer agent uses a host-selected private connection and the same authenticated application API, exact request/revision protocol, uploads and full artifact receiving. The integration does not create another migration engine or bypass the original writer lease.

### Complete parity and intelligible business acceptance

Native parity compares every selected business table using complete typed data. It preserves integers and decimals beyond floating-point precision, text identifiers, binary values, timestamp and NULL meaning, and duplicate multiplicity. It retains all actual destination columns, including original metadata. Every normalized business table must have an explicit acceptance mapping. Pending packages, required native key/schema findings and incomplete output remain visible blockers.

Business rules are a separate retained edition bound to the native plan. They name every selected business object and preserve its native key. Required fields express complete-value obligations. Parent/child relationships use explicit ordered columns and distinguish required references from permitted all-NULL references. Partly NULL composite references, missing parents and ambiguous identities remain findings with their original row references.

Grouped controls count rows or sum exact numeric measures by selected business columns. The calculation retains integer coefficients and decimal exponents; it does not round a large decimal through a JavaScript number. NULL policy and any required scale are explicit. A group present on only one side remains visible even if its total is zero. Full reports retain all groups and failed rows.

The operator evaluates rules against one complete native comparison and records decisions against that exact measured report. An acknowledgement records attention while leaving a finding unresolved. An accepted exception can clear only a condition explicitly marked reviewable in its compiled policy. Required business conditions and native parity cannot be waived through this route. New data or a new evaluation produces a new report; old exceptions do not automatically move to a different population.

The result is useful to a customer reviewer who needs to explain why the migrated edition is acceptable, where an agreed exception applies and which correction remains necessary. The complete evidence remains downloadable and editable at source.

### Explicit selection, rollback and following editions

The original application selects a retained consumer only when the current approved plan, explicit complete verification, exact comparison, business rule edition and measured acceptance report satisfy their original conditions. Any selected decision edition is included in that binding.

The consumer supplies complete pages from the selected closed result. It identifies the retained snapshot and states that it is not a live query. The operator can inspect every business table and download complete typed output. A project change during reading requires review of the current selection rather than silently combining different snapshots.

Rollback restores the exact previous consumer binding from the original cutover record. It preserves later native outputs, reports, decisions and history. A subsequent explicit selection can return to the accepted edition. External production routing and database ownership remain with the customer's existing system owner; the workbench does not imply an unperformed external cutover.

Recurring customer use comes from real subsequent source periods, corrected source editions or changed business requirements. The next task reviews those changes and continues the same project and original native state through its maintained parent selection. Its cadence follows actual source availability and the customer's decisions. Stage counts, package copies and retries are not independent useful purchases.
