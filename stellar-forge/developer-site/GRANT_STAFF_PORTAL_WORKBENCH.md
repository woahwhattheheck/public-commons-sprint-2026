## Staff Portal Workbench: private complete source, accountable staff operations and independent customer receiving

Staff Portal Workbench adds a complete customer operating path to the existing Installation and Merchant application system. A customer can prepare an authorized private staff application, review and start its original server, continue content/migration/analytics/editorial work, use a customer agent against the same saved history, and hand the complete result to an independent receiver. The public contribution is generic integration software. The customer's original source, commercial inputs, tenant identities and full case delivery remain private.

This is a concrete reusable application offering within the existing grant programme. It does not add a new funding request, change the six funded packages, expand the400 engineering hours orUSD38000 budget, extend the150-day delivery period, or treat private customer commercial amounts as grant costs. Existing grant milestones and payment/acceptance rules remain the canonical programme.

### Customer purpose and complete operating result

Organizations accumulate content inventories, staff records, access groups, page hierarchies, editorial drafts, forms and reporting expectations across different tools. A useful delivery must preserve the complete selected population and its meaning while making the next operational action understandable. A list of imported rows alone does not tell an operator whether native identities returned, whether permissions still mean the same thing, or whether an independent colleague can reopen and maintain the delivered workspace.

The workbench exposes the original portal, migration, insights and editorial interfaces. It preserves the actual original workspace model, request fingerprints, complete object store and native client. The adapter adds managed installation/lifecycle, the registered customer-agent transport, durable full-request and response retention, and the existing Installation profile. It does not introduce a parallel content engine or an alternative account authorization model.

A completed customer edition contains full approved source and source-period selections, every required mapping and decision, actual native request/response history, complete reports and an independently received editable workspace. Missing native pages, unresolved differences or an unobserved target outcome remain explicit. A native fixture or an authored example remains a fixture or example. An existing operated source can be reused without recasting its execution as a new run.

### Complete source with private custody

The public package has a strict and useful source boundary. It contains new generic adapters, tools, guides and declarations. The customer or accountable source owner supplies the full original application through a private source manifest and source directory. The manifest lists every actual path, byte count and SHA-256. The managed process verifies every selected file and the exact leaf population, then checks the original delivery implementation's full source inventory before opening its writer.

This supports complete source receiving without publishing confidential customer material. Private guides, commercial inputs or original attachments are not silently removed from an original edition to make it appear public. The complete approved source remains intact in the authorized handover. Public source witnesses below bind the maintained Installation, distribution and provider interfaces used by the generic adapter; they do not claim a public copy or public license for a private case archive.

The selected interpreter and independently received source are observed on the actual host. Preparation preserves the original source body and its actual file identities; it does not create a native tenant operation. The public package and privately supplied application have separate complete inventories, and both are retained by the receiving course.

### Installation and accountable work

The registered Installation profile is `staff-portal-workbench`. It joins the current Workshare, actual customer scope and period, source owner, native operator, acceptance reviewer and independent receiver. Existing integer atomic unit prices/counts, budget/spending selection, network/asset/recipient and workorder/payment controls remain in the original Installation system. The adapter neither creates a payment observation nor bypasses the original acceptance process.

An operating unit is one agreed complete staff delivery baseline or recurring accepted edition. The scope may be a reviewed content population, a useful reporting period or an editorial release with its underlying source and native results. A later approved population, materially useful source change or distinct reporting question can be a new linked task. Replaying one request, receiving one archive on another machine, changing output format and paging a large file remain the same task.

The profile carries the full commissioning course. It starts with private source and authority, prepares and independently receives the application, opens the actual original UI, retains complete inputs and decisions, preserves the original native operation, exports full outputs, uses the customer agent, independently receives and edits the result, and records actual acceptance. There is no acceptance claim based solely on source review.

### Managed Applications and the original writer

The application provider uses the maintained Applications Review → Save → Start procedure. The review freezes the private configuration, source-manifest SHA, original source path, intended actor, selected workspace and interpreter. The managed process opens the original loopback server and its original writer lock. It publishes an actual launch identity and retained process/output record.

Stop closes the listener and joins the original HTTP workers before releasing that writer. The adapter keeps closure ownership through failure rather than declaring inactive state to be proof of completion. The original native history remains the authority for any operation already dispatched.

The native browser retains its ordinary session and CSRF behavior. The customer agent also retains one original authenticated session across calls. It does not silently reconnect or replay a native operation when the application changes launch identity. The operator explicitly selects the new launch and, where needed, reconnects the authorized native account.

### Original semantics across the four views

The migration view preserves complete original files, schema/mapping selections, validation, approved batches and returned-platform differences. The portal view retains full page populations, hierarchy, ownership/audiences, native compiled requests and the returned identities that belong to those exact source pages. An acceptance decision remains tied to that actual plan and returned population.

The insights view preserves the original native tenant/principal binding, query, operation/run ID, pagination, rate-limit cooldowns, raw returned bodies and complete reporting state. Starting a run selects a request; it is not evidence that all results have arrived. The editorial view retains assignments, draft/review states, native identity checks, form/workflow decisions and history. The same original state underlies the visible UI, exports and agent observations.

This continuity matters to recurring operation. A later operator can inspect why a page was included, which source or native response established an identity, what a reviewer accepted, and which local edit occurred after receiving. A full onward handover preserves those distinctions.

### Customer-agent operation and exact recovery

The provider registers25 tools under `merchant_staff_portal_`. They cover status/connection, source handshake, workspace registry/selection/state, complete named reads, original creation/mutation, complete declared-file upload, receiving and original operation lookup, native connection/start/capture, full artifact retention, complete file reads, structured inspection, durable requests and original browser opening.

Every ordinary mutation retains the exact original workspace, actor, request ID, expected revision, action and payload before dispatch. The original workspace transaction owns its saved result. The original operation lookup returns a stored mutation/upload response for the exact fingerprint. The host journal preserves full requests and observed responses, including errors and local retention failures.

Native page capture is handled according to its different contract. It is one explicit original provider exchange and has no generic transport idempotency promise. The adapter saves the selected dispatch before calling it. After an unknown acknowledgement, the same host request yields its saved response or separate current-run evidence; it does not automatically capture another page. A subsequent exchange is an explicit new action against the retained original run.

Workspace creation and receiving preserve the original origin header as well as their body. Their original cached replay remains meaningful when the session has already selected the result workspace. An unrelated current selection is not silently substituted. This lets the operator recover an interrupted response without creating a second workspace or losing later local edits.

Private access keys, cookies, CSRF and native API tokens stay outside tool results and durable request files. Native token inputs are declared separately and are excluded from ordinary source-file upload/retention. Allowed origins and original account authorization remain enforced by the original application.

### Complete output and independent receiving

The customer agent retains full original objects, reports, workspace ZIPs, migration/portal batches and member files, and complete private source delivery ZIPs. Descriptors carry the actual complete returned byte count and digest. A dynamically generated export is not claimed to be byte-identical to a prior export merely because its logical selection is similar.

The original workspace ZIP receiver validates all members, restores a distinct workspace and immediately selects it in that session. A complete source delivery ZIP is a different format: it contains the full original source, workspace and handover, and uses the original delivery receiver or CLI. The guide and tools make this distinction explicit.

Independent receiving compares complete source, state, history, request/upload rows and object identities. It preserves the original workspace as origin history, records the receiving event, allows an explicit local edit and then checks that replay of the first receiving request returns its original receipt without erasing the later edit. A full onward delivery can be independently received again and cold reopened.

Large responses do not become lossy summaries. The complete saved file remains available by its full SHA through maintained196608-byte reads. Bounded JSON pointer inspection explains how to inspect parts without treating a page as the entire original result. Original upload/JSON/metadata/archive limits remain explicit.

The integration source, Installation profile, product/provider declarations, source-manifest schema and complete guides are reviewable engineering deliverables. The installed receiving course joins the existing completed native programme and complete private source/operating handover. It exercises useful actual controls, original edit/replay, full downloads, independent receiving and cold reopen. It does not create additional native operations solely to increase catalog coverage.

The public grant narrative therefore separates an authored integration from a completed native receiving result. Actual run/source/result/rendering identities belong in the existing owner-controlled receiving record when observed. Private source/data and customer communication stay with the original authorized owner. A positive human reply follows the owner's exact-message approval direction; it does not authorize autonomous subsequent outreach.
