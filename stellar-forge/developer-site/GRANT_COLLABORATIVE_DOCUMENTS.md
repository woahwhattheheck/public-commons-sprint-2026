## Collaborative Document Workbench: native shared editing and independent customer receiving

A small merchant or service team needs more than a document editor embedded in a page. It needs to know which original documents were imported, who can edit each tenant’s material, whether an offline change is actually stored, how to withdraw access, what a restore will do to disconnected editors, and whether a receiving customer can reopen the entire service with its history intact. Collaborative Document Workbench makes that complete operating task available through the existing Installation, Applications and Merchant interfaces.

The reusable product is TJLabs’ authored application using pinned Hocuspocus, Tiptap and Yjs dependencies. Its complete original source remains under products/collaborative-documents/workbench, with additive integration outside that directory. The original company workshare and its commercial terms remain a separate case. The product name does not claim endorsement, a partner appointment or a licensed Pro feature. The source selection is the [complete original 50-file workbench](https://github.com/woahwhattheheck/commons/tree/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012), with exact file witnesses in the product declaration.

### What the customer receives

The commissioned output is a complete editable customer document service and an accepted document edition. It includes original source documents, mapping and row-review decisions, tenant and document grants, frozen source/configuration editions, native import/deployment attempts, full binary document state, checkpoints, named handoffs and attributable project/request history. The browser and customer agent operate the same original workspace. The independent receiver gets the original editable application and installed runtime as well as the customer data package; receiving is not satisfied by screenshots or a static text export.

The product supports original Tiptap JSON, HTML and Yjs-update intake. Every input is retained in full and mapped against the installed native schema. Unsupported nodes, marks or attributes remain explicit errors for the operator to resolve. Every source row is reviewed as import or skip, with a reason where required. Import selects a new logical document; existing nonempty document state is not silently overwritten. These semantics are implemented by the [original workspace actions](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/core/workspace.mjs), not by a separate Merchant conversion engine.

The selected original application has a reference-v1 schema and default field. Adapting a customer’s additional content model is a real source/schema integration task with its own mapping, receiving and support scope. The existing reference does not establish that arbitrary HTML or a customer’s proprietary extensions will be losslessly accepted.

### Tenant authority and real shared editing

The existing private host identity supplies actor IDs, roles and tenant memberships. A project records explicit document grants. An empty document list grants access to that one tenant’s documents, not to every tenant. Administrative operator permission does not itself grant native editing or persistence access to all documents. The [original authorization implementation](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/core/auth.mjs) checks these boundaries and rechecks affected sessions when grants change.

The editor uses the original Hocuspocus provider, Yjs document and Tiptap collaboration extensions. The selected native synchronization engine owns concurrent changes, reconnect and merging. The integration does not approximate a CRDT or replace the original native store. Customers can see current deployment, connection, epoch and saved-state information without treating connection status as proof of storage. The [native runtime](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/native/runtime.mjs) and [original editor](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/web/editor.mjs) remain the authoritative implementations.

Durable storage confirmation requires both the complete native Y.encodeStateAsUpdate binary SHA-256/length and the state vector to match the persisted receipt. A pure deletion can change retained content without advancing the vector. Provider synchronization or vector equality alone is therefore not the product’s Saved condition. Offline cached state is bound to instance, project, tenant, document, epoch and schema, so a restored target cannot silently reopen an earlier epoch’s local document.

A customer receiving course operates two distinct authenticated browser clients, concurrent editing, real offline disconnect and local reload, reconnect, full native persistence, read-only behavior and denied cross-tenant access. Those are actual operating outcomes to be recorded after the original programme runs. Authored source, a syntax check or a prepared receipt is not substituted for that native evidence.

### Checkpoint, configuration rollback and content restoration

A drained checkpoint retains the complete native document binaries, names, epochs, hashes and vectors. The operator can download the actual checkpoint archive. Runtime/configuration rollback selects a retained frozen edition while preserving current document data.

Content restoration is a separate explicit decision: select the retained checkpoint, exact documents and reason, drain the deployment, and create new physical document epochs. The former epochs remain in history. Old connected or offline clients must not merge their newer state into the restored target. The receiving operator explicitly starts the selected deployment after restore. This distinction gives the customer a usable recovery path without presenting ordinary configuration rollback as a data undo.

Named handoffs require original native closure and preserve selected project revisions, request history, original sources and binary state. Fresh receiving opens closed; it does not launch jobs or inherit source-host credentials. Forward, same and older receiving follow the original history rules, preserving newer local work. The [complete original receiving programme](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/receiving/receive.mjs) retains the browser and native course against these semantics.

### Installation and Applications

The Collaborative Document Installation profile translates the existing customer Workshare into one complete commissioning task. It records source authority and population, actual users and tenant scope, receiving environment, commercial terms and support owner. It uses the maintained original Installation preview/save and receiving paths. It does not manufacture payments, assignments, completed checks or customer usage.

Runtime preparation is a complete original prepare/export/receive operation. The original runtime manager creates a returned application directory; a received runtime has its own returned directory. The original installer and browser build operate at those locations and generate runtime-ready from that host’s actual Node executable, dependency modules, lockfile and schema. Copying an old ready file or moving node_modules to make a path appear installed is not the receiving contract. The [original runtime manager](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/runtime/manage.py), [installer](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/scripts/install.mjs) and [complete dependency lock](https://github.com/woahwhattheheck/commons/blob/fce1f8b787822513fb1b8a1ed77f41c5f2322fae/revenue/tiptap_hocuspocus_workshare_20261012/package-lock.json) remain unchanged.

Applications Review/Save pins the complete private launch configuration and exact source manifest. ### Customer-agent operation and full files

The private Merchant provider exposes declared workspace aliases to the same original application. It supports status/connect/disconnect, browser and runtime information, full projects and historical revisions, original project creation/actions, durable request history and native request receipts, resumable uploads, declared-host input streaming, authorized document/persistence reads and complete source/checkpoint/handoff/job artifacts. Full JSON responses and binary files retain their complete bytes and identities, with readable JSON references and maintained byte-range reads.

Every mutation retains its exact actor, request ID, expected revision and full payload before dispatch. An HTTP error can occur after an original request commits, including during grant rechecking or native job launch. The agent reads the original actor-scoped receipt and replays the same request instead of inventing another ID. Upload recovery continues the original byte range and digest.

Saved agent content is not an alternate access-control system. Before releasing cached content, the adapter verifies the original installation/actor, current roles and tenant scope, and current access to every document in the retained snapshot. Administrative content requires current operator permission. Live persistence still requires a matching original document grant. Stopped applications must be reopened for this authorization; the complete bytes remain retained while disclosure is unavailable. Ephemeral provider session tokens are never issued or stored by the agent interface.

### A useful recurring service

A recurring customer task is a real reviewed document edition, source population, tenant onboarding or supported change with a complete accepted output and handover. For example, a merchant may commission a maintained operating manual with authorized departmental editing and a monthly accepted edition; another may need a supplier onboarding document set, an offline field-notes workflow, or a controlled customer support knowledge collection. The actual buyer selects the document population, useful output, receiving person and activity calendar before pricing.

Keystrokes, synchronization messages, network retries, duplicate files, and export formats are not separate completed purchases. The original Installation selects actual merchant/buyer deployments, asset, recipient, integer atomic amount/count/budget and spending authority. Professional adaptation and recurring hosting/support remain explicit Workshare terms; the reference application does not establish real customer demand or a tariff.
