## Replication Workbench: complete recurring data editions and independent customer receiving

A recurring data service is useful when the receiving customer can identify its original source, understand what changed, inspect the complete output and continue operating it. Replication Workbench connects those tasks through the existing Installation, Applications and Merchant interfaces. The customer receives retained source/configuration, a reviewed replication plan, original native run history, full typed comparison, explicit consumer selection and rollback, and an independently received editable project.

The reusable product is TJLabs’ authored application around the unchanged Sling 1.6.5 engine and the maintained Airbyte migration semantic module. The complete 70-file application/reference/license source remains under products/replication-workbench/workbench, derived from [Commons d074376ca95c0a5cc6c7abb1f28409201c1082ee](https://github.com/woahwhattheheck/commons/tree/d074376ca95c0a5cc6c7abb1f28409201c1082ee/revenue/slingdata_replication_workshare_20261012). The selected maintained edition is [Commons 6d969651d2f48f1ca620f94ed88c33c65f07577e](https://github.com/woahwhattheheck/commons/tree/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012). It repairs original observer closure and same-request consumer-phase recovery and updates the [full manifest](https://github.com/woahwhattheheck/commons/blob/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012/SOURCE_MANIFEST.json) and active operator instruction, preserving all five preimage/postimage identities. Other native engines, source inputs and licenses remain unchanged. Merchant integration lives outside that directory. The original Sling company workshare, sender and commercial terms remain a separate case. Registration does not imply vendor endorsement, a customer engagement or actual operated results.

### Complete configuration and a reviewed execution contract

The intake starts with the original configuration rather than a hand-written summary of it. The maintained semantic reader recognizes supported Airbyte configured catalogues, configuration/public API shapes and Terraform connection representations. It retains the exact selected connection and source bytes, namespaces, fields, sync/destination mode, cursor/update key, primary keys and explicit source/parallel-target mappings. Unsupported transformations and semantics remain visible adaptation issues. The [original plan compiler](https://github.com/woahwhattheheck/commons/blob/d074376ca95c0a5cc6c7abb1f28409201c1082ee/revenue/slingdata_replication_workshare_20261012/migration/plan.mjs) is the authority for readiness.

The original source and compiled plan remain complete downloadable objects. A reviewer approves the exact plan edition with an attributed reason; an unresolved plan does not silently become a runnable replication. The generated native replication document is retained alongside the full semantic plan. Later input or schema changes create reviewed editions without erasing the prior decision.

The installed native reference has a deliberately precise scope: original CSV intake into SQLite, replication between separate source and parallel SQLite snapshots, complete typed snapshot exports and an immutable SQLite consumer. A different database pair requires its own commissioned complete native execution/export adapter before its results can be claimed. The reusable compiler’s understanding of a connector configuration does not establish that the customer connector has already been operated. These constraints are enforced by the [original workspace](https://github.com/woahwhattheheck/commons/blob/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012/core/workspace.mjs) and [native worker](https://github.com/woahwhattheheck/commons/blob/d074376ca95c0a5cc6c7abb1f28409201c1082ee/revenue/slingdata_replication_workshare_20261012/native/worker.py).

### Consumer choice, rollback and downstream changes

An approved plan and ready complete comparison enable explicit consumer cutover. The selection identifies the actual immutable target snapshot, original comparison, job and stream/table bindings. The original prior consumer selection is retained. The receiving operator can page every selected row through the original SQLite reader, return to the previous selection and explicitly select the final accepted edition.

A consumer page is an actual query of that selected snapshot. It is not a live query of an arbitrary remote customer database, and a historical project view does not retroactively change the current consumer. Complete typed outputs remain independently downloadable.

When commissioned, the [downstream module](https://github.com/woahwhattheheck/commons/blob/d074376ca95c0a5cc6c7abb1f28409201c1082ee/revenue/slingdata_replication_workshare_20261012/migration/downstream.mjs) retains a complete original file map, inventories references, prepares explicit literal edits and binds them to the reviewed plan/comparison. Apply, observation, restore and resume preserve the original files, operation IDs and drift. A private consumerRoot selects the actual authorized customer files; without it the application operates its own retained workspace copy. This makes the distinction between a demonstrated file transformation and a real customer deployment visible.

### Applications and recovery

The existing Applications interface reviews and saves a complete private launch configuration, exact 70-file source and actual runtime identity. Start opens the original HTTP observer, workspace store and lease. The browser provides the original seven sections: overview, sources, plans, native runs, comparisons, cutover/consumers and delivery/history. The [server](https://github.com/woahwhattheheck/commons/blob/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012/server.mjs) and [operator guide](https://github.com/woahwhattheheck/commons/blob/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012/OPERATOR.md) remain the operating authority.

Closing the application observer does not cancel an accepted detached Sling process. That process keeps its original inherited kernel lifetime. Applications Stop closes the listener and its own handles; job.cancel is the explicit original cancellation request. Reopening observes the same accepted job. Failed/interrupted or uncertain target writes retain their original attempts and require the original resume or retry/adopt/abandon decision. A new application instance is not used to erase an unresolved owner.

Every agent mutation retains the exact actor, request ID, expected revision and payload before dispatch. The original application may commit before a later launch, downstream operation, consumer materialization or response fails. Recovery therefore reads the retained host request and replays that identical request. The original Sling server has no separate HTTP request-receipt endpoint, and the integration does not invent one.

### Full customer-agent output

The private Merchant provider exposes 22 tools for the same original application: declared aliases and connection lifecycle; browser/info/projects and historical project reads; original project creation/actions and durable requests; resumable upload and declared-host source streaming; Airbyte connection selection and actual consumer paging; complete artifact retention; JSON inspection and exact byte-range reads.

The original actor roles are operator and viewer, scoped to the installation. A viewer can read the complete original workspace but cannot mutate it. There is no substituted tenant or project-grant model. Retained cached responses/files remain bound to the original actor and installation, and disclosure rechecks its current original roles and read permission. Private mutation history requires operator permission. Bearer tokens and arbitrary filesystem paths are absent from tool arguments.

Full uploads and retained artifacts may be up to 2 GiB, with original 8 MiB upload chunks and bounded196,608-byte inline transport pages. Native request/structured plan JSON remains bounded at 32 MiB. The complete source, plan, replication document, observations, comparison, native file, downstream file and named package retain exact bytes/SHA and original download names. Readable JSON references point into that same complete retained file.

### Independent editable receiving

The [portable implementation](https://github.com/woahwhattheheck/commons/blob/d074376ca95c0a5cc6c7abb1f28409201c1082ee/revenue/slingdata_replication_workshare_20261012/core/archive.mjs) exports complete canonical flat NDJSON, schema tjlabs.sling-portable.v2. It preserves selected project/history, exact frozen requests, original source, complete native files/snapshots, typed results, consumer choices and full editable application source. Earlier named v2 editions are reproducible byte-for-byte from their frozen headers/request selections and complete content-addressed pool. Original gzip-v1 receiving and literal old archive export remain supported.

A handoff requires original native closure. Fresh receiving opens closed; same/older receiving preserves newer local history; forward receiving uses the original receiving fence before adopting its descendant. Source-host native jobs do not silently restart on the receiver. Receiving continuation requires the actual receiving host’s verified engine and explicit original action.

The [whole original receiving programme](https://github.com/woahwhattheheck/commons/blob/6d969651d2f48f1ca620f94ed88c33c65f07577e/revenue/slingdata_replication_workshare_20261012/receiving/receive.mjs) covers baseline and real source change, complete comparison, cancellation/recovery, actual consumer switch/rollback, downstream edits/restoration, desktop/mobile browser operation, full downloads, fresh/forward/same/older handoffs and cold CLI reopening. The Merchant extension joins those same original closed workspaces to Applications and the customer agent, retaining complete source/runtime/product packages. It does not launch another reference just to create demonstration data.

Before presenting an outgoing customer product as ready, the producing owner must run/render that exact edition, look at the actual screens/screenshots, operate important controls at desktop and relevant narrow widths, and reopen complete exports and attachments. Source review and a merged declaration do not replace this observed operating course.

### Installation and funded customer work

The Replication Workbench Installation profile describes one complete commissioning task: source authority and population, original runtime, reviewed plan, baseline/change native work, full comparison, actual consumer/rollback, any commissioned downstream edits, agent operation, independent receiving and actual outcome save. It uses the existing Workshare-derived seed and case/version preview/save. Payment, buyer, merchant, atomic amount/count/budget, assignments and completed observations remain the original Installation selections.

Customer examples include a complete daily orders edition with an accountable finance receiver, an agreed periodic stock/change export with explicit keys, or a supplier catalogue edition with reviewed schema changes and downstream file restoration. The buyer chooses the real source period, full output, receiving person and actual activity calendar before pricing. The product does not assume that every internal data operation is a purchase.

This reusable source/integration is completed work before any prospective award. Funded work is the remaining customer adaptation and operating delivery selected within the existing approved packages: authorized source intake, complete connector/export adaptation where needed, runtime/environment setup, operator/customer-agent integration, full acceptance/independent receiving and agreed support.

The accepted grant programme remains 400 hours/USD 38,000 over 150 days with its six packages, three tranches and four payment steps. This product adds no parallel grant budget or fabricated usage target. Each adaptation belongs once to its selected funded package or separately commissioned Workshare. The original company’s proposed USD 9,600/15-business-day workshare is its separate commercial offer, not a new grant allocation or proof of payment. Actual customer tasks and native settlements remain counted separately under the current customer calendar and buyer-return conditions.

Claims of deployed service, complete parity, accepted consumer transition, independent receiving or paid recurring use require their original observations. Immutable source registration establishes the complete implementation available for commissioning; current Installation and the serial grant composer retain the actual accepted outcomes.
