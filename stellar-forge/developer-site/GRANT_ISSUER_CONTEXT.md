# Receive issuer correspondence and a native plan into an application

The submission editor can receive a complete issuer programme from Grant Operations and retain it with the existing application. The programme contains the original correspondence and attachments, saved terms interpretations, their proposal comparisons, the complete native plan history, and the reviewed commissioning records.

Open **Prepare submission → Submission handover → Issuer programme and selected native plan**. The same controls are available in a saved browser draft and after opening a complete editable draft.

## Prepare the original handover

In Grant Operations, open the relevant case and its **Issuer terms** workspace. Select the saved terms edition to hand over, then use **Export complete issuer case**. This produces the original Operations ZIP with:

- the complete native `planning.zip`;
- the original Operations document, sources, events and reports;
- `award-terms-selection.json`, `award-terms.html` and `award-terms.csv`;
- every retained original source under its native source identity.

The selected terms edition can be historical. Its original case version and original selected plan remain part of that edition. The case's current selected plan is also explicit. A newer working native plan can exist without becoming the case-selected plan; receiving uses the revision recorded by the case.

Keep the complete ZIP. Individual screenshots, copied paragraphs and the printable terms report do not contain the full receiving state.

## Review and retain the programme

1. Open the existing application or its whole editable draft.
2. In **Submission handover**, expand **Receive an original issuer programme** and choose the complete original Operations ZIP.
3. Enter **Issuer context title**, **Issuer context operator**, the optional original URL, and a reception note.
4. Choose **Review original programme**. The panel shows the observed stage, proposed track, issuer-selected track, issued amount, round and deadline source. It also shows the original saved proposal comparison.
5. Open the original correspondence, terms history and commissioning sections. Message text is displayed as text, including HTML MIME parts. Download controls return the complete original message or the exact selected attachment.
6. Choose **Record issuer programme**. The complete ZIP and its reviewed context are retained in this same application draft. The new context becomes the selection for the next prepared edition.

Receiving records the original observation and the saved operator interpretation. For example, an interest-form acknowledgment remains **Interest acknowledged**. Its proposed track can be Open while the issuer-selected track and issued award remain empty. The receiver carries these original values directly from the native case.

An earlier issuer message belongs to the programme history. The editor's separate **Record an actual issuer observation** controls still associate an actual reply or observation with a specific prepared edition. A programme reception does not create that association automatically.

The working filename, metadata and source selection survive saving a draft. Clearing a working file selection leaves previously retained originals and contexts available in their history.

## Receive the exact native plan

After recording the context, choose **Receive selected native plan**. This opens the original native planning receiver with the case-selected revision. The complete planning ZIP and all of its retained revisions stay unchanged.

Continue in **Planning edition**:

- Review the complete budget, work packages, timing and conditional payments generated by the native planner.
- Prepare the original planning preview and record the review selection.
- Choose how to apply the plan to the existing Delivery answer or a mapped issuer field.
- If another revision of the same plan is already selected, use the existing plan-update comparison. It retains current answers, manual changes and prior planning applications. Choose the complete text for each affected target and finish that original review.

Selecting an issuer context and selecting an application plan are distinct operator actions. A prepared edition reports when its selected issuer programme carries a different planning file or revision from the application's current planning review. This lets the operator preserve an existing answer while deciding whether to receive a newer plan.

The native planner remains the source of budget calculations, milestone amounts, work-package costs and payment timing. The issuer receiver reads those original results and selections.

## Prepare an edition and continue editing

Use the existing **Prepare this exact edition** control. A prepared edition freezes:

- the complete current answers and mapped fields;
- the original application and reviewer source selections;
- the original native planning source and selected revision;
- the selected issuer-programme identity;
- selected evidence, review notes, and the exact output format and text.

The issuer programme's full ZIP is stored once in the draft's existing original-file collection. Each prepared edition references its immutable context. Later source receptions, issuer selections and answer edits remain visible in **Compare the present draft with this exact prepared edition**.

The printable prepared report includes the selected issuer stage, original correspondence metadata, terms editions and commissioning selections. Its file list includes the complete original issuer ZIP.

Use **Download whole editable draft** for another operator. Open that JSON through the existing editor to recover the same draft, original sources, saved versions, contexts and prepared editions. **Save version** and the existing browser-draft controls use the same original draft store and revision checks.

## Command-line receiving

Use the existing `grant-export` command. An explicit receiving profile records the operator's choices:

```json
{
  "schema": "stellar-forge.grant-issuer-receiving-profile.v1",
  "title": "SCF issuer programme",
  "actor": "Application operator",
  "note": "Reviewed the original correspondence, selected terms edition and native case plan.",
  "sourceUrl": "",
  "receivePlan": true
}
```

Choose `receivePlan: true` to open the case-selected native plan in the original planning receiver. Choose `false` to retain the issuer programme while keeping the application's existing planning selection. The profile requires that choice explicitly.

```bash
starforge grant-export \
  --draft saved-submission.json \
  --receive-issuer-case complete-issuer-case.zip \
  --issuer-profile issuer-profile.json \
  --out /private/issuer-application-export
```

The direct source command is equivalent:

```bash
node stellar-forge/developer-site/grant-export.mjs \
  --draft saved-submission.json \
  --receive-issuer-case complete-issuer-case.zip \
  --issuer-profile issuer-profile.json \
  --out /private/issuer-application-export
```

Receiving can also follow the existing `--source`, `--source-index`, `--source-url`, `--budget` and `--companion` inputs when creating an application from a complete maintained source edition. An existing draft keeps its original identity and history.

To select a previously retained context, use `--issuer-context CONTEXT_ID`. Use `--issuer-context none` to clear the selection for the next prepared edition. Both leave earlier prepared contexts and original files retained.

The original `--receive-source-package` flow remains available for the complete four-file reviewer source package. It preserves edited answers and the issuer-programme collection through the same source-receiving functions.

### Exported files

The usual editable draft, answer files, form map, source package, review page and manifest remain part of the export. When an issuer programme is selected, the export also contains:

| File | Contents |
| --- | --- |
| `issuer-programme.zip` | Exact complete original Operations issuer handover |
| `issuer-context.json` | The selected typed context, original source identities and history projections |
| `issuer-native-planning.zip` | Exact native planning ZIP retained inside the issuer case |
| `issuer-context.html` | Readable selected stage, correspondence, terms history and commissioning |
| `draft.json` | The complete editable application, including all original issuer ZIP bytes |

The native planning ZIP can include later working revisions. The selected revision is recorded in `issuer-context.json` and in the application's original planning review. Open the complete editable draft to resume that exact selection.

The manifest names every output and its complete byte count and digest. Each original ZIP remains unchanged. A new output directory is required, preserving earlier deliveries.

## Original-source and receiving behavior

The ZIP reader uses the same 32 MiB complete-bundle allowance as native Operations. The existing editable application retains its 16 MiB logical-draft allowance, including embedded originals. A reception that does not fit leaves the prior draft available.

Receiving checks the original ZIP directory, entry names, sizes and checksums, then every complete manifest file identity. It verifies the selected terms source, consecutive terms editions, native save events, correspondence selections and commissioning references. The nested planning ZIP is opened by the maintained native-plan receiver, including its complete original scenario and saved revision digests.

Native JSON number spellings are retained while verifying Python-generated content identities. The receiver uses the existing native JSON decoder and canonical digest convention. Original case and plan identifiers in historical sources remain unchanged after a native reimport; the receiving case's current identifiers are recorded separately.

The complete retained case includes other Operations records and reports. Their original native validation and import remain with Grant Operations. The application receiver retains those original bytes alongside its selected issuer and planning context.

Original correspondence may contain private headers and attachments. Keep the complete receiving draft and programme in the intended application handover location.

## Maintainer integration

The additive modules are:

- `dist/grant-issuer-core.mjs`: typed immutable context and existing-handover validation.
- `dist/grant-issuer-source.mjs`: complete native ZIP reception, original source/history verification, context retention and original planning selection.
- `dist/grant-issuer-workspace.mjs`: the receiving, review and source-download controls inside the existing handover.
- `grant-issuer-context.mjs`: the explicit CLI receiving profile and original source-index/asset contribution.

The original handover owns file objects, versions, prepared editions and issuer observations. The original submission editor owns answers, field mappings and the browser draft store. The original planning receiver and update writer own plan selection and application.

`receivePlanningSource(draft, source, at, {revision})` accepts an optional explicit revision. Existing callers continue to select `source.document.currentRevision`. Issuer receiving passes the case-selected revision, which can precede an uncommitted working head.

The existing source-package interfaces remain `openReviewerSourcePackage`, `receiveReviewerSource`, `reviewerSourceFromDraft` and `createReviewerSourcePackage`. Complete source packages and complete editable drafts retain their existing schemas.

`attachGrantHandover` includes the issuer contribution, so the existing submission composer and asset registration acquire it together. The maintained grant-reviewer contribution exports the typed context and reader modules and includes this guide and the complete receiving programme.

Run the complete original-case walkthrough from the maintained repository, with the original Grant Operations Python source present. An installed application can instead pass `--native-source /path/to/grant-operations/workspace` from its existing native source selection. The operating programme creates an independent workspace beneath its private output directory and retains the original case input.

Run:

```bash
node stellar-forge/developer-site/GRANT_ISSUER_RECEIVING.mjs \
  --case /private/SCF_Issuer_Terms_Complete_Case.zip \
  --out /private/issuer-application-receiving
```

Add `--browser` for the existing source-selected desktop/phone receiving and draft-reopening flow. Use `--resume-browser` with that same output directory to continue its saved model case. The programme records the actual source files, current application edition, original issuer selections, native plan history, complete saved draft and handover outputs.
