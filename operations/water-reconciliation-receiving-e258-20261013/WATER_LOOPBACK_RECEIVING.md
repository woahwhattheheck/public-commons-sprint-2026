## Resume the actual stopped browser operation

Use the exact same receiving path, output directory and installed runtime paths as the original browser attempt. Select the new helper file explicitly:

```sh
/actual/node /absolute/continuation-source/receiving_water_browser.mjs \
  --receiving /absolute/original-native-operation/receiving.json \
  --output /absolute/original-browser-output \
  --playwright /actual/installed/playwright/index.mjs \
  --chromium /actual/installed/chromium \
  --resume --adopt-loopback
```

The two flags have distinct purposes. `--resume` permits the existing browser output and its original dead-process lock recovery. `--adopt-loopback` acknowledges this one reviewed helper successor. It is accepted only when the saved helper is the exact predecessor above and every other original input field matches: completed receiving bytes, all report paths/bytes/hashes/source identities, Playwright and Chromium paths. A changed native case, changed runtime selection or unrelated helper does not qualify.

The existing `browser-input.json` is preserved byte for byte. After obtaining the original operation lock, the helper writes a separate immutable `browser-helper-adoption.json` binding that exact old input hash, predecessor helper hash and actual selected successor hash. The new attempt's progress, failure or completion records keep the original input hash and disclose the actual helper hash and transport. Prior attempt directories and screenshots are never replaced. A live original PID still owns its lock; coordinate that owner instead of starting another course.

Repeat the same command, including both flags, after an interruption. The adoption record must match exactly. Once complete, the helper verifies every retained completion artifact before returning the original completion; it does not recalculate or automatically create another browser attempt.

For a new browser output against an already completed native operation, omit `--resume --adopt-loopback`. Its fresh input selection binds the successor directly.

## Read-only exact-byte presentation

The server binds only to 127.0.0.1 on an available local port and a random process-lifetime URL prefix. It exposes an explicit inventory:

- The original, later and cold `water/report.html` files selected by the existing receiving receipt.
- Their existing result, report and manifest files, original water selection and complete review-items CSV.
- Every source CSV named by the original result, checked against its original byte count and SHA256.
- The complete HTML actually downloaded during this same browser attempt, solely for cold reopening.

No directory listing, arbitrary path, remote fetch or write method exists. Requests require the original local Host and same-origin browser context. Every served file remains an ordinary file with the selected byte length and SHA256; changed or unavailable originals return an error. The browser context blocks HTTP requests outside the selected process-owned loopback route. No browser security switch is disabled. The complete source inventory is retained in the attempt's `loopback-source-selection.json`.

The downloaded HTML is served under the original case's water directory URL so its relative original-source links retain their meaning during cold reopening. The actual downloaded file stays in the browser output directory; neither its bytes nor the native case are rewritten.

The HTTP server closes with this helper. There is no new daemon, queue or provider operation. Later manual opening can use the receiver's existing approved local preview route; preserve the same original files and show any unavailable source link honestly. File:// may work on other browsers, but this continuation does not depend on it.
