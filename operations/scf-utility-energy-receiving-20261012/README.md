# Complete Utility customer receiving

This entry continues the original UtilityAPI and Green Button product through its complete customer workflow. It runs the maintained source operation, browser, customer client, original merchant MCP host, CLI receiving and managed Applications lifecycle in one process tree. It retains each completed phase and packages the actual customer files before that invocation ends.

The original accepted operation is the 56,586-byte `Utility_Original_Customer_Operation_20261012.json`, SHA256 `08ae13edf0ce8c7f5e23ae3c214cc00be104486ec41982dd60ccd9ba5eb9b966`. It records 20 complete original source imports: the Green Button Alliance's 1,340-reading file, its overlapping 96-reading day file, and 18 published UtilityAPI examples. The reviewed native dataset contains 1,340 readings, returned in 14 complete cursor pages. The original comparison retains 96 equivalent day references and the original customer restore retains all source imports, reviews, editions, comparison and bill reconciliations.

## Source and runtime

Use a complete checkout containing the source commit named by `source-manifest.json`, or the complete repository-shaped `source/` directory of a maintained merchant package with the declared exact postimages. The root must contain both `stellar/` and `stellar-forge/`.

The declaration pins all 63 Utility, original source, native Python/XML and receiving transport files. That is an identity check for this workflow's declared source. The entire maintained repository/package supplies the other transitive modules, source-owned contributions, merchant provider registry, Applications worker and selected native dependencies. The runner imports the actual `config.mjs`, `operator.mjs`, `serve.mjs`, Utility owner/client and original Socrata publisher before opening the customer writer.

The installed public Green Button examples are `sf30-seller-sdk/utility-energy/examples/test_usage_data.xml` and `examples/test_usage_data_01.xml`, with the original Apache 2.0 text at `contracts/GreenButtonAlliance-LICENSE.txt`. Their bytes and Git blobs are identical to the retained upstream reference files. The source contract preserves the original upstream paths, URLs and commit. These explicit production example paths are accepted by the existing package collector.

Keep the package's original dependency resolution intact. A selected native runtime must already be complete through the original SF46 runtime manager and must contain the same declared source. Supplying a small overlay on an older installed keeper does not provide that complete source and dependency relationship.

Use the existing supported Node and Python executables. The original managed binding checks Python and its XML parser against the maintained product requirements. Supply an existing Playwright module and Chromium executable explicitly. No dependency installation, browser download or repository build is part of the receiving command.

The main command is:

~~~sh
/absolute/existing/python3 \
  operations/scf-utility-energy-receiving-20261012/run-receiving.py \
  /private/utility-receiving.json
~~~

A configuration for reconstructing the closed original example operation from its unchanged retained inputs is:

  "artifactDirectory": "/retained/utility-customer-delivery",
  "runtimeDirectory": "/completed/original-native-runtime"

~~~

Choose the actual host paths. The Python executable running the command must be the selected `pythonExecutable`. The original operating source is under `stellar/scf-starforge-20261009/sf30-seller-sdk/utility-energy`; the receiver calls its original `operate-example.py`, `operate-browser-client.mjs` and `cli.mjs` directly.

There are three mutually exclusive source receiving modes:

| Configuration | Original input used |
| --- | --- |
| `coreDirectory` | The existing closed `operate-example.py` output, including `operation.json` and its `seller/` workspace. |
| `portable` plus `portableSha256` | The exact original complete workspace packet, restored through the maintained CLI into this receiving operation's own directory. The original report remains preserved verbatim. |
| `reconstructOriginal: true` | Explicit reconstruction from the unchanged original Green Button reference files after the original container's source/customer directories became unavailable. The new result must match the original report's input IDs, hashes, bytes, counts, reviewed row count, native snapshot, overlap count and receiving totals. |

Keep `originalReport` in all three modes. A portable restore retains the packet's original source and review IDs. Source reconstruction invokes the original operation once and retains a new report alongside the original; its newly authored operation/review IDs remain distinct. The comparison uses the exact retained inputs and native results.

If the original example operation included merchant configuration, pass `merchantTerms` with the same original public terms JSON. The runner supplies that existing file to the original operation. Provider access and customer payments are outside this source reconstruction.

## One complete operation

The original receiving journal records these phases:

1. **Source verification and component loading.** Verify all declared source files, the original operation report, and the actual current merchant/provider imports.
2. **Original core receiving.** Reopen, restore or explicitly reconstruct the completed original inputs and customer/native outcome.
3. **Browser and customer client.** Run the original browser operation over the same seller. It inspects and downloads all 20 originals, reviews the complete source selection and priority, builds and compares the native edition, traverses every query page, reconciles original bills, downloads the full customer package, then restores it through the real customer browser and CLI. Chromium and both original console owners close before the following phase.
4. **Configured merchant MCP.** Open one original Python owner and lend its authenticated console to the actual `MerchantReleaseOperator`. The source-owned registry advertises the exact 22 Utility tools alongside the merchant host's ordinary tools. Inspect all source/operation inventories, every original interval record page, complete reviews and original series. Receive the whole customer ZIP, workspace packet, native dataset/configuration/source/query files, an original provider file, native comparison and native project through the maintained retained-file readers. Each download is checked for full length and SHA256, then reopened. The MCP borrower is closed and reattached while the Python owner remains the same.
5. **Original CLI cold receiving.** Export the complete workspace through the original CLI, restore it into the selected new directory and compare original source IDs, review IDs, edition IDs, comparisons and reconciliations. Query the same native snapshot and complete 1,340-row dataset.
6. **Managed Applications.** Review and save the source-owned Utility application against the completed original runtime. Adopt through the existing managed home and worker, start, inspect the authenticated launch/binding, and receive the same MCP/customer files. Stop and independently observe the removed connection file, ended PID and closed listener. Reopen the original application and repeat its read/receiving pass, preserving the source/binding identities and the already retained native export.
7. **Complete handoff.** Save the original reports, source declaration, complete customer/portable packages, screenshots and declared received files. Build one ZIP with a file manifest and independently read each packaged member back to its full byte count and SHA256.

The browser's additional source review is the outstanding product operation. The MCP and managed phases use its completed native export; they preserve that review and do not issue another source capture or purchase.

`runtimeDirectory` can be supplied when the managed phase is ready. An operation that reaches that phase without a completed runtime preserves its finished browser, source, MCP, CLI and customer outputs. Supply the completed runtime in the same configuration and receiving directory; its selection is then pinned for both managed passes. Once selected, keep its `runtimeDirectory`, `expectedSourceCommit`, `environmentFile`, `homeId` and `applicationWorkspace` unchanged.

`environmentFile`, `homeId`, `applicationWorkspace` and `expectedSourceCommit` are optional original managed settings. The underlying Application review, worker lease, original installation state and native runtime checks remain authoritative.

## Recovery

`receiving.json` records the selected source and original inputs. `core/operation.json`, `browser/operation.json`, `mcp/journey.json`, `managed/receiving.json` and the original workspace journals retain their native outcomes.

Invoke the same command and configuration to resume. A completed phase is read from its existing result. If the browser is interrupted after authoring a review, the receiving command preserves that state and points to the exact original report; it does not start the full browser operation again. Resolve the concrete retained browser phase on that owner and continue the remaining command.

The MCP callback retains its original request ID and export selection. When `finalExport` is explicitly used by a caller, an uncertain mutation reply is reconciled through the original operation reader before any continuation. Full downloads retain their manifest, read handle and exact file identity. The managed callback reuses its original saved application, operation IDs, review and worker journal.

The outer receiving lock serializes this one orchestration. Each original product retains its own existing workspace, file, runtime and worker locks. Python ownership passes sequentially between the browser, MCP, CLI and managed stages.

Use a durable receiving/output volume on a VM. In the ChatGPT cloud executor, `/dev` can be invocation-local; keep the complete process tree alive until its original output is copied or uploaded. The `artifactDirectory` is the caller's retained receiving destination and must have room for the complete files. The runner reports an actual storage failure if those bytes cannot be saved.

## Prepared output transfer

The caller may supply existing provider-prepared HTTPS PUT targets. The runner determines each exact file size and digest, streams the whole file during the same invocation, and records the provider's actual HTTP result. It does not create upload accounts or prepare new remote records.

~~~json
{
  "uploads": [
    {
      "id": "existing-provider-upload-id",
      "kind": "bundle",
      "url": "https://existing-prepared-upload-target",
      "headers": {
        "Content-Type": "application/zip"
      }
    }
  ]
}
~~~

Supported kinds are `bundle`, `report`, `portable` and `customer`; supply at most four targets. Keep the URL and any headers in the private configuration. The terminal result contains only the original provider ID, safe status metadata, bytes, SHA256 and artifact paths.

`transfers.json` binds each prepared target ID to the selected URL hash and exact source bytes before dispatch. It records one attempt. An uncertain transfer requires a readback of that same provider record; the receiver does not blindly send the body again. Complete the existing provider's normal finalization from those recorded receipts. The original product reports and files remain the source of truth if only the external transfer requires reconciliation.

The handoff ZIP includes declared customer files and reports. Private connection URLs, host configuration files, command logs, interpreter caches and the receiving configuration are not selected into that archive.

## Callback interfaces

For a caller that already owns the original console:

~~~js
import { runUtilityEnergyMcpJourney } from './receive-mcp.mjs';

await runUtilityEnergyMcpJourney({
  sourceRoot,
  workspaceDirectory,
  consoleUrlFile,
  outputDirectory,
  sourceManifest,
  reviewId,
  exportId,
  finalExport: false
});
~~~

Pass exactly one of `consoleUrlFile` or the original private `consoleUrl`. This callback borrows the original console, creates the ordinary source-configured merchant host in its own receiving directory, exercises the authenticated tool catalog and complete file readers, and drains its own MCP/HTTP handles.

For the complete managed application:

~~~js
import { receiveUtilityEnergyApplications } from './receive-managed.mjs';

await receiveUtilityEnergyApplications({
  runtimeDirectory,
  bootstrapSourceRoot: sourceRoot,
  workspaceDirectory,
  pythonExecutable,
  receivingDirectory,
  sourceManifest,
  reviewId,
  exportId,
  finalExport: false,
  expected: { importIds, reviewIds, buildId, snapshot }
}, {
  onProgress: event => process.stdout.write(JSON.stringify(event) + '\n')
});
~~~

The optional `onOpen` callback receives the existing original console and application after its native MCP receiving. It can inspect the same browser view. Any authored source changes must be a separate reviewed product operation; the managed receiver compares its original source identity across both opens.

The full executable outcome is available when `status` is `COMPLETE` and `passed` is `true`. The saved reports contain the actual source IDs, native snapshot, received file hashes, application ID, managed operations and observed process/listener closure.
