# Catalogue Delivery Workbench — complete installed receiving

This course receives an existing complete customer implementation and its two
original native approval editions into independently prepared installations. It
opens the real catalogue, implementation and approval screens, operates one
deliberate local review-note change in each installation, retains complete agent
and browser exports, and reopens the application and agent file store from disk.

The original destination programme remains the authority for actual upload,
readback, rejection and approval. The course consumes that programme's complete
outputs. Its managed worker is disabled, it supplies no service-token
environment, and it makes no destination upload or native approval request.
A local import or a completed source preparation cannot stand in for the
original native result.

## 1. Select the complete existing operation

Use the current native/company owner to select the exact original operation,
completed implementation archive, initial rejected-edition approval archive,
corrected approved-edition approval archive and the two literal native phase
results. Preserve every original source, job, review, principal, event and
request identity. Do not start a second backend or redispatch the original
decision to fill a missing handover.

The supplied private source contains the complete authorized application and
its original source-owned readers. The public Merchant product contains generic
adapters. Keep private customer code, commercial documents, source authority,
native results and credentials in their existing private custody.

When the original provider course is incomplete or has no accepted host,
continue its existing operation with the complete source and exact opening
instructions. Preparation and source engineering may proceed independently.
The installed receiving command requires its completed native outputs before
it can adopt them.

The native phases must identify the same source bytes, job and review carried
by their corresponding approval archive. Each phase has two distinct retained
principals, two APPLIED original operations, and the exact original request and
decision event identities. The first decision remains rejected/private; the
corrected edition remains approved/public. The course reads those facts from
the selected original files and checks their complete graph.

The row counts come from the original selection and complete CSVs. A course
that originally produced 144 and then 546 rows retains both complete editions;
it never substitutes a sample or compares only the latest row count.

## 2. Prepare the private application

Run the selected installed preparation command with an actual canonical
CPython 3.11 or later:

~~~sh
starforge catalogue-delivery-workbench-prepare prepare \
  --directory /private/catalogue-preparation \
  --python /absolute/python3 \
  --source /private/original-catalogue-source \
  --source-manifest /private/catalogue-source.json \
  --source-manifest-sha256 FULL_LITERAL_SOURCE_MANIFEST_SHA256
~~~

The manifest schema is
stellar-forge.catalogue-delivery-workbench-source.v1. It contains the exact
complete files array, with relative paths, byte lengths and SHA256 values.
The current original selection has 38 files; the generic authority format does
not invent or omit source members to achieve that count.

Preparation copies and verifies the full selected source into two independent
application directories. Each uses its actual returned Python and has a closed
package-import observation. Source copies do not create a Store, native
worker, HTTP listener or destination.

Use the returned path to .preparation/PREPARED.json. Its primary and receiving
objects each contain applicationDirectory, sourceManifestFile,
sourceManifestSha256 and python. There is no fabricated runtimeReadyFile for
this source-owned Python application.

For a separate equipped host, export and receive the complete private source:

~~~sh
starforge catalogue-delivery-workbench-prepare export \
  --directory /private/catalogue-preparation \
  --python /absolute/python3 \
  --output /private/catalogue-source-transfer.zip

starforge catalogue-delivery-workbench-prepare receive \
  --directory /private/catalogue-preparation-on-receiver \
  --python /actual/receiving/python3 \
  --archive /private/catalogue-source-transfer.zip \
  --archive-sha256 FULL_TRANSFER_SHA256
~~~

Select the optional source-authority pair when the receiving host is required
to match an already declared private source authority. This source-transfer ZIP
is separate from the original implementation and approval formats. Preparation
does not reinterpret a business archive as source or relocate an interpreter.

## 3. Freeze the private original-result selection

Create one private JSON input with schema
stellar-forge.catalogue-delivery-original-delivery-input.v1. It has:

- sourceManifestSha256: the exact selected private manifest SHA256.
- donor.nativeOperationId: the existing original equipped operation identity.
- donor.implementationId and donor.revision: the original selected complete
  implementation and revision.
- donor.implementationArchive: {path, bytes, sha256}.
- donor.approvals: exactly the two edition selections, in reject/approve order.

Every approval selection contains:

| Field | Meaning |
| --- | --- |
| recordId | Original retained review identifier |
| jobId | Original completed delivery identifier |
| sourceId | Original full source edition identifier |
| decision | reject for the initial edition; approve for the corrected edition |
| rows, bytes, sha256 | Complete original CSV row count and literal byte identity |
| archive | {path, bytes, sha256} of the selected complete approval ZIP |
| phase | {path, bytes, sha256} of its literal original native phase result |
| phaseArchive | Optional original native approval ZIP descriptor when archive is a later local-notes edition |

Use absolute canonical file paths. Hash the actual complete files. The
phaseArchive distinction preserves the original native evidence when a later
customer archive adds only local notes. It does not relabel a later archive as
the original phase output.

The native operation label provides ownership context; proof comes from the
full literal phase results, source archives, original APPLIED operations,
distinct principals and event identities. Do not manufacture any of those
fields from a desired result.

The receiving course freezes the full JSON and the byte identity of this input.
After the operation begins, change neither the input nor its paths to point at
a later edition. Resolve a genuine new edition through the existing owner's
source/input continuation.

## 4. Run the complete installed course

From the exact installed Merchant runtime:

~~~sh
starforge catalogue-delivery-workbench-receive \
  --directory /private/catalogue-installed-receiving \
  --merchant-workspace /private/merchant-runtime-workspace \
  --merchant-runtime /private/installed-merchant-runtime \
  --preparation-result /private/catalogue-preparation/.preparation/PREPARED.json \
  --original-request /private/original-catalogue-results.json \
  --playwright /absolute/playwright/index.mjs \
  --chromium /absolute/chromium \
  --actor "Installed catalogue operator"
~~~

Use the actual returned preparation and runtime paths, not the placeholders
above. For interruption, run the exact same command with --resume. This
preserves the original course directory, source, inputs, Applications workspace,
saved ports, browser profile, request journals and operation identifiers.

The course opens the maintained Runtime Workspace and attaches the exact
selected distribution. It checks the full prepared source through both source
installations and the executing helper/browser identities before any managed
launch. Its complete final candidate is reconciled before mutable setup so
an already completed operation does not acquire a different setup observation.

The original offline helper imports the verified private package, invokes its
actual implementation and approval readers, and checks every archive member.
All helper writes use the same catalogue-operator.lock as the managed host.
The original Store's selected package-request-journal path is returned by the
receiver and passed literally to managed launch. A second default journal
would be a different request history and is not selected.

## 5. What the course does

### Original result and complete archive receiving

The helper first checks the original implementation package, its embedded
source roster and all complete member hashes. It restores both approval
packages through their unchanged source-owned reader. Before merging the
approval graphs into the implementation workspace, every common source,
target, plan, job and object must already agree byte for byte.

It checks every complete source CSV, its retained producer manifests, all
implementation bindings and full identifier comparisons. Both native phase
results are joined to the selected complete graph. The native operation,
principal and event histories stay unchanged.

The original readers are new-directory readers. The outer helper retains its
exact request and closed result before reuse. If an initial extraction stopped
mid-file, recovery accepts only the exact partial prefix of that selected
archive member and preserves it before completing the same original receive.
A different closed file is a conflict, not permission to overwrite later work.

### Applications and the customer agent

For each actual received Store, the course saves a private launch
configuration, obtains the maintained Applications Review, saves that
application, connects it to the selected release, and starts the same original
HTTP application.

The launch selects worker:false and an empty credential environment. Original
saved feeds and target references remain historical records; they are not
advanced by this installed course.

The agent opens the actual manager with all 49 declarations: the original
34 native operations and 15 installed attachment, source, retention and
implementation operations. It reads the native tool catalog and pages every
source, target, plan, job, feed, profile, review, operation and observation.
Each listed record is reopened through the original inspection method.

For both selected source editions it retains the entire CSV via the original
artifact path, reads the complete original row sequence, and checks the full
row count, header, SHA256 and byte length. Large bytes travel through the
maintained bounded file reader; the course continues each saved read ID to EOF
and verifies the whole digest.

This is useful receiving of the existing customer result. The presence of a
mutating native tool in the catalog does not cause the course to call it.

### Real catalogue, implementation and approval controls

Each source installation opens all three actual views:

| View | Operated controls and complete output |
| --- | --- |
| Catalogue | Source search and empty state, both complete editions, source CSV and JSON downloads, reopened JSON, original completed job and target/plan/feed views |
| Implementation | Exact selected customer profile, edition comparisons, desktop/mobile view, profile download and reopen, complete implementation export |
| Approval | Both retained native reviews, history, desktop/mobile views, complete review JSON and both original-format approval exports |

The source JSON download is opened inside its actual “Complete saved record”
details panel. Complete archive downloads are streamed to private files, not
assembled as giant buffers. A full candidate descriptor is durable before
publication; full SHA/count checks precede reuse. An interrupted unclosed
download is preserved separately. The capacity bound follows the original
2 GiB complete source/archive limit plus the approval format's 64 MiB overhead.

Screenshots retain their original scroll/focus state and then capture the
actual top-of-page desktop and narrow view. This distinguishes responsive
layout problems from a full-page capture taken at a retained scroll position.
The narrow width is 390 pixels.

### Original local-note recovery

The course makes one explicit local note change in the approved review of each
receiving installation. It captures the actual original request body before
dispatch, including the selected revision and note text. It retains the full
HTTP response and deliberately loses the first acknowledgement.

The actual original UI catches the failed acknowledgement and reloads the
record. Its notes endpoint uses revision control, not a fabricated UUID
lookup endpoint. Recovery therefore compares the saved original request,
complete prior record, current revision and exact one-row note history.

If the current record already contains that exact change, the course adopts
the observed original result. It does not resend a stale revision or create a
second note. If nothing changed, the same selected request remains the
continuation. Any unrelated modification is a concrete conflict to resolve
with the owner.

All other native record fields, original observations and request/decision
operations must remain unchanged. The second installation adds its own later
local note, preserving the first installation's history.

### Agent and browser packages

The customer agent creates and retains the complete original implementation
export and both approval exports. It preserves the installed request and
reopens the exact retained response on replay. It then reads the entire
returned archive through the original artifact interface and its full file
ranges.

Browser exports and agent exports are independently selected outputs. They
need not have identical ZIP byte strings: original archive metadata may differ.
The helper opens each complete archive through its actual reader and compares
the full decoded workspace, source objects, implementation bindings and
approval graph to the selected current snapshot.

No completed export is represented by a metadata-only stub. Every full ZIP,
literal phase result, original source file and downloaded CSV remains in the
outgoing private handover.

### Independent receiving and later work

The receiving installation imports the primary browser's complete
implementation plus both approval archives. It checks the exact entire
snapshot before opening its own managed application and customer-agent
connection.

It operates the same three original views, adds one deliberate later local
review note, and exports complete onward browser and agent packages. After
Stop, the helper reopens the original receiving receipt and repeats only the
original implementation reader's safe same-package path. Every later review
note, native operation, source and full object remains unchanged.

Approval restore itself remains an original new-directory operation. The
course does not blindly call that reader over an edited workspace; its
durable helper receipt is the admission boundary for already received approval
graphs.

### Cold reopen and closure

The course closes and recreates the Merchant manager from its original disk
configuration before each cold phase. It then starts a new actual managed
listener and reopens all original records, selected source rows and previous
retained file IDs with their original SHA256 values.

After Stop, the offline helper compares the entire current original snapshot
to the earlier accepted snapshot. Cold receiving includes both the native
workspace and the agent's retained-file store.

Applications Stop is accepted only from the bound unlaunched cancellation or
the actual original command's closed terminal result. A queued, interrupted,
unknown or merely inactive observation is not an ended-owner receipt.
Browser contexts, HTTP/worker owners, accepted native calls and retained file
readers close before the course releases its ownership. A failed close keeps
the same owner in an observable retry loop.

The final ZIP is streamed from the fixed selected artifact list and reopened

capture browser profiles, generated capabilities, service tokens or private
connection files.

Source selection descriptors and customer archives remain private. Do not
publish the handover ZIP simply because the generic Merchant wrapper is public.
Use the existing case's authorized receiving location and original owner.

A completed source review or a successful syntax parse is not this deliverable.
Customer-ready status additionally requires looking at the exact rendered
screens and all outgoing attachments described below.

## 7. Interruption, current owner and practical continuation

Preserve the exact private operation directory. The saved helper request,
browser note, installed export request, Applications review/start and native
phase selection are immutable identities. Resume them; do not create another
controller or receiving directory to evade an unknown result.

A completed final candidate is adopted before new setup observations. If result
publication succeeded but final ZIP creation was interrupted, the same exact
result and artifact roster are reopened and the original closed ZIP candidate
is completed. Partial ZIPs are preserved with interrupted names.

The receiving course does not heal missing original provider outputs by
claiming a local result as native. Ask the current equipped owner for the
actual completed phase files, archives and retained process result from the
same operation. If that original operation is still active, give it the exact
reviewed source edition and continuation command at its existing boundary.

If a displayed control is broken, fix the exact maintained source, retain the
failed output and coordinate source adoption in the same operation. Do not
delete an earlier error or reuse a screenshot from another edition.

For a current positive or warm human conversation, every subsequent outgoing
message and each attachment require Bryce's individual approval. An earlier
approved message does not approve a later one. Keep this engineering and
native receiving coordination in the existing internal owner thread.
