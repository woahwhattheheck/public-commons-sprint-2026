# Hive Routing Workbench — complete installed receiving

This course continues the original Hive application migration through the installed Merchant distribution, Applications, the customer-agent tools, the actual operator UI, complete archive transfer and cold reopening. It retains the original reference operation `HIVE-APPLICATION-MIGRATION-0C7A-20261012` and its three programmes. An existing completed result is adopted without running its GraphQL operations again.

The standalone application is the full maintained 64-file Hive workbench. Its original source capsule is `b05be1ed42b57b447178682f584abb4fa0a6b5c9`, from the original application lineage at Commons `b3b6f57d92c8e704e789728576a3bd95caf40fe6`. The selected maintained source has two explicit changes: the original server can return its real listener for graceful managed shutdown, and the operator distinguishes a retained endpoint selection from a currently ready router. `original-source.json` carries every selected source identity and both original/selected maintenance descriptors. The original Hive upstream source remains `28eafc1bceb3dce8600d0eeea2ce2c2ec9563bb6`; the native router is the original v0.3.4 release.

The commands and receipts below are executable receiving instructions. Source publication and source review do not establish native completion, successful installation or visual acceptance. The original fixture build/controller, including retained build44900 where it is the accepted operation, remains with its existing owner. This course does not compile or replace that fixture.

## 7. Request custody and uncertain effects

The original Hive Controller uses entity revisions and native operation IDs. It does not implement a generic HTTP request-ID API. The Merchant adapter therefore retains the exact original input, resolved file selectors, before-state, original HTTP response and any recovery observation in its own request journal.

A repeated host request reopens its exact confirmed response. A recovered current entity is explicitly labeled as a recovered effect; it is never presented as an HTTP response that was not observed. A failed HTTP response is retained even if the original operation may already have committed some work. Unresolved effects hold that same request for inspection.

The receiving course’s saved intents retain original request IDs across interruption. It reads each complete original request body back through the same file API. Do not resolve an unknown request by generating a fresh ID, deleting a pending record or submitting a different source body.

The browser configuration review is similarly bound to the original edition revision and all existing feature decisions. The exact actual form request is retained before dispatch. If the acknowledgement is lost, continuation first reads the current original entity and compares the selected review’s note, full decisions and subject revision. A changed unrelated revision is a conflict. A same expected-revision continuation uses the original CAS request, so it cannot add the same review twice.

The course does not accept an arbitrary current snapshot as proof that an unknown native start, programme or archive receive succeeded. Original native/controller receipts and their source-owned recovery rules remain authoritative.

## 10. Interruption and continuation

Use the same full command and add `--resume`. Keep the same integration directory, installed distribution, PREPARED file, reference selector, Python and browser selections.

The receiver rehashes retained artifacts before continuation. It reopens the exact final candidate/result before creating mutable setup observations. A completed final candidate can therefore be published after a lost final journal acknowledgement without generating a new completion time or changing the selected artifact set.

During a native reference continuation, retain the original child, its inherited integration lease and original reference/native locks. If the caller disappears, reconcile that actual owner and original journal before another invocation. An unavailable process observation is not evidence of closure.

During Applications continuation, the same saved application/start request is inspected and recovered through the maintained APIs. A new managed lifetime begins only after the previous one is positively closed. The workspace ID, complete source selection and retained listener port remain bound.

During close, the course retains actual browser handles and saved Applications owners until they are closed. Publication failure after all owners close still releases the operation lease normally. A failed close does not become success merely because a boolean flag was set.

If an archive export or receive response is lost, repeat only the same retained host request so its original selected path and original effect can be reconciled. The complete response and current-recovery distinction remain in the result. Do not overwrite an existing receiving directory.
