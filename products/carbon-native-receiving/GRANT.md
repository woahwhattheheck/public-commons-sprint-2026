### Complete customer operation

The staff operator selects an authorized native backup or the official API, the source network and reporting periods. The native backup retains all seven original tables. API capture follows complete transaction and retirement pages and closes related certificates and transactions. Source editions preserve whole original files, exact numeric strings, acquisition scope and available-table coverage. A later API edition can be compared with the backup without treating unacquired distribution and minted-block tables as deleted records.

Actual customer names and projects are operator assignments, separate from source funders, recipients and VCS projects. The operator can assign an individual transaction, recipient or funder, review conflicting assignments and save the current mapping. A statement freezes its original source, customer selection and assignment revision. Later corrections produce another saved version.

Every customer period includes readable HTML, complete JSON and three CSV files covering contributions, certificate allocations and the separately dated retirement register. Contribution dates select the reporting period; all certificate allocations known in the retained source edition remain associated, including later retirements. Whole certificate VCUs and a customer's attributed CARBON are separate measures. Summing every original fill preserves the actual completed amount even when an earlier allocation's native finalized flag is false.

The public April 14, 2026 backup contains 39 contributions totaling 49.158 CARBON, with 49.000 allocated. The retained October 12 API edition contains 40 contributions, 25 certificates and 44 allocations: 52.440 CARBON contributed, 52.000 allocated and 0.440 remaining. In the worked November 2025 customer statement, the original 1.177 contribution advances from 1.019 allocated to 1.177 allocated; the final 0.158 is supplied by a certificate dated July 23, 2026. The November certificate-date register remains empty. This concrete later-retirement case demonstrates why the source edition, contribution period and certificate period travel together.

Staff can export all source editions, mappings, statement versions and history, receive the complete workspace in a distinct private directory, reopen it and continue editing. Individual customer deliveries contain that customer's selected statement files; full staff receiving carries the operating workspace.

### Original donation to customer statement

A staff operator selects the actual organization, original Credits deployment, provider, source dates and reporting groups. Authorized registry capture follows every original list page and includes each donation's impact relationships. Whole original exports can enter through the same intake. Native ledger capture retains complete RPC, Horizon and historical XDR responses, exact token atoms, network and application order. The [historical ledger source operation](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/47b9c48bda957598c67d04abc8d5cbbd7ba04933/stellar/scf-starforge-20261009/partners/carbon-native-receiving/HISTORICAL_LEDGER_SOURCES.md) can close an existing native ledger selection, acquire a finite interval or reselect retained original pages for another observed provider.

The original receipt's payment hash identifies the donor transfer; its minted-token identifier describes the separate receipt. When the legacy Donation UUID association is absent, staff save an explicit association using the original successful transfer and its source explanation. Shared payments retain explicit allocated amounts and are counted once.

The pool register distinguishes incoming donations, immediate vendor payments, provider bucket payouts, accounted provider remainder and actual token balance. Each balance carries its observation ledger. Source-dated fees and ordered events determine funding capacity; current getters do not supply historical rates. A provider and vendor can share an address, so outgoing transfers are interpreted within their original donation call or receive an explicit saved operator classification.

Staff allocate each whole provider payout using original gross-payment weights, native oldest-first order or explicit payment amounts. Original provider capacity limits those allocations, and vendor fees remain outside reusable funding. Payout-to-sink associations retain the selected funding revision and the source that connects the actual transactions. A later funding edit is adopted by an existing association through an explicit update, preserving earlier donor attribution and statement versions.

The statement selects registry creation dates or payment ledger-close dates. It delivers HTML, full JSON and seven CSV files for donations, payments, payout funding, carbon contributions, certificate allocations, the dated retirement register and original receipts. Original token values, reported registry USD, CARBON attribution and certificate VCUs remain separately identified. Donor attribution follows the saved source bridge and funding method; it is not inferred from a pooled balance.
