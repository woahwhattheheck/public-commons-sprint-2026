# Independent source reviewers and original-case adoption

This workflow sends selected, assigned review work to a separate reviewer copy and receives the result into the original Source Monitoring application. The original customer cases, source editions, portfolio comparisons and review cycles remain the operating record. An independently edited copy carries the source selection, unfinished work, named editions and full attached files needed to complete that assigned task.

Start from the installed Source Monitoring application described in [OPERATING.md](OPERATING.md). [Saved review cycles](REVIEW_CYCLES.md) covers creating the actual population, assigning reviewers, retaining evidence, completing work and signing the whole cycle. For customer portfolio changes, also use the original [portfolio review-cycle guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/ndjson/opensanctions/PORTFOLIO_REVIEW_CYCLES.md).

## 1. Select the original work and assigned reviewer

Open **Review cycles** and select the existing cycle for the actual source or customer-portfolio comparison. Inspect its complete selected population and current assignments. Use the customer's stable reviewer ID and name. Reassign through the original cycle workflow when a different person should receive the work.

Open **Reviewer exchange**. Select the same saved cycle, its current version, the assigned reviewer and the exact case IDs being sent. Name the copy for its operating purpose and select any additional retained evidence objects.

The issue operation selects complete source and case material for those cases. Its baseline includes the original case revisions and the cycle assignments that were current when the copy was issued. Later supervisor edits remain separate current work; they do not rewrite the issued baseline.

Review the selected scope before issuing. Source and attachment limits apply to the complete selected copy. A capacity error keeps the original workspace and selection available for an explicit supported selection. No case, original file or source population is silently sampled to make a copy fit.

Download and open the complete issued reviewer HTML. Keep its original issued JSON with the actual project handover. Record the recipient and delivery in the existing customer Installation or Workshare.

## 2. Open and use the independent copy

The issued HTML contains the complete selected review material and its independent editor. Open that actual file in the reviewer's browser. Inspect the selected customer, comparison, source edition or portfolio pair, original case decisions, assignments and retained evidence before editing.

Identity and relevance remain separate decisions:

| Field | Original choices |
| --- | --- |
| Identity resolution | same_entity, different_entity, undecided |
| Relevance | in_scope, out_of_scope, undecided |
| Review disposition | REVIEWED, FOLLOW_UP |

Use the original candidate and source context. A native match's returned candidates, identifier chains and recorded monitoring policy continue to determine which decisions the original application can accept.

The saved working copy has its own physical identity. Name it for the reviewer and task. Keep the full original input, arbitrary unfinished draft and attachments while working. Partially entered text is useful work even when it is not yet a valid completed decision.

Use the editor's source and evidence controls to open the actual complete files. A displayed label, object ID or digest identifies a file; its complete bytes are what the reviewer receives and can reopen.

## 3. Preserve unfinished work and named editions

Save ordinary working changes as a draft. Enter the actual reviewer explanation, identity and relevance decisions, disposition, selected evidence and any applicable original portfolio-review request. Keep further-work notes when a conclusion remains unresolved.

A named edition captures one complete chosen review result at a particular point in that working copy. Create another edition for a later deliberate revision. Preserve earlier editions and their original attribution so the supervisor can select the result actually being returned.

An unfinished return remains useful: it carries the draft and files for continued work. The supervisor receives that material without converting incomplete input into a completed customer decision.

Save both the complete working-copy HTML and its full return JSON. Reopen the saved HTML independently and check that the same source, draft, named editions and attachments are usable. Continue a later edit in that independently opened copy and save another complete return.

## 4. Recover concurrent editing without losing either copy

Two tabs can open the same physical saved copy. A later save must compare the version it originally read with the current saved version. If another tab has saved in the meantime, preserve both the existing saved work and the candidate work that lost the comparison.

Open both retained sides. Review their full drafts, named editions and attached files. Select the intended recovery or deliberately create a separate working copy. Save the recovered complete HTML/JSON and reopen it.

An unavailable browser database must leave the current complete working draft exportable. A storage error is a recoverable operating condition, not evidence that the draft was safely saved. Use the available full-file download and reopen the resulting file before closing the working tab.

The original issued baseline remains unchanged through these recoveries. Recovery chooses which independently edited working copy to continue.

## 5. Receive the exact returned file

Back in the original Source Monitoring application, select **Receive reviewer file** and upload the complete returned JSON or HTML. Select the original physical workspace that owns the issue.

The receiving operation retains the exact return file and all its carried files in the original immutable object store. An identical repeated upload refers to the same original bytes. A later changed return is a distinct retained edition.

Receiving makes the returned work available for inspection. Select its named edition for comparison when the reviewer intended a completed choice. Keep an unfinished return available for continued editing and later delivery.

Open the complete retained returned file and attachments from the original workspace. Check the actual reviewer, original issue, source selection and case IDs before choosing the edition to compare.

## 6. Compare baseline, current work and returned decisions

Choose **Compare named edition**. The comparison places three versions together:

| Version | What it represents |
| --- | --- |
| Issued baseline | The selected original case and cycle work when the reviewer copy was issued |
| Current original work | The present case decisions and cycle assignments in the staff workspace |
| Returned edition | The complete named reviewer edition chosen from the retained return |

A supervisor may have changed the original case while the independent reviewer was working. Inspect those intervening changes beside the return. For each conflicting choice, explicitly select which value the adoption should retain.

Use the comparison's actual current revisions for adoption. If a case, cycle, assignment or relevant original review changes while the comparison is open, obtain the current comparison and review the changed choice. Preserve the earlier returned edition and the supervisor's entered explanation.

The original model validates the resulting case and cycle work. Candidate/source identity, native matching provenance, monitoring policy, reviewer assignment and completion rules remain effective.

## 7. Apply the selected original review atomically

Choose **Apply selected review** after inspecting the selected edition and resolving its differences. Retain the original complete command and request UUID before dispatch.

The application applies the selected case decisions and associated cycle work within one transaction in the original database. An unchanged chosen case keeps its existing revision. A changed decision is saved through the original case writer with its actual observation time. The recorded adoption retains the issued selection, exact return, selected edition, resolved choices and resulting original events.

### Source-edition cycles

A REVIEWED completion must satisfy the cycle's existing identity and relevance requirements and reference its actual following source edition. A same-entity decision must retain one unambiguous current identity when that review requires it. Use FOLLOW_UP for remaining uncertainty or deliberately changed source/monitoring scope.

### Customer-portfolio cycles

A REVIEWED completion also names the original attributed **retain** or **continue** portfolio-review request. That request must refer to the exact customer case and portfolio pair and must have observed the same case revision being completed.

If the returned result agrees with that current original decision, adoption retains the existing case revision and selected portfolio-review event. If the return changes the case decision, preserve it as FOLLOW_UP and complete the actual original portfolio review against that changed revision before selecting REVIEWED in the existing cycle. The original portfolio review remains part of the same customer workflow.

### Complete the cycle

Review the current cycle after adoption. The supervisor signs it through the existing complete-cycle signoff workflow when every selected case satisfies its original requirements. Historical signed reports retain their original case versions and evidence.

For genuinely later work, reopen the appropriate original item with a reason, assign it, issue its current selection and continue the next review. Keep the earlier issue, returned editions, adoption and signed report as the prior operating history.

## 8. Recover an interrupted original request

The exchange uses the same principle as saved review cycles: retain the full original command and UUID before sending, then recover that original request after an uncertain response.

Use **Original requests** in the same physical workspace. A committed request returns its original result even after later case or cycle changes. Reusing the UUID with changed command contents conflicts.

An absent lookup immediately after uncertain transport is not a replacement result. Continue reconciling the original request and retained response in that same workspace. Start a genuinely new command only when making a new reviewed action against its current revisions.

A received customer workspace has its own physical storage identity. Its retained original operation history remains readable, while its browser draft and pending-command selections belong to that received directory. Deliberately select that copy before working there.

## 9. Receive the complete operated workspace

Export the full customer workspace using **Receiving** or the maintained client. Deliver that entire archive with the selected source release and the actual operating instructions.

The complete archive carries original source objects and native build packets, portfolio and case history, source comparisons, native requests/responses, cycle events, issues, returned original files, attached evidence and adoption history. Independent receiving replays the actual saved relationships before accepting them.

On the receiving host:

1. Install the complete selected release and import the full archive into a new private workspace.
2. Open the received application and the original cycle, issue, returned edition and adoption.
3. Open the actual original source files, complete returned file and every carried attachment needed for the selected review.
4. Inspect the original case history and signed report, including a historical version after a later edit.
5. Reopen the selected item for an actual later task, edit and save that work, then export and independently reopen the later whole workspace.

Keep the original exported archive and its historical source selection. A later complete export has its own file identity and retains the earlier history inside it.

## 11. HTTP, installed client and native continuation

The maintained MonitoringClient uses the current original private connection file. Its generic get/post methods preserve complete response bytes and HTTP metadata, while its download method writes the entire selected original file. Every exchange route carries the original physical-workspace header, X-Review-Workspace.

| Operation | Complete input or result |
| --- | --- |
| GET review-exchanges | offset/limit; explicit total and nextOffset for the saved operation list |
| GET review-exchange | id; complete selected metadata, cases, draft and editions, with original files available through their retained roles |
| GET review-exchange-request | requestId; committed and the original event/request/result |
| GET review-exchange-compare | returnId and editionId; full baseline/current/returned comparison and reviewSha256 |
| Historical comparison | Add adoptionRequestId; original event and comparison remain separate from current case/cycle revisions |
| POST review-exchange-issue | requestId, cycleId, expectedVersion, caseIds, reviewer, label, actor, at, evidenceIds |
| POST review-exchange-command | requestId, action, actor, at and complete compact body |
| Download review-exchange | id plus role issued_json, issued_html or returned_file, output and optional expectedSha256 |

Receive body: file with sha256, bytes, name and mediaType after uploading the complete original through the existing object route.

Apply body: returnId, editionId, reviewSha256, expectedCycleVersion, expectedCases and choices. expectedCases names every selected original case revision. Each choices entry explicitly selects action keep or apply and a fields object. A kept case has no field choices. An applied case supplies current or returned for each displayed conflicting field. The original comparison determines nonconflicting values.

The native CLI exposes matching review-exchange commands. Downloads are complete files, rather than shortened response previews. The same original object limit is 256 MiB; the complete reviewer JSON/HTML limit is 256 MiB, unfinished raw editor controls are 4 MiB, and named history retains up to 1,000 editions. The existing 128 MiB client JSON-response boundary applies to metadata/detail/comparison responses; complete file download remains separate. Original customer workspace archives retain their 1 GiB boundary.

| Field | Actual selected value |

The course saves its request UUID and actual dispatch time before each first send. On continuation it reads the original retained result or reconciles the same request; it never substitutes a new UUID for uncertain work.

The return, adoption and following-command files can arrive during the same selected course. Keep their preselected paths stable. The course preserves the first complete accepted contents in its output. If a deliberately different source or comparison is required, keep this original directory and select a new named following course within the same programme.

The adoption file contains actor and choices as described above. The following-cycle file contains a nonempty array of actual authored actions, each with action, actor and body. Supported original actions are reopen, assign, complete and signoff. The course selects the actual current cold-received cycle version and preserves the complete resulting command before execution. Use real case IDs and notes for the later work.

The course retains the original issue and returned file, selected comparison, adoption, all native responses, a complete customer archive, its cold receiving, subsequent authored cycle work and a second complete independently received archive. It reopens the historical adopted comparison after that later work.

For the original GLEIF receiving entry point, the optional --reviewer-exchange-selection file contains connectionFile, output and selection. Its output is a distinct child of the existing programme's output. A completed baseline is reopened from its exact retained intent, nine original files and full archive; the following exchange does not replay or overwrite that earlier baseline.
