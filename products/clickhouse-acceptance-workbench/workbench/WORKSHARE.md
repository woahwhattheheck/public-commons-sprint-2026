## Buyer problem and deliverable

A source-to-candidate move needs more than a successful INSERT. The buyer needs to establish that native types, every business value, duplicate multiplicities, keys and table identity survived the move, then retain a reversible consumer decision and enough source/history for another operator to receive the work.

Deliver one editable ClickHouse migration acceptance application for one approved source/target pair and up to five reviewed scalar tables. The application retains the complete author configuration, compiles an explicit separate-candidate plan, executes native RowBinary transfer, captures whole typed source and target exports, compares all selected business cells and schema/key conditions, and records acceptance or concrete differences.

The deliverable includes the installed operator interface, HTTP API, CLI, native worker and recovery, full source, complete original reference programme, actual receiving evidence, operating guide and complete portable project. The original named-query source can be derived for the accepted candidate with exact pre/post SQL and credentials kept as host references. Existing merchant staging and customer production routing remain explicit handoffs to their current owner.

## Assumptions

- One approved connection pair and up to five scalar table mappings.
- A bounded commissioning dataset of up to 250,000 rows and 512 MiB of complete native response data per selected table, with actual host memory/storage agreed before execution.
- Supported original version selection is explicitly declared; the included reference uses ClickHouse 26.8.24.9.
- Customer supplies an approved quiesced source or snapshot boundary. Multiple separate HTTP queries do not provide a cross-table transaction.
- Target is an owned Atomic database and separate commission_ candidate table names. The source identity and original tables remain retained.
- Customer supplies existing host access and appropriately scoped native accounts through environment references.
- The existing merchant source uses the retained original supported scalar query configuration. Exact query adaptations are reviewed and its owner performs original native validation/activation.
- One acceptance cycle and one planned receiving destination are included. Additional regions, table families, data volume or infrastructure are agreed as a new edition of scope.

## Acceptance

Acceptance requires the agreed native programme to complete against the selected dataset and exact engine, all expected rows and values to compare through the original typed comparator, schema and key conditions to satisfy the reviewed plan, current target UUID/schema to match the retained original candidate, and any differences to be resolved or explicitly excluded through a new approved plan.

The receiver must open the full project and editable source on its selected host, inspect the native requests/responses and complete typed exports, retain the same named archive bytes, receive a forward customer review and reject replacement of live local custody. Same and older received packages must preserve the current descendant history.

A successful source parse alone is not acceptance. A reference result is engineering evidence, not proof that customer production data migrated.

## Changes requiring separate scope

Continuous CDC, replication topology changes, distributed or sharded cutover, cluster upgrades or downgrades, production traffic switching, new authentication infrastructure, mainnet payments, managed hosting, backups of unrelated databases, and nested/aggregate type flattening require a separately reviewed plan. Explicit scalar projections can be designed as additional source work; the tool will not silently discard nested fields or tombstones.

Rollback in this scope restores the retained consumer declaration and original read configuration. It keeps both datasets. It is not an engine downgrade or reversal of external writes.
