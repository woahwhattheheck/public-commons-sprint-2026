## Exact result and returned paths

Successful preparation returns schema stellar-forge.pipeline-delivery-preparation.v1, state READY, with:

- directory and resultPath, where resultPath is the complete .runtime/PREPARED.json;
- request, the exact original REQUEST.json path/bytes/SHA descriptor;
- source with manifestSha256, files40 and the complete byte total;
- primary and receiving;
- portable, the exact full transfer path/bytes/SHA descriptor.

Each primary/receiving selection contains applicationDirectory, programmeDirectory, runtimeDirectory, runtimeReadyFile, python, dbt, runtimeId, the exact ready descriptor and the complete runtime value.

Use these actual returned paths. A primary selection that adopts an existing environment can have its Python outside the preparation directory. Both selections have independent source directories and local runtime-ready records. The portable transfer recreates an environment; it does not relocate a venv with broken absolute entry-point shebangs.

Runtime-ready schema is stellar-forge.pipeline-delivery-runtime.v1. It binds:

- the exact40-file source authority and original three package requirements;
- the full immutable dependency wheel inventory;
- every actual installed distribution and import location;
- normalized complete package/console-entry payload and RECORD contents;
- actual Python binary bytes, version, implementation, ABI, platform and machine;
- the retained full local installed-file observation and identity files.

The path-independent runtimeId is computed from that selected source, wheel inventory and normalized installed identity. Receiving must reproduce it. Actual original file hashes remain in installed.json; normalization does not erase the local installation evidence.

Normalization is limited to location-dependent console-entry paths and pip-generated RECORD rows, with the complete referenced normalized file identities preserved. Generated .pyc files are excluded from the portable payload identity. Original wheel bytes retain the upstream package payload exactly. Unrecorded site-package files and external links are rejected.

## Inspect and resume

~~~sh
starforge pipeline-delivery-workbench-prepare inspect \
  --directory /srv/private/pipeline-delivery/prepared
~~~

Inspect returns the complete result under result. It freshly observes both installed environments, verifies every source file and ready/identity/installed record, and checks the complete portable archive. A previously successful observation does not substitute for current bytes.

For an interrupted preparation, repeat the exact original command with --resume. Keep the same directory, source authority, Python path, adopted runtime and archive selection. The request is immutable. Closed successful commands retain their original stdout/stderr and are reused only when their exact selection and logs match. A failed command has its own retained attempt; an explicit continuation does not overwrite its earlier evidence.

The Python operation acquires a permanent kernel flock before installation, source publication or archive receiving. Actual installer/observer children inherit that same locked file description. The Node wrapper waits for the actual child close event, even after a spawn or running-record failure, and retains its full closed result and logs. An unavailable transport or lost caller acknowledgement does not mean the original child has stopped.

A frozen complete candidate precedes PREPARED.json. If final publication was interrupted, continuation revalidates and adopts that exact candidate before doing any mutable preparation. It does not choose a fresh completion timestamp or a new runtime identity.

The original environment becomes read-only to this preparation after READY. There is no automatic package upgrade, background watcher, controller replacement or dependency-refresh loop.

## Export the complete transfer

~~~sh
starforge pipeline-delivery-workbench-prepare export \
  --directory /srv/private/pipeline-delivery/prepared \
  --output /srv/private/pipeline-delivery-runtime.tar.gz
~~~

The destination parent must be an existing owned private directory outside the preparation. If an output already exists, it is reused only when its complete bytes match the retained original portable archive. The complete copied temporary bytes are verified and synchronized before publishing the destination.

The deterministic gzip/tar contains exactly:

1. TRANSFER.json as its first member;
2. source/ followed by every one of the40 original source paths;
3. wheels/ followed by every exact selected wheel name and byte identity;
4. ORIGINAL-SOURCE.json, dependencies.txt and identity.json.

There are no arbitrary extra members. Receiving compares the member set and every wheel descriptor to the retained runtime identity, and the distinct locked name/version rows to its installed distribution list before installation. Links, duplicate names, path escapes, missing members, changed bytes and extra nonzero trailing data are rejected. Member paths are validated and streamed into owned staging; a generic archive extractor is not used.

Keep the complete portable descriptor with the archive. Compare its bytes/SHA to the actual handoff before selecting it on another host.

## Offline receiving

~~~sh
starforge pipeline-delivery-workbench-prepare receive \
  --directory /srv/private/pipeline-delivery/received \
  --python /absolute/receiving/base-python \
  --archive /srv/private/pipeline-delivery-runtime.tar.gz
~~~

The receiver uses its existing local Python. The original native packages are installed offline from the exact retained wheels; no package index is queried. The selected Python binary/version/ABI/platform/machine must reproduce the original identity. An incompatible host returns a concrete mismatch before it can claim READY.

Receiving creates its own primary and receiving application/runtime selections, preserving the same runtimeId. It verifies all original source, original installed distribution payload and complete transfer identity. The original archive bytes are retained without recompression. Use the receiving host's actual returned paths for its managed Applications configuration and local runtime binding.

Customer project archives are then inspected/received through the original application. They preserve originating machine paths and native IDs as historical facts. A received historical run is not signaled or redispatched on the new machine. New customer work uses a new explicitly saved local runtime binding and original run request. Reopening an accepted result never silently starts another pipeline.
