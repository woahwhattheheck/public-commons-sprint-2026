# Complete Chinook migration and customer receiving

This chapter operates the complete published Chinook reference through the same Definian receiving programme as the original Fruitshop course. It adds a separate Chinook project in the existing primary and receiving workspaces, uses the selected original dlt/DuckDB runtime, and retains the complete source, native destination, acceptance evidence and editable project history.

Run the maintained `receiving/receive.mjs` entry. The Chinook extension follows the original cold-reopen phase. Its source helper, browser reviews and receiving steps belong to that same programme and operation directory. The programme owns the workspace leases, original native job identities, HTTP listeners and browser lifetimes.

The source is the published [Chinook 1.4.5 edition](https://github.com/lerocha/chinook-database/tree/7f67772503d71ba90f19283c38e93923addb43fa), commit `7f67772503d71ba90f19283c38e93923addb43fa`. The upstream README identifies media titles from a music library, fictitious customers and employees, and generated sales. These records are a reference for commissioning the product. The source and licence remain in the full delivered project.

## What this course completes

The original SQLite receiver first establishes the complete published source edition. The maintained adapter then retains every original source member and prepares independent expected tables before native loading. The same product performs a complete original dlt run and a following explicit verification, compares all eleven full table populations, evaluates business relationships and exact monetary controls, and records the selected consumer state.

The operator can open every retained table and control, inspect original source and native result files, review measured findings separately from decisions, select the accepted consumer, observe rollback and reselect the verified result. The primary and receiving browser journeys inspect the actual saved editions. Named H1, H2 and returned H3 packages carry the editable project, original source, native state and history through fresh, forward, same and older receiving, followed by a cold original CLI reopen.

The original Fruitshop exercise remains in its own project and continues to demonstrate required holds, acknowledgement and an explicitly reviewable exception. Chinook adds the complete multi-object source and reconciliation course. Its published baseline does not manufacture a changed customer edition or a fictitious migration exception.

See [OPERATOR.md](OPERATOR.md) for the full application, authenticated roles, original action recovery and runtime controls. See [integration/RECEIVING.md](integration/RECEIVING.md) for the adapter's exact production interfaces.

## Start the same complete programme

Use the delivered complete source tree and its matching full source manifest, the already-prepared original runtime-ready receipt, and an existing supported Playwright/Chromium installation. Keep the operation directory outside the source tree so private state, credentials and browser profiles do not become application source.

The following names are examples of the paths you select for this operation:

```sh
DEFINIAN_NODE=/absolute/selected/node
DEFINIAN_SOURCE=/absolute/complete-product
DEFINIAN_OPERATION=/absolute/private/definian-programme

"$DEFINIAN_NODE" "$DEFINIAN_SOURCE/receiving/receive.mjs" \
  --source "$DEFINIAN_SOURCE" \
  --directory "$DEFINIAN_OPERATION" \
  --config "$DEFINIAN_SOURCE/reference/programme.json" \
  --source-manifest "$DEFINIAN_SOURCE/SOURCE_MANIFEST.json" \
  --runtime-ready /absolute/selected-runtime/runtime-ready.json \
  --playwright /absolute/existing-playwright/index.js \
  --chromium /absolute/existing-chromium
```

The source manifest must cover the complete executing product, including these Chinook leaves, the original source cohort and embedded native dependencies. An older manifest cannot attest new receiver code. Use the programme's original source-adoption process for an already-started operation if its complete executing source must advance; preserve the prior selection and completed artifacts.

The complete course obtains its source from the supplied offline cohort by default. The wrapper invokes the Python executable selected by the existing runtime-ready receipt. It calls the unchanged original `receive(selection, output, inputs)` function with those verified local inputs. That path performs the original SQLite execution and source controls without reacquiring the upstream files.

The source wrapper is an internal step. Starting it manually alongside the whole programme would compete for its source lock. Continue the whole programme at the top-level entry so its source, native stages and receiving history remain coordinated.

Continue an interrupted programme with the same source selection and exact source directory; do not swap the meaning of an existing intake operation.

## Continue an interrupted programme

Repeat the same top-level invocation and add `--resume`. Preserve the same operation directory, selected source/manifest, configuration, runtime receipt, browser selection and optional original reference path.

The programme retains exact mutation requests before dispatch. A lost HTTP reply continues the original request and its original revision guard; it does not create a second source retention, plan, native job or handoff. Completed phases reopen their saved result and files. Native stages use their maintained job and parent-job identities, with explicit recovery when the original native outcome is uncertain.

The maintained runtime first acquires the exact source step's `lifetime.lock` and passes its existing descriptor and path to the Python child. The helper validates that descriptor against the same ordinary lock inode and keeps the inherited open file description for its entire lifetime; it does not open a replacement runtime lease. Its separate `original-source.lock` serializes the original source journal inside that same selected source-step directory. Its `SOURCE_SELECTION.json` binds the exact source cohort, original receiver files, Python and runtime ID. Its `source-operation.json` retains the attempt history. The following cases are distinct:

| Observed source state | Continuation |
| --- | --- |
| Complete received manifest and all complete files verify | Adopt that original result. Complete the saved running/failed wrapper attempt from the actual source receipt; preserve any earlier error in its completion-recovery record. |
| Incomplete `received/` with an existing original attempt | Require explicit `--resume`. Save the preservation intent, then move that exact closed directory into `prior-attempts/source-NNNN` before invoking the original receiver into a fresh source output. |
| Interruption after selecting or performing that move | Reconcile the saved source/destination and exact directory identity, finish the same preservation receipt, then continue. |
| Both rename paths exist, both are absent, or the selected directory identity differs | Hold the preserved evidence for reconciliation; do not guess which directory to replace. |
| Another owner holds the original source lock | Keep that existing owner. A second source helper does not start. |
| Source member, runtime selection or original request differs | Reconcile the selected edition explicitly. Do not overwrite the original record to make it fit. |

A completed-source adoption uses the original receiver's completion and operation identity; a wrapper process losing its response does not turn a completed source into another SQLite acquisition. A genuinely incomplete local source attempt is preserved in full, including its original `OPERATION.json`, partial database, files and failure information. The next explicit attempt runs the unchanged original receiver, whose output directory is created anew.

The wrapper never reuses an incomplete SQLite database as though it were a clean original source. It also never removes the preserved prior directory. The exact retry is recorded within the same Definian programme, and source provenance distinguishes the original receiver's per-attempt operation IDs.

## Review the source and native mapping

The published SQLite edition is the downstream source boundary. The original generator JSON is retained separately. The original receiver documents every row's lineage and the source-proven generator transformations: nullable empty strings become SQL NULL where the original generator specifies it, and naïve local date strings use the SQLite space-separated representation. The adapter consumes those actual native source rows without applying the transformation a second time.

Review these explicit decisions in the saved reference binding and compiled native plan:

- Original table and column identifiers map to recorded lowercase snake-case dlt identifiers. Every original field is selected, and a mapping collision is rejected.
- Ordered primary keys remain complete, including PlaylistTrack's two-column key.
- Integer cells remain exact integer tokens. Monetary strings become the original native `DECIMAL(10,2)` domain.
- Original `DATETIME` fields remain source-local text. The course supplies no invented timezone.
- All eleven resources use complete replacement of their selected reference table edition, explicit type/column hints and flat-table normalization. The adapter introduces no filter, deduplication, trimming or implicit null conversion.
- Independent expected tables are prepared from the complete original SQLite source before loading. Target results never generate their own expected population.
- Only the original dlt metadata columns are excluded from business-cell equality. The complete actual target schema remains available to the comparator.

The project retains each source file and the complete request ledger through normal `source.retain` operations. A completed intake reopened through the original portable receiver validates that ledger and its original request bodies, then adopts the same saved source IDs. It does not reconstruct historical expected revisions from the current project head.

The maintained compiler produces the actual native plan from those IDs. Plan review is a separate saved action. Native run and verification remain original dlt stages with full pipeline/DuckDB state and their native result artifacts.

## Read the full reconciliation

The Chinook evidence has three related layers:

1. **Original source receiving.** The unchanged SQLite receiver executes the pinned SQL, retains all native rows, checks integrity and foreign keys, records complete generator lineage and transformations, and calculates full invoice/group controls.
2. **Native migration parity.** The original dlt comparator checks every selected business row, duplicate multiplicity, mapped type and schema against the independent expected files. Its full native package and table-coverage status remain authoritative.
3. **Relational and business acceptance.** The product binds its rules, complete measured report and any separate decisions to the exact current comparison. The additive relational report also retains full primary-key/FK and invoice/group evidence against the same actual native job.

The relational evaluator verifies the exact original job-selection bytes and full observation bytes against their saved descriptors before it evaluates. It checks that selected source and independent expected files match the original binding, every target export belongs to that job, and the native plan preserves all fields, keys and type hints. The original full comparator is recomputed.

### Keys and relationships

Inspect both source and target key results: full key columns, null-key row ordinals, every duplicate key and all duplicate row ordinals. Review all eleven foreign keys, including nullable child absence and Employee's self-reference. A non-null child tuple without its selected parent is an explicit finding. Every orphan retains its full key and source/target row locator.

A row count that agrees while a key or relationship differs is not a complete acceptance result. The full native parity and current required business findings remain selected together.

### Invoices and grouped totals

The source baseline contains 412 invoice controls and 89 grouped controls: one overall group, 59 customers, 24 billing countries and five calendar years. Its overall invoice-header and extended-line totals are each `2328.60`, with zero difference. These are source-baseline values that the actual complete source and native result must reconcile.

Each invoice compares its original header `Total` with every retained `InvoiceLine.UnitPrice × Quantity`. The evaluator uses exact integer quantities and BigInt decimal minor units. It preserves complete invoice and line locators, quantities, row counts, header and extension amounts, differences and balance state. It compares all source and target invoice controls and the complete groups, including missing or duplicate groups.

The unit is `UNSPECIFIED_REFERENCE_AMOUNT`: the upstream schema declares no currency. Billing country does not imply currency. Track's catalogue price is not substituted for the price on an invoice line. Customer commissioning must define its actual currency/entity grouping and any conversion rule separately.

Download both the full machine-readable report and the complete readable invoice/group report retained by the course. Read the source/target rows supporting a finding, rather than using a displayed example or aggregate as the entire evidence.

### Measurements, review and consumer selection

The additive relational report returns `accepted:false` and `cutoverApplied:false` even when it is `RECONCILED_FOR_REVIEW`. It is complete evidence for the original product's review. Saved operator decisions remain separate from measured reports.

The application selects the current acceptance plan, evaluates it against the exact current complete comparison, and binds any decision to that report's retained row ID and semantic content. Required key/native-parity findings cannot be waived; acknowledgement alone does not resolve a finding. A reviewable exception needs its explicit disposition and reason.

The consumer switch requires the approved current native plan, its latest completed explicit verification, complete ready parity and the matching current acceptance report/decision. Open every selected consumer table and page through its complete retained typed rows. The displayed selection is the saved native result; it does not silently query an external production database.

Rollback restores the retained previous consumer binding. The course verifies every table from the actual selected comparison and side after rollback, then reselects the accepted verified target. A historical comparison or older handoff is not evidence of a newly operated external restore.

## Browser and independent receiving

The browser operates inside the same receiving programme. Select the Chinook project explicitly when opening the primary or receiving workspace; the original Fruitshop project and its history remain present.

The course reviews full source, plan, native runs, comparisons, acceptance, consumer selection, delivery and history on desktop and mobile. Its table checks use every literal native stream ID and that table's actual full row count. Large PlaylistTrack and Track populations are paged to completion. Full source/native/report files are downloaded with their retained length and SHA256 identities.

The primary handoff is a complete named project edition. The receiving installation uses the selected portable original runtime and its own ready receipt, receives the same project, verifies the full source/native/acceptance history and performs the original browser review. A receiving-side review is then exported in a complete returned handoff.

The original primary workspace receives that returned edition forward. Receiving the same package again preserves its identity; an older package preserves the newer current head. Cold CLI reopen verifies both workspaces and the original named package bytes. A package from an earlier revision remains downloadable as that exact named edition.

Keep the full operation directory and completed customer result with the source manifest, original source manifest/database, runtime package, complete native outputs, acceptance evidence, named project handoffs and browser artifacts. The final result inventories the selected files with exact lengths and hashes. Retain the original source attempt journal and any preserved failure directories as part of the operation's history.

## Use the contribution for customer work

For a customer's migration, retain the customer's actual complete source edition and original data-engine selection in its existing project. Agree the field/key/type mappings, business entities and currency/date policies, required relationships and full control populations before the original load. Keep customer approval separate from an automatic report.

The reusable source, compiler, exact comparison, operating desk, recovery and portable receiving in this product are already authored implementation. Paid commissioning covers the remaining customer-specific intake, mapping, integration, operation and acceptance scope agreed in the existing workshare. The published Chinook cohort and its source-only validation record are not customer data or a claim of a completed customer migration.
