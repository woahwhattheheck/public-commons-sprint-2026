# Migration commissioning scope and technical handover

This reusable technical input guide belongs to the public software edition. It contains no customer proposal, agreed price, delivery commitment or contact request. Agree commercial terms privately with the actual customer and delivery owner.

## Select the complete task

Record the accountable data owner, implementation operator, acceptance reviewer, receiving operator and host owner. Identify the original source system/export, complete data population, desired customer outcome, authorized retention and supported source/target boundary. A public reference programme is not a completed customer migration.

Retain every original input filename, raw byte count and SHA-256, source edition and acquisition reference. Supply complete independent expected tables. Record table/resource identities, normalized child mappings, ordered keys, NULL and empty-string meaning, exact numeric types and currencies, timestamp/time-zone semantics, merge/cursor/backfill selections and supported schema changes. Keep missing or disputed requirements explicit.

## Plan and execute through the existing application

1. Select the complete installed software and original dlt/DuckDB runtime. Keep private authentication and connection records outside exported source and project state.
2. Retain sources and review the complete native plan, all business-table mappings, expected population and original request identity.
3. Run the maintained extraction, normalization and loading stages. Preserve pipeline state, load packages, complete destination files, logs and all interrupted attempts. Recover the same recorded job through its original continuation.
4. Run explicit native verification and compare complete typed populations and duplicate multiplicities. Compile business keys, required fields, relationships and exact grouped controls against that same result.
5. Attribute review decisions to the exact report and rule edition. Required findings remain blocking. A reviewable exception does not override native parity. Correct sources or reviewed plans through new editions and retain earlier evidence.
6. Select the retained consumer deliberately. Inspect all pages and complete downloads; exercise rollback to the retained previous binding and deliberate reselection.
7. Export the full working project, all original inputs and outputs, editable software, runtime handoff, reports, decisions and request history. Independently receive and cold-reopen the same project, including older named editions and subsequent forward history.
8. Record actual outcomes in the existing Installation/Workshare case. An additional download, format, recovery attempt or retry continues its original useful task.

## Delivery and change register

Agree the actual population and host resources, source access, calendar, reviewer availability, correction process, support period and completion criteria with the existing owners. Record dependencies and input holds. No schedule, scope limit, payment milestone or production authority is inferred from this guide.

A useful later source period or an agreed requirement change creates a new explicitly linked edition. Changed keys, mappings, rules or runtime require review; retain earlier source, decisions, native receipts and consumer selections. External production switching and live credentials remain with their existing owners.

## Complete handover

Keep OPERATOR.md, COMMISSIONING.md, acceptance/OPERATING.md, the selected SOURCE_MANIFEST.json and the complete original runtime documentation together. The recipient must open the real application, inspect every agreed population and final report, use important controls, download full files, extract handover archives and reopen the working project. Follow the complete producing-peer instruction in ../OPERATING.md and ../RECEIVING.md. Source review and controlled checks do not establish native or rendered acceptance.
