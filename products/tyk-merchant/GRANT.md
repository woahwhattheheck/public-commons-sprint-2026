## API portfolio and cohort commissioning with complete operator receiving

### Customer work and the delivered product

A customer with an existing API estate needs more than a converted definition. The technical owner must select the complete source cohort, understand each routing, authentication, middleware and upstream change, operate a reviewed staging edition, authorize production, and hand the receiving operator a workspace that explains what was requested and what actually happened. The delivered Tyk workspace supports that whole course through the customer's original native Gateway or licensed Dashboard. Its browser, managed Applications entry, installed CLI, typed SDK and merchant agent tools share one durable workspace and the same native request journal.

The complete product is merged in public source at `6bca80855373234ff92d73ddddd823e58c00792a` and the installed workspace at `fd3ea4a2563102e49ee7a031789b73d91611e3e6`. The current contract exposes 27 workspace actions and 33 merchant agent tools. These are source and interface counts, not completed customer migrations, deployed API counts or purchase results. The [Installed customer operating guide](https://github.com/woahwhattheheck/public-commons-sprint-2026/blob/6bca80855373234ff92d73ddddd823e58c00792a/products/tyk-merchant/OPERATING.md) and [Original selected product installation guide](https://github.com/woahwhattheheck/public-commons-sprint-2026/blob/6bca80855373234ff92d73ddddd823e58c00792a/stellar/scf-starforge-20261009/distribution/selections/TYK_MERCHANT.md) define the complete installed route.

The product supports two distinct native operating courses. A licensed Dashboard cohort uses Tyk's own Classic-to-OAS conversion, staging and promotion. A pair of OSS Gateways uses complete original create, import or update requests, explicit reloads and separate staging and production acceptance. Both preserve the actual provider API IDs, source bytes, target identity, request and response evidence, review decisions, operating plan and receiving history. The customer's existing access, licenses and operational authority remain prerequisites selected in the original workorder.

### Select and review complete original sources

The operator saves a named native connection using its original API URL and environment credential references. Credentials remain on the receiving host; the workspace records their reference names. Full paginated inventory and complete original Classic or OAS definitions are retained as immutable content with exact HTTP exchanges and byte hashes. The operator can read and download the full original JSON or YAML alongside the field-level comparison. Large JSON numeric values retain their original text in source and review; a readable field table does not replace that source.

A saved cohort binds selected native IDs and definition identities to the captured target. Before a mutation, the original workspace prepares the exact native request and its preimage. The engineer examines the source and field changes, then explicitly dispatches that saved request. A changed preimage requires a new review through the maintained preparation flow. The product does not silently convert Classic definitions itself: upstream Tyk remains the authority for native conversion and imported configuration.

### Two-Gateway staging and production commissioning

The Gateway course freezes two distinct saved Gateway targets, a full source entry per API, each selected original create/import/update operation and the intended production create or update. The complete source intake is bounded at 16 MiB and supports one to two hundred API entries with one to fifty named checks. These are interface limits, not an assertion that the upper bound has been commissioned in a native installation.

Each source entry is prepared and reviewed against staging through the original rollout. The operator then explicitly reloads staging, captures the complete active portfolio and records each API/check result before production can begin. Production definitions come from the accepted complete staged edition with the actual native identity; they do not come from a second unreviewed input. Production repeats original preparation, explicit dispatch, reload, complete capture and final operational acceptance.

For twelve APIs this is a thirty-step course: twelve staging requests, staging reload/capture/review, twelve production requests and production reload/capture/review. The general plan is two steps per API plus six shared operating steps. Both targets use the same original API controller; the cohort binding coordinates their retained work and does not create another native dispatcher.

Plain OpenAPI import requires a specific decision. Tyk can add its native extension and assign an API ID, so imported active bytes can differ legitimately from the submitted document. The course requires the actual provider-returned ID, the complete submitted and observed definitions and their hashes, and explicit operator acceptance of that native transformation. A caller's expected ID is not evidence of an assigned identity. Imports without the actual returned identity remain unresolved. Create and update retain the original exact native correspondence requirement.
