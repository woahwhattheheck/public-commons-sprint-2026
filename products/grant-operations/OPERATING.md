# Grant Operations — installed operating and receiving guide

## Open the public Grant Operations product

This maintained public edition brings the original customer adoption plan, issuer correspondence and award terms, saved operating procedures, and period reporting into the same Grant Operations installation. The existing plan, case, source, request and Application writers retain their identities and recovery behavior.

Use the public repository **woahwhattheheck/public-commons-sprint-2026** and the complete `grant-operations` selection at one immutable commit. Keep the original source layout: the product guide, distribution builder, Python workspace, JavaScript modules, browser assets and explicitly selected supporting files form one runtime. Copying only the four contribution declarations does not install that runtime.

~~~sh
node /absolute/public-commons-sprint-2026/stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /absolute/public-commons-sprint-2026 \
  --ref FULL_PUBLIC_COMMIT_SHA \
  --selection grant-operations \
  --out /absolute/new-grant-operations-release
~~~

The command uses the existing source-selection builder. Read its returned `distribution.json`, archive path and digest; use those actual values for the installation in section 2. Add `--offline` only after the exact selected Git objects are available. If the same build was interrupted, use its existing output and `--resume`; a different source commit or selection gets a separate output.

The package manifest identifies this public source repository and commit. Upstream modules retain their original paths, APIs and license notices. The source selection and its full per-file inventory identify the installed edition. Retain that identity when using an older guide example. The separately maintained Highway product consumes these Grant contributions through its own selection and keeps its original operating case and receiving owner.

### Install and inspect

Use Linux, Node.js 22.16 or newer, Python 3.11 or newer, npm and util-linux flock. Choose a Node version satisfying the resolved profile. Prepare private parent directories under the receiving operator's account. Keep runtime source, mutable workspace, working inputs and delivery exports in separate named directories.

The examples below use absolute paths. Set them to the selected host's actual locations; the archive name and hash come from its original receipt.

~~~sh
GRANT_TOOLKIT=/absolute/maintained/source/stellar/scf-starforge-20261009/distribution
GRANT_RUNTIME=/srv/grant-operations/runtimes/edition-01
GRANT_DATA=/srv/grant-operations/private/grant
GRANT_RECEIVING=/srv/grant-operations/private/receiving
GRANT_PYTHON=/usr/bin/python3

node "$GRANT_TOOLKIT/runtime-install-cli.mjs" prepare --dir "$GRANT_RUNTIME" --archive /absolute/downloads/ORIGINAL_GRANT_ARCHIVE.tgz --sha256 EXACT_ARCHIVE_SHA256 --operator --feature mcp
node "$GRANT_TOOLKIT/runtime-install-cli.mjs" install --dir "$GRANT_RUNTIME"
node "$GRANT_TOOLKIT/runtime-install-cli.mjs" inspect --dir "$GRANT_RUNTIME" --load --source
~~~

The mcp feature uses the selected archive's original pinned dependency declaration. The browser and Python operator alone can be installed with --operator and without --feature mcp. Installation readiness is established by the actual inspect result. Keep its profile, lock, source inspection and installation receipt.

For an existing complete npm cache, the same install supports --offline --cache /absolute/cache. If installation is interrupted, use resume on that same prepared directory. An upgrade or recovery creates a new runtime and keeps the prior edition available; follow the original [runtime installation guide](../../stellar/scf-starforge-20261009/distribution/RUNTIME_INSTALL.md).

Use the original installed dispatcher for subsequent commands:

~~~sh
grant() {
  node "$GRANT_TOOLKIT/runtime-install-cli.mjs" run --dir "$GRANT_RUNTIME" -- grant-workspace --python "$GRANT_PYTHON" "$@"
}
grant --help
grant init --workspace "$GRANT_DATA"
grant serve --workspace "$GRANT_DATA" --port 8467
~~~

The explicit --python option precedes the grant subcommand. The original launcher also accepts SF47_PYTHON and passes its running Node executable to native buyer/support readers. Keep the private access file and access-fragment URL returned by the original server within the operator's custody.

Choose the profile used by the actual file. Those options remain with its full original parser report after export and reopening.

Preview the complete selected account before importing. ## Contributor agreements and the received resource allocation

Open **Delivery operations → Contributor engagements** in the same operating case. An agreement edition retains the original contributor, role and scope; the work period; actual weekday availability and dated exceptions; compensation and payment terms; source files and notes; and the recorded acceptance state. It also retains explicit remaining hours and uninvoiced cost against the original grant packages. A proposed agreement stays proposed until an operator records actual confirmation, the confirming person and its timestamp.

Use the complete [Contributor engagements guide](../../stellar/scf_2026/sf47_budget_model/workspace/ENGAGEMENTS.md) for the editor, every HTTP/CLI field and the typed agent/Merchant workflow. A practical receiving sequence is:

1. Attach the original agreement and availability evidence through the case's existing source controls. Select the original contributors and grant-package IDs. Review the complete agreement document, including its as-of date, unallocated work and payment basis, and save it with a nonempty review note.
2. When terms change, seed a successor from the exact saved review. Preserve its original review ID and SHA as the superseded edition. Earlier confirmations, proposals, declines and withdrawals remain in the saved history.
3. Select confirmed agreements and an existing source-current Forecast with the same as-of date. Review every affected package's complete remaining amount, any explicit unassigned remainder, and its payment timing. Save the returned full input through the original Forecast writer.
4. Map every selected contributor to one distinct original or new Portfolio resource. Review the complete original allocation, all alternatives, working calendars, task hours and any selected Installation phases. The handover captures the original Installation and Workshare source through the maintained phase reader. Save the returned full input through the original Portfolio writer.
5. Retain the final receiving review joining the exact book, saved Forecast, saved Portfolio and both normalized selections. The browser keeps the original requests and intermediate receipts in its Resume workflow. It preserves the actual allocation outcome and unfinished alternative findings.
6. Export the selected agreement edition as its complete operating-case ZIP, then receive that ZIP through the original case importer. The export includes the readable agreement, all original sources and editions, case history, Forecasts, Portfolios and the complete receiving review. Reopen the destination's original source and native IDs.

Each of the three handover writes retains its own native request ID, reviewed case version and exact full input. After an uncertain response, resume that original request. A source or preview conflict requires a fresh review; changing the meaning of an accepted key does not recover it. Agreement preparation records the selected terms; actual work, invoice review and cash observations continue through their original native records.
