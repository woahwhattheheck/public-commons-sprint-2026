# Staff Portal Workbench — complete installed receiving

This course opens the privately supplied complete staff portal through the installed Merchant Applications and agent interfaces. It adopts a completed original provider delivery, receives it into independent local workspaces, exercises the original portal, migration, insights and editorial views, changes only local project notes, exports the current complete operating package and reopens its history on the receiving installation.

The public integration supplies generic wrappers. The original application, its source authority, customer documents, source data, native results and outgoing operating packages remain in the existing private delivery. Keep the original company sender and original native provider operation with their current owner. This installed receiving is a separate, explicitly selected installation exercise that adopts the completed provider result.

original operating ZIP, or its private source-transfer ZIP and returns

There is no runtimeReadyFile for this standard-library application.

Run the full course from the installed distribution:

~~~sh
node /absolute/installed/package/source/products/staff-portal-workbench/receiving.mjs \
  --directory /absolute/private/staff-installed-receiving \
  --merchant-workspace /absolute/private/runtime-workspace \
  --merchant-runtime /absolute/installed \
  --preparation-result /absolute/private/staff-preparation/.preparation/PREPARED.json \
  --original-request /absolute/private/original-delivery-selection.json \
  --playwright /absolute/existing/playwright/index.mjs \
  --chromium /absolute/existing/chromium \
  --actor "Installed staff portal operator"
~~~

The installed command name is staff-portal-workbench-receive. The direct module
invocation above uses the same exported main(argv) contract as the dispatcher.

The course freezes complete source, preparation, donor, interpreter, Node,
Playwright and Chromium selections before application work. It selects and

Only one receiving invocation owns this operation. Do not run the same course
from a second terminal, create a parallel replacement directory after an

## 5. What the complete course performs

### Original result and independent primary receiving

The course keeps the literal original donor ZIP and operating ZIP, the original
result and request, every member descriptor and a full decoded workspace
snapshot. It receives the original operating package into a new local
primary workspace using the original stable request ID and receiver. Repeating
that same original request returns the same received workspace and full receipt.

The original donor's selected workspace and its already completed cold receiver
remain historical inputs. No tenant token or external native connection is
configured.

### Installed Applications and agent operation

Applications reviews, saves, connects and starts the exact managed staff portal
using the prepared source, private manifest, actual Python, selected actor and
received workspace ID. Managed startup independently verifies every original
source member and the actual listener identity.

The agent setup retains all25 declared tools. This course uses local source,
state, read, action, upload, operation, browser and complete retained-file
surfaces. It does not invoke native_connect, native_start or native_capture.

The course reads the full original state and portal context, both preview
surfaces and every paginated portal page. It saves a local notes-only
project.configure request through the original API, repeats its exact full
request and checks the original operation lookup. It uploads one declared
local receiving note and repeats the same upload request. Those retained
objects and receipts are additional history; all original objects and requests
stay intact.

Each agent response is read through the actual SHA-bound byte-range file
interface. The bounded presentation value is never treated as the complete
response. The agent's actual delivery artifact tool also retains a complete
operating ZIP for the selected current revision. Its own returned digest and
length are retained; the original delivery reader verifies its full source,
workspace and history. The course compares complete decoded snapshots with
the same selected edition, without assuming separately generated browser and
agent ZIPs have identical container bytes. The full files are retained, and the complete file catalogue is
reopened from the same store during cold receiving.

### Actual browser controls and lost acknowledgement

The browser opens the original portal with the managed private access key and
the selected actor, preserving the original cookie and CSRF session privately.
No access key, cookie, CSRF value or native token is written to result artifacts.

The original migration UI creates a project notes request in its own IndexedDB.
Before forwarding it, the course retains its complete actual request and actual
pending record. It saves the full original server response, deliberately loses
the first browser acknowledgement, reopens the original operation and uses the
UI's Recover original request control with that exact pending record. It
compares the original full response and verifies that the pending request clears.

It then operates portal intake, mappings, pages, review, returns, demonstrations,
costs and delivery. It opens the migration sources/assets controls, selects an
actual saved analytics run, and exercises the editorial empty filter and
selected queue. Desktop and narrow/mobile captures retain dimensions, scroll,
focus and overflow observations. The UI is rendered at the top of the page
after the original focus/scroll state is saved.

The browser downloads the actual handover HTML and JSON, selected pages and
differences CSV, pricing and demonstrations HTML, complete operating ZIP and
complete workspace ZIP. It opens every HTML report in that same owned browser
and captures desktop and mobile states. Closed screenshots/download candidates
retain complete literal bytes before publication.

### Independent editable receiving and onward handover

After the primary listener is confirmed closed, the helper checks the actual
browser operating ZIP using the original full readers and compares its complete
state/history with the current primary audit.

A separate receiving workspace consumes that complete current operating
package using the independently prepared application source. The second
Applications listener opens the actual returned workspace. Its four-view
browser course saves another local notes edit and produces an onward full
operating archive.

The original receiving request is invoked again after that later edit. Its
original receipt must replay unchanged, and the later workspace revision,
notes and history must remain intact. No receive action substitutes an older
workspace for a customer's later working edition.

### Cold reopen and complete closure

For each installation the course closes and reopens the Merchant agent manager
from its original disk configuration and retained file store. Applications
starts a new actual managed listener, the entire selected public state is
compared, and the same earlier agent file IDs and SHA256 values are read again.

After Stop, the offline helper checks the complete original state plus every
history, request, upload and object row against the prior snapshot. Original
rows are preserved exactly; permitted local additions remain visible.

Stop is complete only when the original Applications observer confirms the
bound unlaunched cancellation or the actual original command's closed terminal
result. Generic inactive, interrupted, queued or observation-unavailable states
are not closure evidence. The course retains its owner and retries closure of
the same original handles until the actual listener and browser are closed.

## 7. Interruption and deliberate continuation

Resume the exact same command with --resume. Preserve the private operation,
original selection, preparation, donor archives, Applications workspace, saved
loopback origins and browser profile.

The saved step intent is written before each original request. Original
request IDs, bodies, origin workspace IDs, upload identities and selected
revision stay unchanged. Full helper candidates and browser candidates are
verified before replay. An already complete final candidate is adopted before
mutable setup can add a different reused observation.

If interruption occurs after the final result is published but before complete
handover packaging, the exact result and artifact selection are reopened and
the same closed ZIP candidate is completed. Partial unclosed ZIP candidates are
retained under an interrupted name; they are never treated as accepted output.

A failed original native action is not reclassified as a completed action.
This course adopts an already complete donor result. A missing, mismatched or
unverifiable donor/source/output remains a concrete input error to resolve
with the existing owner.

When an actual displayed page is broken, repair the exact source with the
maintained owner and preserve the previous source/result history. Do not erase
a browser error or substitute a screenshot from another version. Coordinate a
source adoption for the same operation before continuing a corrected edition.
