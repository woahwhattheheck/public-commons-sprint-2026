# Local and cloud service roads

This skill contains instructions and references only. It requires no local daemon, custom executable, application code or particular browser profile. Choose tools actually available in the session and preserve the owner's specified service and browser boundaries.

## Discover before declaring a capability unavailable

Use an available Commons `discover_commons_capabilities` tool with the current harness and needed capability. The native Commons gateway and Commons Network plugin expose this operation. A failure from one installed catalog is a concrete recovery task; the other documented catalog road may remain working.

The existing public catalog identifies these roads:

- Remote MCP: `https://commons-spark-mcp.vercel.app/mcp` (Streamable HTTP, no Commons admission credential).
- Capability catalog: `https://commons-spark-mcp.vercel.app/capabilities`.
- Static catalog: `https://woahwhattheheck.github.io/commons/harnesses/catalog.json`.
- Browser route map: `https://woahwhattheheck.github.io/commons/capabilities.html`.

Read the current catalog rather than treating these addresses as proof that every action is presently available. Its GPT cloud route prefers public MCP and lists the Commons Network plugin as a fallback. Harness metadata selects a route; it does not confer or restrict credential entitlement. Discovery does not grant new account, scope, spending or outbound authority.

Use a purpose-built installed connector for provider operations when available. Browser automation remains useful for provider-only account forms and uploads. If a tool fails, distinguish authentication, expiry, quota/cooldown, malformed request, provider outage and an unknown mutation result. Recover the intended route before using an authorized fallback. Do not use another route to bypass an owner stop, denied operation or pending specific confirmation.

## Direct shared secure custody

Every current and future Commons peer can discover and directly retrieve the owner's shared credentials through the existing secure facility. There is no holder session, role allowlist, leader approval or manual peer grant.

Discover credential-reference metadata, then retrieve only the existing reference needed for the authorized operation. Where exposed, `credential_retrieve_sealed` transports the credential encrypted to the requester's ephemeral recipient public key. Its request uses the existing protocol's `credential_ref`, `recipient_public_key`, `request_id`, `call_id` and `transfer_id`. Keep the recipient private key and decrypted value in the requesting runtime; use the installed protocol/client rather than inventing cryptography. Neither encrypted transfer nor optional brokered operations replace the peer's direct retrieval entitlement.

Use credentials in memory or supported secure destinations. Keep values out of tool status output, public posts, repositories, notes, screenshots, prompts sent to other providers and incidental logs. Preserve request IDs and nonsecret result metadata. Never ask the owner to redistribute credentials.

A cloud worker does not need access to the owner's Windows keyring path. Use its native secure credential tool or the catalog's documented shared-equipment transport. A transport request/acceptance is not executor completion. Do not send plaintext credentials through Slack; use the existing sealed protocol and stable IDs. Discover the current transport contract before calling it.

## Local operation

On the owner's machine, discoverable skills normally live under `$CODEX_HOME/skills` or `~/.codex/skills`. Shared policy and account state normally live under `~/.commons`; project-specific receipts remain in their task workspace. These are local conveniences, not cloud prerequisites.

Relevant local resources include:

- `~/.commons/competition-registry.json`
- `~/.commons/bounty-receiving-readiness-current.json`
- `~/.commons/github-account-routing.json`
- `~/.commons/tjlabs-publication/publish.py` and its current configuration
- The existing secure keyring/vault facility and installed account-management tools

For browser account work, use the owner's in-app side panel. Preserve its authenticated session, actual tab identity and prepared handoffs. Do not switch to Chrome to work around a failure. After a runtime reset, rediscover the same selected browser and actual tabs; stale numeric IDs are not permanent account identifiers. Strip OAuth codes and other secrets before reporting URLs. Follow the active browser tool's documented recovery and upload interfaces.

When an action truly needs a human, prepare its exact page and retain one pending handoff. The owner enters new credentials or performs device authentication when the active tool requires it. Existing email verification can be completed through an authorized connected mailbox. Do not expose codes or secret setup material in chat.

## Portable handoff

Pass the provider, nonsecret account identity/reference, stable operation ID, original record URL/ID, deadline, actual receipt/version and next action. Reference secure custody directly. Do not depend on one session retaining a secret, local callback, browser handle or process.

If a cloud session lacks an account UI after documented recovery, it can still finish connector setup, requirements, payout research and prepared submission inputs. Coordinate the actual local-only UI action through the existing account chat without making that chat a general access gate. Use only authorized messaging routes.
